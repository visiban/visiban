    Find bottlenecks and measure flow¶

    Switch the toolbar toggle (Board, Summary, Analytics) to see where cards stall and how fast work finishes. Beta.

    Why it matters: The two views turn your board's movement history into bottleneck and flow data, for anyone checking pipeline health rather than moving cards.

    Done columns must be marked before analytics data is accurate

    The dwell-time heatmap excludes columns that are marked as done. If your "Done" or "Released" column is not marked, closed work continues to accumulate dwell cycles and distorts the heatmap.

    To mark a column as done: Board → Column header overflow menu → Edit → "Mark as done column" checkbox.

    The Summary view's velocity counts and the flow charts rely on this flag too: a card counts as finished the first time it enters a marked-done column. See Board Setup for a step-by-step walkthrough.

    Flow metric definitions¶

    These are the definitions every flow metric follows. They are quoted verbatim from the flow metric definitions decision record, which also covers reopened cards, missing history, percentiles and time zones.

    • Lead time: the time from when a card was created to its first entry into a done column. A card created in a done column has no lead time.
    • Cycle time: the time from a card's first move out of the column it was created in, to a column that is not done, until its first entry into a done column. A card created in a done column, or moved straight from its first column to done, has no cycle time.
    • Dwell time: how long a card stayed in one column, from entering it to leaving it, or until now if it is still there. Moving to another swimlane does not end a stay. Archiving ends it, and restoring starts a new one.
    • Age: how long an in-progress card has been in progress: the time since it first moved out of the column it was created in, or since it last left a done column, whichever is later.
    • Throughput: the number of cards whose first entry into a done column falls in a period.
    • WIP: the number of cards, not archived, currently in each column that is not done.
    • Cumulative flow: for each day, the number of cards in each column at the end of that day.
    • Blocked time: the time cards spent blocked, reported as its own metric: total, per column and per reason. It is never subtracted from lead time, cycle time, dwell time or age.
    • Needs attention: the cards, not archived and not in a done column, that are blocked, have been in progress longer than the 85th percentile of cycle time, or have not moved for longer than the board's stalled threshold. A planned child is never stalled, and a released one is measured from the later of its last move and its release.

    Commitment point (new in 1.3, #2050): a board admin can choose the column where cycle time starts, in Board Settings → Rules & limits → Flow metrics (or search Find a setting for "commitment point"). With one set, a card starts its cycle when it first reaches that column or any later column that is not done, and age follows. A card created in that column starts at once; a card that reaches done without passing it has no cycle time. Boards without one keep the definitions above. On such a board the charts and the API quote these instead:

    • Cycle time (commitment point): the time from a card's first entry into the board's commitment column, or a column after it that is not done, until its first entry into a done column. A card that reaches a done column first has no cycle time.
    • Age (commitment point): how long an in-progress card has been in progress: the time since it first entered the board's commitment column or a column after it, or since it last left a done column, whichever is later.

    Changing the commitment point re-measures the board's past, the same way marking a column done does.

    "Created" in lead time means the card's creation movement, the first history row that places it in a column. A card with no creation movement, for example one imported without its history, starts at its created_at instead. The two can differ for an imported card.

    Summary view¶

    A table of all swimlanes with:

    • the total card count and an inline proportional bar
    • 7-day velocity: cards that first entered a column marked is_done = true in the last 7 days, archived since or not. A card counts once, even if it later moves between done columns or is reopened.
    • 30-day velocity: the same over 30 days
    • Blocked (1.3+): how many active cards in the swimlane (not in a done column) are blocked right now, manually or by a relation

    Mark columns as done in the Edit Column modal ("Mark as done column"). Multiple done columns are supported: a board with both "Done" and "Released" counts the first entry into either as completion. See Board & Cards — Columns.

    Use it for a quick health check across all active pipelines.

    Changed in 1.3 (#448)

    The velocity columns count cards by first completion. Before, they counted moves into done columns, so a card that bounced between done columns counted more than once and a card archived since left the count. Boards with either pattern see different numbers. avg_cycle_days in the API is now the mean cycle time, so it starts at a card's first move out of its creation column rather than at its creation.

    API: GET /api/v1/boards/{id}/summary/

    Extension panels¶

    1.1+

    The summary response includes an extension_panels field (always an empty list in the OSS edition). Enterprise extensions can register additional panels here.

    Added in 1.2 (#1770)

    The Summary tab renders stats and table panels below the swimlane table. See the extension panel payload for the shape. With no extensions registered, the Summary tab looks the same as before.

    Changed in 1.2 (#1826)

    Each panel declares the lowest board role that may see it. A member below that role does not get the panel, and a panel that declares nothing is shown to board admins only. See panel visibility by role.

    Analytics view¶

    Time-in-stage and flow data derived from CardMovement records, on one scrolling page. From the top:

    1. Title row: "Analytics", a Beta badge, the board name and the period shown.
    2. Filter bar: one Date range, Swimlane and Label selection for the whole page (see Filters), and Export CSV for admins.
    3. Four sections, one per question:
      • What is happening? The Bottleneck panel and four headline tiles.
      • How fast does work move? Throughput and Cycle time, side by side.
      • Where is work stuck? How work flows, with Where the time goes under it (its Table view is the dwell time heatmap; see How work flows), then Cumulative flow and WIP age, side by side.
      • Why is it stuck? Why cards get blocked and the Needs attention list, side by side.
    4. A footnote on days, time zone and filters.

    From 1024px wide the paired panels sit side by side; below that every panel takes the full width, and the page never scrolls sideways. When the board has no flow history, or no card matches the filters, one message replaces the four sections (see Page states).

    1.3+ Analytics is in beta: data may be incomplete in some configurations, so use the results as directional guidance.

    Swimlanes view¶

    1.3+

    Under the page title, two links switch between Overview and Swimlanes. The Date range and Label you picked carry over. The selected view is kept in the URL (a_tab=swimlanes), so a reload or a copied link opens the same view. The Swimlanes view ranks swimlanes by how long work takes:

    • Controls: Date range, Label, Group lanes by (None, or a dropdown or checkbox swimlane custom field; admin-only fields are offered to admins only) and Sort (slowest first by default). There is no Swimlane filter, because every swimlane is shown.
    • Finding panel: names up to two swimlanes that are slower than the board, or says none is.
    • One row per swimlane: the name (select it to open the Overview filtered to that swimlane) with a status line; a cycle-time bar for the median, a thin line to the 85th percentile and a tick at the board median, all on one scale; eight small bars and a word for the trend inside the period; the share of elapsed time blocked (Blocked time); and cards in progress and finished.
    • Status: "Slower than the board" or "Faster than the board" when the median is more than 20% away from the board median, otherwise "In line with the board". A swimlane needs 10 finished cards for a status; with 5 to 9 it shows its median and no status line. Color repeats the words and never replaces them.
    • Small samples: under 5 finished cards a swimlane shows no median, bar or trend; with 5 or 6 it shows no 85th percentile line.
    • Cards that changed swimlane (changed in 1.3, #2334): finished cards and their cycle times count under the swimlane each card entered the done column in, cards in progress under the swimlane they are in now, and blocked share splits a card's time between the swimlanes it was in. A card dragged straight into done in another swimlane is finished in the new swimlane and blocked in the one it left. The board median includes every finished card, also one that finished in a swimlane since deleted.
    • The server computes every number. See GET /api/v1/boards/{id}/metrics/swimlanes/ in the API reference.

    Below 1024px each row's cells wrap under the name.

    Filters¶

    1.3+

    One filter bar drives every panel on the page, the heatmap, stalled and blocked sections included; no panel has a period control of its own.

    • Date range: the last 30, 90, 180 or 365 days. 90 by default, because a weekly median needs five whole weeks and percentiles need enough finished cards.
    • Swimlane and Label: use each card's current swimlane and labels. The Swimlane filter selects the cards in that swimlane now, even when a breakdown or the Swimlanes view counts some of their work under another swimlane (see Break down by).

    Share a view by its URL¶

    1.3+

    Period, Swimlane, Label, Break down by and the Overview/Swimlanes choice are kept in the page's URL, beside ?view=analytics. Reload the page, or send the address to a teammate, and they see the same view. Changing a filter replaces the current history entry, so Back still leaves the Analytics tab rather than stepping through every filter you tried.

    Parameter Values Left out when
    a_days 30, 90, 180, 365 90 (the default)
    a_swimlane a swimlane id on this board no swimlane filter
    a_label a label id on this board no label filter
    a_by swimlane, label or field_<id> (a dropdown or checkbox card field) None
    a_tab swimlanes Overview

    For example, ?view=analytics&a_days=30&a_swimlane=12&a_by=label. A link with only ?view=analytics still opens the default view. A value the board does not offer (a deleted swimlane, a period that is not in the list, a field that cannot be a breakdown) is ignored and the default applies. Leaving the Analytics tab clears these parameters, and Clear all filters removes the filter ones.

    A filter change refreshes every panel once. The panels keep showing the previous numbers, dimmed, until the new ones arrive, and an open drawer closes.

    Changed in 1.3 (#2261)

    The heatmap's own 7 / 30 / 90 days buttons are gone, and the 7-day window with them: the heatmap uses the filter bar's date range, so it now defaults to 90 days instead of 30. Pick Last 30 days for the old default.

    Break down by¶

    1.3+

    Break down by in the filter bar colors the flow charts by group. Pick None (the default), Swimlane, Label, or any dropdown or checkbox card custom field. With None the page is unchanged.

    • A legend under the filter bar names each group with its color. Select a group to isolate it: its marks stay at full strength and the rest fade to 20%. Select it again to show every group. Changing the breakdown clears the isolation.
    • Where the time goes shows one bar per group, on one scale, so the longest bar is the slowest group.
    • Throughput bars stack by group. WIP age marks and Cycle time dots take the group color; aging marks keep the ring (past the 85th percentile) and the square (blocked).
    • Each chart's summary says what the color means, and its table view has a group column, so color is never the only cue. Cumulative flow does not change.
    • Up to five groups get a color. With more, the five largest are shown and the rest collapse into a neutral Other.
    • Labels: a card with several labels is counted once in each, so the group numbers can add up to more than the board's.
    • Custom fields: cards with no value for the field are left out.
    • When no card in the view has a value to break down by, a status line replaces the legend ("No cards in this view have a swimlane to break down by.", or the same for label or the field) and the charts stay uncolored.
    • Swimlanes count at the time of the work (changed in 1.3, #2334): counts follow the swimlane the card was in at the moment they are dated by, blocked share is split by time across the swimlanes the card sat in, and a column stay counts whole under one swimlane. A finished card counts under the swimlane it entered the done column in, a card in progress under the swimlane it is in now, and a stay in a column, counted whole, under the swimlane the card was in when it left the column (a swimlane change made by the exit move itself does not count, and a change during the stay moves the whole stay to the later swimlane). A card that moved to another swimlane after it finished stays with the first. A card dragged straight into done in another swimlane counts as finished in the new swimlane, while its blocked time and its last stay count in the one it left. Work recorded in a swimlane that has since been deleted is left out of the swimlane groups and still counts in the board's numbers.
    • Labels and custom fields use each card's current values: their history is not recorded.
    • The Summary view velocity and average cycle time, and the dwell time heatmap rows, still use each card's current swimlane, so for a card that changed swimlane they can differ from the breakdown and the Swimlanes view.

    Bottleneck¶

    The panel names the column the server reports as the bottleneck (the column that is not done and whose queue grew the most across the period, the hatched band of the cumulative flow chart; the first column that is not done (where new work arrives) is never named) and states its numbers in one sentence:

    • Median wait: the 50th percentile of completed time in that column (dwell).
    • Share of the cycle: the column's median wait divided by the median cycle time, in words ("about half of the whole cycle"). It is a ratio of two medians, worked out in the browser from the numbers the server returns, so it is approximate; it is left out when either median is withheld or the median cycle time is 0.
    • Queue: cards in the column at the start and end of the period, the column's WIP limit when one is set, and how many cards arrive and leave per week.

    See the N cards opens the column drawer for that column; Open on board goes back to the board. Without a bottleneck the panel says Too early to say (no 85th percentile of cycle time yet) or No bottleneck (no column's queue grew in the period). Both also cover a board where only the first column's queue grew, since that column is never named.

    Column settings show the first column that is not done as a checked, disabled Not named as the bottleneck checkbox, so the rule is visible where you edit the column.

    How work flows¶

    One row, left to right, inside a box that scrolls sideways when the panel is narrower than 980px:

    • Connector before each column: the average cards per week entering it over the range ("avg / wk"; the Throughput tile's "/ week" is a weekly median instead), a bar whose thickness follows that rate, and a one- or two-word note ("started", "move on", "fewer leave"). Connectors are neutral, and warning-colored after the bottleneck.
    • Column box for each in-progress column, a button that opens the column drawer: the name, one square per card in the column now (every card not archived in it, as the column header counts them, including cards that have not started; at most 30 are drawn, then "+N more", and the count beside them stays exact), "N of limit" (plus "M over limit"), the median wait, and the queue change over the period ("Queue +7 since Aug 16" or "Queue steady"). Squares beyond the WIP limit are hollow, outlined in the danger color. The bottleneck's box has the warning border.
    • A final connector, the average number of cards finished per week, each card counted once at its first entry into a done column (a card moved from one done column to another is not counted again), and a Done box with the number of cards finished in the period: every card whose first entry into a done column falls in the selected range, partial weeks included. It uses the same date window as the cycle time, so it can be higher than the Throughput chart, which counts whole weeks only. It can also be higher than the number of cards in the cycle-time chart, because it counts every finished card, including one that went straight to done or has incomplete history; cycle time needs a start, so those cards have no cycle time.

    Where the time goes sits under the row: one bar, "All cards" (or one bar per group under Break down by), segmented by in-progress column. A segment's width is the column's median days, labeled with that number (a segment too narrow to hold it drops the number: in both bars it shows on hover and in the segment's accessible name, and the single bar's legend also names it; under a breakdown the legend names the columns only, because the all-cards medians would contradict the group bars). The number printed at the end is the sum of those medians, not the cycle time, and the panel says how many columns were left out of it for lack of enough finished cards, for example "3 columns without enough data left out"; under a breakdown each group's bar says it for that group. The bottleneck's segment is hatched in the warning color. When no median is available yet, the panel says so instead.

    A Chart | Table switch on the panel changes it to the dwell time heatmap table.

    Column drawer¶

    Opens from a column box or from the bottleneck panel's See the N cards button, and traps focus until you close it (Escape, the close button, or the backdrop); focus returns to the button that opened it. It shows the column name and "N cards in this column now, limit L" (the same count as the column box), three figures (in column against the limit, median wait, cards past the 85th percentile of cycle time), the oldest card expanded with its owner, swimlane and blocked state, its time by column and an Open card button, then the other cards oldest first. Five show at first; Show N more reveals the rest. Only cards with an age are listed: cards that have not started, or have missing history, count toward N, and a note says how many are not listed. Choosing a card in the list shows its transitions, with Back returning to the column.

    Headline tiles¶

    Tile Number Sentence
    Cycle time Median days The 85th percentile and how many finished cards it is based on
    Throughput Median cards per week How many whole weeks, and how many cards finished in the selected range, partial weeks included (the number in the Done box; it counts every finished card, even one with no start, so it can exceed the cycle-time sample)
    Work in progress Cards in the in-progress columns now, including cards that have not started (the total of the flow row's counts) Columns over their WIP limit, and cards past the 85th percentile
    Blocked time Days blocked in the period Number of blocks, and cards blocked now

    A tile shows only what the server returns. Without a median it shows a dash and says when the median appears ("Median appears at 5. 3 so far."); with a median but no 85th percentile it is marked Provisional. With too few whole weeks, Throughput shows the cards finished so far instead of a weekly median. With a swimlane or label filter on, Work in progress leaves out the over-limit count, because a WIP limit counts every card in the column. The over-limit count counts every card in the column too, including cards that have not started, as the column header does.

    Medians. Every median on this page is the nearest-rank 50th percentile: with an even number of values it is the lower of the two middle values (of 6 values, the 3rd), never their average. The board_medians field of the older GET /api/v1/boards/{id}/analytics/ response uses the conventional median, which averages the two middle values, so it can differ from the medians here even over the same visits.

    Flow metrics¶

    1.3+

    Four charts built from the movement log, so you can see how long work takes and where it piles up. Each chart has a one-sentence finding, its definition, and a Chart | Table toggle. They follow the page's filters. All dates are UTC, and weekends count.

    Chart Read it as Marks
    Cycle time How long finished work took. "85th · 8.1d" means 85% of these cards took 8.1 days or less. One point per finished card. 50th percentile dashed, 85th solid and heavier, 95th dotted. A hollow point was reopened after finishing, and keeps its first finish.
    Throughput How many cards finish per week. One point per whole week, its count printed on it, the median dashed. A hollow diamond beside each point is the number of cards started that week (a legend names both), and the table has a Started column. Started under-reports on imported boards. Only whole Monday-to-Sunday weeks inside the range are shown: the partial week at the start of the range and today's unfinished week at its end are both left out, so a partial week never reads as a slow one. A 30-day range covers 21 or 28 days and 90 days always 84.
    Cumulative flow Whether work arrives faster than it finishes. A widening band is a queue. One band per column, labeled at its right edge, finished work at the bottom, then the deleted-columns band when it holds cards, so the top of the Done band is the number of finished cards. The hatched orange band is the bottleneck: the column that is not done and grew the most across the range, leaving out the first column that is not done (where new work arrives), named in a small key under the chart. The Done band is gray.
    WIP age Which unfinished cards are in trouble now. One dot per in-progress card, over its column. The shaded zones are the cycle-time percentiles. Dots are gray up to the 50th percentile, orange past it, and red past the 85th percentile. A ringed card is past the 85th percentile, a square is blocked, so color is never the only cue. A key under the chart shows each gray, orange and red tier that has a dot on screen (under a breakdown the dots take group colors, so no tier key appears) and a "Blocked card" entry for the square.

    Too few cards. A percentile line appears only with enough cards behind it: the 50th needs 5, the 85th needs 7 and the 95th needs 20. Until then the chart leaves that line out and says so, rather than presenting one card's time as a trend. The throughput median needs five whole weeks.

    What is left out. A card with missing or broken history (for example, imported without its history) has no cycle time or age, and the chart says how many were left out. It still counts toward throughput once it reaches a done column. Blocked time is part of cycle time and age, never subtracted, because the wait is real.

    Work and wait in gated stages. 1.3+ In a stage with sub-columns, the sub-columns before the last count as work time and the last one counts as wait time (#1102). The split comes from the recorded gate history: the sub-column a card entered in, then every gate passed or reopened while it stayed. A card reopened from the last sub-column goes back to work time, and a card that leaves with gates still open stops waiting when it leaves. The API reports the split as additive fields, and no existing number changes:

    • each cycle-time sample carries wait_days (its time in the last sub-column of gated stages, 0 when it crossed none) and work_days (value_days minus wait_days);
    • each dwell column carries work_percentiles and wait_percentiles, null for a stage with no sub-columns, and for every stage when the filters select no cards (the work-in-progress age samples carry no split);
    • each heatmap swimlane carries throughput_wait_avg_days_per_column (In period) and age_wait_avg_days_per_column (Age), keyed only by gated stages.

    Cycle-time samples carry the same two fields: wait_days is 0 and work_days equals value_days when the card crossed no gated stage. The gate history is read for the board's cards and is not limited to the selected date range, so its load grows with the board's gate-transition history.

    Time a card spends archived inside a cycle counts as work time: only visits are split into work and wait, and archiving closes the visit, so an archived span is never wait. This is a known simplification.

    Work time here includes blocked time, so work_days plus wait_days is always the sample's value_days. #1102 describes work time as "minus blocked time"; this release does not subtract it, pending a product decision, and blocked time stays its own metric (Blocked time above).

    Which sub-column is "last" is read from the stage as it is now. Each recorded gate change names the sub-column the card landed in, so time follows that sub-column through a later edit of the stage: if the stage gains a sub-column after it, or its sub-columns are reordered, time a card spent there counts as work once it is no longer last. Two positions have no sub-column on record and are judged by their place in today's stage instead: a card that entered a stage at its first sub-column, until its first gate change, and history recorded before 1.3. For those, an edit that adds, removes or reorders sub-columns after the history was written can move time between work and wait. A gate changed while a card moves to another swimlane inside the stage counts from that move, and a restored card picks up in the sub-column it was archived in.

    See the cards behind a number. Click a point or a day, or use the table, to open a drawer with the card's owner and transitions, or the list of cards behind that week or day. From an aging dot the drawer also shows days in progress, the 85th percentile, blocked time, and time per column, counted from when the card's age started so the columns add up to the days in progress. Open card opens the card; an archived card has no Open card.

    Very large boards (new in 1.3, #2429). The page asks for at most 300 cards per list, so a board with thousands of cards in flight transfers far less: on a test board with 12,000 cards in flight, opening the Overview went from about 9.75 MB to about 1.67 MB of uncompressed JSON. Most of what remains is the time-in-stage heatmap, which is not capped and grows with the number of swimlanes. Every number stays exact: the headline tiles, percentiles, sample sizes, WIP counts and per-week counts are computed from every card. Only what is drawn shrinks. Cycle time and WIP aging then plot a sample of 300 dots, always including the longest cycle times and the oldest work, and say so under the chart ("Showing 300 of 2,430 cards, the longest always included"); their table view lists the same sample. A week's drawer lists its first 300 cards and names how many more there are, and a column drawer names the aged cards the sample left out. The full lists are still available from the API without limit (Capped lists).

    Keyboard. Tab reaches the filters, each chart's toggle, then the aging dots in column order, and Enter opens the drawer. The table view is the complete keyboard path: every point of every chart is a row there, with a button to open it.

    Page states¶

    • Loading. Each region shows a gray skeleton the size of its final panel (a chart panel gets a title, a summary line, the 260px chart and two note lines), the first chart panel says "Loading flow metrics…", and the filters stay usable. The pulse stops under reduced motion. A refetch keeps the previous numbers on screen, dimmed.
    • Nothing has moved yet. A board with no card movement shows a short explanation, a dimmed example bar labeled as an example, and Go to board.
    • Too little data. The page still renders. The bottleneck panel says "Too early to say" with the reason, and a tile marks its value Provisional and says what is withheld and when it appears.
    • Could not load. The Overview's charts come from one request (changed in 1.3, #2426), so they load, and fail, together: each chart and tile then says it could not load, the page shows Some panels failed to load. with Retry, and the dwell time heatmap, which has its own request, still draws.
    • Busy or too much history. Added in 1.3 (#2428). The server computes a limited number of Analytics requests at once. When it is busy, the page waits and retries once on its own, then shows Analytics is busy right now with Retry. A board with more history than the server is set up to analyze in one request shows This board has more history than this server is set up to analyze and suggests asking your administrator; it is not retried. Where a shorter period would help (the charts and the swimlanes table, which read only the cards active in the period), the message also suggests a shorter period. A chart's day drill-down reads every card on the board whatever the period, and the Summary tab has no period, so those only suggest asking your administrator. Administrators: see Analytics limits.
    • No cards match these filters. The message names the active swimlane, label and period, with one removable chip per filter. Show last 90 days appears when the period is shorter than 90 days, and Clear all filters resets everything. It does not predict how many cards a wider filter would match.

    Dwell time heatmap¶

    Swimlanes are rows and active columns are columns. Each cell shows the average days cards spent in that stage during the selected period.

    Done column exclusion¶

    Columns marked is_done = true are excluded from dwell-time calculations and hidden from the heatmap, because time in a done column is post-completion idle time. The API response lists the excluded column names in done_columns, and a footer note reads "N done column(s) not shown".

    Velocity column¶

    The rightmost column shows Velocity per swimlane: the average deal_velocity_days, the number of days from a card's first movement ever to its most recent movement, for cards whose most recent movement falls in the selected period. It counts cards whether or not they reached a done column, so it is not cycle time. A card that has only been created, and never moved, is left out rather than counted as 0 days (changed in 1.3, #2297). A dash (—) means no velocity data for that swimlane.

    Color-coding¶

    Cells are colored from the board's staleness_threshold_days and stale_warning_pct. The warning boundary is threshold * stale_warning_pct / 100, the share of the threshold a card has used.

    • With the defaults (7 days, 50%), the boundary is 3.5 days. With 75%, it is 5.25 days.
    • A value of 0 turns the yellow band off, so cells are green until the threshold.
    • The card aging tint uses the same boundary.
    • A cell turns red only when its unrounded average reaches the threshold: an average of 6.96 days shows as 7.0d but stays green against a 7-day threshold when the yellow band is off, or when it begins at the threshold, and yellow otherwise (changed in 1.3, #2297). At a threshold of 0 (accepted by the API, blocked in the settings UI) the red tier also counts the threshold as 1 day, so an average of 0.96 days shows as 1.0d and stays green (fixed in 1.3, #2331).
    • The yellow boundary compares the unrounded average the same way: with a 14-day threshold at 50%, an average of 6.96 days shows as 7.0d but stays green (changed in 1.3, #2306). A threshold of 0 counts as 1 day for the colors.

    Changed in 1.2 (#1841)

    Before 1.2 the boundary was computed as threshold * (1 - stale_warning_pct / 100), the inverse of what the setting says. Boards on the default 50% are unaffected. Boards with any other value see the yellow band move.

    Color Marker Condition
    Green ● OK Average dwell time is below the warning boundary
    Yellow ◆ Warning Average is at or above the warning boundary but below the full threshold
    Red ▲ High Average is at or above staleness_threshold_days (outlier / bottleneck)
    Grey / dash none No data for that swimlane-column combination

    Color is never the only signal: each colored cell shows its marker next to the value, screen readers announce the level text ("OK", "Warning", "High") after the value, and a legend below the heatmap maps each marker and color to its level.

    Tip

    Both staleness_threshold_days and stale_warning_pct are configurable per board in the board settings modal. Changes recolor the heatmap on the next analytics load.

    The heatmap follows the page's filters: its period is the filter bar's date range, and the swimlane and label filters are sent with the request.

    Table modes: Current vs In period¶

    The heatmap is the Table view of How work flows. A button pair above it toggles its mode. The choice persists per board in localStorage (board:{boardId}:analytics-view-mode) and defaults to Current.

    Mode What the table shows Use it to
    Current Average time (days) cards have currently been sitting in each stage: a snapshot of in-flight work. High values mean cards blocked or idle right now. Find current bottlenecks
    In period Average time cards that left a stage during the selected period spent there, each stay at its full length. Reflects historical flow efficiency, not current queue depth. View historical time in each stage over the filter bar's date range

    Neither mode measures throughput (cards finished per period); both measure dwell time. In In period each cell's tooltip shows how many stays are behind its average (for example "5 stays"; a card that visits a stage twice is two stays), and stages with no stay in the period show a dash (—). The green/yellow/red thresholds apply to both modes, using the same staleness_threshold_days.

    Dwell time and archived cards¶

    Analytics includes archived cards as part of the historical record.

    • Archived card: dwell time in its most recent stage uses the archive timestamp as the exit time, not the current date. Dwell stops accumulating when the card is archived.
    • Active card: keeps accumulating dwell time in its current stage until it moves again.
    • Archive and restore events: archiving ends a stay and restoring starts a new one, so the archived period is not counted as time in the stage, in either mode.
    • Swimlane moves: moving a card to another swimlane does not end its stay, in either mode.

    Changed in 1.3 (#448)

    Current and In period follow the flow metric definitions. Before, a swimlane-only move reset a card's age and split its stay in In period, a restored card's archived period counted as time in its stage, an archived card added a near-zero stay, and a stay that began long before the selected period was lost. A column deleted and recreated under the same name no longer inherits the old column's history, done flag or blocked time.

    Needs attention¶

    Under Why is it stuck?, next to the block reasons, one list shows each card that is blocked now, has not moved for longer than the stalled threshold, or is older than the 85th percentile of cycle time. A card with no movement history, such as an imported one, counts days without movement from when it was created. A planned child is never listed as stalled while it is planned, and once released it counts days without movement from its release if that is later than its last move, the same rule as the Stale flag on the board. It can still be listed as blocked. A card appears once; cards in progress come first, by age, then the rest by days without movement. Each row shows the title, then its column, swimlane and reason, with its age in days on the right: red past the 85th percentile, orange otherwise. A manually blocked card names its block's reason, as in "blocked: waiting on security review", after any other reasons so a long one does not hide them; the line is cut to fit the row, and hovering it or opening the card shows it in full. A card blocked only by another card shows just "blocked". Five rows show at first; All N cards expands the list in place, 25 per page. On a very large board the page loads only the first 300 cards in this order, so a long-unmoved card that is not in progress can be left out before a younger one that is; the expanded list then says "Showing the first 300 of N cards, in progress first" (new in 1.3, #2429). Select a row, with the mouse or the keyboard, to open the card.

    • Default threshold: the board's staleness_threshold_days.
    • Override: none. This list always uses the board's threshold. The stalled_days query parameter applies only to the analytics endpoint's own stalled list, not to this list or to the heatmap coloring.
    • Filters: the list follows the page's filters; it is built from GET /api/v1/boards/{id}/metrics/attention/.
    • Excluded: archived cards and cards in done columns, since they are no longer in flight and flagging them would mislead.

    Why cards get blocked¶

    1.3+

    Under Why is it stuck?, Why cards get blocked ranks the reasons cards were manually blocked during the selected period, longest first:

    • Each reason: the days it cost, the number of blocks, and a red bar sized against the longest reason. A footnote says which column most blocks started in. At most ten reasons show. The subtitle reads "Every blocked day had the same reason" when there is one reason, "One reason accounts for more than half of all blocked time" when the top reason is 50% or more of blocked days, and "One reason accounts for nearly half of all blocked time" from 40% up to 50%. Otherwise it names the period. Reasons that differ only in capitals or spacing count as one.

    A block counts for the part of it inside the period. A block that is still open counts up to now; on a card that is archived it stops at the archive, and if the card is restored it counts up to now again, archived period included. A deleted card's finished blocks still count, and their reasons still appear, as its movements do in the heatmap; a block that was still open when the card was deleted is left out, reason included. Times under a day show in hours. Blocks by another card (relations) are not timed. When nothing was blocked in the period the panel stays in place and says so, so the layout does not shift.

    Terminology¶

    A few labels look alike but measure different things:

    • 7d Velocity and 30d Velocity on the Summary view are cards finished in the last 7 and 30 days, a throughput count. The API fields velocity_7d and velocity_30d keep their names.
    • Velocity in the dwell heatmap is deal_velocity_days: days from a card's first movement to its latest movement. It is not a flow metric. Tracked in #2545.
    • aging_cards in the MCP server compares a card's current dwell with the column's completed-dwell percentile. It is not the WIP age chart, which ages whole in-progress cards against cycle time.

    Empty states¶

    Every empty state names the next action, except Needs attention with nothing to list, which is good news and says so. When no block overlapped the period, Why cards get blocked stays on the page and says no blocked reasons were recorded, and that marking a card blocked with a reason on the board fills it. The other panels say how to get data into them (move cards between columns) or how to widen the view (a longer Date range, or Clear all filters).

    Empty period¶

    When the selected window has no movement data at all (a new board, or a period before any activity), the view shows an informational message instead of an empty heatmap. Widen the period or add some card movements.

    CSV export¶

    Click Export CSV, at the right of the filter bar, to download the heatmap data for spreadsheets: the rows of the mode last chosen, in a file named analytics-{mode}-{days}d.csv. It includes all active columns, the velocity column, and a stalled card count per swimlane. The stalled count follows the same planned-child rule as Needs attention. The button is visible only to admin and site_admin users. Names in the export are quoted where needed, and leading =, +, - and @ characters are removed, the same as the board CSV export.

    API reference¶

    API: GET /api/v1/boards/{id}/analytics/?days=30. The charts use the flow metrics endpoints: the Overview reads all of them through one metrics/overview request, which loads the board's history once instead of once per chart (#2426).

    Parameter Type Default Constraint
    days integer 30 1–365. Returns 400 if non-integer or out of range.
    stalled_days integer Board's staleness_threshold_days Optional override, 1–90. Returns 400 if non-integer or out of range. When omitted, the board setting is used.
    swimlane_id integer None Optional, 1.3+. Narrows every section to one swimlane. Returns 400 if malformed or not a swimlane on this board.
    label_id integer None Optional, 1.3+. Narrows every section to cards with this label. Returns 400 if malformed or not a label on this board. Combined with swimlane_id, both must match.

    The response includes two threshold fields:

    Field Meaning
    staleness_threshold_days The board's configured threshold, used for heatmap cell coloring. Always reflects the board setting regardless of any stalled_days override.
    stalled_threshold_days The effective threshold used for the stalled cards list. Equals the board setting by default, or the stalled_days query parameter value when provided.
    stale_warning_pct The board's warning percentage (0--100). Controls the yellow/green boundary in the heatmap.
    done_columns List of column names excluded from the heatmap because they are marked as done.
