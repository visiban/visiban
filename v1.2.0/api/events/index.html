    Replay missed board changes with one cursor request¶

    GET /api/v1/boards/{id}/events/?after=<last event_id> returns what happened on a board since your last event, in order.

    curl -H "Authorization: Token $TOKEN" \
  "http://localhost:8000/api/v1/boards/3/events/?after=84200"
# 200 {"results": [{"id": 84213, "event": "card.moved", ...}], "next_cursor": 84213, "next": 84213}

    Why it matters: a consumer that drops offline can resume from its last cursor and miss nothing, without re-fetching the whole board.

    How it works: every board mutation is appended to a durable, ordered feed that a consumer outside the Django process — a second front end, a CRM sync job, the MCP REST client — can read with a cursor instead of holding a WebSocket open and hoping it never drops.

    Yes, but: history is bounded by an operator-set retention window, so handle 410 Gone by re-fetching GET /api/v1/boards/{id}/full/. See Retention.

    Go deeper: the endpoint, stability guarantees (the last section), what each reader sees.

    Since 1.2

    The change feed is new in Visiban 1.2.

    The feed completes the WebSocket API rather than replacing it. The socket tells you about a change now; the feed tells you what happened while you were not listening. Both carry the same payloads, so one handler serves both.

    How the two surfaces fit together¶

    1. Open the board WebSocket and process frames as they arrive.
    2. Remember the event_id of the last frame you processed.
    3. When the socket drops and reconnects, call GET /api/v1/boards/{id}/events/?after=<last event_id> and replay the results through the same handler. No /full/ re-fetch, no diffing.
    4. If that call returns 410 Gone, events after your cursor have aged out of the retention window. Keep the next_cursor from the 410 body, re-fetch GET /api/v1/boards/{id}/full/, then resume with GET /api/v1/boards/{id}/events/?after=<that next_cursor> (1.3+). An event written between the 410 and your re-fetch can arrive both in /full/ and on the resumed feed, so apply events idempotently; none is skipped.

    A consumer with no socket can poll the feed on its own schedule; the cursor makes repeat reads exact.

    (1.3+) A consumer that would rather be called than poll can register a webhook: each delivery is one row of this feed, as a viewer reads it, signed and sent in id order.

    GET /api/v1/boards/{id}/events/¶

    Returns committed events for one board, in ascending id order.

    Access — the requesting user's board role, exactly as for GET /api/v1/boards/{id}/full/ and for the WebSocket handshake. Every board role, including viewer, may read the feed. A caller with no access to the board gets 404. The feed returns the board's retained rows whenever the reader joined the board, bounded by retention, and each row is filtered for the reader by the rules in Fields that depend on who is reading, which match what the WebSocket sends that reader.

    Query parameters

    Parameter Default Description
    after 0 Return only events with an id strictly greater than this. Pass the last id you processed. 0 (or omitted) starts at the oldest retained event.
    limit 100 Maximum events to return. Must be between 1 and 500.

    Both parameters are validated, not clamped. A malformed after is a 400, not a silent restart from the start of the feed, because a consumer that quietly replayed processed history would never notice. A limit outside the range is a 400 for the same reason: a consumer that asked for 10000 and silently got 500 would read len(results) < limit as "caught up" and stop paging with events unread.

    Response

    {
  "results": [
    {
      "id": 84213,
      "event": "card.moved",
      "data": { "card": { "...": "..." }, "movement": { "...": "..." } },
      "actor_id": 7,
      "actor": { "id": 7, "username": "alice", "display_name": "Alice", "avatar_url": "" },
      "created_at": "2026-09-15T10:22:41.881Z",
      "redacted_at": null
    }
  ],
  "next_cursor": 84213,
  "next": 84213
}
    Field Type Description
    id integer The event's id. This is the value that appears as event_id on the matching WebSocket frame, and the value to pass back as after.
    event string Event type — the same dotted names the WebSocket uses. See the event reference.
    data object The broadcast payload, verbatim. Identical to the WebSocket frame's data, except on a redacted row.
    actor_id integer / null The user the row attributes the event to, or null when the row records no actor: there was no authenticated actor, or the event is a system record not attributed to a user (for example share_link.updated and the board.updated recorded with a share-link change). A plain column, not a foreign key: it keeps its value even after the account is deleted.
    actor object / null Added in 1.2 (#1663). The same user as actor_id, in the nested BoardUser shape (id, username, display_name, avatar_url) used by every board-scoped actor field except invite links — see Actor fields. It resolves even when the actor has since left the board, so you do not need the member list to label a row. null when actor_id is null or the account no longer exists. Every actor on a page is fetched in one query, so page cost does not grow with the number of distinct actors.
    created_at string ISO 8601 timestamp of the write.
    redacted_at string / null Added in 1.3 (#1816). ISO 8601 timestamp at which an operator's card-history purge redacted this row's card content, or null for a row that was never redacted. See Redacted card events.
    next_cursor integer / null Cursor for the following page, or null when the caller is caught up. null means "this page was short, so it was the last one"; a non-null value means "ask again with after=<next_cursor>". It is an integer, not an opaque string: it is the exclusive id cursor that after takes.
    next integer / null Deprecated; use next_cursor. Always identical to next_cursor. Kept through 1.x for clients written against 1.2.0-beta.1.

    Paging¶

    curl -s -H "Authorization: Token vbn_..." \
  "http://localhost:8000/api/v1/boards/42/events/?after=0&limit=200"

    Call again with after set to the previous next_cursor until next_cursor is null. Order is by id, which follows insertion order and is usually, but not always, commit order (see Event coverage and #2053). Never re-sort by created_at: two events can share a timestamp.

    Pagination shapes¶

    Besides the standard offset envelope ({count, offset, page_size, results}) and bare arrays for small bounded lists, the API has three cursor/link shapes (see Pagination for the full list). They differ on purpose, and each is frozen by the release that introduced it (decision recorded for #1869):

    Endpoint Shape Why it stays
    Change feed, GET /boards/{id}/events/ {results, next_cursor: int \| null} (plus deprecated next) The cursor is the exclusive event id, a monotonic integer a consumer also gets as event_id on WebSocket frames, so it is an integer rather than an opaque string. The key name matches /cards/, but the request parameter and type differ: the feed takes an integer via after, while /cards/ takes an opaque string via cursor. The two do not share a request contract.
    Cross-board GET /cards/ {results, next_cursor: string \| null} The cursor is an opaque string the server may re-encode, so clients must not parse it.
    Card timeline (1.1) limit/offset with next / previous as URL strings A limit/offset shape, not a cursor. Frozen in 1.1; a field cannot be renamed or retyped without a major bump.

    New cursor-paginated endpoints should name the response key next_cursor but document their own request parameter and cursor type. A client cannot reuse the feed's after for /cards/, nor cursor for the feed (the feed ignores an unknown cursor and returns page 1 again). The feed's earlier next key (1.2.0-beta.1) stays as a deprecated duplicate, so the rename is not breaking.

    Errors¶

    Status Body Condition
    400 Bad Request {"detail": "after must be an integer event id.", "code": "invalid_query_param"} after is not an integer, or is negative ("after must not be negative.").
    400 Bad Request {"detail": "limit must be between 1 and 500.", "code": "invalid_query_param"} limit is not an integer ("limit must be an integer."), or is out of range.
    404 Not Found — No board with that id, or the requesting user has no access to it.
    410 Gone {"detail": "...", "code": "cursor_expired", "resync_url": "http://.../api/v1/boards/42/full/", "next_cursor": 84213} An event after the cursor that you could have read has been pruned, so the consumer has missed events it can no longer read. Re-sync via resync_url, then resume with next_cursor as after. next_cursor (1.3+, #2058) is the board's newest event id or its highest pruned id, whichever is greater, taken when the 410 is sent. Resuming from it does not return 410 again unless a later prune removes events after it.

    When a cursor expires

    (1.3+, #2058, #2079) The pruner records, per board and event type, the highest event id it deleted, and a cursor is expired when an event you could have read was pruned after it:

    • Your cursor's own event was pruned, but nothing after it was. Not expired. A consumer idle on a quiet board for longer than the retention window has missed nothing: it gets an empty page, or the new events once they arrive.
    • An event after your cursor that you could have read was pruned. 410, even when the page would otherwise be empty. The events you missed are gone, whether or not anything newer has been written since.
    • The only events pruned after your cursor are ones you would never have been shown. Not expired. Those are another user's per-user events (stars and saved filters) and share_link.updated when you are below admin. Your own stars and saved filters do count.
    • after omitted or 0. Never 410: it means "start at the oldest retained event", not a position you held.
    • A cursor that was never one of this board's event ids (for example, one taken from another board's feed). 410 once the board has newer events, if it is above everything pruned from the board, or 410 if an event you could have read was pruned after it. Otherwise the feed cannot tell it from a position you really held, so it reads on from that id. Keep each board's cursor separate: a cursor is only meaningful on the board that issued it.

    Your role now decides, as it does for every row of the feed. If you have become an admin since, a pruned share_link.updated after your cursor returns 410, because the feed now shows you those rows and that one is gone. If you have stopped being an admin, it no longer does.

    Where the record has no type detail, it counts for you. A record written before the per-type detail existed does not say what was pruned, so it counts as an event every reader could have read. That costs a re-sync you may not have needed; it never skips an event you could have read.

    Boards not pruned since the upgrade to 1.3. An install that pruned with 1.2 recorded nothing, so for a board whose events have not been pruned since the upgrade the feed keeps the 1.2 rule: a missing cursor returns 410 when newer events exist and an empty page when none do. The board switches to the exact rule the first time the pruner deletes one of its events. That first prune also records where its record begins: a cursor older than the first event it deleted returns 410, because what 1.2 removed before that is unknown.

    Event coverage¶

    Every event type the WebSocket emits on the board channel is persisted: board.*, column.*, swimlane.*, label.*, custom_field.*, swimlane_custom_field.*, card.*, member.*, saved_filter.*, lens_connection.*, and (1.2+) invite_link.* (payload { "id" } only, readable by every board member like the socket frame). The WebSocket event reference is the single list of payload shapes for both surfaces.

    Two consequences worth knowing:

    • Blocking is a card.updated row (since 1.3). Blocking or unblocking a card records card.updated with the full card, whose additive is_blocked, blocked_at and blocked_reason fields carry the new state (#1149). There is no card.blocked event type.
    • A rolled-back mutation appears nowhere. The feed row is written inside the same database transaction as the mutation it describes, and the broadcast is deferred until that transaction commits. A mutation the database refused produces neither a row nor a frame.
    • board.deleted is in the feed. The event outlives the board it describes, so a consumer holding a cursor learns the board is gone rather than simply losing access mid-stream. Its own board is of course no longer readable, so fetch it from the cursor you already hold, not from a fresh call.
    • Ids follow insertion, not commit. A row's id is assigned when the transaction that writes it inserts the row, and that transaction may commit after a later transaction with a higher id. A reader that pages with after= at exactly that moment can move its cursor past the lower id before it becomes visible, and never see it. The window is the length of the slower transaction, normally milliseconds. Until #2053 adds a commit-ordered cursor, a consumer that needs every row should re-read a short overlap (for example, the last few seconds of rows) and deduplicate on id. The webhook dispatcher does the equivalent by reading only rows older than WEBHOOK_SETTLE_SECONDS.
    • A container delete is one delete event. Deleting a column, swimlane, or board deletes its cards too, and the feed records only the column.deleted, swimlane.deleted, or board.deleted row, with no card.deleted row per card. Treat it as the delete of every card in that container. A surviving card that one of the deleted cards was blocking gets a card.updated row with its lowered blocker_count (since 1.2), on its own board's feed. See Deleting a container deletes its cards.

    Fields that depend on who is reading¶

    • is_moderator is stripped from member.added and member.updated payloads for readers below admin, exactly as the WebSocket consumer strips it per subscriber (#978) — except on the row belonging to the reader themselves, which always carries the field (#1191, mirroring the /full/ self-row exception from #1173). Replaying from the feed cannot surface a field the socket withheld from that same reader.
    • is_site_admin is stripped from the same payloads for readers below admin, with no self-row exception, matching the WebSocket consumer (since 1.2). An unknown reader role strips it.
    • is_starred on board.created and board.updated rows is the actor's star state at the time of the event. Since 1.2 it is returned only to the reader who is that row's actor_id; every other reader gets the row without the is_starred key, and a row with a null actor_id omits it for everyone (#1705). This matches the WebSocket, which sends the field only to the acting user's own sockets. Clients should not rely on it for star state: use board.star_changed, or read GET /api/v1/boards/{id}/ for the caller's own value (#1559).
    • share_token, share_token_expires_at, share_link_active (1.2+) and share_token_hash (which no serializer declares) are dropped from every payload for every reader, whatever their role. Board admins read them over REST only (GET /api/v1/boards/{id}/full/ and the share action response; share_token on /full/ is deprecated since 1.2, see Boards).
    • board.star_changed, saved_filter.created and saved_filter.deleted rows are returned only to the user named in their user_id, matching the WebSocket, which delivers those frames only to that user's own sessions (#1677). Other readers' pages simply do not contain them; a page is still filled to limit from the remaining rows, and cursors are unaffected.
    • share_link.updated rows (since 1.3) are returned to admin / site_admin readers only, matching the WebSocket, which sends that frame to admin sockets only (#1967). As with per-user rows, other readers' pages simply do not contain them and are still filled to limit. See Share link events.
    • invite on an invite-redemption member.added row is returned to admin / site_admin readers only, with no self-row exception, matching the WebSocket consumer (#1677). An unknown reader role strips it.
    • custom_field_values on swimlane.created, swimlane.updated and swimlane.reordered rows is re-filtered on every read against the board's current swimlane field definitions (#1677). A stored row keeps the values that were shareable when it was written; a field marked is_admin_only or deleted since then is omitted from that row for every reader, admins included, because the WebSocket never carries admin-only values to anyone. Stored rows are not rewritten, so a field made shareable again replays again. The custom_field_values key itself is always present.

    Redacted card events¶

    Added in 1.3 (#1816)

    An operator can erase a card's content on request with the purge_card_history command (see Card History Retention). It redacts that card's card.created, card.updated, card.unarchived and card.moved rows rather than deleting them, so cursors and paging are unaffected.

    A redacted row has a non-null redacted_at, and in its data:

    • title, description and blocked_reason are null, in the card object (the top-level data, or data.card for card.moved);
    • each custom_field_values entry keeps its field_definition and has value: null;
    • external_ref, when the card had one, keeps provider and has ref: null and url: null;
    • in card.moved, movement.card_title and movement.notes are null. sibling_positions (since 1.3, #1890) holds only ids, positions and versions, and is kept unchanged.

    Every key is kept, at every level, so the row has the same shape as when it was written. uid, id, column, swimlane, labels, is_blocked, blocked_at and the other fields are unchanged. A consumer that replays rows into local state should skip the content fields of a row whose redacted_at is set. Otherwise it overwrites a live card's title with null, which can happen after a purge that included live cards.

    Retention¶

    Events are kept for BOARD_EVENT_RETENTION_DAYS days (default 30) and removed by a management command. Nothing expires on its own: an install that never runs the pruner grows the board_events table forever. Retention bounds how much history the feed returns: any reader with access to the board receives every retained row for it, whenever they joined, each filtered by the rules in Fields that depend on who is reading. Run the pruner on a schedule:

    # See what would go, without deleting anything
python manage.py prune_board_events --dry-run

# Prune using the configured window
python manage.py prune_board_events

# Override the window for one run
python manage.py prune_board_events --days 7

    Schedule it nightly. Both deployment paths ship an opt-in scheduler with this job off by default. Turn it on with SCHEDULE_PRUNE_BOARD_EVENTS=03:00 in .env for the Compose scheduler profile, or scheduledJobs.pruneBoardEvents.enabled=true in Helm. Host cron also works:

    0 3 * * * docker compose run --rm backend python manage.py prune_board_events

    See Scheduled Jobs.

    Deletion runs in batches (--batch-size, default 5000), so a large cleanup does not hold locks against concurrent writers for the whole run. Each batch also records, per board and event type, the highest event id it deleted, in the same transaction; that record is what decides when a cursor expires. --dry-run records nothing.

    See Configuration for BOARD_EVENT_RETENTION_DAYS.

    A webhook that falls further behind than the window, and misses an event it would have been sent, is turned off with disabled_reason: "cursor_expired" instead of skipping what was pruned, the webhook counterpart of 410.

    Sizing the window¶

    Pick a retention window longer than the longest outage a consumer should survive. A consumer offline longer than the window is not broken: if events it could have read were pruned, it gets a 410 and re-syncs; if the board was quiet and nothing it could have read was pruned, it keeps reading. But every re-sync is a full /full/ fetch, so a too-short window makes routine restarts expensive.

    Using the client¶

    Experimental, 0.x

    The Python and TypeScript clients are new in 1.3 and are not published to PyPI or npm. Their API can change in any 0.x release, and they follow the 1.x compatibility rules only once they reach 1.0. The feed itself is the stable contract; the clients are a convenience over it.

    Every consumer outside the Django process ends up writing the same loop: hold a cursor, page the feed, save the cursor, and handle 410 by re-syncing. The clients in clients/python and clients/typescript implement exactly that and nothing else. They are not a general REST SDK. Both need server 1.3 or later, because only 1.3 returns next_cursor on a 410 (see When a cursor expires). Against a 1.2 server a 410 raises ResyncUnsupported rather than guessing a resume point.

    Standard library only, Python 3.10+. Install from a checkout: pip install ./clients/python.

    from visiban_client import Client, Resync

client = Client("https://visiban.example.com", token)  # a PAT with the `read` scope
for item in client.iter_events(board_id):               # returns once caught up
    if isinstance(item, Resync):
        replace_local_state(item.snapshot)               # the /full/ board state
    else:
        handle(item)                                     # one feed row, as a dict

    No runtime dependencies, Node 20.3+ (global fetch, AbortSignal.any). npm cannot install from a Git subdirectory, so build a tarball from a checkout: cd clients/typescript && npm ci && npm run build && npm pack, then npm install ./visiban-client-0.1.0.tgz.

    import { Client, Resync } from "@visiban/client";

const client = new Client({ baseUrl: "https://visiban.example.com", token });
for await (const item of client.iterEvents(boardId)) {
  if (item instanceof Resync) replaceLocalState(item.snapshot);
  else handle(item);
}

    What the client does

    • Pages with after and limit until next_cursor is null, and yields rows in id order. "Caught up" is the server's next_cursor: null; the client never counts rows, because a full page may or may not be the last one (see Paging).
    • Advances the cursor only after your loop body returns for an item, through a pluggable cursor store (pass your own get/set for durable storage). Leaving the loop early, or an exception in your handler, leaves that item uncommitted. To redeliver it, call iter_events / iterEvents again for a new iterator over the same store; resuming the old generator after an exception would treat the failed item as handled and commit it. That is at-least-once delivery: make handlers idempotent. The clients do not offer exactly-once. The default store is an in-memory one created per call, so a bare iter_events(board_id) replays from 0 every time: keep one store across calls, or pass cursor, to resume.
    • On 410 cursor_expired, keeps the 410's next_cursor, fetches /full/, and yields a Resync carrying the snapshot and that cursor. The stored cursor moves to it only after your handler returns for the Resync, then the feed resumes from it. An event written around the re-sync can arrive both in the snapshot and on the resumed feed, so apply events idempotently.
    • Passes redacted rows, unknown event types and unknown fields through untouched; it never raises on them.
    • Backs off on 429, 5xx and network errors (honoring Retry-After, capped), and polls on a configurable interval. Without a poll interval it returns once caught up.
    • Authenticates with a scoped personal access token only (read is enough: the clients issue only GETs). It sends requests only to the host in the base URL you configured: a resync_url is reduced to its path and redirects are never followed. It refuses plain http:// to a non-loopback host unless you opt in. Proxies: Python's urllib honors the HTTP_PROXY / HTTPS_PROXY environment variables, so the token travels through that proxy (and is readable by it over plain http); Node's built-in fetch does not read them by default. Use https and review proxy variables in the consumer's environment.

    Late-committing rows. Ids follow insertion, not commit (see Event coverage), so a paging reader can step past a row that commits a moment later and never see it. The clients have no overlap option in 0.x and their reads are not gap-free. A consumer that needs every row can re-read a short overlap itself and deduplicate on id, as described under Event coverage, until #2053 adds a commit-ordered cursor.

    Verifying webhooks. The same packages include verify_signature / verifySignature for webhook deliveries. It is experimental until the webhooks API is declared stable (#2070). In TypeScript it lives in the separate @visiban/client/webhooks entry point, so the main entry stays free of node:crypto and browser-safe.

    Tested against a real server. The clients-contract CI job boots a backend and runs both packages' live tests, with the VISIBAN_CONTRACT_REQUIRED flag set so missing configuration fails the job instead of skipping. It runs on merge request and main pipelines (never on schedules) when clients/**, the boards feed code (views, serializers, models, URLs, permissions, broadcast, services/feed.py, the pruner), backend/accounts/**, backend/visiban/ settings, URLs, permissions or exceptions, backend/webhooks/**, backend/requirements.txt, .gitlab-ci.yml, or the events and webhooks docs change. A shared fixture file drives both languages' unit suites, which keeps them behaving alike on the scenarios it covers; it does not prove they match elsewhere.

    Stability and versioning¶

    Added in 1.2

    The change feed is a public contract from 1.2 and follows the same compatibility rules as the REST API from 1.0 onward. It is not experimental.

    • The endpoint, its after and limit parameters, and the response envelope (results, next_cursor, and the deprecated next) are never removed or renamed in a minor or patch release. The cursor semantics (after is exclusive, ordering is by id, next_cursor is null once a page comes back short) and the 400, 404, and 410 error behavior described on this page do not change, with one stated exception: the condition for 410 was corrected in 1.3 (see the bullet on it below). The 410 status, code, detail and resync_url did not change; the body only gained next_cursor.
    • Row fields (id, event, data, actor_id, actor, created_at, and since 1.3 redacted_at) only gain fields; an existing field keeps its name and type and is never removed.
    • Redacted rows are the exception to "verbatim". A row an operator's purge redacted keeps every payload key but carries null content values (see Redacted card events). Clients must accept null for those fields on a row whose redacted_at is set.
    • Event types and payloads carry the same {event, data} payloads as the WebSocket, so the same rules apply: an event type is never removed, a payload field is never removed, and new event types and payload fields can appear in any minor release. Clients should ignore event types and fields they do not recognize. Retiring an event follows the process in Retiring an event.
    • Per-reader fields are the exception. The fields documented under Fields that depend on who is reading are per-reader and may be withheld from recipients who lack access, including when the rule is tightened for security reasons (as in 1.2). Clients must treat them as optional.
    • next_cursor is the cursor; next is deprecated. next_cursor is the documented cursor field. next was the name in 1.2.0-beta.1 and is still emitted with an identical value in every response, so clients written against the beta keep working. New clients should read next_cursor. next is removed only at a major version bump. See Pagination shapes.
    • When 410 fires was corrected in 1.3 (#2058). It now fires when an event after the cursor that you could have read was pruned (#2079): an idle consumer whose own cursor event was pruned no longer gets it, and a consumer whose missed events were all pruned now does, rather than an empty page. The status, code and resync_url are unchanged, and the body gained next_cursor, the cursor to resume from after re-syncing. A client that handles 410 by re-syncing keeps working; reading next_cursor lets it resume the feed without a socket event_id. See When a cursor expires.
    • A part of the feed that must go away is marked deprecated here for at least one minor release, and removal needs a major version bump.
    • Not covered: how long history is kept. The retention window is an operator setting (BOARD_EVENT_RETENTION_DAYS), so a consumer must handle 410 Gone rather than assume any particular depth of history. See Retention.
