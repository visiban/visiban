    Create, move, and track cards¶

    Create a card with POST /api/v1/boards/{board_id}/cards/, sending a title, a column, and a swimlane (member role or above):

    curl -X POST -H "Authorization: Token $TOKEN" -H "Content-Type: application/json" \
  -d '{"title": "Fix login bug", "column": 1, "swimlane": 2}' \
  http://localhost:8000/api/v1/boards/3/cards/

    List a board's cards with GET on the same path.

    Yes, but: the target column must have allow_card_creation enabled, and WIP or weight limits can answer 409. See create and WIP and weight limit enforcement.

    Go deeper: Cards, Archive, Move, History, Timeline, Comments, Attachments, Relations, Parent and children, Checklist.

    Why it matters: card writes appear in activity history and reach connected clients over WebSockets, so a script's moves are visible to the team.

    The big picture: cards and everything attached to one — moves, comments, attachments, checklists, relations, and activity history.

    Cross-board card query¶

    GET /api/v1/cards/¶

    Added in 1.2

    Paginated, filterable card query across every board the requesting user can access — for table/list views over large boards and for incremental sync (?updated_since=). This is additive: it does not change GET /api/v1/boards/{board_id}/cards/ (a bare array of up to 200 cards per request, offset-paged with optional limit/offset) or GET /api/v1/boards/{board_id}/full/ (every active card, unpaginated) below.

    Access scoping: identical to GET /api/v1/boards/ — boards you own, are a direct member of, or have via group-ancestry inheritance, or every board if you have can_access_all_content. A card never appears here unless its board would appear in your board list; this holds even if you pass ?board=<id> for a board you cannot access — the result is an empty page, not a 403.

    Response shape: {results, next_cursor} — not the {count, offset, page_size, results} envelope OffsetCountPagination uses elsewhere. This endpoint uses cursor pagination instead of offset pagination because it is designed for a card feed under concurrent writes (incremental sync): offset pagination needs a stable row order and COUNT(*), and a page walk can otherwise skip or repeat rows as cards are created/updated/archived between page fetches. There is no previous field — walk forward only, re-fetching page one (no cursor) to restart.

    {
  "results": [
    { "id": 101, "uid": "3a9f1c2d7e4b8a05", "board": 4, "column": 2, "swimlane": 1, "...": "..." }
  ],
  "next_cursor": "cD0yMDI2LTA0LTAxKzAwJTNBMDAlM0EwMA%3D%3D"
}

    next_cursor is null on the last page. Pass it back as ?cursor=<value> to fetch the next page; treat it as opaque.

    Query parameters

    Parameter Description
    ?board=<id> Restrict to one board
    ?swimlane=<id> Filter by swimlane ID
    ?column=<id> Filter by column ID
    ?assignee=<id> Filter by assignee user ID
    ?label=<id> Filter by label ID
    ?priority=<value> Filter by priority (low, medium, high, urgent)
    ?due_before=<YYYY-MM-DD> Cards with a due date on or before this date (ISO 8601)
    ?due_after=<YYYY-MM-DD> Cards with a due date on or after this date (ISO 8601)
    ?updated_since=<ISO 8601 datetime> Cards updated at or after this timestamp — the incremental-sync filter. A UTC offset of 16 hours or more returns 400
    ?include_archived=true Include archived cards. Omit or false to exclude them (the default, matching the endpoints below)
    ?search=<q> Filter by title and description (partial, case-insensitive; results are unchanged for ASCII text; case folding of some non-ASCII letters, such as Turkish dotted/dotless i and Greek final sigma, may differ from earlier releases). A value containing a NUL (0x00) character returns 400 with {"detail": "search must not contain NUL (0x00) characters.", "code": "invalid_query_param"} (Changed in 1.3, #1887; it was a 500 on PostgreSQL)
    ?ordering=<field> Sort results. Allowed values: updated_at (default: -updated_at, i.e. most recently updated first), -updated_at, created_at, -created_at. Every value is a 2-tuple with an id tiebreaker under the hood, so cursor pagination stays stable when many cards share the same timestamp. An unrecognized value falls back to the default rather than erroring. due_date is deliberately not an ordering option — it is nullable, and a nullable cursor field can silently skip or duplicate rows across a page boundary.
    ?cursor=<opaque> Page cursor from a previous response's next_cursor. A cursor that cannot be decoded, or whose position is not a timestamp Postgres can store (not a valid date and time, or a UTC offset of 16 hours or more), returns 400 with {"detail": "cursor is not a valid page cursor.", "code": "invalid_query_param"}
    ?page_size=<n> Rows per page (default 50, max 200)

    Rate limit: 120 requests/minute per user (scope card_query), counted separately from the general 5000/hour per-user budget. Over the limit the endpoint answers 429 Too Many Requests with {"detail": "Request was throttled. Expected available in N seconds."} and a Retry-After header. A client doing incremental sync should pace its page walk and honor Retry-After. See Rate limits.

    A filter value that fails its type check (?updated_since=x, ?assignee=x) returns 400 with {"updated_since": ["Enter a valid date/time."], "detail": "updated_since: Enter a valid date/time.", "code": "invalid_query_param"}: the bad query parameter shape, plus a field-keyed entry for the parameter.

    Card response fields: the same fields as the card response field table under GET /api/v1/boards/{board_id}/cards/{id}/ below, plus board (the board's integer ID) — single-board endpoints omit board because the URL already scopes to one board; a cross-board list has to say which board each row belongs to. assignee_id and label_ids (the write-only fields used to set an assignee or labels) are not present — this endpoint is read-only. This includes external_ref (read-only here; null when unset). Since 1.3 (#1922) this includes dimension_plans, in the same shape ([] when nothing is planned), and since 1.3 (#2651) dimension_states, in the same shape ([] when no dimension has a value).

    Cards¶

    GET /api/v1/boards/{board_id}/cards/¶

    List the board's active (non-archived) cards, optionally filtered. Returns at most 200 cards per request.

    Response shape: a bare JSON array ([ {...}, {...} ]), not the standard {count, offset, page_size, results} envelope of other list endpoints, and not the {results, next_cursor} shape of the cross-board GET /api/v1/cards/ above. Generic clients that assume an envelope must special-case it. The board UI bulk-loads cards via GET /api/v1/boards/{board_id}/full/ (no cap); use this endpoint for targeted lookups such as search.

    200-card cap and truncation headers (since 1.2)

    Without limit/offset the response is the first 200 matching cards, as before. Every 200 response also carries two headers that tell a client whether it got everything:

    Header Value
    X-Total-Count Number of active cards matching the filters, ignoring limit/offset
    X-Truncated true when more matching cards exist after the returned ones, otherwise false

    Both headers are CORS-exposed, so cross-origin browser clients can read them. Before 1.2 a board with more than 200 matching cards was truncated with no signal.

    To walk past the cap, page with limit and offset (offset paging, not the cursor paging of GET /api/v1/cards/):

    GET /api/v1/boards/4/cards/?limit=200&offset=0     -> X-Total-Count: 450, X-Truncated: true
GET /api/v1/boards/4/cards/?limit=200&offset=200   -> X-Total-Count: 450, X-Truncated: true
GET /api/v1/boards/4/cards/?limit=200&offset=400   -> X-Total-Count: 450, X-Truncated: false

    Rows are ordered by ordering with the card ID as tiebreaker, so a walk over an unchanged board returns every card exactly once. Cards created, moved or archived mid-walk can still shift rows across a page boundary; for a feed under concurrent writes use the cursor-paginated GET /api/v1/cards/?board=<id>.

    Query parameters

    Parameter Description
    ?limit=<n> Maximum cards to return. Default and maximum 200; a larger value is clamped to 200. 0 returns [] with the headers set (a count-only request). A blank value means the default; a negative or non-integer value returns 400 with {"detail": "...", "code": "invalid_query_param"}
    ?offset=<n> Number of matching cards to skip. Default 0. An offset past the end returns []. A blank value means the default; a negative or non-integer value is treated as 0, as on every other endpoint (Changed in 1.2, #1823). Only a value above 2^62 returns 400, with {"detail": "...", "code": "invalid_query_param"} like a bad limit
    ?search=<q> Filter by title and description (partial, case-insensitive; results are unchanged for ASCII text; case folding of some non-ASCII letters, such as Turkish dotted/dotless i and Greek final sigma, may differ from earlier releases). A value containing a NUL (0x00) character returns 400 with {"detail": "search must not contain NUL (0x00) characters.", "code": "invalid_query_param"} (Changed in 1.3, #1887; it was a 500 on PostgreSQL)
    ?assignee=<id> Filter by assignee user ID
    ?unassigned=true Return only cards with no assignee (false returns only assigned cards)
    ?priority=<value> Filter by priority (low, medium, high, urgent)
    ?column=<id> Filter by column ID
    ?swimlane=<id> Filter by swimlane ID
    ?due_before=<YYYY-MM-DD> Cards with a due date on or before this date (ISO 8601)
    ?due_after=<YYYY-MM-DD> Cards with a due date on or after this date (ISO 8601)
    ?overdue=true Cards past their due date (due date is set and is before today in INSTANCE_TIMEZONE: UTC by default; before 1.3, the server host's local date). false returns the rest: cards with no due date or a due date of today or later
    ?blocked=true Cards that are blocked, manually or by an active blocks relation (the card's is_blocked). false returns the rest. Added in 1.3 (#1149)
    ?ordering=<field> Sort results. Prefix with - for descending. Allowed fields: position (default), due_date, created_at, priority. Example: ?ordering=-due_date

    A filter value that fails its type check returns 400 with the field-keyed body this endpoint has returned since 1.1, plus detail and code (added in 1.2, #1832): ?assignee=x gives {"assignee": ["Enter a number."], "detail": "assignee: Enter a number.", "code": "invalid_query_param"}. Branch on code. See Error responses.

    POST /api/v1/boards/{board_id}/cards/¶

    Create a card. Requires member or above. The target column must have allow_card_creation enabled.

    The target column's WIP and weight limits are enforced exactly as on a move into it: 409 with wip_limit_exceeded, wip_hard_blocked, or weight_limit_exceeded, and a board admin (or the card's assignee, when enabled) may pass the optional ?force=true query parameter to override a soft limit (anyone else gets 403; hard mode has no override). Changed in 1.2 (#1428): creates were not checked before.

    notify_assignee (optional boolean, default false, since 1.3, #2211): true sends the card's assignee the assigned notification ("You were assigned to ..."), the same one an assignee change sends, once the create commits. It is skipped when the assignee is the caller, is inactive, turned off notif_card_assigned, or is not a current member of the board. The web app sends it only for a swimlane default team's pre-assignment; without it, a create with an assignee_id sends no assigned notification, as before (the MCP create_card tool and board import never send it). A value that is not a JSON boolean returns 400 keyed notify_assignee. Ignored on update. When the assigned notification is sent, the card's creation does not also send the "moved to <first column>" one, so the assignee gets exactly one notification (changed in 1.3, only for creates with notify_assignee: true). Every other create keeps its "moved" notification: an assignee who has Card moved on is still told the new card "moved to" its first column.

    Since 1.3 (#2191), the role is checked before the body is validated: a caller below member (a viewer or collaborator) gets 403 even when the body is invalid, where they previously got 400 with field errors for an invalid body. Members still get 400 for an invalid body, and a caller with no access to the board gets 404.

    Since 1.2, a create returns 404 Not Found (nothing is written) when its target column or swimlane, or the board, was deleted while the request was in flight (#1602).

    Request 

    {
  "title": "Fix login bug",
  "column": 1,
  "swimlane": 2,
  "priority": "high",
  "assignee_id": 5,
  "label_ids": [1, 3],
  "due_date": "2026-04-01",
  "weight": 2
}

    GET /api/v1/boards/{board_id}/cards/{id}/¶

    Get a single card. The response includes a read-only uid (a stable 16-character hex identifier that survives rename, move, and reassignment) and a version integer that increments when the card's fields are updated (including its labels and custom-field values), the card is blocked or unblocked (since 1.3, #1149), or the card is moved, and on every Django admin save of the card, including one that only archives or restores it (since 1.3, #2040). Archiving and restoring through the API or MCP, and comment, attachment, checklist or relation changes, leave it unchanged; it never decreases. Clients may pass version back on the move endpoint as an optimistic concurrency token.

    Card response field table

    Every card object has these fields, in this endpoint, POST /cards/, PATCH /cards/{id}/, GET /cards/, and all mutation responses (archive, unarchive, move).

    Field Type Read-only Nullable Description
    id integer yes no Database primary key
    uid string yes no Stable 16-character hex UID; never changes after creation
    column integer no no Column FK ID; update via the move endpoint only
    swimlane integer no no Swimlane FK ID; update via the move endpoint only
    title string no no Card title
    description string no no Rich-text description (plain text or Markdown); empty string if unset
    priority string no no One of "low", "medium", "high", "urgent"
    assignee object / null yes yes Assignee user — { id, username, display_name, avatar_url } or null
    assignee_id integer / null write-only yes Write-only FK for setting the assignee; omitted from responses
    labels array yes no Array of label objects — [{ id, uid, name, color }]
    label_ids integer[] write-only no Write-only list of label PKs; omitted from responses
    due_date string / null no yes ISO 8601 date (e.g. "2026-04-01") or null
    weight integer no no Story-point weight; default 1
    position integer no no Sort order within the column/swimlane cell (0-based); update via the move endpoint only — a PATCH/PUT that changes position returns 400 Bad Request (since 1.2, #1275). Echoing the current value back is accepted.
    created_by object / null yes yes User who created the card — same shape as assignee; null for cards created before the field was added
    created_at string yes no ISO 8601 creation timestamp
    updated_at string yes no ISO 8601 timestamp of last field update
    last_moved_at string / null yes yes ISO 8601 timestamp of the card's most recent CardMovement; null for cards that have never been moved
    last_move_is_creation boolean yes yes true when the most recent CardMovement is the card's creation (empty from_column_name, type move) rather than a move. Clients use it to avoid labeling a new card "moved"; last_moved_at is unchanged
    column_entered_at string / null yes yes ISO 8601 start of the card's open visit to its current column, since 1.3 (#459): the clock the dwell time overlay runs from. A swimlane-only move does not change it, unlike last_moved_at; a move to another column, a restore or a reopen does. null for an archived card, a card in a done column, and a card with no measured open visit (no recorded movement, or a column that does not match its history). Not on the anonymous share-link payload. Definition: Flow metric definitions
    attachment_count integer yes no Number of attachments on this card
    checklist_total integer yes no Total number of checklist items
    checklist_done integer yes no Number of checked checklist items
    checklist_open_due_dates array of strings yes no Since 1.3 (#445). Sorted YYYY-MM-DD due dates of the unchecked checklist items that have one. Not on the anonymous share-link payload.
    checklist_open_assignee_ids array of integers yes no Since 1.3 (#445). One user id per unchecked checklist item that has an assignee (a user repeats once per item). Not on the anonymous share-link payload.
    is_stale boolean yes no true when the card has not moved within the board's staleness_threshold_days window; false otherwise. is_stale ignores the card's column, so a Done-column card can be true; clients decide display. The stale-card notification digest, by contrast, skips Done-column cards.
    archived_at string / null yes yes ISO 8601 timestamp of archiving, or null for active cards
    version integer yes no Optimistic concurrency counter; increments when the card's fields are updated (including its labels and custom-field values), the card is blocked or unblocked (since 1.3, #1149), or the card is moved, and on every Django admin save of the card, including one that only archives or restores it (since 1.3, #2040), so a move sent with the version read before an admin save gets 409 version_conflict. Archiving and restoring through the API or MCP, and comment, attachment, checklist or relation changes, leave it unchanged. It never decreases, so a client can discard a copy of the card whose version is lower than the one it holds. Pass as version in the move endpoint to enable OCC. PATCH and PUT do not accept or check version.
    custom_field_values array no no Values for the board's custom fields — [{ field_definition, value }]. Readable and writable in the same shape; see below. Empty array when the card has no values.
    dimension_plans array yes no Added in 1.3 (#1922). One entry per planned dimension: [{ field_id, owner, next_action, target_date, updated_at }]. owner is a user object or null, target_date is YYYY-MM-DD or null. Read-only here; written through the dimension plan endpoint. Empty array when nothing is planned. Not part of the public share payload.
    dimension_states array yes no Added in 1.3 (#2651). When each dimension's value last changed: [{ field_id, changed_at }], one entry per dimension field that has a value, in the board's field order. changed_at is an ISO 8601 timestamp, or null when the time is unknown (a value set before 1.3 with no matching history entry, or one written on 1.3 by CSV import or the seed and demo commands, which record no time). Only a real change moves it: saving the value a card already has does not. Clearing a value removes its entry; a dimension with no value is "not set", and its age is the card's column_entered_at. Carried by the card's existing value read, so it adds no query. Not part of the public share payload.
    external_ref object / null no no Link to the GitLab/GitHub merge request, pull request, or issue that implements this card (since 1.2) — { provider, ref, url } or null. Always present; null when unset. Readable and writable in the same shape; see External ref.
    is_blocked boolean yes no Added in 1.3 (#1149). true when the card is blocked manually (blocked_at is set) or by at least one active blocks relation (blocker_count > 0). Derived; the one signal the card face and the board's Blocked only filter show.
    blocked_at string / null yes no Added in 1.3 (#1149). When the card's open manual block started, or null when it is not manually blocked. Changes only through the block and unblock endpoints; PATCH ignores it.
    blocked_reason string yes no Added in 1.3 (#1149). The open manual block's reason; "" when not manually blocked. Changes only through the block endpoint.
    blocker_count integer yes no Number of active cards blocking this one — see Relations. Counts only the blocks relation type, only where this card is the blocked end, and only where the blocking card is not archived. relates_to never contributes. The relation list itself is not on the card payload; fetch it from the relations endpoint.

    PATCH /api/v1/boards/{board_id}/cards/{id}/¶

    Update card fields. Requires member or above. Returns 404 Not Found if the card was deleted concurrently; nothing is saved. A PATCH/PUT racing an archive or move is evaluated against the card's state when written, not when the request began: it returns 404 Not Found if the card was archived concurrently (as for any archived card), and a concurrent move is kept. Only the submitted fields change, and echoing the pre-move column/swimlane/position is rejected with use_move_endpoint (see below).

    Ownership gate: Members may only edit cards they created. A member who did not create the card must have the is_moderator entitlement or be a board admin. Non-moderator members who did not create the card receive 403 Forbidden.

    Patchable fields: title, description, priority, weight, due_date, assignee_id, label_ids, custom_field_values, external_ref

    PUT /api/v1/boards/{board_id}/cards/{id}/ is also accepted, with the same permissions, ownership gate, side effects and errors. The difference is which fields are required. PATCH needs none. PUT requires title, column and swimlane, as on create; column and swimlane must be the card's current values (see the note below on moving cards), so a PUT is in practice a round trip of a card you just read. Any other field a PUT leaves out keeps its current value; it is not reset. Prefer PATCH for edits.

    Weight limit: raising weight in a column with a weight_limit, on a board with enforce_weight_limits on, returns 409 with weight_limit_exceeded (same body as a move) when the column's total would exceed the limit; a board admin (or the card's assignee, when enabled) may override with the optional ?force=true query parameter. Lowering weight, leaving it unchanged, or editing any other field is never blocked, even in a column already over its WIP or weight limit. The WIP limit is not checked, since the column's card count does not change. Changed in 1.2 (#1428).

    Custom field values (since 1.2)¶

    custom_field_values reads and writes in the same shape, so a returned representation can be sent straight back:

    { "custom_field_values": [{ "field_definition": 12, "value": "raid10" }] }
    • Only the fields named in the payload are touched. A PATCH naming one field leaves every other value alone.
    • Sending "" or null clears a field, removing its value rather than storing a blank. A cleared field is absent from later responses.
    • Values are validated and normalized per the definition's field_type: a number must parse as a finite decimal, a date must be YYYY-MM-DD, a dropdown value must be one of the definition's current choices, and a checkbox accepts true/false, "true"/ "false", "1"/"0" and "yes"/"no" and stores "true" or "false". A url must be an absolute http:// or https:// URL — see URL fields. A multi_select value is read back as a JSON array string ("[\"web\",\"ios\"]") and may be written as that string, as an array of strings, or as one plain choice; every entry must be a current choice or one already on the card — see Multi-select fields. A value may be at most 500 characters; a longer one (a long URL or a long multi-select included) is rejected, not truncated.
    • (Since 1.3, #2218) A date value is stored and read back as YYYY-MM-DD, whichever other spelling of the same day the server also accepts (20260105, 2026-1-5, or an ISO week date such as 2026-W02-1 or 2026-W02, which is that week's Monday). A number value keeps the spelling you sent ("1.50", "1e3"), except that digit-group underscores and non-ASCII digits are rewritten ("1_000" is stored as "1000"). The value is still a string. Values stored by earlier versions are rewritten the same way by the upgrade's migration, so a value you read back may differ in spelling from the one you wrote.
    • A field_definition id that does not belong to this card's board is rejected with 400, as is the same field appearing twice in one payload.
    • Setting a value is a card edit: it uses the same role allow-list and ownership gate as any other field, bumps version, and appears in the card.updated WebSocket payload.
    • is_required is not enforced in this release.

    Errors: - 400 Bad Request with the message on custom_field_values for any of the above. The whole update is rolled back, so one failed value never leaves a card half-updated.

    External ref (since 1.2)¶

    external_ref links a card to the merge request, pull request, or issue that implements it. It is also accepted on POST /api/v1/boards/{board_id}/cards/. Read and write share one shape:

    {
  "external_ref": {
    "provider": "github",
    "ref": "acme/webapp#123",
    "url": "https://github.com/acme/webapp/pull/123"
  }
}
    Key Type Description
    provider string One of "gitlab", "github", "other"
    ref string 1-255 characters. Surrounding whitespace is trimmed; no inner whitespace, control, or invisible Unicode formatting characters (e.g. zero-width space, bidi overrides). Freeform, e.g. owner/repo#123 or group/proj!45
    url string At most 2048 characters. Must be an absolute http or https URL with a host. Surrounding whitespace is trimmed; embedded whitespace, control, or invisible formatting characters are rejected, as are backslashes and a percent-encoded host
    • Omitting the key leaves the link untouched. Sending null removes it. Sending an object replaces the whole link; all three keys are required even on PATCH, and a partial object is a 400.
    • The response always includes the key; it is null when no link is set.
    • javascript:, data:, ftp:, protocol-relative, and relative URLs are rejected, as are URLs that embed credentials (user:pass@host). The host is not checked against provider, so self-hosted GitLab and GitHub Enterprise URLs are accepted.
    • Setting the link is a card edit: it uses the same role allow-list and ownership gate as any other field (viewers receive 403), bumps version, and appears in the card.updated WebSocket payload. This release writes no activity-history entry.
    • Not included in the anonymous public share-link payload, because a ref can reveal private repository names.
    • The field names and value rules above are a stable public contract. The model's full_clean() enforces the same rules, so an integration that writes the table directly must call it (or use the API).

    Errors: 400 Bad Request with the error nested under external_ref, keyed by sub-field:

    { "external_ref": { "url": ["Only http and https URLs are allowed."] } }

    A non-object value (other than null) returns { "external_ref": { "non_field_errors": ["..."] } }.

    column, swimlane, and position cannot be changed via PATCH/PUT. Echoing the card's current value is accepted, so a PUT client that round-trips the full representation still works. Submitting a different value, on the same board or another, is rejected with 400 and body {"code": "use_move_endpoint", "detail": "..."}. To move a card, always use POST /api/v1/boards/{board_id}/cards/{id}/move/, which enforces WIP/weight limits and writes the CardMovement audit trail.

    column and swimlane are also rejected on create (POST) when they reference a column/swimlane belonging to a different board — 400, not 404.

    uid is not patchable — any uid value sent in the request body is silently ignored.

    DELETE /api/v1/boards/{board_id}/cards/{id}/¶

    Delete a card. Requires member or above. Returns 404 Not Found if the card was deleted or archived concurrently; the request has no effect. Returns 409 Conflict with {"code": "links_changed", "detail": ...} if the card's parent/child links kept changing while it was being deleted; nothing is deleted, retry the request (#2409).

    Ownership gate: same rule as PATCH: members may only delete cards they created. A member who did not create the card must have the is_moderator entitlement or be a board admin. Non-moderator members who did not create the card receive 403 Forbidden.

    Deleting a card also deletes its relations. Broadcasts card.deleted, plus card.updated for every card this one was actively blocking, whose blocker_count drops as a result.

    Archive¶

    POST /api/v1/boards/{board_id}/cards/{id}/archive/¶

    Soft-delete a card. Takes no body. Sets archived_at to now, removes the card from the active board view, and excludes it from WIP/weight counts. Minimum role: Member. Returns 404 Not Found if the card was deleted concurrently. If the delete lands after the archive committed, the archive stays applied but the response is still 404, since no card is left to return (#1585).

    Ownership gate: same rule as PATCH: members may only archive cards they created. A member who did not create the card must have the is_moderator entitlement or be a board admin. Non-moderator members who did not create the card receive 403 Forbidden.

    If the card is already archived this is a no-op — 200 OK is returned with the current card state.

    Response — full card object with archived_at set.

    Broadcasts card.archived to all board WebSocket subscribers. Also broadcasts card.updated for every card this one was actively blocking, whose blocker_count changes when it leaves (or rejoins) the board.

    POST /api/v1/boards/{board_id}/cards/{id}/unarchive/¶

    Unarchive a card. Takes no request body (force is a query parameter, below). Clears archived_at; the card re-enters its original column and swimlane. It keeps its original position when no live card has taken that slot since; otherwise it goes to the end of the cell. Minimum role: Member. Returns 404 Not Found if the card was deleted concurrently (including a no-op restore of a card that vanished before the response was built, #1585); nothing is saved.

    Ownership gate: same rule as PATCH: members may only unarchive cards they created. A member who did not create the card must have the is_moderator entitlement or be a board admin. Non-moderator members who did not create the card receive 403 Forbidden.

    Response — full card object with archived_at: null.

    Archived cards do not count toward a column's limits, so a restore is checked like a move into the card's column: 409 with wip_limit_exceeded, wip_hard_blocked, or weight_limit_exceeded, nothing restored. A board admin (or the card's assignee, when enabled) may override a soft limit with the optional ?force=true query parameter; hard mode has no override. Restoring a card that is not archived is still a no-op 200. Changed in 1.2 (#1428).

    Broadcasts card.unarchived to all board WebSocket subscribers. Also broadcasts card.updated for every card this one was actively blocking, whose blocker_count changes when it leaves (or rejoins) the board.

    Block and unblock (since 1.3)¶

    Added in 1.3 (#1149)

    A card can be marked blocked with a reason ("Waiting on customer", "Vendor outage") and later unblocked. It is a state, not a dependency: use a blocks relation when the blocker is another card. Each block is recorded with who, when and why, so blocked time can be measured per card, summed per column in Analytics, and grouped by reason. See Blocked cards.

    Both actions follow the edit rule: minimum role Member, and a member may block or unblock only cards they created unless they have the is_moderator entitlement or are a board admin (403 otherwise). Viewers and collaborators get 403 before the body is read. An archived card, or a card on another board, is 404. Each bumps version, writes a CardActivity row (blocked / unblocked), and broadcasts card.updated with the full card after the transaction commits. There is no new WebSocket event type.

    Move¶

    POST /api/v1/boards/{board_id}/cards/{id}/move/¶

    Move a card to a new column/swimlane/position. Creates a CardMovement record if column or swimlane changes. Requires member or above. Since 1.2 it also returns 404 when the destination column or swimlane, or the board, was deleted while the request was in flight (#1602).

    Since 1.3 (#2225), the role is checked before the body's shape: a caller below member (a viewer or collaborator) gets 403 even when the body is not a JSON object, where they previously got 400 with {"detail": "Request body must be a JSON object."}. Members still get that 400, and a caller with no access to the board gets 404.

    Ownership gate: Members can freely move unassigned cards, cards assigned to themselves, and cards they created. Moving a card that is assigned to a different user and that the member did not create requires the is_moderator entitlement or Admin role.     Entry requirements (since 1.3, #1923)¶

    A column can require conditions on a card's custom fields before the card enters it (configured per column). They are checked on a forward move into another column (target position greater than the source), on create and on restore, never on a backward move, a swimlane-only move, a sub-column move or a weight update. The column's entry_enforcement decides what happens:

    • warn: the write succeeds, and the 200/201 body gains an additive entry_unmet list (the same item shape as below). The movement stores it (CardMovement.entry_unmet), and since 1.3 (#2655) every movement read returns it as entry_unmet: card and board movement history, the move response's movement, a timeline move entry's data, the JSON export and the MCP movement objects. It is null on a movement that recorded nothing. The key is absent from the 200/201 body when everything was met.
    • block: 409, unless an eligible actor (as for a soft WIP limit) retries with ?force=true and an override_reason. A missing reason is 400 override_reason_required, whoever the actor is.
    • hard: 409 for every role; force is ignored.
    {
  "code": "entry_requirements_unmet",
  "detail": "This card does not meet 1 entry requirement of \"Proposal\".",
  "column_name": "Proposal",
  "mode": "block",
  "unmet": [{"requirement_uid": "r1", "operator": "gt", "operand": "50000",
             "field_uid": "f1", "field_name": "Amount",
             "field_set_uid": null, "field_set_name": null}],
  "also": []
}

    also lists the bodies of the other limits the same write trips (for example a soft wip_limit_exceeded); one force and reason covers them all. When a hard WIP limit trips alongside an entry requirement, the hard body is returned and gains also naming the entry requirement. Bodies of writes that trip no entry requirement are unchanged. Over MCP there is no force, so block acts as hard. Clients older than 1.3 show their generic conflict message for this code; it can only occur on a column that opted into block or hard.

    WIP / weight limit enforcement¶

    When enforce_wip_limits or enforce_weight_limits is enabled on the board and the target column is at or above its limit, the move returns 409 Conflict. Since 1.2 (#1428) the same check, bodies, and override rules also apply to card create, restore from archive, and a PATCH that raises weight (see those endpoints above). Board import is exempt by design, because it restores a board as exported. The bodies:

    { "code": "wip_limit_exceeded", "column_name": "Doing", "current_count": 5, "wip_limit": 5 }

    { "code": "weight_limit_exceeded", "column_name": "Doing", "current_weight": 10, "weight_limit": 10, "card_weight": 2 }

    When enforce_wip_hard is enabled on the board, the limit cannot be overridden by any role — all users receive 409 Conflict with code wip_hard_blocked:

    { "detail": "WIP limit enforced — move blocked.", "code": "wip_hard_blocked", "column_name": "Doing", "current_count": 5, "wip_limit": 5 }

    When enforce_wip_hard is not enabled, board admins (or the card's assignee, when enabled) may override the limit by appending ?force=true to the move URL:

    POST /api/v1/boards/1/cards/42/move/?force=true

    ?force=true only matters when the move would otherwise be blocked by a real WIP or weight breach; on a move that hits no limit it is a no-op that succeeds for any role. A non-admin whose move does hit a limit and sends ?force=true receives 403 Forbidden.

    Swimlane limits¶

    Added in 1.3 (#1150)

    A swimlane can have its own wip_limit and weight_limit (see Swimlane limits). The same paths enforce them: move, create, restore, and a PATCH that raises weight. A move is checked against the target swimlane only when it adds to the swimlane's counted total, so a move between two counted columns of one swimlane, or into a column that does not count, never trips it. A move into a counted column from a column of the same swimlane that does not count (for example Done -> Doing under the default, where done columns do not count) is checked. Each swimlane chooses limit_enforcement: "block" (board admins (or the card's assignee, when enabled) can override with ?force=true), "hard" (no override for the WIP limit), or null to follow the board's flags as a column does. The bodies add swimlane_name; column_name names the target cell's column, and the counters are the swimlane's:

    { "code": "swimlane_wip_limit_exceeded", "column_name": "Doing", "swimlane_name": "Acme Corp", "current_count": 3, "wip_limit": 3 }

    { "detail": "Swimlane WIP limit enforced — move blocked.", "code": "swimlane_wip_hard_blocked", "column_name": "Doing", "swimlane_name": "Acme Corp", "current_count": 3, "wip_limit": 3 }

    { "code": "swimlane_weight_limit_exceeded", "column_name": "Doing", "swimlane_name": "Acme Corp", "current_weight": 8, "weight_limit": 10, "card_weight": 3 }

    When more than one limit trips, the response names the strictest: a hard limit before a soft one, then the column before the swimlane, then WIP before weight. A board with no swimlane limits gets exactly the column bodies above. One ?force=true from a board admin (or the card's assignee, when enabled) overrides every soft limit the move trips, and none of the hard ones.

    The *_uid fields in the movement record are permanent: they stay set after the referenced column or swimlane is deleted (the FK *_id becomes null, the UID is preserved). See Stable UIDs.

    History¶

    Paging a card's history lists¶

    1.3+

    GET on a card's movements/, activities/, comments/ and attachments/ returns a bare JSON array of every row on the card, as it always has. A long-lived card's activity log grows on every field edit, so since 1.3 each of the four also accepts optional paging parameters and always sends the card list's count headers. The body is the same bare array either way.

    Query param Notes
    limit Maximum rows to return, at most 200 (larger values are clamped). Omit it for every row. A negative or non-integer value is a 400 with {"detail": ..., "code": "invalid_query_param"}
    offset Rows to skip (default 0). A negative or non-integer value is treated as 0; a value above 2^62 is a 400 (invalid_query_param)
    Response header Notes
    X-Total-Count Number of rows on the card, ignoring limit/offset
    X-Truncated true when more rows exist after the returned ones, otherwise false

    Timeline¶

    GET /api/v1/boards/{board_id}/cards/{id}/timeline/¶

    Unified, paginated timeline that merges card movements, field-change activities and (since 1.3) gate transitions into a single chronological feed, sorted newest-first. Minimum role: any board member (viewer and above).

    Use it for one list combining moves, comments, field edits, checklist events, attachments, and system events, instead of fetching movements/ and activities/ separately and merging client-side.

    Query parameters

    Parameter Type Default Description
    limit integer 50 Page size. Capped at 200; a negative value is treated as 0 and a non-integer value as the default. count is the real total even when the page is empty (limit=0).
    offset integer 0 Zero-based page offset. A negative value is treated as 0; a value above 2^62 returns 400 with {"detail": "...", "code": "invalid_query_param"}.
    event_types string (all) Comma-separated filter groups. Valid values: move, gate (added in 1.3, #2365), comment, field, checklist, attachment, system. Omit to include all event types.
    include_counts boolean false Added in 1.3 (#967). true adds a counts object to the response. Any other value, or omitting it, leaves counts out and skips its aggregate queries (up to three; a group the page already counted is reused).

    event_types group mapping:

    Group Included event_type values
    move All CardMovement records
    gate Added in 1.3 (#2365). CardGateTransition records with no movement: gate_passed and gate_reopened. See Gate entries
    comment comment_added
    field priority_change, weight_change, assignee_change, label_change, title_change, description_change, due_date_change, and since 1.3 blocked, unblocked (#1149), custom_field_changed (#1921) and the dimension plan edits dimension_owner_changed, dimension_next_action_changed, dimension_target_date_changed (#2703)
    checklist checklist_item_added, checklist_item_checked, checklist_item_unchecked, checklist_item_deleted
    attachment attachment_added, attachment_deleted
    system archived, reactivated, and since 1.3 parent_linked, parent_unlinked, child_linked, child_unlinked (#1104), children_removed_board_deleted, parent_removed_board_deleted (#2208), planned_released, needed_changed (#2371)

A needed_changed entry has from_value created, manual or column_deleted (no actor; also written when a site admin moves the Needed column to another board in the Django admin, which the parent can then never reach) and to_value planned or now. Neither names the parent, its board, its column or the person who moved the parent.

    An unblocked entry's data also carries block_duration_seconds (added in 1.3, #1149): how long the block it closed lasted, or null when no closed block matches (an imported entry whose block history was not imported).

    Gate entries (added in 1.3, #2365). A card moving between the sub-columns of a gated stage (see Gated stages and gate transitions) writes a CardGateTransition row per gate crossed, and no movement. Those rows are kind: "gate" entries, with event_type gate_passed or gate_reopened, and data in the same shape as the move response's gate_transitions items (id, card_uid, card_title, column, column_name, column_uid, sub_column_name, sub_column_uid, kind, from_index, to_index, reason, cause, movement, actor as a username, created_at, imported_from_username). sub_column_name is the sub-column the card reached. cause is move for a move between sub-columns, stage_edited when a stage-settings change moved the card (its sub-column was removed), or import.

    A gate crossed as part of a column or lane move is not a separate entry: that move's entry carries it in data.from_gates_passed, data.from_gates_open and data.to_gates_passed (also added in 1.3; null when neither column is a gated stage). So one move never shows as several entries.

    Gate entries are included when event_types is omitted, because omitting it means every event type. A client that names its groups (any list without gate) gets the same entries and count as before 1.3. A client that omits event_types and does not know kind: "gate" should skip those entries; the entry envelope is unchanged.

    Relations (since 1.2)¶

    Typed links between two cards on the same board. The board stores one canonical direction per relation and derives the inverse at read time, so "A blocks B" and "B is blocked by A" are the same row read from two ends — they cannot drift apart.

    Relation types:

    relation_type Meaning Symmetric
    blocks The card this row was created from blocks the other card no
    relates_to The two cards are associated, with no ordering implied yes

    relates_to is stored in a canonical order (lower card id first), so adding the same pair from either end is the same relation and the second attempt is rejected as a duplicate.

    Cross-board relations are not supported. A to_card on another board is rejected with 400 and the response discloses nothing about that card.

    Parent and children (since 1.3)¶

    A card on a board whose cards can have children (cards_can_have_children, see Boards) can be the parent of cards on another board, its children (#1104). Relations stay same-board; this link is the cross-board one. The rules:

    • Two tiers. The parent is on a board with cards_can_have_children: true, the child on a board with false. A child is never a parent.
    • One parent per child, one child board per parent. All of a parent's children are on one board, and a parent has at most 100 children.
    • Roles. Linking needs member or higher on both boards. Either end may unlink with member or higher on its own board; the child's side does not need to be able to open the parent.
    • No oracle. A parent_id that does not exist and one on a board you cannot open both answer the same 404.
    • Moves. A card moved to another board in the Django admin loses its links. Deleting either card deletes the link.
    • Links are not exported or imported, and the public share link shows none of this.
    • Rate limit. The four link writes below (link, Add child, child-side unlink, parent-side unlink) share a per-user limit, the card_link_write throttle scope (default 300 per hour, CARD_LINK_THROTTLE_WRITE_RATE), on top of the general per-user API limit. Over it, a write gets 429 Too Many Requests with a Retry-After header and changes nothing. Reading children does not count against it.

    Planned children (since 1.3)¶

    On the reads that carry parent (/full/, the card list, retrieve and archived/), every card also carries:

    Field Type Meaning
    planned bool Needed is a later parent column and the child is not yet released. Its due_date is inactive: not Overdue, Due soon or Stale. is_stale applies this rule on every read (board, card, card query, share link) whether or not these fields are present.
    needed_now bool Released (the parent reached or skipped past the column, its column was deleted, or Needed was set to Now by hand), and still in its board's first column with no move since. needed_now_reason says which.
    needed_at_column int or null The parent board's column; null for Now and whenever you cannot open the parent's board.
    needed_at_column_name string or null That column's name, under the same rule.
    planned_released_at datetime or null When the child stopped being planned: the parent reached its column, it was pulled, its column was deleted, or Needed was set to Now by hand. Stale restarts from it. An already released child keeps its first value.
    needed_now_reason "parent", "cancelled" or null Why a needed_now child was released; null whenever needed_now is false. parent: the parent reached or skipped past the Needed column. cancelled: the plan was called off (its column was deleted, or Needed was set to Now by hand, which also turns an earlier parent into cancelled; deleting the Needed column of an already released link does the same, and writes no history row). It carries the cause only, never the parent, its column or who moved it, so every reader gets it, including one who cannot open the parent's board.

    Like parent, they are absent from write responses, card.* event payloads, webhooks, MCP, exports and share links. A release by the parent sends no new event type: the parent's move already sends card.parent_changed to the child board, and clients re-read. History rows: planned_released (from_value parent_reached or pulled, to_value the due date now counting, blank for none; no actor when the parent's move caused it) and needed_changed (from_value created, manual or column_deleted; to_value planned or now).

    children_rollup (since 1.3)¶

    On a board with cards_can_have_children, each card carries children_rollup (#2210), the progress of its children computed for the caller:

    {"visible": true, "total": 5, "done": 2, "doing": 1, "todo": 1, "blocked": 1,
 "last_moved_at": "2026-11-19T14:02:00Z",
 "planned": 0, "planned_due_dates": [], "needed_not_started": []}

    The states partition total: a child that is blocked (a manual block or an open blocks relation, the same rule as is_blocked) counts as blocked whatever its column; otherwise done when its column has is_done, todo when it is in the child board's first column, else doing (a planned child is its own bucket, below). Archived children are not counted. last_moved_at is the latest movement of any counted child, or null. A card with no children reads total: 0.

    Since 1.3 (#2551). A planned child that is not blocked or done counts in planned, not todo, and its moves never feed last_moved_at, so a parent whose remaining work is all planned does not read as "not started" or idle. planned_due_dates lists the planned children's stored dates (YYYY-MM-DD, sorted; compare with today yourself, as the board does for "1 planned date has passed"). needed_not_started is [{"column_name", "count"}], in column order: children the parent released by reaching their Needed column that have not moved since. The column is on the parent's own board. Older clients that ignore the three keys read todo without planned children.

    When the caller cannot open the child board, the rollup is {"visible": false, "total": N} and nothing else (none of the planned keys): no state, time, title, board or id (an accepted count-only disclosure, #1104).

    children_rollup is present on GET .../full/, the per-board card list and GET .../cards/{id}/, on cards of a parent-tier board only. It is absent from every other board's cards, archived/, the cross-board GET /api/v1/cards/, write responses, every event payload, change-feed row and webhook, and share links. Refetch the card on card.children_changed or card.children_bulk_changed (#2500), and carry the last value over when a frame replaces the card, as for parent.

    History and real-time¶

    Both cards record parent_linked / child_linked (and parent_unlinked / child_unlinked) in their history, with from_value and to_value blank: a history row never names the other card, not even by id.     Checklist¶

    New in 1.3 (#445)

    Checklist items carry an optional assignee and due_date. Responses add assignee (a nested user object, or null) and due_date (YYYY-MM-DD, or null). Write the assignee with assignee_id (a user id, or null to unassign) on POST and PATCH; it must be an assignable member of the board (admin, member or collaborator; never a viewer), otherwise the request answers 400. Assigning and dating are edits, so the creator-only rule below applies: a collaborator or member may change them only on items they created. An assignee who later leaves the board stays assigned, as on cards. Each change records a History event: checklist_item_assigned (from/to are usernames, blank for none) and checklist_item_due_changed (from/to are ISO dates), both in the timeline's checklist group. Since 1.3 (#2199) both also carry item_text, the item's text at the time of the change. Cards add two read-only fields for the card-face suffix: checklist_open_due_dates (sorted due dates of unchecked items) and checklist_open_assignee_ids (one entry per unchecked assigned item). The public share link omits both. A checklist due date never affects the card's own due date, urgency or staleness.

    Stability: new in 1.3. The fields below are additive; the stage action is a first-release surface and may gain optional keys in a minor release, but no existing key will change meaning.

    Move: gates_passed¶

    POST /api/v1/boards/{board_id}/cards/{card_id}/move/ accepts an optional gates_passed integer: the index of the sub-column the card should end in on the target column (0 = first sub-column).

    Case gates_passed omitted gates_passed sent
    Same column (reorder or lane change) Unchanged Each gate crossed is passed or reopened; no movement is written and no WIP limit is checked
    New column Card starts at 0 Applied as passing that many gates, one record each, linked to the movement

    An invalid value (a boolean, a non-integer, a negative number, past the column's last sub-column, or above 0 on a column with no sub-columns) is a 400:

    {"code": "invalid_gates_passed", "detail": "gates_passed must be between 0 and 2 for this column.", "max_gates_passed": 2}

    A non-integer omits max_gates_passed. Every gate change bumps the card's version. When a move crosses a gate the response (and the card_moved WebSocket event, and the MCP move_card result) carries gate_transitions, a list of:

    Field Type Notes
    kind "pass" | "reopen"
    from_index, to_index integer One row per gate, so passing two gates is two rows
    cause "move" | "stage_edited" | "import"
    movement integer | null Set when the gate was passed as part of a column move
    column, column_name, column_uid, sub_column_name, sub_column_uid Snapshots; readable after the column or sub-column is deleted
    card_uid, card_title, reason, actor, created_at, imported_from_username

    On an in-stage move the body has no movement key. Leaving a stage with gates open is allowed (phase 1 warns and records only).

    New read fields¶

    • Card: gates_passed (integer, read-only).
    • Column: sub_columns ([{id, uid, position, name}], [] on a plain column) and tracks ([{id, field_id, field_uid, name, position}]). Both are read-only on the column endpoints and are included on the public share view.
    • Swimlane: not_applicable_field_ids (integer list; not on the public share view).
    • Movement: from_gates_passed, from_gates_open, to_gates_passed (integer or null; null where that end's column is not a gated stage). "Left with gates open" is from_gates_open > 0.
    • Movement (#2655): entry_unmet, the Warn record, a list of unmet items (requirement_uid, operator, operand, field_uid, field_name, field_set_uid, field_set_name) or null. Read-only; never a card's value.

    PUT /api/v1/boards/{board_id}/columns/{column_id}/stage/¶

    Board admins only (403 for members, 404 for callers without board access). Saves sub-columns, tracks and lane exceptions in one transaction. Every key is optional; an omitted key is unchanged.

    {
  "sub_columns": [{"id": 12, "name": "Doing"}, {"name": "Ready to pull"}],
  "tracks": [41, 42],
  "not_applicable": [{"swimlane_id": 3, "field_id": 42}]
}
    • sub_columns: [] (a plain column) or 2 to 4 entries. An entry with an id keeps and may rename that sub-column; one without is new. The list order is the new order: kept sub-columns may be reordered (#2368), but not in the same request that removes one: that returns 400 with Reorder and remove sub-columns in separate saves. A reordered sub-column keeps its cards: each card follows its own sub-column to its new index, passes no gate and writes no history, and appears in remapped. Removing a sub-column moves each card in it back to the nearest kept sub-column before it (or the first) and records a stage_edited gate transition for that card. A card that is only re-indexed, because a sub-column was inserted or removed ahead of the one it is in, keeps its sub-column, passes no gate and writes no history; it still appears in remapped with its new gates_passed and bumped version.
    • tracks: ordered ids of the board's dimension fields. Removing a track unbinds it only; the field and every card's value stay.
    • not_applicable: replaces the lane exceptions for this stage's tracks.

    Response: {"column": <Column>, "remapped": [{"id", "gates_passed", "version"}]}. The same remapped list rides the column_updated WebSocket event; changed lanes emit swimlane_updated.

    Archived cards in the column are remapped too, since they keep gates_passed. The remap writes its gate transitions in one insert and its cards in one update per target sub-column (at most four), so a save runs a constant number of queries however many cards the stage holds (#2362).

    GET /api/v1/boards/{board_id}/columns/{column_id}/stage-card-counts/¶

    Board admins only (403 for members, 404 for callers without board access or an unknown column). New in 1.3 (#2368). The Stage settings panel reads it for its "N cards will move" summary, because a stage save also remaps archived cards, which the board payload does not carry.

    {"sub_columns": [{"id": 12, "cards": 3, "archived_cards": 1}, {"id": 13, "cards": 0, "archived_cards": 0}]}

    One entry per sub-column, in order: cards counts active cards and archived_cards archived ones. A card whose gates_passed is past the last sub-column counts in the last. A plain column returns [].

    Card activity: custom_field_changed¶

    Every custom field value set, changed or cleared, on any transport, writes a card activity row with event_type custom_field_changed, from_value / to_value ("" = no value), the actor, and item_text = the field's name at the time.

    Card activity: dimension plan edits (since 1.3)¶

    Added in 1.3 (#2703). Each dimension plan write records one card activity row for each part of the plan that changed, with the actor and item_text = the dimension field's name at the time. A write that repeats the stored plan records nothing.

    event_type from_value / to_value
    dimension_owner_changed The owner's username; "" = Unassigned
    dimension_next_action_changed The next action text in full (at most 200 characters); "" = none
    dimension_target_date_changed YYYY-MM-DD; "" = no target date

    They are in the timeline's field group and carry item_text like custom_field_changed. Board export and JSON import carry them with the card's other activities. purge_card_history removes them with the card's other activity rows.

    Force overrides: assignee basis, reasons and audit (since 1.3, #1923)¶

    ?force=true on move, create, restore (POST .../unarchive/) and a weight-raising PATCH overrides a Block WIP or weight limit. Hard WIP still refuses every role.

    • Who: board admins and site admins, as before. When the board's allow_assignee_override is true (default false, admin-only to change), also the card's assignee with role member, provided someone else assigned the card to them (assigned_by is set and is not the caller).
    • override_reason (optional body field, string): stripped, at most 500 characters, no NUL bytes; otherwise 400 {"override_reason": ["..."]}. Required for an assignee override: 400 {"code": "override_reason_required", "detail": "..."}. Optional for an admin force (recorded as ""), so existing clients keep working. Visible to everyone on the board.
    • 403 body gains code (additive): {"detail": "Only board admins can override a WIP limit.", "code": "force_not_permitted"}. On a board with the switch on, detail reads "Only board admins, or the card's assignee when someone else assigned it to them, can override a WIP limit." (or weight). A self-assigned assignee on a board with the switch on gets {"detail": "You assigned this card to yourself, so a board admin needs to move it anyway.", "code": "force_not_permitted", "reason": "self_assigned"}.
    • Response/broadcast: when a limit was overridden, the create (201), move and restore bodies and the card.moved / card.created / card.unarchived frames carry an additive override: {kinds: ["wip"|"weight", ...], actor_basis: "admin"|"site_admin"|"assignee", actor: {id, username}, reason}. Absent otherwise.
    • Card field assigned_by (read-only, user id or null): who set the current assignee. null when unassigned, imported, or the assigner was deleted; a null value is never eligible for the assignee basis.
    • History: each override writes one CardOverride row per kind and an override_used activity (from_value = basis, to_value = kinds, item_text = reason, assigned_by = who assigned the card on an assignee basis, #2594). The card's History reads "… (assignee override). Reason: … · Assigned by {name}"; with no assigner on the row it names no one.
    • MCP tools take no force: a Block limit acts as Hard over MCP.
