    Create and manage boards over the API¶

    Create a board with POST /api/v1/boards/ and a name; it answers 201. Every other call here hangs off the returned board id.

    curl -X POST -H "Authorization: Token $TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "Sales Pipeline"}' http://localhost:8000/api/v1/boards/

    Omit template for the simple_kanban layout; omit swimlane_name for no swimlane. List boards with GET /api/v1/boards/.

    Go deeper: Boards, Templates, Export & Import, Members, Board invites, Board sharing, Columns, Swimlanes, Labels, Custom fields, Children mode, Public share endpoint.

    Why it matters: columns, swimlanes, labels, membership, and sharing all enforce board roles, so check the role a call needs before you script it.

    The big picture: everything you do with a board short of the cards inside it (see Cards API).

    Boards¶

    GET /api/v1/boards/¶

    List all boards accessible to the current user.

    Query parameters

    Parameter Description
    ?starred=true Return only boards the requesting user has starred
    ?expand=group Populate group_detail on each board with a GroupBrief object (see GET /api/v1/boards/{id}/full/ for the shape). Without this parameter group_detail is null. Triggers a one-query ancestor bulk-fetch — safe to use on list responses.
    ?offset=<n> Zero-based row offset (default 0)
    ?page_size=<n> Rows per page (default 50, max 200)

    Response — the standard paginated envelope: { "count", "offset", "page_size", "results": [ ...boards ] }. Read the boards from results; the response is not a bare array.

    POST /api/v1/boards/¶

    Changed in 1.2

    Create a board.

    Request

    Field Required Description
    name ✓ Board name
    description Board description (default: "")
    template Template slug to use for column layout (default: "simple_kanban"). See GET /api/v1/boards/templates/ for available slugs. Omit it (or send ""/null) for the default; a non-blank slug that matches no active template returns 400 (see Errors).
    swimlane_name Name for the first swimlane. Omit it (or send blank) and the board gets no swimlane; no template supplies a default. By contrast, POST /groups/{id}/boards/, defaults an omitted value to "General".
    group Integer group ID — assigns the board to this group at creation time. Since 1.2 the caller must be an admin of the group or of one of its ancestor groups (or a site admin with all-content access), the same rule as POST /groups/{id}/boards/. null or omitted creates a personal board.

    Since 1.2, a non-string swimlane_name returns 400 Bad Request with the error keyed to swimlane_name (it returned 500 before).

    Errors

    Status Body Condition
    400 Bad Request {"code": "unknown_template", "detail": "Unknown board template: '...'."} (both plain strings, #1660) template was sent as a non-blank value that doesn't match an active template's slug. Deliberately distinct from a per-field validation error: a stale or mistyped template once created a simple_kanban board with a 201 and hid the mistake (#1115).
    400 Bad Request {"group": ["Unknown group, or you are not an admin of it."]} group names a group that does not exist or that the caller does not administer. Both return the same body.

    GET /api/v1/boards/{id}/¶

    Get board summary. Response includes:

    Field Type Description
    id, uid integer, string Database ID and stable 16-char hex UID
    name, description string Board name and description
    owner object Owner user object
    group, group_name integer / null, string / null Group ID and name (null for personal boards)
    group_detail object / null Populated with a GroupBrief object when ?expand=group is appended to the request; null otherwise. GroupBrief shape: { id, name, parent, parent_name, ancestors } where parent is the parent group FK ID (or null) and ancestors is a root-first [{ id, name }] chain.
    member_count integer Number of direct board members. Reported as the true total for every viewer, including non-owner members, on list, retrieve and the board.created / board.updated payloads (before 1.2 a direct member who was not the owner saw 1 on GET /api/v1/boards/). card_count and archived_card_count are likewise true totals for every viewer.
    card_count integer Number of active (non-archived) cards
    archived_card_count integer Number of archived cards. Reported separately because card_count excludes them, yet DELETE /api/v1/boards/{id}/ deletes them too. Clients that confirm a board delete should treat card_count + archived_card_count as the number of cards at stake. Also present on GET /api/v1/boards/, GET /api/v1/groups/{id}/boards/, and /full/. Added in 1.2 (#1289).
    staleness_threshold_days integer Days without movement before a card is considered stale (default: 7). Must be between 0 and 36500 (100 years); a larger value returns 400 Bad Request keyed to the field. Before this cap a value near 30 million returned 500 on create and update.
    allowed_priorities array / null Deprecated (#1429). Has no effect and is kept only for API compatibility; marked deprecated: true in the OpenAPI schema. Still accepted on write and returned unchanged, but not enforced: card create and update accept any priority regardless of this list (scaffold, see Field Enforcement). It will be removed only in a future major release. Duplicate entries are silently de-duplicated (order of first occurrence is kept); a submitted list longer than 100 entries is rejected with 400 Bad Request.
    enforce_wip_limits boolean When true, moving, creating, or restoring a card into a column at its WIP limit returns 409 Conflict (default: true for new boards); board admins (or the card's assignee, when enabled) can override with ?force=true. Board import is not checked (by design). Create and restore checked since 1.2 (#1428)
    enforce_wip_hard boolean When true, WIP limits on card move, create, and restore cannot be overridden by any role — all users are blocked (default: false). Active regardless of enforce_wip_limits. Board import is not checked (by design). Create and restore checked since 1.2 (#1428)
    enforce_weight_limits boolean When true, moving, creating, or restoring a card, or raising a card's weight with PATCH, so that a column would exceed its weight limit returns 409 Conflict (default: true for new boards); board admins (or the card's assignee, when enabled) can override with ?force=true. Lowering a weight is never blocked. Board import is not checked (by design). Create, restore, and PATCH checked since 1.2 (#1428)
    export_min_role string Minimum role required to export this board. One of "viewer", "collaborator", "member", "admin" (default: "viewer"). Owners and site admins always bypass. Limits only the export action and its file formats; it does not restrict ordinary reads (/cards/, /full/, /api/v1/cards/, timeline, MCP), which follow board membership. Admin-only when writing; sending any other value (including "site_admin" or "owner") returns 400 Bad Request. A stored value outside this set is treated as "admin" by the export gate. Added in 1.1 (#843).
    card_density string Per-board card layout density. One of "comfortable", "standard", "dense" (default: "comfortable" for new boards; existing boards on upgrade are migrated to "dense" to preserve their pre-1.1 visual). Drives how much metadata renders on the card face — see the Card density feature doc. Admin-only when writing; sending any other value returns 400 Bad Request. Added in 1.1 (#961).
    show_wip_at_limit boolean When true, a swimlane row's WIP line shows a calm at limit reading once the row's card count exactly equals its wip_limit (default: false); the expanded column header ignores it, and the collapsed column strip shows a calm = cue at the limit (#972). Purely ambient — does not affect move enforcement. Admin-only when writing. See the At-limit WIP indicator feature doc. Added in 1.2 (#973).
    show_row_chip_field_names boolean When true (the default), pinned swimlane field chips in a row's header band show Field name: value. When false, they show the value alone; the name stays in the chip's tooltip, for screen readers, and, when the lane has more than two fields, in the row's field grid. Checkbox fields always show their name, and card-face chips are unaffected. Display only. Admin-only when writing. See Hiding field names on row chips. Added in 1.2 (#1418).
    lane_details_cap integer Since 1.3 (#2439). The most swimlane fields a lane's Show N more details hold: one of 4, 6, 9, 12, 16 (default 6). Admin-only when writing. Changing it materializes the board's band visibility; lowering it below the number of "details" fields is a 400 keyed lane_details_cap. Announced with board.updated. Exported and imported with the board JSON; an older export without it imports as 6.
    stale_warning_pct integer Percentage (0--100) of staleness_threshold_days a card has used before the warning step. It sets the yellow/green boundary in the analytics heatmap and the yellow step of the card aging tint. 0 turns the warning step off
    is_starred boolean Whether the requesting user has starred this board
    created_at, updated_at string ISO 8601 timestamps
    health_status string / null The board's own health status: "on_track", "at_risk" or "off_track", or null to inherit from the nearest group above it that sets one (default: null). Admin-only when writing; any other value (including "") returns 400 Bad Request. See Health Status. Added in 1.3 (#1133).
    effective_health_status string / null Read-only. The status that applies: health_status when set, otherwise the health_status of the nearest ancestor group that sets one, walking up from the board's group through at most six groups; null when none does. Computed on every read, so a group change applies to every board that does not set its own value. Added in 1.3 (#1133).
    health_status_source object / null Read-only. { "id", "name", "changed_at" } of the group that supplies effective_health_status; null when health_status is set on the board itself or when nothing applies. changed_at (1.3+, #2242) is when that group's own status was last set, or null; the group's setter and note are not included. Added in 1.3 (#1133).
    health_status_changed_at string / null Read-only. When the board's own health_status was last set or confirmed (ISO 8601), or null if never recorded (including a status set before 1.3's history existed). Added in 1.3 (#2242).
    health_status_changed_by object / null Read-only. Who last set or confirmed it, as { "id", "username", "display_name", "avatar_url" } (the owner shape), or null for a removed account, an automatic change or no recorded change. Added in 1.3 (#2242).
    health_status_note string / null Read-only. The note given with the last set or confirm (at most 280 characters), or null. Added in 1.3 (#2242).
    health_review_days integer / null "Review status every N days": 1 to 365, or null for off (default: null). Once the board's status is older than this since it was last set or confirmed, clients show it as not reviewed. Admin-only when writing; 0, 366 or a non-integer returns 400 Bad Request. Read-only on /full/. See Ask for a review every N days. Added in 1.3 (#2244).
    health_review_due_at string / null Read-only. When the status shown is due for review (ISO 8601): health_status_changed_at + health_review_days when the board sets its own status, or, when it is inherited, the source group's changed_at + that group's health_review_days (the board's own setting does not apply). null when that setting is off, nothing applies, or the change time was never recorded. Past it, the status is not reviewed; POST .../health-status/ with the same value (a confirm) moves it forward. A fixed time rather than an age, so a cached payload stays correct. For an inherited value it is published to every reader of the board, like health_status_source, even when the source group is one the reader can only navigate to. Added in 1.3 (#2244).
    default_preset string / null The board preset members see until they pick one themselves: "classic" (the board's own density and no overlay; it renders the redesigned board) or "default", or null for no board default (default: null). Presets are defined by the web client in 1.3; this field stores only the id. A member's own choice and a ?preset= link take precedence over it. Admin-only when writing; any other value (including "") returns 400 Bad Request. On every board payload, including /full/ (read-only there), the group board lists and the board.created / board.updated WebSocket events. Added in 1.3 (#1146).
    health_auto_enabled boolean (1.3+, #2245) Compute this board's health status from its lanes' cards. Default false, which is exactly the behavior before 1.3. Turning it on computes at once, in the same request; turning it off clears every computed value (computed_health_status, health_computed_at, health_computed_counts on the board and its lanes) and records a computed history row when a computed value existed. Board admins write it (403 otherwise).
    health_off_track_cards integer (1.3+, #2245) Auto health threshold, an absolute count of flagged cards in one lane, not a share of the lane's open cards. A card is flagged when it is open (not archived, not in a Done column) and overdue, stale or blocked; it counts once whatever signals it has. A lane with at least 1 flagged card computes at_risk; with at least this many, off_track; otherwise on_track; with no open cards, null. Default 3, 1 to 1000 (400 otherwise). Changing it on an auto board recomputes at once. This meaning is fixed from 1.3; a different rule would be a new field.
    computed_health_status string / null Read-only (1.3+, #2245). The board's computed status: the worst of its lanes' effective statuses (a lane's pin, else its computed value; lanes with none are ignored). Readable while the board's own pin (health_status) overrides it. null when auto health is off, never computed, or no lane has a status.
    health_computed_at string / null Read-only (1.3+, #2245). When the auto status was last computed, whether or not it changed. null = never computed (auto off, or the scheduled job has not run: see scheduled jobs).
    health_computed_counts object / null Read-only (1.3+, #2245). { "open", "overdue", "stale", "blocked", "flagged" }, summed over the board's lanes. null when never computed.
    health_status_origin string / null Read-only (1.3+, #2245). Where effective_health_status comes from: manual (this board's own pin), computed (auto health), inherited (a group; health_status_source names it), or null for no status. Precedence: pin, then computed (auto on), then the nearest group. A computed value has no review cue: health_review_due_at is null while the origin is computed.
    swimlane_rollup_field integer / null Id of one of this board's card number fields whose values each swimlane band sums over the lane's cards that are not in a done column, shown as {total} open; null for no rollup (default: null). Must be a number field on this board: a non-number field returns 400 Bad Request (swimlane_rollup_field must be a number field.), and an id that is not one of this board's fields returns the same 400 as an id that does not exist. "", booleans and fractions are 400 too; send null to clear. Not accepted with a non-null value on create (a new board has no fields yet). Deleting the field sets it to null; retyping the field away from number keeps the id, and clients hide the rollup until the field is a number again. Sending the board's current swimlane_rollup_field back unchanged (for example in an echoing PUT of the GET body) is accepted even if the field has since been retyped away from number; naming a different non-number field is still 400. The total is computed by clients from the /full/ card values, which every member can read. Admin-only when writing. On the board payloads (list, retrieve, create, update), /full/ (read-only there) and the board.updated WebSocket event; not on the public share-link payload. See Swimlane rollup. Added in 1.3 (#2275).
    commitment_column_uid string / null The board's commitment point: the uid of a column of this board that is not a done column, where cycle time and age start (default: null, which keeps the default definitions: the first move out of the column a card was created in). A done column or another board's column returns 400 Bad Request; send null to clear. Not accepted with a non-null value on create (a new board has no columns yet). Sending the current value back unchanged is accepted even if that column has since been deleted or marked done; such a value reads as unset. Changing it re-measures the board's history and the definition the metrics endpoints return for cycle time and age. Admin-only when writing. On the board payloads and /full/ (read-only there); not on the public share-link payload. Added in 1.3 (#2050).
    cards_can_have_children boolean Whether cards on this board can have child cards on another board: true lets every card on the board get children; false (the default) is an ordinary board. The two-tier rule is per card, not per board (since 1.3, #2446): a card is never both a parent and a child, and a board with the setting off may still hold leftover parent cards that keep their children. Readable by every board member; admin-only when writing (a non-admin PATCH is 403). Turning it on is refused with 400 (keyed cards_can_have_children), here and in the Django admin (#1104), while cards on this board are children of cards on another board, and while another board names this one as its default_child_board. Turning it off is never refused (#2446): cards that already have children keep them and stay parents until their last child is unlinked. Turning it off clears this board's own default_child_board in the same write. GET /boards/{id}/children-setting-blockers/ lists the reasons. On the board payloads and /full/ (read-only there), and on the board.updated WebSocket event and change feed; not on the public share-link payload. Added in 1.3 (#2208).
    parent_name_singular string What a parent card on this board is called, for example "Initiative" (#2212). Empty (the default) means the client says "Parent". Stripped; at most 24 characters; control, format (bidi, zero-width) and surrogate characters are refused with 400. Admin-only when writing. The character and length rules are enforced on API writes and JSON import (ORM and migration writes skip them; the Django admin shows the field read-only). Shown on the child side of a link (board_parent_name_singular on parent). On the board payloads and /full/ (read-only there) and board.updated; not on the public share-link payload or MCP. Stable from 1.3.
    parent_name_plural string The plural, for example "Initiatives" (#2212). Empty means "Parents". Same rules as parent_name_singular; each falls back on its own. Shown in the parent picker's helper line through GET /boards/{id}/parent-boards/. Stable from 1.3. The character and length rules are enforced on API writes and JSON import (ORM and migration writes skip them; the Django admin shows the field read-only).
    default_child_board integer | null Id of the board where Add child on this board's cards creates the new child card, in that board's first column and first lane; null (the default) asks each time. A preference, not a link: setting, changing or clearing it never touches an existing parent/child link, and a parent whose children are already on another board keeps them there (one child board per parent). Setting it needs board admin on both boards, this board's cards_can_have_children on, and a target whose cards_can_have_children is off and whose first column allows card creation; an unknown id, a board you cannot open or do not administer, and a board that does not qualify all get the same 400 ({"default_child_board": ["Unknown board, or not a board you administer that can take child cards."]}). Re-sending the current value is a no-op, and clearing it (null) needs admin on this board only. Refused on POST /boards/ (set it after creating the board). When the target board is deleted it becomes null. Id only, never a name. On the board payloads and /full/ (read-only there), and on board.updated; not on the public share-link payload. Read-only in the Django admin. Added in 1.3 (#2208).

    The health fields are on every board payload: list, retrieve, create and update responses, /full/, GET /api/v1/groups/{id}/boards/, descendant-boards/ and its paged form, and the board.created / board.updated WebSocket events. A list resolves every row's inherited value from one ancestor lookup for the whole page.

    PUT /api/v1/boards/{id}/ / PATCH /api/v1/boards/{id}/¶

    Update board fields. PUT and PATCH are both accepted, and every field is optional in either. Requires board admin. (1.3+, #2009) A caller below admin gets 403 before the body is validated, so an invalid body no longer answers 400 with the field errors for them; a caller with no access to the board still gets 404.

    Writable fields: name, description, staleness_threshold_days, stale_warning_pct, allowed_priorities, enforce_wip_limits, enforce_weight_limits, enforce_wip_hard, export_min_role, card_density, show_wip_at_limit, show_row_chip_field_names, lane_details_cap (1.3+), health_status (1.3+), health_review_days (1.3+), default_preset (1.3+), swimlane_rollup_field (1.3+), commitment_column_uid (1.3+), cards_can_have_children (1.3+), default_child_board (1.3+), parent_name_singular (1.3+), parent_name_plural (1.3+), group (see below; since 1.2, changing it to a different group also requires admin of that group). The whole request requires board admin (or site admin); no field is editable by a non-admin, so even a one-field description PATCH from a non-admin gets 403 Forbidden.

    group on update: POST /api/v1/boards/{id}/move-group/ is the preferred way to change it. Since 1.2, setting group to a different group requires admin of that group or of one of its ancestor groups (or a site admin with all-content access). Otherwise, or if the group does not exist, the request returns 400 with {"group": ["Unknown group, or you are not an admin of it."]} and changes nothing. The check runs against the board's group when the update is applied. Sending the current group unchanged (for example in an echoing PUT) or null (detach to a personal board) needs only board admin. Since 1.2, a group change made this way sends the same group-channel events as move-group: board.deleted to the old group and board.created to the new one.

    DELETE /api/v1/boards/{id}/¶

    Delete a board. Requires the board owner or a user with can_access_all_content (the site_admin role). A board admin who is not the owner gets 403 Forbidden; see the role matrix. Deletes every card, including archived cards (see archived_card_count above).

    Since 1.2, if cards keep being created in, or moved into, the board while it is being deleted, or the cards' link peers keep changing, the delete gives up after a bounded number of internal retries and returns 409 Conflict with {"code": "container_changed", "detail": "Cards were added while this was being deleted. Please try again."}. Nothing is deleted; retry the request (#1602). A create or move that targets the board while it is being deleted waits for the delete and then returns 404. Other requests that write to the board while it is being deleted also wait for the delete and then return 404 with nothing written: board PATCH/PUT, share link enable and revoke, move-group, column and swimlane create, update, reorder and set-collapsed, card and swimlane custom-field definition create, update and delete, label create, update and delete, saved-filter create, star and unstar, member add, role change and removal, and invite link create and send. A delete of a board, column or swimlane that waits behind another delete of the same object also waits and then returns 404; the deletion event is sent once. A PATCH of a board that waits behind another write to the same board (for example a share link change or a move to a group) applies only the fields it sends: the fields it did not send keep the other request's committed values. While a column or swimlane is being deleted, an update of that column or swimlane waits and then returns 404; other column and swimlane requests wait for it and then proceed (a column reorder that still lists the deleted column returns 400).

    GET /api/v1/boards/{id}/full/¶

    Full board state — columns, swimlanes, cards, labels, members, current_user_role, and capabilities. All objects include their uid field. Also includes share_token (the board's public share UUID, returned only to admin and site_admin role members, null when no share link exists; lower roles always get null) and share_token_expires_at (ISO-8601 timestamp of the share link's expiry, or null for no expiry; admin-only, mirrors share_token visibility — added in 1.1, #804). The capabilities object contains boolean feature flags for enterprise-registered extension points (all false in OSS). The keys are additive-only (never removed or renamed), and a client should treat an absent key as false. Current keys: movement_export (true when an enterprise movement-export backend is registered; gates the export UI on the movements view).

    (1.2+, #1935) share_link_active is true when the board has a share link set and false when it has none, for admin and site_admin role members; lower roles get null. A link past its share_token_expires_at still reads true until it is rotated or revoked (its public page answers 410 Gone). (#1939) A link with no recorded enabler (enabled before the enabler was recorded (for example under 1.1, or 1.2.0-beta.3 and earlier)) reads false, and share_token and share_token_expires_at read null, since such a link does not resolve; turning sharing on issues a new link. Use this field to tell whether a link exists.

    Deprecated: share_token on board reads

    share_token in this response is deprecated since 1.2 and will be removed in 2.0, together with the stored token. Until then it keeps its name, type and admin-only visibility and is still populated for a link that can resolve, so existing clients keep working (a link with no recorded enabler reads null, as described above). New clients should read the token only from the POST /api/v1/boards/{id}/share/ response, which returns it when a link is created or rotated, show it to the admin then, and use share_link_active to tell whether a link is set. The Visiban web app works this way from 1.2: it shows the link once, right after it is created, and offers Rotate link for a link created earlier.

    cards lists active cards only. Since 1.2, the payload also carries archived_card_count (integer) — the number of archived cards that cards omits but that a board delete would remove (#1289).

    Since 1.2, each card in the payload also carries external_ref ({ provider, ref, url } or null) — see External ref.

    Since 1.2, also includes custom_field_definitions (the board's card custom field schema) and swimlane_custom_field_definitions (the board's swimlane custom field schema) — both read-only lists, available to every board role. Definition schemas disclose nothing a board reader does not already have; which of a swimlane's values a given role may read is decided per-definition by is_admin_only, not by this field.

    members is the effective roster, not membership rows. It lists everyone who can act on the board: direct members, members inherited from the board's group (and its ancestors), and the board owner. For a site-admin requester (board role site_admin, or an instance site admin) it also lists every user with all-content access who holds no other role on the board, so they appear in @mention autocomplete and member management; for every other requester it lists the board's own members only (since 1.2, #1714). Mentioning a user with all-content access by typing their @username notifies them either way. Only direct members have a BoardMembership row on the board, so for the other rows id is null; all-content rows carry role: "site_admin", which is not a membership role. In the OpenAPI schema this is the EffectiveBoardMember component (role enum EffectiveBoardRoleEnum), distinct from the strict BoardMembership component returned by POST /api/v1/boards/{id}/members/, whose id is never null and whose role never includes site_admin. Since 1.2 the schema documents /full/ as its own BoardFull component; before that it was mis-documented as Board (#1137), a schema-only correction that did not change the response body.

    ?expand=group: populates group_detail with a GroupBrief object: id, name, parent (parent group FK ID or null), parent_name (or null), and ancestors (root-first [{ id, name }]). Without it, group_detail is null.

    GET /api/v1/boards/{id}/events/¶

    Board change feed: committed board mutations in ascending id order, so a consumer can resume after a dropped WebSocket instead of re-fetching /full/. Added in 1.2.

    Query parameters: after (cursor — a feed row id, never a WebSocket frame's event_id; default 0) and limit (1–500, default 100). Both are validated, not clamped; an out-of-range or malformed value returns 400.

    Response: { "results": [{ id, event, data, actor_id, actor, created_at }, ...], "next_cursor": <int|null>, "next": <int|null> }. next_cursor is the cursor for the following page (pass it as after), or null when the caller is caught up. next is a deprecated duplicate with the same value; use next_cursor. actor (since 1.2, #1663) is the acting user as a nullable nested BoardUser object (id, username, display_name, avatar_url), alongside the unchanged integer actor_id; see Change Feed.

    Permissions: any board role, the same gate as /full/ and the WebSocket handshake — the feed replays events the caller could already have streamed. is_moderator is stripped from member.* payloads for roles below admin, exactly as the WebSocket consumer strips it — except on the row belonging to the reader themselves, which always carries the field (#1191).

    410 Gone: an event after the cursor that the caller could have read has aged out of the retention window (BOARD_EVENT_RETENTION_DAYS, default 30 days) and been pruned. Re-sync via /full/, then resume with the body's next_cursor as after (1.3+; /full/ carries no event id). A cursor whose own event was pruned, with nothing the caller could have read pruned after it, is not expired (1.3+, #2058, #2079); see When a cursor expires for the exact rule and for boards not pruned since the upgrade. The detail text's "newest event id" means a row id of this feed, never a WebSocket frame's event_id.

  "code": "cursor_expired",
  "resync_url": "https://your-instance.example.com/api/v1/boards/1/full/",

    POST /api/v1/boards/{id}/health-status/¶

    (1.3+, #2242) Set or confirm the board's own health status. This is the explicit action behind the editor's Save and Confirm status: it always records a history row, even when status equals the current value (a reconfirm, which refreshes health_status_changed_at), and it is the only write that stores a note. A PATCH/PUT of health_status (and a create, or a Django admin edit) records a row only when the value changes, with no note. Board admin only (403 Forbidden otherwise; 404 Not Found for a board you cannot see).

    Field Type Description
    status string / null Required. "on_track", "at_risk" or "off_track", or null to clear the board's own value (inherit). Clearing when nothing is set here returns 400 ({"status": ["Nothing set here to confirm."]}).
    note string / null Optional. The reason, at most 280 characters (400 if longer). Surrounding whitespace is trimmed, line breaks become spaces, and an empty note is stored as null.

    Response 200 OK: the board, with the same fields as a PATCH response. Sends board.updated, like any board edit.

    POST /api/v1/boards/{id}/health-recompute/¶

    (1.3+, #2245) "Recompute now": runs the auto health computation for this board at once, the same code path as the nightly compute_health_status job. Takes no body. Board admins and site admins only (403 for other roles); a non-member gets 404. Returns 409 with {"detail": "...", "code": "health_auto_disabled"} when health_auto_enabled is false, and 429 after 30 calls per user per hour (throttle scope board_health_recompute). Always advances health_computed_at; a status change is recorded in the health history as kind: "computed" with no user, and broadcast as swimlane.updated (each changed lane) and board.updated (board status changed), with no acting user.

    200 OK:

    {"board": {"id": 1, "computed_health_status": "at_risk", "health_computed_at": "2026-11-15T02:00:04Z", "...": "..."}, "swimlanes": [{"id": 4, "computed_health_status": "at_risk", "...": "..."}]}

    board is the board as GET /boards/{id}/ returns it; swimlanes are the board's lanes as GET .../swimlanes/ returns them. "Today" for overdue is the date in the instance time zone (INSTANCE_TIMEZONE, UTC by default; see Instance time zone), so for a team far from that zone a card can turn overdue a few hours early or late.     (1.3+, #2242) The board's own health status changes, newest first, at most 20 per request. When has_more is true, repeat the request with ?offset=20, ?offset=40, and so on to reach older changes (optional; default 0). Any board role (viewer and up) may read; anyone else gets 404 Not Found.

    Extension panel payload¶

    Added in 1.2 (#1770)

    Each extension_panels entry comes from an ANALYTICS_EXTENSIONS callable (boards/hooks.py), normalized by the API encoder: tuples become lists, date, time and UUID values become strings, and Decimal values become numbers. The web UI renders two panel types, stats and table. The shape is a public contract: existing types only gain optional fields, and an incompatible shape gets a new type name. There is no version field.

    Field Required Rule
    id yes String, 1-100 characters, unique per response (the first valid panel with an id wins; a later duplicate is skipped, but renders if the earlier one was malformed)
    title yes String, 1-120 characters
    type yes, to render "stats" or "table". A panel with a missing or unknown type (including legacy {id, title, data} panels) is returned by the API but has no renderer and is skipped
    description no String, up to 500 characters
    data yes Shape depends on type, below

    stats data: {"items": [{"label": ..., "value": ..., "hint": ...}]}

    • 1-24 items; label is a string of 1-80 characters; value is a string of up to 200 characters, a finite number, or null (rendered as —); hint is an optional string of up to 200 characters.

    table data: {"columns": [{"key": ..., "label": ..., "align": ...}], "rows": [{...}]}

    • 1-12 columns; key is a string of 1-64 characters, unique within the panel, and not __proto__, constructor or prototype (a panel using one of those keys is skipped); label is a string of 1-80 characters; align is "left" (default) or "right".
    • 0-200 rows. Each row is an object keyed by column key; every cell is a string of up to 200 characters, a finite number, or null. A missing key renders as null. Zero rows renders No data.

    Rendering rules:

    • At most 20 panels are rendered; extras are skipped. Unknown fields are ignored at every level.
    • A null optional field (description, hint, align) is treated as absent, so a Python None is fine; omitting the key is still preferred.
    • Any other violation (wrong type, a value over a limit, NaN or infinity, a boolean or object cell) skips the whole panel. Panels are never truncated. Skipped panels log one browser console warning that names the panel id (or its index when the id is missing, empty, not a string, or over 100 characters) and the reason, never the title or data. Panels over the 20-panel cap log a single summary warning.
    • The backend also validates each panel before responding: a panel that is not an object, or that contains NaN, infinity or a value that cannot be serialized to JSON, (including a string with a lone surrogate) is dropped by the API, with a server warning that names the callable and the exception type but never the panel contents or exception text, so a bad panel does not fail the summary response. The frontend skips any panel that still breaks the rules above.
    • Chart panel types are not part of v1; they are tracked in #1774.
    • Panels supply text and numbers only. Every string renders as plain text: there is no HTML, Markdown, link, class, color, or style support. A URL in a string is shown as text, not as a link.

    Example:

    {
  "id": "delivery-risk",
  "title": "Delivery risk",
  "type": "stats",
  "data": { "items": [{ "label": "Blocked cards", "value": 4, "hint": "since Monday" }] }
}

    Panel visibility by role¶

    Changed in 1.2 (#1826)

    The summary goes to every member who can read the board, viewers included, so each ANALYTICS_EXTENSIONS callable sets a min_role attribute naming the lowest board role that may see its panel:

    def delivery_risk(board, request):
    return {"id": "delivery-risk", "title": "Delivery risk", "type": "stats", "data": {...}}

delivery_risk.min_role = "viewer"
ANALYTICS_EXTENSIONS.append(delivery_risk)
    min_role Panel is shown to
    "viewer" Every member who can read the board
    "collaborator" Collaborators, members, admins
    "member" Members and admins
    "admin" Board admins, including the owner
    "site_admin" Users with all-content access only
    • The summary resolves the caller's board role the way it authorizes the request (all-content access, then owner, then explicit membership, then the nearest group membership) and drops every panel above that role before calling any panel. A dropped panel's callable is never invoked.
    • Fail closed: a callable with no min_role (or None) is admin-only, and so is one with an invalid value (unknown, miscased or not a string), which also logs a server warning naming the callable. Panels registered before 1.2 are therefore admin-only until their author sets min_role.
    • A callable class can set min_role as a class attribute. For a bound method, set it on the function in the class body; a bound method object does not accept new attributes.
    • A panel can still narrow its output by checking request.user, but needn't gate access itself.
    • A dropped panel leaves no trace: it is absent from extension_panels, as if none were registered.

    Time-in-stage heatmap derived from CardMovement records.

    Errors: besides 400 for a bad query parameter, 404 for a board you cannot access, 503 analytics_busy (with Retry-After: 10) and 422 analytics_too_large. Added in 1.3 (#2428). See Analytics refusals.

    Query parameters:

Heatmap color-coding uses staleness_threshold_days and stale_warning_pct to determine green, yellow, and red thresholds (see Analytics — Color-coding). Done columns are excluded from dwell-time calculations entirely — cards that have moved into a done column are considered complete and do not accumulate further dwell time in the heatmap. Archived cards contribute their dwell time up to the archive timestamp; active cards accumulate dwell time until they move again. Cards are excluded from stalled detection once archived.

    CSV export (Export CSV button) is available to any board member whose role meets the board's export_min_role threshold. Owners and site admins always bypass.

    Flow metrics¶

    1.3+

    GET /api/v1/boards/{id}/metrics/cycle-time/, .../throughput/, .../cumulative-flow/, .../wip-age/, .../dwell/, .../blocked/, .../attention/ and .../swimlanes/ and .../overview/ (nine endpoints) return flow numbers for the Analytics tab, for any board member, viewers included. Every number follows the flow metric definitions, and each response quotes its definition in definition. The swimlane comparison's own numbers (blocked share, the rolling median, status and trend) are defined in Swimlane comparison.

    Query parameters (days, from_date, to_date and label_id on all nine; swimlane_id on all but swimlanes):

    Parameter Type Default Constraint
    days integer 90 Rolling range, 1-365. Cannot be combined with from_date or to_date.
    from_date date 90 days ending at to_date First UTC day of the range, inclusive.
    to_date date Today (UTC) Last UTC day, inclusive. A range holds at most 366 days.
    swimlane_id integer none Cards now in this swimlane of this board.
    label_id integer none Cards now carrying this label of this board.
    group_by swimlane, label or custom_field none Break the numbers down (see Breakdowns). On cycle-time, throughput, wip-age, dwell and overview; ignored elsewhere.
    group_by_field_id integer none A dropdown or checkbox custom field of this board. On cycle-time, throughput, wip-age, dwell and overview it names a card field, is required with group_by=custom_field and is refused with any other group_by. On metrics/swimlanes it names a swimlane field and is honored on its own, with no group_by. Ignored on the other endpoints.
    limit integer or all all Added in 1.3 (#2429). Cap each per-card list at this many entries, 1 or more. On cycle-time, throughput, wip-age, attention and overview; ignored elsewhere, whatever its value. See Capped lists.

    A bad value, or a swimlane or label that is not on this board, returns 400 with {"detail": "...", "code": "invalid_query_param"}. A group_by_field_id that does not exist, is on another board, or is not a dropdown or checkbox field of the right kind (card field, or swimlane field on metrics/swimlanes) gets one and the same 400 (group_by_field_id: Not a dropdown or checkbox card field on this board., or ... swimlane field ... on metrics/swimlanes), so the answer says nothing about the field. A board you cannot access returns 404.

    Analytics limits (added in 1.3, #2428). These nine endpoints, summary and analytics can also return 503 analytics_busy (with Retry-After: 10) when no analytics slot comes free in time, and 422 analytics_too_large when the request needs more of the board's movement history than one request may hold (ANALYTICS_MAX_MOVEMENTS). On cumulative-flow and overview the cards that rest outside the range are read one at a time and count against a fixed ceiling of four times that setting instead, so an old board's standard range is not refused for its age. The date drill-down reads every card of the board whatever the range, and counts each card's few deciding rows against that same ceiling, so a shorter range does not help there. Both bodies are constant; see Analytics refusals. These codes and settings follow the 1.0+ compatibility rules.

    Capped lists (limit, added in 1.3, #2429). A per-card list grows with the board: on a board with 12,000 cards in flight, wip-age alone is several megabytes. limit is an optional cap on each per-card list, taken by cycle-time, throughput, wip-age, attention, overview and analytics. Its value is a positive integer, or all for no cap. Without limit, or with limit=all, every response is exactly what it was before this parameter existed, so an existing API or MCP client sees no change. An empty limit= counts as absent and returns the uncapped response too. Any other value returns 400 (code: invalid_query_param, limit: Must be a positive integer or "all".).

    Every number a response states (sample_size, percentiles, cycle_time_percentiles, wip_count, count, total, median, the grouping aggregates) is still computed from the whole set. Only the lists shrink:

    Endpoint What limit cuts Added with limit
    cycle-time samples, downsampled: the limit / 4 longest cycle times are always kept, the rest an even spread over the others in their usual order (by completion) samples_total, sampled
    wip-age samples, downsampled the same way: the oldest are always kept samples_total, past_p85_count (samples older than the cycle-time p85, strict >), each column's sample_count and past_p85_count, sampled
    throughput each period's card_uids (and by_group[].card_uids) to the first limit; count is never cut sampled
    attention items to the first limit, in their usual order: cards in progress first, oldest first, then the rest by days without movement, so a card not in progress is cut before any card in progress items_total, sampled
    overview each section as its own endpoint does as above, per section

    sampled is true when a list was actually cut, false when it fit. cards names exactly the cards the cut lists still name, throughput's by_group[].card_uids included. Downsampling is deterministic: the same board and query give the same samples. The Analytics page sends limit=300. dwell, cumulative-flow, swimlanes and blocked have no per-card list to cap and ignore limit like any unknown parameter, whatever its value.

    Response sizes quoted for limit are raw JSON bytes. The shipped nginx and Helm frontend configurations gzip application/json, so a browser behind them receives much less; daphne itself and the development Vite proxy do not compress, so a development or direct-to-backend client receives the raw size.

    Breakdowns (group_by, #2265). The new parameters follow the 1.0+ compatibility rules, but may still change until 1.3 GA. Without group_by every response is exactly what it was before this parameter existed. With it, the response is the same plus:

    • a top-level grouping: {by, field_id, excluded, overlapping, groups}. overlapping (new in 1.3, #2297) is true when at least one of the board's cards in the range counts in two or more groups, which only label grouping can do, so the group sizes can add up to more than an endpoint's ungrouped total (the flag reflects label overlap across the cards active in the range, not only the ones that endpoint counts; a card finished before the range does not set it); false otherwise. Each group is {key, name, member_keys, ...} with the endpoint's own aggregates: cycle-time {sample_size, percentiles}, throughput {total, median}, wip-age {sample_size}, dwell {sample_size, columns} (the same per-column shape and order as the top-level columns);
    • on each cycle-time and wip-age sample, group_keys: the card's keys, [] when it has none; on each throughput sample, by_group: one {key, count, card_uids} per entry of grouping.groups, in the same order, zeros included. Throughput's started and wip-age's cycle_time_percentiles stay board-level. Dwell has no samples.

    Keys are strings: the swimlane or label id, the dropdown choice text, or "true"/"false" for a checkbox. name is the swimlane, label or choice text, and null for a checkbox value. Label and custom-field groups use each card's current labels and field value, as the filters do. Swimlane groups are dated by the sample (changed in 1.3, #2334): cycle-time samples and throughput completions count under the swimlane the card was in at its first completion, a dwell visit under the swimlane the card was in when it left the column (the one in effect just before the move that ended the visit, even when that move also changed swimlane), and a wip-age sample under the card's current swimlane. Each sample is in exactly one swimlane group, so overlapping stays false; a sample whose swimlane was deleted, or an imported movement whose swimlane name matched none on the board, counts in excluded. The swimlane_id filter still selects the cards now in that swimlane, and cards[].swimlane stays current. Groups are ranked by how many of their cards are active in the range (started and not yet done, first completed in the range or on one of its bucketed days, or with a visit that closed in the range), so all four endpoints list the same groups in the same order; ties go by swimlane position, label name, choice order, or true before false. A group with no active card is left out; a listed group may still have size 0 on one endpoint. With more than five groups, the five first are named and the rest collapse into one last group with key and name null and every collapsed key in member_keys. A group's index in groups is its chart color, and Other is always last. Group percentiles follow the same sample-size rule as the board's.

    excluded counts, in the endpoint's own unit (completed cards, completions, cards in progress, visits), what belongs to no group: a card with no value for the field, a dropdown value that is no longer one of the choices, or a checkbox value other than "true"/"false". A checkbox that was never set has no stored value, so on a new checkbox field most cards count as excluded. For swimlane and custom-field groups, the group sizes plus excluded equal the ungrouped number. For labels a card counts once in each named label group it carries, and at most once in Other, so the group sizes sum to the ungrouped number, minus excluded, plus, for each sample that has a group, the number of distinct groups its card lands in minus one.

    How a range applies. A duration sample belongs to the range its completion falls in. Bucketed outputs (throughput, cumulative flow) report only whole UTC days and whole ISO weeks, and today, which is still running, is never a bucket. WIP age is a snapshot: the range moves only its cycle_time_percentiles.

    Percentiles are nearest-rank, in days at full precision (round for display). A percentile is null when its sample is too small: p50 needs 5 values, p85 needs 7 and p95 needs 20. Clients draw nothing for a null, and never recompute it.

    cards. The responses name cards by uid. cards lists each one they name, as {uid, id, title, archived, assignee, swimlane}, so a client can show a card's title and owner, including an archived card's, without another request. swimlane (added in 1.3, #2283) is the card's current swimlane, as {id, name}; every card has one. For its transitions, use GET /api/v1/boards/{board_id}/cards/{id}/movements/ with that id.

    GET /api/v1/boards/{id}/metrics/throughput/¶

    Adds an optional period, week (the default) or day.

    {
  "definition": "the number of cards whose first entry into a done column falls in a period.",
  "period": "week",
  "total": 9,
  "completed_in_range": 11,
  "median": 2,
  "samples": [
    { "start": "2026-06-01", "count": 3, "card_uids": ["3a9f1c2d7e4b8a05"], "started": 4 }
  ],
  "cards": []
}

    median is the nearest-rank p50 of the period counts, zero periods included, and null under five whole periods. start is the period's first UTC day.

    total sums the whole periods only. With period=week a range holds only the Monday-to-Sunday weeks that fit inside it: the partial week at the start of the range and the one at its end (today's, for a rolling range) are both left out, so a 30-day range covers 21 or 28 days of completions. completed_in_range (added in 1.3, #2288) counts every first completion in the range itself, the same [start, end) window a cycle-time sample belongs to (for days, from exactly days × 24 hours ago to now), so it equals total only when the range is whole weeks. It is always the ungrouped number. It counts every card whose first entry into a done column falls in the range, including one that went straight to done and one with incomplete history; cycle time needs a start, so those cards have no cycle-time sample, and completed_in_range can therefore exceed cycle_time.sample_size.

    started (added in 1.3, #2260) counts the cards whose cycle started in the period: their first move out of the column they were created in, to a column that is not done (or, on a board with a commitment point, its first arrival at or past it, #2050). Archived cards count, as in count. A reopen is not a start. A card with no creation movement, such as one imported without its history, can finish but never starts, so on an imported board started under-reports next to count.

    GET /api/v1/boards/{id}/metrics/swimlanes/¶

    1.3+

    One row per swimlane for the Swimlanes tab of Analytics, plus the board median for the same filters. Any board member, viewers included, as for metrics/cycle-time/. It takes days, from_date, to_date and label_id as above and no swimlane_id (a stray one is ignored). One optional parameter:

    Parameter Type Default Constraint
    group_by_field_id integer none A dropdown or checkbox swimlane custom field of this board ("Group lanes by"). An admin-only field is accepted only for board admins. Any other id is a 400 (invalid_query_param).

    Response (cycle time is the same measure as metrics/cycle-time/; every number is computed on the server). A card counts under the swimlane it was in at the time (changed in 1.3, #2334): finished, median_days, p85_days and rolling_median use the swimlane at the card's first completion, in_progress its current swimlane, and blocked_share splits each in-progress second across the swimlanes the card was in. Counts follow the swimlane at their moment and blocked_share the swimlane the time was spent in, so a card moved into done and into another swimlane in one move is finished in the new swimlane and blocked in the one it left. A completion in a swimlane since deleted is in board and in no row. The summary endpoint's per-swimlane velocity and avg_cycle_days stay on each card's current swimlane.

    • definition, board {finished, median_days, p85_days}, and the two thresholds status_threshold_pct (20) and status_min_finished (10).
    • swimlanes: every swimlane in position order, empty ones included, each {id, name, position, group, finished, in_progress, median_days, p85_days, blocked_share, rolling_median, status, trend}.
      • median_days is null below 5 finished cards; p85_days is null below 7.
      • blocked_share is the fraction (0 to 1) of the swimlane's in-progress time inside the period that its cards were blocked, with overlapping blocks counted once; a reopened card's time after the reopen counts too, from the reopen to its next completion (or archive, or now), so blocked share covers the same in-progress time as age and in_progress (changed in 1.3, #2297; before, the window ended at the first completion); null when no card was in progress.
      • rolling_median has eight {at, median_days, sample_size} points. Each is the median of the cards finished in a window half as long as the period, ending at at; the first window ends at the middle of the period and the last at its end, or at now when the period ends later (a to_date of today ends at tomorrow's midnight). A window with fewer than 5 cards has median_days: null.
      • status is slower, in_line or faster against the board median: more than 20% above or below, and only with at least 10 finished cards. Otherwise null.
      • trend is {direction, first_days, last_days} comparing the first and last rolling medians with the same 20% rule (slower, steady, faster). null with fewer than 5 finished cards or when either end point is withheld.
    • grouping: null, or with group_by_field_id, {field_id, field_name, field_type, groups: [{key, name}]} in the field's order; each swimlane's group is its value, null when it has none.

    Nothing here compares with an earlier period. The response shape is additive and stable from 1.3.

    state_json shape¶

    The server rejects unknown top-level keys and type-checks each known key, but does not validate values semantically (the frontend must confirm, for example, that an assigneeId is a real user):

    Key Type Notes
    search string Free-text search term
    assigneeIds integer[] User IDs to include
    labelIds integer[] Label IDs to include
    priorities string[] Subset of low, medium, high, urgent
    dueDate string | null One of overdue, today, this_week, none, or null for "no filter"
    blockedOnly boolean Added in 1.3 (#1149). true shows only blocked cards (manual or relation). Absent means false
    customFields object Custom-field filter values keyed by numeric field id (digit string), at most 50 entries. Each value is {kind: "text", query}, {kind: "number" \| "date", equals} (strings), or {kind: "choice" \| "multi_choice", values} (at most 50 strings). Strings are capped at 500 characters. Added in 1.3 (#2357): a number value may also carry op, one of eq (the default when absent), between, empty or not_empty, and min / max strings. A between needs a non-blank min or max; one empty bound means "at least" or "at most", both bounds are inclusive, and min greater than max is accepted (it matches no card). Every number value still carries equals, and clients write equals: "" for any op other than eq. An unknown op returns 400. date values are unchanged: equals only.
    visibleCustomFieldFilterIds integer[] IDs of custom-field filters shown in the filter bar, at most 50
    laneFilter object Added in 1.3 (#2205). Rules that hide swimlanes by swimlane field values: {items: [...]}, at most 20 items and 50 rules in all. A rule is {kind: "rule", id, join, field, op, value?, min?, max?}: id a non-negative integer, join "and" or "or" (ignored on the first), field a swimlane field id, "name", "contact_email" (added in 1.3, #2336: the lane's built-in name and contact email, matched as text; they take no between, min or max) or "health_status" (added in 1.3, #2247: the lane's effective health status; it takes is / is_not with a value of on_track, at_risk or off_track, or is_set / is_empty with no value, min or max; any other op or value is rejected, except that an absent or "" value on is / is_not is accepted as a rule not finished yet, which the client ignores), or null (not chosen yet), op one of is, is_not, between, contains (added in 1.3, #2226, for text and URL fields), is_set and is_empty (added in 1.3, #2247, valid only on health_status), not_contains and wildcard (added in 1.3, #2227, text and URL fields: a case-insensitive negative substring match, and a match of any part of the value where * is any run of characters and ? one character), and value / min / max strings of at most 500 characters. A contains, not_contains or wildcard rule must carry a value string (empty while the user has not typed yet) and no min or max. Added in 1.3 (#2438): a rule on a checkbox swimlane field uses is with a value of "true" or "false" (a lane with no stored value counts as "false"); a rule on a multi-select field uses is or is_not with a value holding one entry (any-of is an or chain of single entries). The shape is unchanged, the server checks the shape and not the field's type, and neither type takes is_set or is_empty. A client that does not know these types treats such a rule as unusable and ignores it. The op list only grows; a client drops a rule whose op it does not know. A group is {kind: "group", id, join, rules: [rule, ...]}; groups do not nest. hideUnmatched (added in 1.3, #2214) is an optional boolean beside items: hide lanes with no matching card while a card filter is active; it is a setting, not a rule, so {items: [], hideUnmatched: true} is valid. Unknown keys are rejected. Absent means no lane filter
    subColumnIds integer[] Added in 1.3 (#2367). Show only cards in these sub-columns (ids from a column's sub_columns); at most 50 integers. Absent means no sub-column filter
    trackStates string[] Added in 1.3 (#2367). Show only cards with at least one track on their own stage in one of these states: done, open, not_applicable. Absent means no track-state filter
    parentFilter string | integer Added in 1.3 (#2209). The Parent filter on a child board: "any" (cards with a parent), "none" (cards without one) or a parent card's id (a positive integer). The server checks the shape only; the client matches it on each card's parent, so an id that names a card the viewer cannot open matches nothing. Absent means any card
    plannedFilter string Added in 1.3 (#2550). The Planned filter on a child board: "hide" (leave planned children out) or "only" (only planned children). Optional; absent means Any. Matched in the browser on each card's own planned field, so it names no column. Any other value is a 400

    All keys are optional. The total serialized size of state_json must not exceed 64 KB. String values (search, custom-field query, equals, min, max and values entries, and lane-rule value, min, and max) must not contain NUL (0x00) characters; they return 400.

    Compatibility (#2357): the number op, min and max keys are additive and follow the 1.0+ API stability rules: the op list only grows, and equals is never removed or retyped. A client released before 1.3 reads only equals, so it treats a range, "is empty" or "has a value" entry (whose equals is "") as no filter on that field; it keeps the op, min and max keys when it saves a preset again, unless the user edits that field's filter in the old client, which rewrites the entry as equals only.

    Errors: 400 Bad Request if name is empty, exceeds 100 characters, a filter with the same name already exists for this user on this board, state_json contains unknown keys or wrong-typed values, or state_version is not an integer between 1 and 32767.

    Export & Import¶

    GET /api/v1/boards/{id}/export/¶

    Export the board. CSV is the default; append ?format=json for a JSON dump. ?format=csv returns the same CSV bytes as omitting format whenever Accept is absent or allows application/json or */*.

    • Under format=csv and format=json, error responses (401, 403, 404, 406, 429) are JSON.
    • Accept: text/csv alone returns 406 Not Acceptable on the CSV paths, with or without format, because no renderer serves text/csv. Send */* or omit Accept.
    • With format omitted and a browser Accept (text/html), or with format=api, errors render as HTML from the browsable API.

    Query parameters

    Parameter Values Default Description
    format csv, json csv Response format. Omit it, or send csv, for CSV; send json for the JSON dump. Other values such as xml return 404 Not Found from the API's format negotiation. csv is accepted since 1.2 (#1790); earlier versions returned 404 for it, so omit format to target older servers.

    Both formats are file downloads (Content-Disposition: attachment): CSV as text/csv, JSON as application/json.

    The suggested filename is <board-slug>-<YYYYMMDD>-<HHMM>.<csv|json>, for example my-board-20261120-1430.json (board when the name has no slug characters). The date and time are the moment of export in the caller's profile timezone, or UTC when the profile has none or it is not a valid zone. Before this change the name carried only the server date (my-board-2026-11-20.json); do not parse it, since the filename is a suggestion for the browser.

    Rate limit: 20 exports/hour per authenticated user (scope: board_export). Exceeding the limit returns 429 Too Many Requests.

    Requires board membership; a caller with no access gets 404 Not Found, as for a missing board. A member whose role is below the board's export_min_role gets 403 Forbidden with body {"detail": "...", "code": "export_restricted", "min_role": "<threshold>"}. Owners and site admins always bypass the threshold.

    CSV columns: Card ID, Title, Description, Column, Swimlane, Priority, Assignee, Labels, Due Date, Weight, Created At, Created By, Last Moved At, Movement Count, Movement History

    Movement History is a semicolon-separated list of pipe-delimited records: <timestamp>|<from_column>|<to_column>|<moved_by>. Since 1.2, a record created by a board import with history has <moved_by> followed by (imported, originally <name>), or (imported) when the import file named nobody. Any |, ; or line break in that source name is written as a space, so the record keeps its four parts. Since 1.3, when a column has been deleted, <from_column> and <to_column> come from the movement's saved column-name snapshot instead of being empty.

    Since 1.2, one column is appended per custom field on the board, in display order, headed Custom: <field name>. The fixed columns keep their positions, so index-based consumers are unaffected, and the prefix keeps a field named Title from colliding with a built-in header. A multi-select value is written as its entries joined with "; ".

    Also since 1.2, one column is appended per swimlane custom field, after the Custom: block, headed Swimlane Custom: <field name>. A row field's value repeats on every card row of its swimlane, so the CSV stays one row per card. The distinct Swimlane Custom: prefix (rather than reusing Custom:) is required: a card field and a row field may share a name, and a shared prefix would produce identical headers. A field with is_admin_only: true produces no column for an exporter below admin, so its existence is not disclosed (the rule contact_email/notes already follow in this export).

    GET /api/v1/boards/{id}/export/?format=json¶

    Export the board as JSON (application/json). Same permissions as the CSV variant: board membership and the export_min_role threshold. Owners and site admins always bypass.

    Rate limit: 20 exports/hour per authenticated user (scope: board_export). Exceeding the limit returns 429 Too Many Requests.

    Response shape:

    The top-level schema_version is always 2 in 1.1+ exports. The importer reads versions 0 (pre-1.0, no field present), 1, and 2. Version 2 adds archived_at per card, movement_type, movement notes, and comment created_at.

    Each card also carries movements ({from_column, to_column, from_swimlane, to_swimlane, moved_by, moved_at, notes, movement_type}, one per CardMovement) and activities ({event_type, from_value, to_value, actor, created_at}, one per CardActivity) arrays, mirroring the movements and activities endpoints. moved_by/actor are usernames, not user objects, and null once the acting user is deleted. Since 1.2 both also carry imported_from_username (additive; schema_version stays 2): null for history recorded on the board, and the source username for a row that came from an earlier import. Each card's comments ({author, body, created_at}) carry it too since 1.2, with the same meaning (#1702). Since 1.3 (#2199) each activity also carries item_text: the checklist item's text on checklist_item_assigned and checklist_item_due_changed entries, and the custom field's name on custom_field_changed entries (#1921), null otherwise (additive; schema_version stays 2). On import a missing item_text is null; a present one must be null or a string of at most 500 characters, otherwise the import fails with 400. Since 1.3 (#2052), a movement whose column or swimlane was deleted carries its recorded name instead of null; schema_version stays 2.

    On import with history on, every movement and activity entry is recorded under the importing user and keeps the file's time. Its source name is kept as text in imported_from_username: the entry's own value when the file has one (a re-exported import), otherwise its moved_by / actor, or "". Only assignee is resolved to an account; source names never are. imported_from_username must be a string or null, at most 150 characters, with no NUL characters.

    Since 1.2 (#1906), import also restores each card's created_at from the file, whatever the history option. It is used when it is not in the future and, with history on, not later than the card's first imported history entry (movement, activity or comment). Otherwise, or when the field is absent or unusable, the card is dated to the import. A bad created_at does not reject the file.

    Comments (with comments on) work the same way since 1.2: each is posted under the importing user, keeps the file's created_at, and keeps its source name in imported_from_username: the comment's own value when the file has one, otherwise its author (a string; any other value is ignored, as before), or "". An author is never resolved to an account, and one over 150 characters is cut to 150. The same imported_from_username validation applies.

    Since 1.2 the payload also carries the board's custom_fields schema and each card's custom_field_values, keyed by field name. Both are additive: schema_version stays 2. JSON import restores both (see Custom fields on import).

    Also since 1.2, each card carries external_ref ({ provider, ref, url }, or null when unset). On import it is restored after validation against the same rules as the card API; invalid entries are silently dropped. CSV export and import do not carry it.

    Since 1.3 (#1149), each card also carries its manual blocked state: blocked_at (ISO 8601 or null), blocked_reason ("" when not blocked), and blocks, the full block history oldest first ({blocked_at, blocked_by, reason, unblocked_at, unblocked_by, resolution, column, imported_from_username}; blocked_by/unblocked_by are usernames, column the name of the column the block started in). Additive: schema_version stays 2, and an importer that predates these keys ignores them. The blocked and unblocked activity entries ride in activities as usual. On import, the card's current block (blocked_at/blocked_reason) is restored whatever the history option, as card state like archived_at; the closed entries of blocks are restored only with history on, attributed to the importing user with the file's blocked_by kept in imported_from_username, keeping their times and resolution. An open entry in blocks is not restored as such: the card's own blocked_at decides whether it is blocked, so the card and its open block cannot disagree. An entry without a valid blocked_at, or that ends before it starts, is dropped. A reason is required, as on the block endpoint: a card with blocked_at but a missing or blank blocked_reason, or a blocks entry with a blocked_at but no reason, makes the import fail with 400 naming the card and entry, rather than importing a block with no reason; reasons and resolutions are trimmed. blocks is capped at 1000 entries per card and its text values at 500 characters; CSV export and import do not carry it.

    Also since 1.2, each swimlane object carries custom_field_values (keyed by swimlane custom field name), and a top-level swimlane_custom_fields array carries that schema. These are separate keys from the card-level pair because they are independent per-board sets on different objects. Both are additive, and JSON import restores them. A definition with is_admin_only: true, and any value under it, is omitted for a caller below admin, the same gate this export applies to a swimlane's contact_email and notes.

    Since 1.3 (#1796), a top-level deleted_card_history array, after cards, carries the retained history of hard-deleted cards: their movements (since 1.2, #1469) and activities (since 1.3, #1799). One entry per deleted card, ordered by its first record: {card_uid, card_title, movements, activities, blocks, gate_transitions}. card_uid is the deleted card's UID, card_title the newest title recorded on its rows, and the four lists have exactly the shape of a card's own lists, oldest first. blocks and gate_transitions (since 1.3, #2413) are the deleted card's retained block and gate transition records; a gate transition's movement_index points into the same entry's movements. A block that was still open when the card was deleted is exported open (unblocked_at: null). A movement whose column or swimlane was deleted too carries the name recorded with it instead of null. The array is empty when no card was hard-deleted. Additive: schema_version stays 2, and an importer that predates the key ignores it. It is readable by whoever may export the board, under the same export_min_role gate: Board History already shows these movements to every member. The CSV export does not carry it, because a CSV row is a card and the CSV importer would create a card from it; whether the CSV should carry the retained movement history in another form is tracked in #2414.

    On JSON import with history on, each entry's movements, activities, blocks and gate transitions are restored as the new board's retained history of a deleted card: no card, the entry's card_uid and card_title, attributed to the importing user with the file's moved_by / actor / blocked_by kept in imported_from_username, like every other history entry. Unlike a live card's list, an open block is restored open, because a deleted card has no blocked_at of its own to decide it; as on the source board, it does not count toward blocked time. Blocks without a usable blocked_at or that end before they start, and gate transitions with an unknown kind, are dropped, as on a live card. With history off they are skipped and counted in import_summary.skipped.movements / activities / blocks / gate_transitions. Entries are validated like a card's lists (same per-entry caps, text limits, timestamp rule and block reason rule, and they count toward the 50,000-row and 1,000-username limits); an entry without blocks or gate_transitions (a file from before 1.3's #2413) imports as before; card_uid must be "" or 16 lowercase hex characters, card_title at most 500 characters, and the array holds at most 10,000 entries. A malformed entry makes the import fail with 400 naming it.

    Since 1.3 (#1448), a top-level relations array, last in the payload, carries the board's card relations: {from, kind, to}, where kind is blocks ("from blocks to") or relates_to (symmetric, written lower card id first), and from / to are 0-based indexes into this file's cards array. A card in the file has no other key: it carries no id or UID, and a title (even with its swimlane) need not be unique, while the importer creates the cards in file order, so an index names the same card in the file and on the new board. This follows the file's existing cross-reference, a gate transition's movement_index. A tool that reorders, inserts or removes entries of cards must rewrite relations to match. Cards are in position order, ties by card id, so the indexes are reproducible. Additive: schema_version stays 2, the key follows the 1.x compatibility rules like every other export key, and an importer that predates it ignores it; it is [] when the board has no relations. Archived cards are in cards, so relations to them are kept.

    On JSON import, relations are restored after the cards are created, with the cards option (with cards off they are counted in import_summary.skipped.relations), under the importing user. A file without relations imports without relations. relations must be an array (otherwise 400) of at most 10,000 entries (400 with code limit_exceeded), and each entry counts toward the 50,000-row limit. Its entries are lenient, like external_ref: an entry that is not an object, has an unknown kind, names an index that is not an integer or is outside cards, or relates a card to itself is dropped, not fatal. So is any entry the relations API would refuse: a duplicate, the reverse of a relates_to already listed, and the second half of a direct blocks cycle (A blocks B and B blocks A; the first listed is kept). Dropped entries are not counted in skipped.

    Both export formats read the card rows in chunks of 500 (since 1.3, #1962): the cards and their related rows (movements, comments and the rest) are fetched from the database one chunk at a time rather than for the whole board at once. Only those database rows are bounded by the chunk. The file is not streamed: the JSON document, with every card's entry, and the CSV body are still built whole in memory before the response is sent, and deleted_card_history and relations are each read in one pass. A board of fewer than 500 cards reads its cards in the same queries as before chunking; one of 500 cards or more adds one query for the ordered list of card ids and, per further chunk, one card query plus one per related collection. No snapshot is held across chunks, but cards come in the order of that id list, so no card appears twice and a card that exists throughout the export is never skipped, even if cards move meanwhile. A card deleted while the export runs may be left out, and one deleted after it was exported is not also listed in deleted_card_history. There is no size limit, so a board that exported before still exports.

    Since 1.3 (#1101), each column object also carries its policy (null when it has none). Additive: schema_version stays 2, and JSON import restores it after checking it like the column API does.

    Since 1.3 (#2454), the payload also carries the board's parent_name_singular, parent_name_plural and cards_can_have_children. Additive: schema_version stays 2. JSON import restores them on the new board, applying the same rules as a PATCH (names are trimmed, at most 24 characters, and refused with 400 if they contain control, zero-width or bidi characters; cards_can_have_children must be a boolean). A file without the keys imports with the defaults (empty names, flag off). Links are not exported, so an imported board with the flag on starts with no links. CSV import and export carry no board settings and are unchanged.

    Since 1.3, each swimlane object also carries its limits: wip_limit, weight_limit, limit_enforcement, and limit_columns, the names of the columns that count (or null for the default, every column not marked done). Names, not ids, because the file keys columns by name and an import creates new ids. All four are additive (schema_version stays 2), and JSON import restores them without enforcing them. A limit_columns name that is not one of the file's columns, an empty list, a limit below 1, or a limit_enforcement other than "block", "hard" or null is a 400.

    Since 1.3 (#1102, #1921), the export carries gated stages and dimension fields, all additive (schema_version stays 2; an older file without the keys imports as a plain board):

    • Each column carries sub_columns (the ordered sub-column names; [] for a plain column) and tracks (the names of the dimension fields bound to the stage, in order). Each swimlane carries not_applicable_tracks, the names of the dimension fields the lane is exempt from. Each custom_fields entry carries is_dimension and choice_resolutions (choice name to satisfied or not_applicable).
    • Each card carries gates_passed (its sub-column index, 0 to the column's sub-column count minus one; larger or non-integer values are a 400) and gate_transitions, its gate history oldest first ({kind, from_index, to_index, column, sub_column, reason, cause, actor, created_at, imported_from_username, movement_index}). movement_index is the position of the movement that caused the transition in the same card's movements array, or null.
    • Each movement carries from_gates_passed, from_gates_open and to_gates_passed (integers 0 to 4, or null for a move that did not touch a gated stage; anything else is a 400).

    On import, gates_passed is restored whatever the history option. gate_transitions are restored only with history on, attributed to the importing user with the file's actor kept in imported_from_username; an unknown kind is skipped and an unknown cause becomes import. A transition is re-linked to its movement through movement_index; a null, absent or out-of-range index leaves the link empty, because the file has no other safe key.

    Since 1.3 (#2243), each swimlane object also carries its lane health status, health_status ("on_track", "at_risk", "off_track" or null for no status), as the last key. Additive: schema_version stays 2, an older file without the key imports as null, and any other value is a 400.

    POST /api/v1/boards/import/¶

    Import a board from a Visiban JSON or CSV export file. Accepts multipart/form-data with a file field and optional name (board name override), group_id (place the board in a group), and options (choose what to import) fields. Creates a new board atomically.

    Permission: authenticated user. When group_id is set, since 1.2 the caller must be an admin of that group or of one of its ancestor groups (or a site admin with all-content access), the same rule as POST /api/v1/groups/{id}/boards/. A group the caller can see but does not administer returns 403 Forbidden; a group that does not exist or is not visible returns 404 Not Found.

    Rate limit: 10 imports/hour per authenticated user (scope: board_import). Exceeding the limit returns 429 Too Many Requests.

    Import limits: up to 500 cards, 50 columns, and 100 swimlanes per import. Payloads exceeding these limits return 400 Bad Request.

    A JSON import also caps its child collections (#1507). The caps sit well above a real board, but are hard limits: a file over any of them, including a board's own export, is refused with 400 Bad Request.

    Collection Limit
    labels (board label definitions) 1,000
    Label names on one card (cards[].labels) 1,000
    comments per card 1,000
    checklist items per card 500
    movements per card 2,000
    activities per card 5,000
    Distinct usernames referenced (assignee, movement moved_by, activity actor) 1,000
    Rows written by the whole import (see below) 50,000

    The whole-import limit caps every row the import inserts. It is counted from the file before anything is written, regardless of the import options, so no import writes more than 50,000 rows. It counts 3 for the board itself (the board, your membership, and its board.created event); one per column, swimlane, label, and custom field definition; one per swimlane custom field value; and, for each card, 1 for the card, 1 for its MR/PR link, one per custom field value, one per comment, movement, activity, and label name, two per checklist item (the item and its "checklist item added" entry), and 2 for the "label added" and "weight changed" entries the importer may add.

    Malformed values in a JSON file return 400 Bad Request naming the item and key, and nothing is created. Since 1.2 (#1507) this covers:

    • Column and swimlane position, card weight and position, and column wip_limit and weight_limit must be integers from 0 to 2,147,483,647. Only wip_limit and weight_limit may be null.
    • Column positions must be unique. A column with no position takes its index in the list, so an explicit position can collide with another column's default. Swimlane positions may repeat.
    • Text values must not be null, a list, or an object, and must not contain NUL characters: column, swimlane, and label color; swimlane contact_email and notes; board and card description; comment body; checklist text; movement notes; activity from_value and to_value. A plain number or true/false is stored as its text (5 → "5", true → "True"), as in earlier releases, except for color on columns, swimlanes, and labels, which must be hex (since 1.3): a number or boolean there is replaced by the default and counted in import_summary.skipped.colors; NaN and Infinity are refused. A key left out takes its default.
    • Text values stored in a limited column must fit it: column and swimlane name (255), label name (50), color (7), contact_email (254), card title (500), checklist text (500), movement notes (500), the column and swimlane names in a movement (255), the name form field (255), usernames in assignee, checklist item assignee, moved_by, and actor (150), and imported_from_username on movements, activities, and comments (150).
    • Column is_done and allow_card_creation, and checklist is_checked, must be true or false.
    • Since 1.3, a column policy must be null or follow the same rules as the column API; it is stored normalized (criteria trimmed, an empty policy as null).
    • Dates and timestamps (due_date, archived_at, and comment, movement, and activity timestamps) must be strings that name a real date or time; a number such as 20200101, an impossible value such as 2024-02-30 or T25:00:00, or a time whose UTC equivalent falls outside years 1–9999 (such as 9999-12-31T23:59:59-12:00) is rejected.
    • A file that cannot be parsed, including one with an integer literal of more than 4,300 digits or nesting too deep to parse, returns {"detail": "The uploaded file is not valid JSON."}.

    Error messages quote only a short, truncated part of any file value. A value that passes these checks but cannot be stored returns 400 with {"detail": "The import file contains a value that cannot be stored."}. Every exported file imports unchanged within the caps above; a board too large for them must be split before re-import.

    Default board name¶

    Changed in 1.2 (#1446) — earlier releases named a JSON import after the file's name verbatim and every CSV import Imported Board. API callers that relied on the old default should send name explicitly.

    Without a name field, both formats name the new board Imported: <name>:

    • JSON — <name> is the name field in the file. An unpaired UTF-16 surrogate in it ("\ud800", which PostgreSQL cannot store) is replaced with U+FFFD in the default name.
    • CSV — a CSV carries no board name, so <name> is the uploaded filename without its extension (Q3 plan.csv → Imported: Q3 plan). An empty filename stem falls back to Board.

    If a board with that exact name exists, the lowest unused number is appended: Imported: Roadmap - 1, then - 2, and so on. A gap left by a deleted or renamed board is reused first.     Import options¶

    Added in 1.2

    Board structure (name, columns, swimlanes) is always imported. Every option is an optional boolean that defaults to true:

    Key Imports Formats
    cards Cards. JSON: with their assignees, due dates, weights, and MR/PR links, plus the "weight changed" activity entry for a non-default weight when history is on. CSV: title, description, priority, weight, due date, and assignee (the Assignee username, matched case-insensitively; blank or unknown usernames import unassigned) — no MR/PR link. JSON, CSV
    labels Label definitions, the labels on cards, and the "label added" activity entries the importer records for them JSON, CSV
    comments Card comments. Requires cards. JSON
    checklist Card checklist items, and the "checklist item added" activity entries the importer records for them. Requires cards. JSON
    history Card movements, the card activities from the file, and the "weight changed" activity entry the importer records for a non-default weight. Requires cards. JSON

    The importer writes its own "label added", "checklist item added" and "weight changed" entries only for history the file does not already record. With history on, a card whose activities already contain that event type keeps the file's entries (original timestamp and source name, recorded under the importing user) and gets no synthetic copy, so re-importing an export does not double its history.

    Three more options are not include flags. They move the file's dates (see Date shifting):

    Key Type Effect
    shift_dates_from YYYY-MM-DD string, JSON only, optional The day to move dates from. Moves every date in the file by the whole days between this date and the target day (shift_dates_to, default today): card due dates, checklist item due dates (since 1.3, #445), date custom field values on cards and swimlanes, the timestamps on cards (including a blocked card's blocked_at), comments, movements, activities and, since 1.3 (#1149), block history entries (blocks[].blocked_at / unblocked_at, so block durations are unchanged), and the old and new values of due-date-change history entries (card and checklist item). Spacing between dates is preserved. When absent, a file's own top-level date_anchor is used in its place; a file without one is not shifted. Must not be in the future or more than 10 years ago. Used by the sample gallery with a sample's date_anchor. When given, it is echoed in import_summary.options_applied and the board.created event's import_options.
    shift_dates boolean, JSON only, optional, default true false turns all shifting off: the file's dates are imported exactly as written, its date_anchor is not read, and shift_dates_to is ignored. Sending it with shift_dates_from is a contradiction and is rejected. Added in 1.2 (#1949). Echoed in options_applied when sent.
    shift_dates_to YYYY-MM-DD string, JSON only, optional, default today (UTC) The day to move dates to: the shifted board is dated around this day instead of today. Used only when dates shift (an explicit shift_dates_from or the file's date_anchor); otherwise ignored. It may be earlier than the source date, which moves dates back. Must not be in the future (UTC) or more than 10 years ago, so imported history never lands after the moment of import. Added in 1.2 (#1949). Echoed in options_applied and import_options when sent and applied.

    Yes, but: A CSV import rejects all three as unknown options: dates in a CSV are always imported as written.

    Date shifting¶

    Added in 1.2 (#1452; the file's own anchor, shift_dates and shift_dates_to since #1949)

    The shipped sample boards are generated around a fixed day, so imported as written most cards would be overdue. Each sample file carries that day as a top-level "date_anchor": "YYYY-MM-DD" key. The importer resolves the shift like this:

    1. shift_dates is false: nothing moves.
    2. Otherwise the source day is shift_dates_from when sent. An explicit option always wins over the file.
    3. Otherwise it is the file's date_anchor, when the file has one.
    4. With no source day, nothing moves. A file without date_anchor, which includes every board export, imports exactly as in earlier releases.

    Dates then move by the whole days from the source day to shift_dates_to, or to today's UTC date when it is not sent. The importer, not the web client, reads the anchor, so the import dialog, a curl upload, and any API client get the same board from the same file. When the file's anchor was used, options_applied.shift_dates_from reports it.

    Only a string counts as an anchor: a date_anchor that is null, a number, a list, or an object is ignored, and the file imports unshifted. A string date_anchor the importer would use is validated like shift_dates_from. One that is not a real YYYY-MM-DD date, or is out of range, returns 400 Bad Request, for example The file's 'date_anchor' is invalid: date_anchor cannot be in the future. Send the import option shift_dates as false to import its dates as written. With shift_dates: false, or an explicit shift_dates_from, the key is not read.

curl -X POST https://visiban.example.com/api/v1/boards/import/ \
  -H "Authorization: Token $TOKEN" -F file=@sales_overlay.json

# The same file dated around 1 June 2026, or with its dates as written
curl ... -F file=@sales_overlay.json -F 'options={"shift_dates_to": "2026-06-01"}'
curl ... -F file=@sales_overlay.json -F 'options={"shift_dates": false}'

    Custom fields on import¶

    Added in 1.2

    A JSON file's custom_fields and swimlane_custom_fields definitions are restored with the board's structure, in list order, whatever the options. Each is validated as the custom field and swimlane custom field APIs validate a new definition, and the per-board limits apply to the whole list: at most 30 card fields (2 shown on the card) and 30 swimlane fields (15 before 1.3; the band shows 2 and the lane details up to 16), with unique names. A failing definition returns 400 Bad Request and creates nothing, for example 'custom_fields' entry at index 1: 'choices': … or Duplicate swimlane_custom_fields names: Owner.

    Values (custom_field_values on each card and swimlane, keyed by field name) go through the same normalizer as PATCH. A value naming no imported field, or one its field's type refuses, is dropped and the import proceeds. Card values follow the cards option; swimlane values are structure and always import. Values exported by Visiban are already in stored form and round-trip unchanged.

    Custom fields in a CSV import¶

    Added in 1.2

    A CSV import reads the Custom: <name> and Swimlane Custom: <name> columns the CSV export writes, so card and swimlane field values survive a CSV round trip.

    • Every field becomes a text field. A CSV carries no field type, so nothing is inferred: a number, date, dropdown or checkbox column imports as text, and dropdown choices, number formatting and pin settings are not restored. JSON is the lossless format for field definitions; use it when types matter. A multi-select cell such as UI; DB is stored as that plain text, not parsed into entries.
    • Cells are stored exactly as exported. The export removes leading formula characters (=, +, -, @, tab, carriage return) from text values so a spreadsheet cannot run them, and that removal is irreversible: a text value =1+1 is exported, and re-imported, as 1+1. The importer does not un-escape and does not sanitize. (Number and checkbox values are written as stored, so a number such as -5 keeps its sign.)
    • Definitions are created in header order, subject to the same limits as a JSON file: at most 30 card fields and 30 swimlane fields, unique names, validated as the field APIs validate them. A violation returns 400 Bad Request and creates nothing, as does the same custom header appearing twice (Duplicate custom field CSV headers: Custom: Region). A card field and a swimlane field may share a name. A header with an empty name (Custom:) is skipped with a warning.
    • Swimlane values are repeated on every card row of the lane in the export, so the importer takes the first non-empty cell per lane and field; a later, different value is ignored and reported once as a warning. Swimlane values import whatever the cards option says; card values follow it.
    • Blank cells create no value. A value longer than 500 characters, one containing a NUL (\x00) byte, or one an extension validator refuses, is dropped with a warning and the import proceeds.

    Cell limits (since 1.2, #1512). The importer checks every row before creating anything. A violation returns 400 Bad Request as Row N: <field> ... and creates nothing. N counts data rows from 2 (the first data row is row 2), so it can differ from the physical line number when a quoted cell spans several lines. Echoed values are truncated. Only cells the import writes are checked: with cards set to false the Title, Description, Assignee and Weight cells are skipped, and with labels set to false so is Labels. Ignored columns (Priority, Card ID, unknown headers and so on) are never checked.

    Field Limit
    Title At most 500 characters
    Column, Swimlane At most 255 characters
    Labels Each comma-separated label at most 50 characters
    Weight An integer from -2147483648 to 2147483647 (a non-numeric value still imports as 1)
    Due Date A real calendar date; 2020-02-30 is refused like any other invalid date
    Title, Description, Assignee, Column, Swimlane, Labels No NUL (\x00) bytes (Custom: cells keep the drop-with-warning rule above)
    name form field At most 255 characters and no NUL bytes, as for a JSON import

    The response gains import_summary.warnings, a list of strings (always present on a CSV import, [] when nothing was dropped). It holds at most 20 entries followed by one …and N more entry. A JSON import does not return the key.

    Import summary¶

    Added in 1.2

    Field Description

    POST /api/v1/boards/import/trello/¶

    Added in 1.2 (#456)

    Import a Trello JSON export (Trello: Menu → Print, export, and share → Export as JSON) into a new board. The flow is stateless and has two steps: call with ?dry_run=true for a preview of exactly what will be created, then re-upload the same file with ?confirm=true to create the board. Both modes run the same parsing and mapping code, so the preview is what the import does.

    The import is synchronous: the board exists when the 201 returns, bounded by the upload size cap, the count caps below, and the rate limits. Imported content sends no notifications (no @mention, assignment, or card-moved) and records no movement history for imported cards.

    Permission: authenticated user. When group_id is set, the caller must be an admin of that group or of one of its ancestor groups (or a site admin with all-content access) in both modes, so a preview cannot be used to probe a group the caller could not import into. The caller becomes the board's owner and admin.

    Query parameters — specify exactly one:

    Parameter Description
    dry_run=true Parse and plan only. Returns 200 OK with the preview. Creates nothing.
    confirm=true Create the board. Returns 201 Created.

    Sending neither, or both, returns 400 Bad Request ("Specify exactly one of ?dry_run=true or ?confirm=true.").

    Request (multipart/form-data)

    Field Type Required Description
    file file yes The Trello JSON export. Maximum size is IMPORT_MAX_SIZE_BYTES (default 25 MB).
    name string no Board name. Defaults to the Trello board's name. Maximum 255 characters. Only used on confirm.
    group_id integer no Place the imported board into this group. Requires group admin. Also widens the pool used for member matching.
    mapping string (JSON) no JSON-encoded object of mapping options, described below. Omitted or blank means all defaults. Send the same mapping on dry_run and confirm.
    file_sha256 string no On confirm, the file_sha256 returned by the preview. If present and it does not match the uploaded file, the request is rejected with 400, so a different file cannot be swapped in between preview and confirm.

    mapping options — unknown keys return 400.

    An export, or a mapping, that contains an unpaired UTF-16 surrogate ("\ud800", valid JSON that PostgreSQL cannot store) returns 400 naming the surrogate's code point.

    Key Type Default Description
    swimlane_label_ids string[] [] Trello label ids (from mapping.labels[].trello_id in the preview) to turn into swimlanes, in the order given. Only named labels are eligible (swimlane_eligible: true).
    default_swimlane_name string "Unassigned" Name of the swimlane for cards that have no mapped label. Must be non-empty and must not equal the name of a label mapped to a swimlane.
    include_archived_lists boolean false Import archived (closed) lists as columns, and their cards as archived cards.
    add_matched_members boolean false Add matched members to the board and assign them to their cards.

    Mapping rules

    • Lists to columns, ordered by Trello position and renumbered densely from 0. Archived lists are skipped unless include_archived_lists is true; their cards are then imported as archived cards. Without that option, cards in archived lists are skipped. Cards that reference a list missing from the export are skipped.
    • Labels keep their names. Trello color names are converted to hex (#RRGGBB); an unnamed label is named after its color. A duplicate name gets a " (2)" suffix (then (3), and so on).
    • Labels to swimlanes for the labels listed in swimlane_label_ids. A card goes to the swimlane of the first mapped label in the card's own label order; any other mapped labels stay as ordinary labels. Cards with no mapped label go to the default swimlane.
    • Checklists are flattened into one checklist per card. When a card has several checklists, each item's text is prefixed with its checklist name. Since 1.3 (#2197) a checklist item keeps its Trello due date (due, converted to a UTC date like a card's; an unreadable one is left empty and counted in invalid_due_dates) and its member (idMember), matched like card members below.
    • Comments are imported with their original timestamps.
    • Archived cards (closed in Trello) are imported archived.
    • Attachments are not copied. Each attachment is appended to the card description as a link, and only http and https URLs are kept. Uploaded files are reported under unmappable as attachment_files.
    • Due dates are converted to a UTC date.

    Member matching¶

    A Trello member matches a Visiban user when the Trello username equals the Visiban username exactly, ignoring case. Display and full names are never used.

    Matching considers only users the caller can already see: co-members of the caller's boards and groups, and members and owner of the target group. Site admins can match any active user. This stops a crafted file from probing whether a username exists. The response reports only a count of matches, never which accounts.

    • add_matched_members: false (default): matched users are not added to the board and cards are left unassigned.
    • add_matched_members: true: matched users are added to the board with the member role and assigned to their cards (the first matched Trello member on each card) and, since 1.3, to their checklist items. Since 1.3 (#2122) each added user gets a board_invite notification, as an add through the members endpoint does, unless they turned board invite notifications off; assigning cards or checklist items still sends none. No member.added change-feed event is recorded for them: the board is new in the same request, and its board.created event carries the member count.
    • A checklist item whose member did not match, or any checklist item when add_matched_members is false, imports unassigned (#2197).

    Since 1.2 (#1702), with either setting, every comment is authored by the importer and keeps its Trello time. The Trello author's display name is kept as text in the comment's imported_from_username (at most 150 characters, line breaks collapsed), never matched to an account, and the body starts with the plain-text line (imported from Trello). Earlier versions authored a matched member's comments as that member when add_matched_members was true, and put the author's name in the body (Full Name (imported from Trello):) otherwise; comments imported then are unchanged.

    Unmatched members are listed in the preview by their Trello name (from the uploader's own file).

    Members¶

    POST /api/v1/boards/{id}/members/¶

    Add or update a board member. Requires board admin: a caller with no access gets 404, a member below admin gets 403. Cannot modify a site admin's existing board membership (the same restriction as DELETE below); a site admin with no membership on the board is added like any other active user.

    For a caller who is not a site admin, the response (and the member.added / member.updated event) omits is_site_admin for every target. When the target is a site admin with no direct membership, the stored role is the higher of the requested role and the role the user already holds through a group, so the new membership never lowers it (any other user's new direct membership keeps its ordinary precedence over a group-inherited role). is_site_admin is therefore optional here (not in the OpenAPI required list): a site-admin caller gets it, others do not.

    (1.3+, #1828) A request that would give the board owner a stored role below admin returns 400 Bad Request and writes nothing, for every caller including site admins:

    {"detail": "The board owner's membership cannot be removed or demoted. The owner keeps admin access to the board while they own it.", "code": "board_owner_protected"}

    Branch on code, not on detail, which may be reworded. That covers naming a lower role for the owner, and adding an owner who has no membership row without role (a new row defaults to member). Setting the owner to admin is accepted, and so is a request that names no role for an owner who already has a row (it keeps the stored role, so it is not a demotion). Before 1.3 these requests succeeded, but changed nothing the owner could do: the owner holds admin through board ownership whatever the row says. The other 400s from this endpoint carry detail only.

    Since 1.2, a request body that is not a JSON object returns 400 Bad Request (it returned 500 before). Since 1.2 a user_id that is present but not an integer, or is beyond the 64-bit integer range, is a 400 too: a non-integer value used to answer 404 and an out-of-range one 500. An omitted user_id still answers 404.

    Request { "user_id": 42, "role": "member", "is_moderator": true }

    Field Required Description
    user_id ✓ ID of the user to add or update. A new membership needs an active user: an id that matches no user and an id that matches an inactive user both return the same 404 Not Found. A user who already has a membership can have the role updated whatever their status
    role Role to assign. When omitted, a new membership gets "member" and an existing membership keeps its current role (before 1.2 an omitted role reset an existing member to "member").     is_moderator Boolean. Grants content-moderation rights (delete/archive others' content). Only valid for member and admin roles — setting true on a collaborator or viewer returns 400 Bad Request.     Visibility of is_moderator in board responses (since 1.1; self-row exception since 1.2): the is_moderator field is included in the members array of GET /api/v1/boards/{id}/full/ for admin and site_admin requesters, on every row. A lower-role requester (member, collaborator, viewer) receives the field only on the row belonging to themselves — so a member promoted to moderator can see their own entitlement — and every other row omits it. This endpoint's own response always carries the field, since it requires board admin. The member.added / member.updated WebSocket broadcast and the change feed apply the identical self-row rule per recipient (#1191): the subscriber's/reader's own row always carries the field, every other non-admin-visible row omits it.

    Member row role and assignability (since 1.3, #1905): in the members array of GET /api/v1/boards/{id}/full/, the board owner's row has role: "admin", the role the board grants them, even when they hold an explicit membership with a lower stored role; that row keeps its membership id. (1.3+, #1828) The members endpoints refuse to remove or demote the owner's membership (see below), so such a row can only be raised back to admin. Before 1.3 such a row showed the stored role. A row whose stored role is not one of admin, member, collaborator or viewer is listed as stored, so an admin can find and remove it; it grants no access, and the server refuses that user as a card assignee. A client building an assignee picker should offer only rows with role admin, member, collaborator or site_admin, plus any row with has_all_content_access: true; the Visiban web app does this in every assignee picker since 1.3. What the server enforces is unchanged.

    has_all_content_access on member rows (since 1.3, #1301): for a board admin or site_admin requester (board role site_admin, or an instance site admin on any board role), each row in the members array of GET /api/v1/boards/{id}/full/ carries a boolean has_all_content_access: true when the member has can_access_all_content, which always resolves to full access ahead of any explicit membership. A row can therefore carry a stored role such as viewer while the member still has full access; use this field, not role, to tell. It is present on every row the requester receives (direct, group-inherited and owner rows), and rows with role: "site_admin" are always true. Requesters below admin omit the key. It does not widen who is listed: the all-content users with no role on the board still appear only for a site-admin requester (#1714). It is never added to the nested user object.

    is_site_admin on member rows (since 1.2): each row in the members array of GET /api/v1/boards/{id}/full/ carries a boolean is_site_admin; the response of this endpoint and the member.added / member.updated events this endpoint produces (WebSocket broadcast and change feed) carry it only when the caller who made the change is a site admin (the payload is built once, so subscribers of any role do not receive it otherwise; a client re-reads the board to get the flag). A member.added event from invite redemption keeps its documented payload, which subscribers receive according to their role — the member's instance-level site-admin flag, the same flag this endpoint and DELETE below check. Use it, not role, to decide whether a row can be edited: role: "site_admin" means the member has can_access_all_content, which is a separate flag. The field is present only for admin and site_admin requesters, subscribers and readers, and there is no self-row exception (read your own flag from /api/v1/auth/me/). On /full/, a board admin who is not a site admin receives it only on rows backed by a membership on this board (id not null), which are the only rows this endpoint refuses to change for them; group-inherited and owner rows omit it for that requester (since 1.2, #1714). A site-admin requester (board role site_admin, or an instance site admin) receives it on every row. It is never added to the nested user object.

    DELETE /api/v1/boards/{id}/members/{user_id}/¶

    Remove a member. Requires board admin. Cannot remove a site admin who is a member of the board. Returns 204 when the membership is removed. (1.3+, #1828) Removing the board owner's membership returns 400 Bad Request with the same {detail, code} body as POST above (code board_owner_protected) and writes nothing, for every caller including the owner and site admins; before 1.3 it answered 204 but the owner kept admin access through board ownership and only disappeared from the roster. The owner leaves a board by deleting it. If the user has no membership on the board, the response is the same 404 Not Found (status and body) whether the id is unknown, belongs to an inactive user, or belongs to an active user who is not a member; an inactive user who has a membership can be removed.

    Board invites¶

    Added in 1.2

    A board admin can email a single-use invite to someone who may not have an account yet, or create a shareable invite link to paste anywhere. The invite token (vbnb_ prefix) travels only in the email, or — for a shareable link — in the create response, once; it is never returned again. Only its first 8 characters (prefix) are shown. The address it was sent to is not stored. (1.2+, #1678) An emailed invite stores a keyed fingerprint of that address instead, and redeeming it requires an account with that address (see POST /api/v1/boards/join/{token}/ below). The fingerprint is never returned by any endpoint or event. Shareable links have no fingerprint. Invites grant member, collaborator or viewer — never admin, and never the moderator flag. A board invite never adds anyone to the board's group.

    GET /api/v1/boards/{id}/invite-links/¶

    List the board's invites, newest first, as a bare array (not paginated). Requires board admin (an admin of the board, the owner, an admin of the board's group, or a site admin with all-content access). Returns every pending invite plus at most the 50 most recent past ones (used, expired or revoked); older history is not returned. (1.3+, #1885) The X-Total-Count response header gives the board's invite count including the ones left out, and X-Truncated is true when older past invites were left out (false otherwise). A caller with no access to the board, or for a board that does not exist, gets 404, an unauthenticated request 401 — the same as the members endpoints.

    Field Description
    id, prefix, name Identity. name is empty for emailed invites, and optional for shareable links.
    role member, collaborator or viewer.
    delivery email for emailed invites, link for shareable links.
    created_at, created_by_username When and by whom it was sent. created_by_username is null when the sender's account was deleted.
    expires_at, is_expired, single_use, used_at Lifetime.
    status pending, used, expired or revoked (precedence revoked > used > expired). A pending invite whose sender's account was deleted, or who is no longer an admin of the board, is reported as revoked — the join endpoints refuse it the same way — although nobody revoked it explicitly, and it frees its slot in the cap for its kind — the 50 pending emailed invites, or the 5 active shareable links. This is not written to the invite: if the sender regains board admin, the invite reads as pending and can be redeemed again (until it expires). To make it permanent, revoke it with DELETE below, which accepts it because it was never actually revoked.
    can_register Advisory: whether a new person could create an account from this invite under the site's current registration mode — computed when you read it, so it changes if the mode or the sender's site-admin status changes. Always false when status is not pending, and always false for a shareable link unless the site is open.
    use_count (1.2) How many distinct people have redeemed the invite: the first redemption by each account counts once, and following the link again later does not add to it. A multi-use shareable link never sets used_at, so this is its only usage signal.

    POST /api/v1/boards/join/{token}/¶

    Redeem an invite as the signed-in user. Returns { "board_id", "board_name", "role", "created" } — 201 when a membership was created, 200 otherwise. Same 404 / 410 / 429 responses as the preview, plus:

    Status When
    401 Unauthorized No credentials.
    403 Forbidden {"detail": "..."} with no code: the account must change its password or username first (must_change_password / must_change_username), a personal access token lacks the write scope, or a session request fails the CSRF check.

A consumed invite followed again by the person who redeemed it is not checked either.

    Redeeming depends on the access you already have, because an explicit board membership replaces any role inherited from the board's group rather than adding to it:

    • No access → you become a board member with the invite's role (created: true).
    • Only a group-inherited role ranked below the invite's (for example a group viewer redeeming a member invite) → an explicit membership with the invite's role is created (created: true).
    • An equal or higher inherited role, an explicit board membership of any role, board ownership or all-content access → nothing changes (created: false). A group admin who redeems a viewer invite is not downgraded to viewer.

    A redeemed single-use invite is consumed either way. Redeeming it again as the person who already has access returns 200 with nothing changed (created reports whether this invite created your membership, true after signing up from it); anyone else gets 410 {"code": "used"}. When a membership is created, the board's member.added event carries an extra invite: { "id", "created_by_id" } key for admin and site_admin recipients, on the WebSocket and in the change feed; other recipients get the event without it.

    Board sharing¶

    POST /api/v1/boards/{id}/share/¶

    Generate (or regenerate) a public share token for the board. Requires board admin.

    If a token exists, this call invalidates it immediately and returns a new UUID, so existing share links stop working. This is how a link is rotated.

    (1.2+, #1935) This response is where clients should read the token: show it (or share_url) to the admin now. The share_token field on GET /api/v1/boards/{id}/full/ is deprecated and will be removed in 2.0; to tell later whether a link is set, read share_link_active there.

    Permissions: board admin or site_admin only.

    Request (optional) 

    {
  "expires_in_days": 7
}

    expires_in_days is optional. Allowed values: 7, 30, 90, or null. Omitting it or sending null creates a link that never expires; this API default is part of the 1.x contract and does not change. Any other integer returns 400 Bad Request. New in 1.1 (#804).

    (1.2+, #1865) The Sharing tab in board settings pre-selects 30 days and sends it explicitly; choosing Never sends null. Clients calling the API directly keep the "never expires" default unless they send a value.

    (1.2+, #1865) The link records the admin who enabled it, and lasts only while that account keeps the standing that let it enable sharing on this board: active, and a board admin or site_admin there (by membership, ownership, group role, or all-content access). When that account is deactivated or deleted, demoted below board admin (including by being added to the board directly with a lower role, which takes precedence over a group role), removed from the board or from the group that made it an admin, loses that group role because it joined a nearer group with a lower role, the board's group is changed (PATCH/PUT with group, or move-group), or a group is moved or deleted, or loses all-content access, the token and its expiry are cleared and a board.updated event is sent, plus (1.3+) the admin-only share_link.updated event with active: false. An account that is still an admin of the board another way keeps the link. Links enabled before the enabler was recorded (for example under 1.1, or 1.2.0-beta.3 and earlier), record no enabler and do not resolve from the upgrade on (#1939); a POST here issues a new link that records the caller. No response body or event payload includes the enabler.

    Column policy (since 1.3)¶

    policy holds a column's entry criteria and definition of done (#1101). It is advisory: no card move, create or restore is ever refused because of it.

    Key Type Rules
    v integer Required. Always 1.
    entry array of strings Entry criteria, in display order. Up to 8, each non-blank and at most 200 characters after trimming. Default [].
    done array of strings Definition of done, same rules. Default [].
    mode string "advisory" (default) or "confirm". "confirm" asks the web app to list the entry criteria for the mover to confirm after a drag-and-drop move into the column. The server never checks it.

    A criterion containing a control character (including NUL or a line break) is refused too. Any other key, a wrong v, or a value breaking these rules returns 400 with a policy error. Criteria are stored trimmed, and a policy whose two lists are both empty is stored as null. Send "policy": null to remove it. Leaving policy out of a PUT keeps the current value.

    { "policy": { "v": 1, "entry": ["Has an owner"], "done": ["Reviewed", "Docs updated"], "mode": "confirm" } }

    The column.updated socket event carries the column with its policy, like every other field.

    (1.3+, #2500) A change of is_done also sends card.children_bulk_changed to each parent board whose cards have live children in this column, so their child progress refreshes; nothing is sent when is_done is unchanged. See WebSockets.

    Swimlane limits (since 1.3)¶

    Added in 1.3 (#1150)

    A swimlane can carry its own wip_limit and weight_limit, enforced on the same card write paths as a column's: a move, a card create, a restore from archive, and (weight only) a PATCH that raises a card's weight. Only cards in the swimlane's counted columns (limit_column_ids) count, and archived cards never do.

    • When a move is checked. Only when it adds to the swimlane's counted total: the card enters a counted column of the swimlane from another swimlane, from an uncounted column of the same swimlane, or from nowhere (create, restore). A move between two counted columns of one swimlane, or a reorder, never trips the swimlane's limit, exactly as a swimlane-only move never trips a column's.
    • Errors. 409 with swimlane_wip_limit_exceeded, swimlane_wip_hard_blocked or swimlane_weight_limit_exceeded. The bodies are the column codes' bodies plus swimlane_name; column_name names the target cell's column, and current_count / current_weight / wip_limit / weight_limit are the swimlane's. See Cards — Move.
    • Several limits at once. When the column and the swimlane (or WIP and weight) both trip, the response names the strictest one: a hard limit before a soft one, and the column before the swimlane when they are equally strict. A board that never sets a swimlane limit gets exactly the bodies it got before 1.3. One ?force=true from a board admin overrides every soft limit the move trips; it never overrides a hard one.
    • Import and export. The JSON export carries wip_limit, weight_limit, limit_enforcement and limit_columns (column names, or null) per swimlane, and the JSON import restores them. Import never enforces a limit, so an imported swimlane can be over its limit.

    URL fields¶

    A "url" field stores a web address, on card and swimlane custom fields alike. Like every type it is text-backed: the value is the stored string.

    • Validated on write, through the same rule as a card's external ref URL: the value must be an absolute http:// or https:// URL with a host. Any other scheme (javascript:, data:, ftp:, mailto: — matched case-insensitively), a missing scheme (example.com), embedded whitespace or control characters, a backslash, a percent-encoded host, credentials (user:pass@), or an invalid port is rejected with 400 Bad Request.
    • At most 500 characters, the cap that applies to every custom field value. A longer URL is rejected, never truncated.
    • Stored as sent (after trimming surrounding whitespace) — the scheme's case and the rest of the URL are not rewritten. The API does not add a missing https://; the web UI does that before it sends the value.
    • choices is rejected for a "url" field, as for every type that cannot carry choices (anything but "dropdown" and "multi_select").
    • Clients that do not recognize "url" should render the value as plain text (it is always a string). A client that renders a link must still check the scheme at render time and use rel="noopener noreferrer".
    • Enterprise CUSTOM_FIELD_VALIDATORS hooks receive "url" as the field_type and run after this validation.

    Multi-select fields¶

    Added in 1.2

    A "multi_select" field holds any number of the definition's choices, on card and swimlane custom fields alike. It is text-backed like every type: the value on the wire is still a string, a JSON array encoded as a string, never a JSON array.

    { "field_definition": 14, "value": "[\"web\",\"ios\"]" }
    • Canonical form. The stored (and returned) string is compact JSON (["web","ios"], no spaces, non-ASCII characters unescaped), deduplicated, with entries that are current choices in choices order, followed by any orphaned entries (see below). Resubmitting the same set in a different order is therefore not a change: the stored row is not rewritten and no custom_field_value_changed / swimlane_custom_field_value_changed signal fires.
    • Accepted on write — any of: an array of strings ("value": ["ios", "web"]); the JSON array string a read returned (so echoing a payload back is a no-op); a plain string, read as a single entry ("value": "web"). "", null and [] (or an array of blank strings) clear the field. Surrounding whitespace on each entry is trimmed.
    • Every entry must be a current choice — or already stored on that card or swimlane. Anything else is a 400: '<entry>' is not a choice for '<name>'. A non-string entry (or a nested array) is a 400: Each value of '<name>' must be a string. An object, a boolean, or an entry containing NUL (\u0000) is also a 400.
    • At most 500 characters, measured on the canonical string. Over the cap is a 400, never a truncation: '<name>' value is longer than 500 characters. The same message is returned, without parsing, for an array of more than 500 entries or a JSON array string longer than 2,000 characters.
    • Permissions are those of the owner's other writes: a card value needs board member or above and is subject to the same ownership gate as any card edit; a swimlane value can be written by board admins only.
    • Orphans are kept. Renaming or removing a choice never rewrites stored values: an entry that is no longer a choice stays in the value, is returned as stored, and may be kept (or dropped) on later writes to that same card or swimlane. It cannot be added anywhere it is not already stored. Clients should render an orphaned entry like any other value.
    • field_type follows the same freeze rule as every type — it cannot change once any value exists — so there is no conversion path to or from "dropdown".
    • Clients that do not recognize "multi_select" should render the value as plain text; it is always a string.
    • Export. The JSON export carries the stored string unchanged. The CSV export writes the entries joined with "; " (web; ios), each entry formula-sanitized like every other CSV cell.
    • Extension points. Enterprise CUSTOM_FIELD_VALIDATORS / SWIMLANE_CUSTOM_FIELD_VALIDATORS hooks receive field_type == "multi_select" and the canonical string (for example '["web","ios"]'), never a list; a hook that rewrites the value must return a string of the same shape. A rewritten value is re-canonicalized and re-checked against the 500-character cap; one that is not a JSON array of strings is refused with a 400. The custom_field_value_changed and swimlane_custom_field_value_changed signals send old_value/new_value as the canonical strings — the whole set, not a per-entry diff.

    Field Type Default Rule
    number_prefix string "" At most 10 characters. Stored exactly as sent — leading and trailing spaces are not trimmed ("$ " is a valid prefix).
    number_suffix string "" At most 10 characters, stored exactly as sent (" h").
    number_decimals integer or null null 0–10 inclusive. null means "render the number as typed".
    • All three are optional on create and PATCH; omitted, they keep their defaults (or current values), which reproduce the pre-1.2 rendering exactly. Existing clients that ignore them are unaffected.
    • Only on a number field. On any other field_type, a non-default value is a 400 Bad Request keyed by the offending field: {"number_prefix": ["Number format options can only be set on a number field."]}. Sending the defaults ("", "", null) is always accepted, so a client may send all three keys for every type. A PATCH is checked against the definition's stored type when field_type is not in the body.
    • Changing the type clears them. When a definition with no values is retyped away from "number", all three are reset to their defaults in the same write. Sending a non-default format in the same request as the retype is a 400.
    • Other 400s: number_decimals below 0 (Ensure this value is greater than or equal to 0.), above 10 (Ensure this value is less than or equal to 10.), or not an integer (A valid integer is required.); a prefix or suffix over 10 characters (Ensure this field has no more than 10 characters.), containing NUL (Null characters are not allowed.), or null (This field may not be null.).
    • Rendering (the web UI's rule, recommended for other clients): a value that does not parse as a finite number is shown raw. With number_decimals null, the number is shown with its digits as typed, plus thousands grouping for a plain decimal ("33000" → $33,000; changed in 1.3, #2387); a +-signed or exponent form stays as typed ("+5" → $+5, "1e3" → $1e3). With it set, round to that many places with thousands grouping (1e3 → 1,000); values beyond 2^53 lose precision in the display only — the stored value is untouched. Then add the prefix and suffix verbatim, with a minus sign before the prefix (-$5.00).
    • Export. The JSON export's custom_fields and swimlane_custom_fields entries carry the three keys (additive — schema_version is unchanged); card and swimlane values stay the raw number string in both JSON and CSV.
    • Events. custom_field.created / custom_field.updated and swimlane_custom_field.created / swimlane_custom_field.updated carry the full definition, so the three fields arrive with them.

    Threshold marking¶

    Added in 1.3

    Optional, display-only thresholds on a card custom field of type "number" or "date". A client marks a card's value once it reaches a threshold; the value itself never changes. Swimlane (row) custom fields have no thresholds (#2217). These are new fields on an existing endpoint: they are stable and additive, and a client that ignores them is unaffected.

    { "name": "Spend", "field_type": "number", "threshold_direction": "above", "threshold_warn": 5000, "threshold_alert": 6000 }
{ "name": "Renewal", "field_type": "date", "threshold_direction": "below", "threshold_warn_days": 14, "threshold_alert_days": 0 }
    Field Type Default Rule
    threshold_direction string "" "" (off), "above" or "below".
    threshold_warn, threshold_alert number or null null "number" fields only. Finite, between -1e15 and 1e15.
    threshold_warn_days, threshold_alert_days integer or null null "date" fields only. A signed day offset from today (-3 = three days ago), between -3650 and 3650.
    • All five are optional on create and PATCH. Omitted keys keep their current values (or the defaults on create). A PATCH is checked against the stored values for any key it does not send, and against the stored type when field_type is not in the body.
    • Direction and values go together. With threshold_direction "", every threshold must be null (400 keyed threshold_direction). With a direction set, at least one threshold of the field's type is required (400 keyed threshold_warn or threshold_warn_days). Turning thresholds off therefore means sending "" and the nulls together.
    • Ordering. When both are set, the alert threshold must be strictly beyond the warning in the direction: above, alert > warn; below, alert < warn. Otherwise 400 keyed threshold_alert / threshold_alert_days. Changing only the direction re-checks the stored pair.
    • Wrong type. A non-null number threshold on a "date" field, a day threshold on a "number" field, or any non-default threshold on another type is a 400 keyed by the offending field. Sending the defaults ("" and nulls) is always accepted.
    • Changing the type clears them. Retyping a definition (possible only while it has no values) resets all five to their defaults unless the same request sets thresholds valid for the new type.
    • Other 400s: NaN or infinity (A valid number is required.), a value out of range (Ensure this value is less than or equal to …), a non-integer day offset (A valid integer is required.), an unknown direction ("sideways" is not a valid choice.). Errors are plain field-keyed lists, like number formatting.
    • Evaluation (the web UI's rule, recommended for other clients): boundaries are inclusive. "above" marks a value at or over a threshold, "below" one at or under it, and the alert level wins over the warning. A number value is compared as a finite number ("1e3", "+5", "1.50" all parse); one that does not parse is not marked. A date value is compared by its day offset from today in the viewer's timezone (the same "today" as due dates); a value that is not a calendar date is not marked.
    • Export and import. The JSON export's custom_fields entries carry the five keys (additive — schema_version is unchanged), and import validates them with the same rules. An older server ignores them on import.
    • Events. custom_field.created / custom_field.updated carry the full definition, so the five fields arrive with them.

    Choice colors¶

    Added in 1.2 · Changed in 1.3: a value may also be a custom #RRGGBB hex (#2096).

    An optional, display-only color per choice on a "dropdown" or "multi_select" definition, on card and swimlane custom fields alike. choices stays a plain list of strings; the colors live in a separate map keyed by choice text. Values are never touched.

    { "name": "Severity", "field_type": "dropdown", "choices": ["Low", "High"], "choice_colors": { "High": "red", "Low": "#2F855A" } }
    • Shape. An object mapping a choice (its text, exactly as in choices) to a palette key or a hex color. Default {}. A choice with no entry has no explicit color; the web UI renders it with its automatic dot, the same as before 1.2.
    • A palette key or a hex color. The palette keys are slate, blue, green, amber, red, violet, pink, teal (case-sensitive: RED is refused); the client owns how each key looks in light and dark themes. Since 1.3, a value may instead be a custom #RRGGBB hex. The server accepts either case and stores and returns it upper-case (#2f855a reads back as #2F855A), so every response matches the schema pattern ^#[0-9A-F]{6}$. #RGB, CSS names and rgb() are refused. The web UI derives a legible text and tint pair for any hex in both themes, so a near-white or near-black custom color stays readable.
    • Optional on create and PATCH; omitted, the map keeps its default (or current value). Sending {} is always accepted, for every field_type.
    • Stale keys are pruned, not refused. On every write, entries whose key is not one of the definition's current choices (after the choices in the same request are applied, or the stored ones when choices is not sent) are dropped silently. Keys are matched after trimming surrounding whitespace, like choices. So renaming or removing a choice drops its color — the choice text is the key, and a color is not carried over to a renamed choice. A PATCH that only changes choices prunes the stored map the same way.
    • Changing the type clears it. When a definition is retyped away from "dropdown" / "multi_select", the map is reset to {} in the same write. Retyping between "dropdown" and "multi_select" keeps it.

    • Errors — all 400 Bad Request, keyed by choice_colors:

      Cause Message
      A non-empty map on any other field_type (judged against the stored type when the body does not change it) Choice colors can only be set on a dropdown or multi-select field.
      Not an object (a list, string, number, boolean) Choice colors must be an object mapping a choice to a color.
      null This field may not be null.
      More than 100 entries (the per-field choice cap) At most 100 choice colors are allowed.
      A key containing NUL (\u0000) Choice color keys must be choice names without NUL (0x00) characters.
      A value that is neither a palette key nor a #RRGGBB hex (other case of a key, #RGB, a CSS name, a non-string) Choice colors must be one of: slate, blue, green, amber, red, violet, pink, teal, or a hex color as #RRGGBB.

    • Rendering (the web UI's rule, recommended for other clients): a value whose choice has a known color key or a hex renders as a tinted badge with its text label — color never carries meaning alone. A value that is no longer a choice (an orphan), or a value the client does not recognize (a key added by a newer server), renders neutral, label shown. A client built before 1.3 that only knows palette keys renders a hex choice neutral the same way.

    • Export. The JSON export's custom_fields and swimlane_custom_fields entries carry choice_colors (additive — schema_version is unchanged; choices is unchanged). Card and swimlane values are unchanged in JSON and CSV. A non-admin exporter does not receive an is_admin_only swimlane definition at all, colors included. Exports from before 1.3 import into 1.3 unchanged. An export that carries a hex choice color, imported into a server older than 1.3, is refused with a 400 for the whole import (that server validates choice_colors as palette keys only); remove the hex entries, or upgrade the target server first. During a rolling upgrade to 1.3, a pre-1.3 server process that handles a write to a definition holding a hex color drops that entry (it re-filters the stored map against palette keys); re-pick the color once the upgrade completes.
    • Events. custom_field.created / custom_field.updated and swimlane_custom_field.created / swimlane_custom_field.updated carry the full definition, so choice_colors arrives with them (an additive field).

    Band visibility (since 1.3)¶

    band_visibility says where a swimlane field shows on each lane band (#2439):

    • "band": always visible on the band. At most 2 per board.
    • "details": behind the band's Show N more toggle. At most the board's lane_details_cap (4, 6, 9, 12 or 16; default 6).
    • "hidden": off the band and out of the details count; listed last in the lane details under Hidden on band. Still filterable and exported.
    • null: derived from position. Every field created before 1.3 is null, and a board whose fields are all null renders as before 1.3: the first two non-empty values on the band. PATCHing band_visibility: null is allowed, including on a board that already has tiers: it means "derive from position", and on such a board the resolver treats a null field as "details" while there is room, else "hidden", never "band". Send an explicit tier to put a field on the band.

    Materialization. The first write that affects tiers (a band_visibility PATCH or create, or a lane_details_cap change on the board) writes an explicit tier to every null field on the board, in one transaction under the board row lock: the first two by position become "band", the next ones up to the cap "details", and the rest "hidden". Each changed field is announced with its own swimlane_custom_field.updated event. After that, reorder/ changes positions only and never moves a field between tiers; deleting a field does not refill its slot. A null field on a board that already has tiers (one created by an older server during an upgrade) is never "band": it counts as "details" while there is room, else "hidden".

    A create that sends no band_visibility stays null on a board without tiers, and gets "details" (or "hidden" when the details are full) on a board with tiers, so an older client never gets a 400 for leaving it out.

    Errors (400, keyed band_visibility): "The band holds 2 fields. Move one to Details first." for a third band field, and "Lane details hold N fields. Move one to Hidden first, or raise the limit." past the cap.

    Stability: band_visibility and lane_details_cap follow the 1.0 API rules: the values are only ever added to, null stays a valid value, and the field is never required on write.

    rows[].children[] id, title, column_id, swimlane_id, position, state (todo, doing, blocked or done), assignee (or null), blocked, blocked_at (the manual block's start, else null). Not-done children, plus done ones with done=true, ordered by column then position.
    child_boards[] id, name, role (your role there: admin, member, collaborator, viewer or site_admin), enforce_wip_limits, enforce_wip_hard, columns[] (id, name, color, wip_limit or null, is_done, card_count).
    next_cursor Opaque: send it back as cursor for the next page; null on the last page. Don't parse it; its format may change.

    • Rows. One per live parent card with at least one live child, 20 per page. Rows with blocked children come first, then the most recent child move; parents with nothing in progress (folded) come last in their lane. Without lane, rows run lane by lane, in lane order.
    • States. The same partition as a card's children_rollup: blocked (a manual block or an open blocking relation, in any column) overrides the column, then done (a done column), to do (the child board's first column), else doing. "In progress" is everything but done. Archived parents and children are not counted.
    • Children you can't open. A parent whose child board you can't open is a locked row: rollup is {"visible": false, "total"}, in_progress and child_board_id are null, and children is empty. Its children count only in the lane's and the board's hidden, never in total, the states or folded, and never change the row order. No title, board, column or state of theirs is sent.
    • Child boards. child_boards describes each board you can open that the page's rows use: your role there and its columns, each card_count counting the whole column. A parent reads only the board of its first live link.
    • Cost. The number of queries does not grow with lanes, parents or children.

    Public share endpoint¶

    GET /api/share/{token}/¶

    Returns a read-only board payload identified by its UUID share token. No authentication is required.

    Authentication: none required (public endpoint).

    Rate limiting: 120 requests/hour per IP, plus a 240 requests/hour per-token limit as defense in depth against CGNAT/proxy-pool abuse of a single link. Exceeding either returns 429 Too Many Requests.

    Caching (1.3+, #1965): the response body is cached for up to 15 seconds (SHARE_BOARD_CACHE_TTL_SECONDS; 0 disables it), so a write that does not broadcast a board event, and time-based fields such as is_stale, can lag by up to that window. Revocation, rotation, expiry and enabler deactivation are checked on every request, before the cache, and are never delayed. Suited to read-heavy boards that are shared widely.

    Errors: - 404 Not Found if the token is invalid, has been revoked, or does not exist. (1.2+, #1865) Also when the admin who enabled the link is no longer active or no longer an admin of the board; the link is cleared on that read and does not come back if the account regains admin. This is checked before the expiry, so such a link answers 404 even after its expiry has passed. (1.2+, #1939) Also when the link has no recorded enabler (enabled before the enabler was recorded (for example under 1.1, or 1.2.0-beta.3 and earlier)), with the same response; the link is cleared on that read. - 410 Gone if the token's TTL has elapsed (an admin set an expiry at enable time and it has passed). The token is not auto-rotated: an admin must disable and re-enable sharing for a fresh link. Body: {"detail": "This share link has expired."}. Added in 1.1 (#804).

    Color values¶

    Changed in 1.3

    color on columns, swimlanes, board labels, and group labels is stored as text of up to 7 characters. Since 1.3 every write checks it:

    • #RRGGBB is accepted as sent. The server does not change its case.
    • #RGB is accepted and stored expanded, digit by digit: #abc is stored as #aabbcc.
    • Anything else (red, #12345, #GGGGGG, an empty string) returns 400 Bad Request with the error under color.
    • A value equal to the one already stored is accepted unchanged. Rows saved before 1.3 can hold a non-hex color, and clients resend the current color when they rename a row; those edits keep working. Changing such a row to a different non-hex value is 400.
    • Responses are unchanged: no pattern is published for color, because existing rows may not match it.
    • JSON board import does not fail on a non-hex color. It stores the default for that field (#6B7280 for a column, #3B82F6 for a swimlane, #EAB308 for a label), expands #RGB, and counts each replacement in import_summary.skipped.colors. A color longer than 7 characters is still 400.
    • Board templates and Trello imports apply the same rule and fall back to the default.
    • The Django admin forms for columns, swimlanes, and labels (superuser-only) apply the same rule: a non-hex color is refused with a field error, and an unchanged legacy value still saves.

    Children setting blockers (since 1.3)¶

    GET /api/v1/boards/{id}/children-setting-blockers/ — what stands in the way of changing cards_can_have_children, for the Board settings Rules page (#2208). Minimum role: board admin (or site admin); a member gets 403, a user who cannot open the board 404.

    {
  "child_cards": 4,
  "parent_cards": 0,
  "default_of": [
    {"hidden": false, "id": 12, "name": "Pipeline", "can_change": true},
    {"hidden": true}
  ]
}
    • child_cards: cards on this board that are children of cards on another board. Turning the setting on is refused while this is above 0.
    • parent_cards: cards on this board that have children (archived children count). Since 1.3 (#2446) turning the setting off is not refused while this is above 0: these cards become leftover parents. Each keeps its children, its children_rollup and the right to get more children (Add child, Link existing), while no other card on the board can get children. A leftover parent stops being one when its last child link is removed. The web app asks first with a confirm that quotes this count. Before #2446 a PATCH turning the setting off answered 400 while this was above 0.
    • default_of: the boards whose default_child_board is this board. Turning the setting on is refused while it is not empty. A board you cannot open is {"hidden": true}, with no id or name; can_change is true when you administer that board.

    Default child board options (since 1.3)¶

    GET /api/v1/boards/{board_id}/swimlanes/{id}/default-team-access/: default team members who can't be assigned on a child board this lane feeds (#2211, since 1.3), for the Edit Swimlane warning. Minimum role: admin (403 below it; 404 without access to the board). Read-only.

    {"members": [{"id": 12, "boards": [{"id": 7, "name": "Delivery"}], "hidden_count": 0}]}

    The child boards are the boards this lane's parent cards already have children on, plus the board's default_child_board. One entry per team member who can't be assigned on at least one of them; members with access everywhere are omitted, as are members no longer listed as non-viewers on this lane's board (they are never pre-assigned). boards names only boards you can open; the others are counted in hidden_count.

    GET /api/v1/boards/{id}/default-child-board-options/ — the boards you may pick as this board's default_child_board, for the Board settings Rules select (#2208). Minimum role: board admin (or site admin); a member gets 403, a user who cannot open the board 404.

    {"boards": [{"id": 7, "name": "Delivery"}], "boards_total": 1}

    Only boards where you are admin, whose cards cannot have children and whose first column allows card creation are listed: the same rule the PATCH applies, so the select never offers a board the write would refuse. At most 100 boards are listed, by name (CHILD_BOARD_OPTIONS_LIMIT, since 1.3, #2449); boards_total counts every qualifying board. This board's current default_child_board, when it qualifies for you, is always listed: past the first 100 it takes the last slot. The read costs the same number of queries however many boards qualify (pinned in boards/tests/test_query_counts.py).

    Delete impact (since 1.3)¶

    GET /api/v1/boards/{id}/delete-impact/ — what deleting this board does to parent/child card links on other boards, for the delete confirm (#2208). Minimum role: the delete's own gate, the board owner or a site admin; anyone else gets 403 (or 404 without access).

    {"child_cards": 14, "parent_boards": [{"id": 3, "name": "Pipeline"}], "hidden_parent_boards": false, "parent_cards": 0}
    • child_cards: this board's cards that are children of cards on other boards. Their parents lose them, and each parent records one children_removed_board_deleted history row whose to_value is how many it lost.
    • parent_boards: the boards those parents are on that you can open, by name. hidden_parent_boards is true when some are on boards you cannot open; those are never named or counted per board.
    • parent_cards: this board's cards that have children on other boards. The children stay as ordinary cards and record parent_removed_board_deleted.

    Deleting a board also clears default_child_board on every board that named it, and each of those boards gets a board.updated event.

    allow_assignee_override (since 1.3, #1923)¶

    Boolean, default false. When true, a card's assignee (role member) may move it past a Block WIP or weight limit with ?force=true and a required override_reason, unless they assigned the card to themselves. Only board admins can change it. Not on the public share payload.

    Every change to allow_assignee_override, enforce_wip_limits, enforce_wip_hard, enforce_weight_limits, and a swimlane's limit_enforcement is recorded in BoardSettingChange (actor, setting, old and new value), which is not pruned with the change feed (#2584).
