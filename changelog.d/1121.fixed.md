Fixed `PATCH /api/v1/boards/{board_pk}/custom-fields/{id}/` silently allowing a board admin to change a custom field's `field_type` (e.g. `text` -> `number`) after cards already hold values in it. Nothing revalidated, migrated, or cast the existing `CustomFieldValue` rows against the new type, so the change corrupted stale data in place — later readers (export, filtering, the upcoming Phase 2 card-face rendering) would trust `field_type` and crash or silently misrender against the old free-text/number/etc. content. `field_type` is now frozen once at least one value exists for the field; attempting to change it returns `400` naming the field instead of succeeding. A field with zero values is unaffected. **Behavior change:** a `PATCH` that previously succeeded (silently corrupting data) now returns `400` in this one case. There is intentionally no `text` -> `dropdown` (or other) conversion path in this release — deleting and recreating the field is the only way to change its type once it has values.
