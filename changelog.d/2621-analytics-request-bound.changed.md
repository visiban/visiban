Analytics requests now have a wall-clock bound, `ANALYTICS_MAX_SECONDS` (default 60, Helm `backend.settings.analyticsMaxSeconds`). Each query an admitted request starts checks the time left and, on PostgreSQL, runs under a `statement_timeout` of that time; a request that runs past it is refused with `503` `analytics_timeout` (a new, additive refusal code, no `Retry-After`) and releases its analytics slot for the next request, so a request that ends early, or whose client went away, no longer holds the slot indefinitely. The time-in-stage heatmap (`GET /api/v1/boards/{id}/analytics/`) with `days` over 90 and no swimlane or label filter now refuses over-cap requests up front: when the movements dated inside the range alone exceed `ANALYTICS_MAX_MOVEMENTS`, it answers `422` `analytics_too_large` before reading the board's history. The MCP flow tools return the same `analytics_timeout` error.
