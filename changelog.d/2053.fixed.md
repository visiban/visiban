Fixed: a change-feed reader (`GET /api/v1/boards/{id}/events/` and the webhook dispatcher) could permanently skip an event. Event ids are assigned when an event is written, not when it commits, so a lower id could commit after a higher one. A reader that polled in between moved its cursor past the lower id and never saw it. The feed now stops each page below any event still committing on that board. During such a write a page can come back empty for a moment, and is filled on the next poll. Writes to a board do not wait for each other because of this change.
A new webhook, or one re-enabled with `resume_from: latest`, now sets its start point once no write on the board is in flight, waiting up to about 0.2 s, so an event that commits after it is never left below it. The dispatcher logs `webhook run held back by an open write` once per run, naming the board ids, so an operator can find a transaction that has been left open; see "Event coverage" in the change feed API docs. Each board a transaction writes events on uses one entry in PostgreSQL's lock table (deleting boards uses none); see "PostgreSQL lock table and the change feed" in the configuration docs.
