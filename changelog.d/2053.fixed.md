Fixed: the board change feed (`GET /api/v1/boards/{id}/events/`) and webhooks could permanently skip an event, because event ids are assigned when an event is written, not when it commits, and a reader polling between two out-of-order commits moved its cursor past the lower id. The feed and the webhook dispatcher now stop below any event still committing on that board (a page can come back empty for a moment and is filled on the next poll), a new webhook or one re-enabled with `resume_from: latest` starts once no write on the board is in flight (waiting up to about 0.2 s), and the dispatcher logs `webhook run held back by an open write` once per run so an operator can find a transaction left open; each board a transaction writes events on uses one entry in PostgreSQL's lock table, see the configuration docs (#2053)
