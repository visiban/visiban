Fixed several unhandled `500`s the `backend-schema-fuzz` CI job's baseline triage (#1120) turned up:

- A non-numeric id in a request (board id, group id, board/group member user id, group invite-link id, group label id, or — defense in depth alongside a related routing-level fix — card/comment/attachment/checklist-item id) crashed instead of returning the documented `404`. `boards/views/_helpers.py` and six other view modules resolved these with `django.shortcuts.get_object_or_404`, which doesn't catch the ORM's `ValueError` on an invalid pk the way `rest_framework.generics`'s version does.
- A malformed nested board-resource id (board/card/column/swimlane/label/custom-field) that no longer matches any URL pattern (a related, independent fix constraining those routes to digits landed on main just ahead of this branch) now gets a plain JSON `404` from a new catch-all route instead of Django's raw, unmatched-URL response — see the `backend-schema-fuzz` job comment in `.gitlab-ci.yml` for the full mechanism.
- `POST /api/v1/boards/{board_pk}/cards/{id}/move/` and `POST /api/v1/groups/{id}/transfer-ownership/` crashed on a JSON request body that isn't an object (a bare number, string, array, `null`, or bool) — every `request.data.get(...)` call raised `AttributeError` on a non-mapping body. Both now return `400`. (Other endpoints follow the same `request.data.get(...)`-without-a-type-check pattern and may still be exposed to the same crash if a future fuzz run's randomness happens to hit one — see the `backend-schema-fuzz` job comment in `.gitlab-ci.yml`.)
- `GET /api/v1/cards/` and `GET /api/v1/boards/{board_pk}/cards/` crashed with an `OverflowError` when a `board`/`column`/`swimlane`/`assignee`/`label` filter value was outside the 64-bit integer range (e.g. `?column=1.03e34`) — `django_filters.NumberFilter`'s default bound (1e50) is far looser than what the database driver can actually bind. A new `BoundedIdFilter` (`boards/views/_helpers.py`) bounds these to the 64-bit range every id-backed model actually uses; out-of-range values now return `400`.
