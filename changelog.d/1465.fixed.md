A Valkey outage no longer takes the whole app offline: the readiness probe (`/api/health/readiness/`) now depends on the database only and returns `200 {"status": "degraded"}` when just Valkey is unreachable, instead of `503`. While Valkey is down, ordinary REST requests keep working: the global `anon`/`user` rate limits fail open (they are not enforced until Valkey returns) and maintenance mode, registration mode and the uploads toggle are read from the database. Endpoints with their own security rate limit (login and the failed-login lockout, registration, password reset, user search, invite and share-link redemption) fail closed with `500` until Valkey returns, and realtime updates pause. Cache calls now give up after 0.5 seconds (new `REDIS_CACHE_SOCKET_CONNECT_TIMEOUT` and `REDIS_CACHE_SOCKET_TIMEOUT`, Helm `backend.settings.cacheTimeouts`), so a Valkey that drops packets instead of refusing connections fails fast instead of hanging requests and the readiness probe. The experimental Git lens board answers `503` (`code: "lens_unavailable"`) during a Valkey outage instead of `500`, and makes no GitHub or GitLab request until Valkey returns.
