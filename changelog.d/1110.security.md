Personal access tokens now carry explicit, non-hierarchical **scopes** (`read`, `write`, `admin`, `mcp:read`, `mcp:write`), so a token issued to a script, a CI pipeline, or an AI agent can be given less authority than the account that created it. Previously every token carried its owner's full read/write authority on every endpoint, including the admin API. No scope implies another — `admin` does not grant `read` or `write`, and nothing grants the `mcp:*` scopes — and requirements compose, so an admin write needs both `admin` and `write`. Scopes only ever narrow a token; board membership and role checks are unchanged.

**Upgrade notes:**

- Tokens that already exist keep working unchanged across the entire REST API — the migration adds a nullable column and backfills nothing.
- Pre-existing tokens are **refused by the MCP server**, which now requires `mcp:read`. Create a new token with that scope to reconnect an MCP client.
- `POST /api/v1/auth/tokens/` accepts an optional `scopes` list and **defaults to `["read", "write"]`** when it is omitted. API callers that relied on a newly created token carrying admin authority must now request `admin` explicitly.
- A scoped token can no longer create or revoke tokens; without this a `read` token could mint itself an `admin` one. Tokens created before this release keep the old behavior.
- `scopes` is exposed on the token list and create responses.
- `POST /api/v1/auth/ws-ticket/` (the WebSocket ticket endpoint added in this release) requires the `write` scope, because minting a ticket is a `POST` and the scope baseline is resolved from the path and method. A `read`-only token cannot currently open a WebSocket.

Also fixes three pre-existing gaps found while auditing the authentication and permission chain as scope-enforcement sites:

- The `/api/v1/admin/*` endpoints omitted the `MustNotHavePendingUsernameChange` gate, so a site administrator with a forced username change pending could still reach them.
- `POST /api/v1/auth/password/change/` (the dj-rest-auth route) did not revoke the user's personal access tokens, unlike `POST /api/v1/auth/change-password/`. "Change your password to cut off a leaked token" therefore worked or not depending on which endpoint the caller used. Both routes now revoke.
- A token revoked concurrently with a request already in flight returned `500` instead of `401`.
- `GET /api/v1/cards/` (the cross-board card query endpoint added alongside this release, #1112) did not declare `TokenHasScope`, so a token's scope was never checked before reaching it. Caught by the same permission-chain conformance test that found the `WSTicketView` gap above.
