## Card density (#961)

Each board has an admin-controlled `card_density` setting that drives how much renders on the card face. Under the redesign (#2272; `docs/development/board-redesign.md` § Cards, screenshot `components.png`) the three tiers are:

| Tier | Default for | Card face shows |
|---|---|---|
| `comfortable` | New boards (1.1+) | Bold title and a subtitle (text after ` -- `), one primary label + `+N`, checklist progress, assignee, then the status line on its own row under the metadata. *Weight, attachments, last-moved, extra labels, priority badge, description indicator move to the hover peek.* |
| `standard` | (admin opt-in) | The title on one line (no subtitle), and the status line inline in the metadata row with the labels (2 + `+N`), pinned fields, due date when not folded into the status, weight pill (`>1`) and attachment count. **Named `standard` not `compact`** to avoid colliding with the per-user *Card layout: Compact / Expanded* toolbar pref. |
| `dense` | Existing boards migrated from 1.0 | One row (`data-testid="card-dense-row"`): the title, a **short status** ("Overdue", "Due soon", "39d"), the first pinned field that has a value, and the assignee avatar. Labels, checklist, attachments, due date, weight, the reference link, the description icon, last-moved text, the recently-moved dot and the priority badge are off the face; § Cards names the surface that carries each. When no pinned field has a value the row shows the first pinned field as a dashed ghost (#2193), so an unset dropdown or checkbox can still be set from the face. A dense card never has a second row. |

- **The status line is the one place a card's status shows (#2272).** `classifyCardUrgency()` (`utils/cardUrgency.ts`, pure, server-anchored staleness) picks it: **overdue > due soon (<=72h) > stale (server `is_stale`, ignored in a done column)**; "just moved" stays a calm badge and an on-track card has no line. Wording lives in `utils/cardStatusLine.ts`: `Overdue Nov 12` (danger text, flag), `Due in 3 days` (`text-fg-secondary`, flag, no color), `Stale 39d` (warning text, clock). Dense uses `Overdue`, `Due soon`, `39d` with a screen-reader-only `Stale ` prefix. Every status is words plus an icon plus a tone, never color alone. Icons are `UrgencyGlyph` kinds `overdue`, `due-soon-flag`, `stale` (inline SVG, `currentColor`, decorative).
- **Planned children (#2371) have their own quiet status lines, never glyphs.** A planned child's due date is inactive: `CardItem` classifies urgency with `activeDue` (null while `card.planned`), so it is never overdue or due soon. Only when no overdue, due-soon or stale line applies, `buildPlannedStatusLine` (`utils/cardStatusLine.ts`) picks: `Dec 4 passed while planned` (warning) > `Needed now: parent is in Proposal` (`needed_now_reason` `parent`, the parent visible) / `Needed now: the parent moved on` (`parent`, a hidden parent: it names no column) / `Needed now` alone for `cancelled` (a column delete or "Needed: Now", including on a link the parent already released) or no reason (warning; Dense shows `Needed now` for all three; the Stale line replaces it once the card is stale) > `Planned for Proposal` / `Planned for a later stage`, plus ` · Dec 4, counts once needed` when a date is stored (`text-fg-tertiary`, the quietest line). Full card-face priority: blocked > overdue > due soon > date passed while planned > needed now > health > stale > planned, with the one exception that Stale replaces Needed now. These lines draw **no glyph**: the clock means Stale or idle only (#2206 rule 4). A `parent` release with a visible parent but no `column_name` also falls back to `the parent moved on`. The parent's column comes from two sources, both closed to a viewer who can't open the parent: the planned line's from `needed_at_column_name` (the server nulls it), the needed-now line's from `parent.column_name`, read only when `parent.hidden` is false. Never name a column from any other field.
- **The Show chips use the same classification** (`utils/showChips.ts` `cardShowChip`), so a chip count equals the number of cards whose status line is that chip. This is scoped to the chips: the swimlane band stats and collapsed squares use `cardBoardStatus` (`constants/laneStatus.ts`), which ranks overdue > stale and ignores due soon, so a stale card that is also due soon is a Due soon chip and status line but counts as stale in the band and squares. Deliberate and owner-approved (the band has no due-soon stat); `showChips.test.ts` pins both precedences. See § Show chips.
- The status text is `text-xs font-semibold`; on an aging-tinted card the status row carries `card-aging-meta` like the metadata row, so its tones stay on-tint (`urgencyBadgeToneClass`, `staleBadgeToneClass`).
- The urgency badge, due pill and border rules of the pre-#2272 face are gone (#2279); the calm face is the only face.
- At Comfortable the standalone due-date pill stays suppressed (the status line is the single visible date signal; a date that is not overdue or due soon is not drawn on the Comfortable face, but is spoken as `sr-only` text and shown in the hover peek's due row, the peek sheet and the card detail, #2399). At Standard the pill is restored for dates outside the status window, as plain `text-fg-tertiary` words: it never carries an urgency glyph or tone (#2393).
- **The badge is only the "Just moved" cue (#2393).** `CardItem` classifies the badge and the status line at one `Date.now()` reading with the same inputs except `last_moved_at`, which decides only the lowest-priority `recent` kind, so an overdue, due-soon or stale badge can never coexist with a missing status line. `cardUrgencyAgreement.test.ts` pins both this and the due-pill property above; if either ever fails, the deleted branches are needed again.
- `density` is a *required* prop on `CardItem`'s public TypeScript shape but defaults to `"comfortable"` so any caller that forgets to pass it (e.g. drag overlay constructed without a board context) degrades gracefully.
- The hover peek (`CardPeekPopover`, suppressed while the card detail sheet is open: see § Card detail sheet placement, #1918) renders the hidden metrics as a single muted line — `Weight 5 · 3 attachments · Moved 2d ago`. **Never stack them into multiple rows** — that recreates the wall-of-icons we just removed from the card face.
- **Non-pinned custom fields get exactly one line of their own in the peek, above the metrics line — never one row per field (#1308).** This is the one deliberate exception to the single-line rule above: a label that scopes custom fields cannot also scope weight/attachments sharing its line. When the board has any `show_on_card` definition, the line opens with `Other fields — ` (`font-medium text-fg-tertiary`) so a peek entry (`AE: Bob`) can never be read as the card-face chip (`SA: Glenda`) disagreeing with itself; with nothing pinned, no label. Key the label off `show_on_card`, never a pin count (#1146 presets). Pinned fields are **not** repeated in the peek. Each entry is its own `<span className="inline-block max-w-full truncate align-bottom" title="{name}: {value} — {help_text}">` (clipped like the card-face chip, so a long unbroken value never overflows the 288px panel) (help text omitted when empty) — there is no separate full-name field, so the field's help text is the only place an abbreviated name can be spelled out, and a per-entry element keeps room for #1122 threshold coloring. Cap at 6 visible slots: 5 entries + `+N more`, whose `title` lists the hidden field names.
- **The peek's due row and labels row are two more bounded exceptions to the single-line rule (#2399, #2391, owner decision).** `card-peek-due` is one `text-xs text-fg-secondary` line of words (`formatDueDate` label) with no urgency tone, because the face's status line owns overdue and due soon. `card-peek-labels` is one wrapping `<ul aria-label="Labels">` of `colorChipStyle` chips with the full label name. Both sit above the checklist, custom-fields and metrics lines and render only when the card has a due date or labels. Never add a further row to the peek without a row in the § Cards calm-face omission table.
- Per-user per-field hide toggles (the prior `hideLabels` / `hideDueDate` / `hideAssignee` / `hidePriority` / `hideLastMoved` checkboxes in Board Settings → Display) are removed in 1.1. Density is the single knob; legacy localStorage values for those keys are silently ignored.
- The Board Settings *Display* tab gives admins a radio group (Comfortable / Standard / Dense) with a one-line description of each tier. Non-admins see a read-only line stating the current density.
- **Per-user density override, layered on the board default (#974).** Every user (admin or not) can additionally set a personal density that overrides the board admin's `card_density` for their own view only, via a "Use my own density" toggle beneath the admin radio in Board Settings → Display. Rules:
  - **Storage is board-scoped, not global**: `useCardDensityOverride` (`frontend/src/hooks/useCardDensityOverride.ts`) persists to `board:{boardId}:card-density-override`, holding one of `comfortable` / `standard` / `dense`. Absence of the key — not a stored `null` — means "follow board default"; toggling the override off calls `localStorage.removeItem`. A global `user:prefs:*` key would be wrong here because "follow board default" only has meaning relative to *this* board's admin setting.
  - **Resolution happens once, in `BoardView`**: `effectiveCardDensity = cardDensityOverride ?? board.card_density` is computed a single time and passed through the *same* `density` prop that already flows `BoardView` → `SwimlaneRow` → `BoardCell` → `CardItem` (and the drag-overlay `CardItem`). Never read `board.card_density` directly at a card-rendering call site again — always the resolved value — or a density change ends up half-applied (e.g. dense card face but a comfortable-computed row height).
  - **The admin's board-level radio and the personal toggle+radio are separate, non-stomping storage locations by construction** — writing one never touches the other. An admin changing the board default does not clear any user's personal override, including the admin's own.
  - **The personal radio group is a distinct `name` (`personal-card-density`) from the admin group's (`card-density`)** so the two native radio sets never collide, and is conditionally rendered (not just visually hidden) when the toggle is off, matching the personal Columns/Swimlanes section's own conditional-render pattern in the same tab.
  - **Gate the personal-override UI on `onSetCardDensityOverride` alone** — never couple it to `isAdmin` or to the `viewPrefs`/hidden-column gate. Density override and column/swimlane visibility are unrelated personal settings that happen to share this tab; admins get both the board radio and their own personal toggle, since an admin may want a personal view that differs from the team default they set.

**Card aging ramp (#1841).** `agingTint()` in `src/utils/agingTint.ts` is the single source for the card's aging stage, idle days, overlay and body-opacity classes. Never recompute the idle ratio in a component. The analytics heatmap's `heatLevel` shares its edges through `agingStage()`.

- **Stages, by uncapped ratio = idle / `staleness_threshold_days`, lower bound inclusive:** none (below the warning point), `warning` (warning point ≤ r < 1), `stale` (1–2), `stale2x` (2–3), `stale3x` (≥ 3). The multiples are fixed, not a setting. The warning point is `stale_warning_pct / 100` (percent of the threshold *used*). `0` turns it off, `100` leaves it empty.
- **No green stage.** Color means "needs attention". A fresh card is never tinted.
- **Cards in a done column (`column.is_done`) never age.** `BoardCell` (and the drag overlay in `BoardView`) passes `inDoneColumn`, and `CardItem` then shows no tint, no aging tooltip and no "Stale" badge, even when the server's `is_stale` is true (it does not look at columns). A finished card is not idle. The stale-card digest (`notify_stale_cards`) currently still includes Done-column cards, tracked in #1845.
- **Age from `agingReference(card)`, never `card.last_moved_at` directly.** It falls back to `created_at` for a never-moved card (Trello/CSV imports), mirroring the server's `is_stale` fallback, so imported boards get the ramp and `Stale Nd` too. Test fixtures with `last_moved_at: null` therefore need a relative-to-now `created_at`, or the card tints.
- **A selected card drops its `bg-primary-emphasis/20` fill while an aging tint is shown** and keeps only `ring-2 ring-primary-soft`. The fill under a 3× tint pulled the badge to 3.71:1 light / 3.95:1 dark.
- **Urgency badges on a tint use an on-tint token that clears 4.5:1 on that stage** (`urgencyBadgeToneClass()`): the badge hue's on-tint token, except that on the red 2×/3× stages a warning-toned badge (due-soon) takes `text-danger-on-tint`, because amber `warning-on-tint` measures 4.38:1 / 3.94:1 in light mode there. `onTintTokens.test.ts` pins these ratios.
- **Overlay + opacity per stage:** `bg-warning-emphasis/10` + `opacity-90` (yellow), `bg-stale-tint/15` + `opacity-85` (orange; `--stale-tint` is pinned to the pre-#2029 orange-600/400 so the light `--warning` retune cannot darken it, #2029), `bg-danger/15` + `opacity-85` (red), `bg-stale-severe/20 ring-2 ring-inset ring-stale-severe` + `opacity-85` (deep red). Do not go below `opacity-85` or above these fills. The old `bg-warning/20` + `opacity-60` stale stage put the card title at 4.15:1 dark / 4.33:1 light and the badge at 1.9 to 2.6:1.
- **The 3× outline is an inset ring on the overlay div, never the card border.** The card's border (neutral, or danger when overdue) must stay visible. In dark mode `--stale-severe` is red-500, not a maroon: a maroon `/20` over slate-800 measures about 1.03:1 and is invisible, so the ring is what separates 3× from 2× there. Never use black or near-black for the last stage, because the dark canvas is near-black.
- **Text carries the age; color and opacity only reinforce it.** The non-color cues are the status line `Stale 41d` (every non-compact density, server `is_stale`; the short `41d` with sr-only `Stale ` at dense), the `AgingCue` stage meter where the status line is not stale (#1843; the warning stage's hollow-bar meter, #1863), the tooltip (`formatAgingTooltip()`) and the 3× ring. The opacity step (100 → 90 → 85) is a weak supplementary cue, not a channel of its own: 1–2× and 2–3× share `opacity-85` and differ by hue plus text. The tooltip claims "Stale" only when the server agrees, and otherwise reads `Idle 15d · stale at 14d`.
- **The aging tooltip opens on hover and on keyboard focus (`:focus-visible`), never on a pointer click's focus.** It wraps at `max-w-[16rem]` (`w-max`, centered) instead of `whitespace-nowrap`, so the longest string (`Stale · 41d · 2.9× the 14d threshold · blocked by 2 cards`) cannot overflow a narrow column.
- **Every tinted card carries a non-color cue at a glance (#1843, #1863):** the `Stale Nd` status line where it is visible, otherwise the `AgingCue` stage meter at the start of the title. The stale status is absent on every compact card (any density) and when an overdue or due-soon status takes the line. The `warning` stage never gets the stale status (it is not stale), so its meter shows on every warning card in every layout and density: the same three bars with no solid bar and the shortest bar drawn hollow (outline only). The meter is hidden whenever the status is stale, so the cue is never doubled.
- **`AgingCue` (`components/Card/AgingCue.tsx`) is the only stage glyph — never re-inline it.** CardItem renders it when `!staleBadgeShown` (`!compact && status?.kind === "stale"`), and it returns null only for `none`. Three ascending bars in a 12×12 viewBox, solid count = stage multiple (1/2/3), the rest `opacity="0.3"`, tone `staleBadgeToneClass()` (no new tokens; the badge's measured on-tint ratios apply). `warning` has 0 solid bars and draws the shortest bar hollow: `fill="none" stroke="currentColor" strokeWidth={1}`, inset by half the stroke (`x 0.5, y 7.5, 2×4`) so the outline's outer edge matches the filled bar's footprint and stays inside the viewBox. Hollow → 1 → 2 → 3 solid reads as a progression by shape, and the outline reads as a hint, not an alarm. The hollow bar's 1px interior was checked in a browser at device pixel ratios 1, 1.25, 1.5 and 2 in both themes and stays open (it does not smear into a solid bar). Any change to the meter's geometry or stroke must repeat that fractional-DPR check, because jsdom renders no pixels. A new `AgingStage` needs a `SOLID_BARS` entry, or the cue silently returns null for it. Gate on the client `aging.stage`, never `is_stale`, so the cue always matches the tint.
  - **Placement: first, inline, inside the title `<p>`** (`inline-block w-3 h-3 mr-1 align-[-0.125em]`). It shares the clamped title line box, so card height cannot change. Never in the metadata row (that adds a row and `mt-1.5` to a title-only compact card), never trailing (the bulk-select checkbox covers the top-right), and never wrapped in `inline-flex` (moves the baseline onto the SVG).
  - **Height guard:** any inline glyph in the card title `<p>` is at most 12px (`h-3`) and sits at `align-[-0.125em]`, not `align-baseline`: on the baseline a 12px glyph leaves under 1px of headroom in a `text-xs leading-snug` line, so a different font stack can grow the line. `card-aging-compact.spec.ts` measures the stale and warning titles' line boxes against the fresh card's and their own `line-height`, compact and non-compact dense, and the warning title at non-compact comfortable and standard.
  - **Contrast model (WCAG 1.4.11):** the solid bars carry the stage and must hold at least 3:1; they inherit the badge's on-tint ratios (at least 4.55:1), so never give the cue its own tone. The warning stage's hollow bar is its only stage-bearing mark and must stay at full opacity: `text-warning-on-tint` in the `opacity-90` body measures 6.25:1 dark / 5.53:1 light on the warning tint (pinned in `onTintTokens.test.ts`). Never render the warning stage as an all-ghost meter: the ghosts are well below 3:1 (not pinned). The `opacity="0.3"` ghost bars are deliberately below 3:1 and redundant, since the solid count (or the hollow bar) alone carries the stage. Do not raise their opacity, or the stages blur together. The cue is a text-free graphic, so the `text-xs` floor does not apply; never add text such as `41d` to it at a smaller size.
  - **Accessibility:** `role="img"` on the `<svg>` with an `aria-label` that states days and multiple (`Idle 41 days, at least 2 times the stale threshold`; warning: `Idle 9 days, approaching the stale threshold`), never "Stale" and never `×`. No `title`: the card's aging tooltip already covers hover and keyboard focus (touch has the accessible name only, as with the tooltip). Because the cue leads the title, the card button's content-derived name starts with `Idle N days, …` before the title. That reading order is accepted, since the leading position is the hard visual constraint. Do not move the cue after the title to fix it.
  - **A compact card's `hasMetadataRow` must not count anything the compact branch does not render.** Only the assignee, blocked glyph, recently-moved dot and dense priority badge render in compact; every other condition sits inside a `!compact &&` group. Counting the rest (urgency badge, labels, checklist, moved-ago text and others) added an empty row and 6px to compact cards.
- **Metadata on a tint is rescoped, not restyled per element (#1844).** Whenever a tint is shown, `CardItem` adds `AGING_STAGE_CLASSES[stage].metaClass` (`card-aging-meta`) to the metadata row, and that class in `index.css` rescopes the row's text tokens for the subtree: `fg-tertiary`, `fg-muted` and `fg-faint` → `muted-on-tint`, `info` → `info-on-tint`, `danger` → `danger-on-tint`, `success` → `success-on-aging-tint`. At rest, every metadata element (blocked glyph, external-ref badge, `+N` labels, custom-field chip names and links, the dense empty-field ghost, multi-select `+N`, checklist, attachments, due date) and every child component in the row picks it up with no per-element class, in both default and compact layouts. Rules: (1) Never put the class on an untinted card, and never on the title or the avatar, which sit outside the row. (2) A new metadata element must use a token in that list, `fg-secondary`, or an explicit `*-on-tint` token, and, because the same element also renders untinted, not `fg-muted` or `fg-faint` (#1862, below). `onTintTokens.test.ts` scans `CardItem` and every component it mounts inside the row (`CustomFieldLink`, `MultiSelectChips`, `ChoiceValue`, `ExternalRefGlyph`; a `./` import that is in neither that list nor the portaled list fails the test) for every `text-<color>` utility and fails on any other (for example plain `text-warning` or `text-primary-soft`, which the class does not rescope) and on any opacity modifier on a text color (`text-fg-muted/60`), because the pinned ratios assume full-opacity text. (3) On a tint, `fg-tertiary`, `fg-muted` and `fg-secondary` all render slate-300 dark / slate-700 light (`fg-secondary` is not rescoped; its value currently equals `muted-on-tint`, which the test asserts). The tertiary/muted gradation is lost there on purpose: slate-400 dark and slate-600 light both measure below 4.5:1 on the 3× stage, so size, weight and position carry the hierarchy. The empty-field ghost takes the same tone; its dashed border and `—` still mark it as unset. (4) Tuning the overlay alpha or body opacity cannot fix this. Plain `fg-muted` was 3.07:1 on an untinted dark card before #2030 retuned it (4.69 now), and it is still below AA on every tint, so only the text tone can clear it. The ramp's fills and opacities are therefore unchanged. (5) `success-on-aging-tint` exists because `success-on-tint` (green-800) is 3.80:1 in light mode on the 3× stage. Light uses green-900 (4.62:1). Dark is green-300, the same as `success-on-tint`.
- **Exceptions, not rescoped:** label pills (user-assigned colors, § Badges and labels), which compensate for the stage opacity instead: `CardItem` passes `aging.stage` to `colorChipStyle`, so a label chip holds 6:1 as rendered on every light stage and 5.91 at worst on a dark one (#2102, pinned in `colorContrast.test.ts`; before it was 4.26-4.34 light on the stale stages); choice badges and multi-select chips, which carry their own background and measure at least 4.66:1 under the stage opacity (asserted in the same test; the AA floor for them, #2102 left their recipe unchanged); and two filled elements whose contrast is a property of their fill, not of the tint, neither fixed by the tint rules (the #1861 audit that tracked them is closed, and no open issue covers them): the dense-only priority badge (white on `PRIORITY_COLORS`: medium 2.80:1 and high 3.76:1 even untinted, 2.43 and 3.18 at worst under the stage opacity; urgent stays at least 5.12) and the assignee avatar initials (`Avatar`, `text-on-primary` on its `PALETTE` fill: teal 3.74 and cyan 3.68 untinted, as low as 3.06 on a tint; `warning-bg` was 3.19 / 2.67 until #2169 made it amber-700, now 5.02 untinted and 3.88 at worst on a tint). The avatar sits outside the metadata row, so `card-aging-meta` does not reach it.
- **Drag preview exception (measured, transient).** The `DragOverlay` copy of a card renders at `opacity-95` (`overlay` in `CardItem`), which lets the board behind it bleed through the tint, so a tinted card's text dips below 4.5:1 only while it is being dragged. Worst measured values, over canvas, sunken, surface and surface-hover backdrops: light 3× `info-on-tint` 4.14, `success-on-aging-tint` 4.18 and `danger-on-tint` 4.21; the #1841 `warning-on-tint` badge on light stale 4.18; dark worst `danger-on-tint` 4.47 on stale over a surface-hover backdrop. The at-rest guarantee above is unaffected. Do not change the drag-preview opacity to fix this, because it would restyle every dragged card, and do not cite the ramp as AA during a drag.
- **Untinted card-face text is `fg-tertiary` at its quietest (#1862).** `text-fg-muted` was 3.07:1 on an untinted dark card (before #2030) and the dense empty-field ghost's `text-fg-faint` was 1.93 dark / 2.56 light, both informative text, so every such element moved to `text-fg-tertiary` (5.71 / 7.58): the external-ref badge without a link, custom-field chip names (card face, and `CustomFieldValueDisplay` `chip`/`row-chip` so the row chip still matches), the multi-select `+N` and the dense empty-field ghost, plus, in the swimlane row-chip cluster, the `+N`/`All fields` trigger and the admin-only padlock (`AdminOnlyFieldGlyph`, every surface). The sibling surfaces that carry the same metadata or field names got the same floor: `CardPeekPopover` (other fields, the metrics line that comfortable density moves off the face, the footer, completed checklist items), `SwimlaneFieldsPopover` (field names and the `Fields`/`On row` headings), `SwimlaneFieldEditRow` (field label and help text) and `ArchivedCardsPanel` (the count, `Loading…`, and the archived-from / archived-at lines on its `bg-sunken` rows, where `fg-muted` was 3.75:1 dark before #2030 and `fg-tertiary` is 6.96 / 7.24). `LensIssueCard` was deferred here because its `hover:bg-surface-hover` put even `fg-tertiary` at 4.04:1 dark; #2238 moved its hover to a border step and its text to `fg-tertiary`, so it is now in the guard (next-but-one bullet). The card-detail panel (`CardDetail`, `CustomFieldEditRow`, the shared `CustomFieldValueInput`) was deferred to #2030, which retuned the token instead: its `fg-muted` text now clears AA on its resting surfaces, both `Select a date` fields on `bg-surface-hover` are `fg-secondary`, and the clear, delete and empty-state text moved off `fg-faint`. **Superseded 2026-11-14 by #2030:** this bullet decided "promote per use, do not retune the tokens" because a retune needed its own measured review. For the card face that still stands (`fg-tertiary` stays the floor), but #2030 retuned `fg-muted` in both themes after measuring the side effects recorded in § Color tokens. `fg-faint` stays the decorative/hover-reveal tone. Retuning it would erase the faint step everywhere, so the ghost is promoted instead. Consequences: (a) on the card face, field name and the other quiet metadata share one tone, as they already did on a tint; the value (`fg-secondary`, 9.85 / 10.35) is still a step above. (b) The ghost now reads as loud as a set chip's name, so the dashed border and `—` are what mark it unset; never rely on tone alone for that. (c) Tinted rendering is unchanged, because `card-aging-meta` maps `fg-tertiary` to `muted-on-tint` just as it mapped the old tones. `onTintTokens.test.ts` scans the card-face files plus `CustomFieldValueDisplay`, `AdminOnlyFieldGlyph` and the sibling surfaces above, each with the backgrounds its text sits on (`ArchivedCardsPanel`: `bg-surface` and `bg-sunken`), fails on any `fg-muted`/`fg-faint` text (the archived panel's 📦 emoji is the one listed non-text `fg-faint`, exempted as that exact element, so any other `fg-faint` in the file still fails), and pins every other text token used at >= 4.5:1 on each background in both themes (worst: `danger` 5.29 dark on surface / 4.62 light on sunken). No contrast exceptions since #2029: the checklist-complete count (`text-success`, now green-700, 5.02:1 on white / 4.79 on sunken) is checked by the floor test like every other token. The due-soon tone uses `text-warning-on-tint` (#871); since #2393 the due pill has no urgency tone. A new card-face element must use `fg-secondary`, `fg-tertiary`, `text-info`, `text-danger` or an explicit `*-on-tint` token. The scan reads class literals in the listed files only, so a tone produced by a util (`urgencyBadgeToneClass`, `staleBadgeToneClass`) must be fed to the test separately, as the untinted urgency tones and the stale badge tone (`text-warning-on-tint`, 8.67 / 7.31 on surface) are. Known trade-off: the unlinked external-ref badge (`fg-tertiary`) and the linked one (`text-info`, no underline at rest) now have nearly equal luminance in dark mode and differ by hue; accepted because the unlinked form only appears for an invalid URL and its `aria-label`/`title` differ.
- **Dim a card with its surface, never with whole-card opacity (#2238).** Opacity on a card root blends every text tone toward the backdrop, so it silently drops text that was AA at rest. The closed Lens card was `opacity-70` over the lane's `bg-canvas`: the `Closed` pill (`bg-surface-hover text-fg-muted`) fell to 2.58:1 light / 1.72 dark and the `#number` to 2.75 / 2.13. It now recedes by surface, not alpha: `bg-sunken` (one step below the open cards' `bg-surface`, on the lane's `bg-canvas`), a `text-fg-secondary` title (12.02 dark / 9.90 light on sunken), the neutral state pill `border border-line text-fg-tertiary` (6.96 / 7.24), and `text-fg-tertiary` for the `#number`, lane count and metadata (5.71 / 7.58 on surface). Its label chips are opaque again, so the #2102 `lens-closed` dim is gone from `DIMMED_CHIP_SURFACES`. The card hovers with `hover:border-line-emphasis` rather than `hover:bg-surface-hover`, because on that fill even `fg-tertiary` is 4.04:1 dark. The `Closed` word carries the state; the surface step only reinforces it. The aging stages keep their `opacity-85`/`opacity-90` body dim only because every tone in that body is measured through it (above); a new dimmed card state needs either that measurement or a surface step like this one. `onTintTokens.test.ts` adds `LensIssueCard` to the #1862 guard on `bg-surface` and `bg-sunken`, rejects any `opacity-<n>` in the file, and pins these ratios and the old ones.
- **Subtree token rescope is a narrow pattern (#1844).** Rebinding semantic tokens for a subtree, as `card-aging-meta` does, is allowed only when all of these hold: (1) the subtree always sits on one known tinted surface; (2) only text-role tokens are rebound (`fg-*`, `info`, `danger`, `success`), never `surface`, `line`, `primary` or focus-ring tokens; (3) each rebound token maps to an existing on-tint token, or to a new one recorded with its ratio; (4) a test parses the CSS block and pins the ratios, and lists any non-text utility (`bg-`, `border-`, `ring-` and so on) on a rebound token with a reason, because those shift too; (5) portaled children (the peek, the quick-edit popover) are outside the subtree and are not covered. A token the scope does not rebind (for example `warning`) uses its explicit `*-on-tint` class, as the urgency badge does. Prefer this pattern for a whole tinted region and per-element `*-on-tint` classes for one-off elements, and never use both for the same token in one component.

**Card-face blocked indicator (#449) — the one card-face signal with no density gate.** When `blocker_count > 0`, `CardItem` renders a danger-toned glyph as the **first** element of the metadata row, outside the `!compact` branch and outside every density conditional.

- **No density gate, and outside `!compact`.** It shows on the one-row Dense face too, and blocked-ness is more actionable than checklist progress. `comfortable` is the default for every board created since 1.1, so gating it out there would remove the whole-board scan signal — the entire point of the feature — from most boards.
- **First in the row.** The metadata row is `overflow-hidden` with no wrap at rest, so it clips right-to-left: anything placed after a variable-width neighbor (a long label pill, an overdue badge with a long date, a `max-w-[10rem]` custom-field chip) can be cut off on a narrow column. Leading position also keeps every blocked card's marker in one x-gutter, which is what makes a top-to-bottom column scan work.
- **Inline SVG with `currentColor`, never an emoji.** `⛔`/`🚫` paint in their own fixed color and would ignore `text-danger`, so the badge would stop tracking the theme. The neutral `📎`/`✓` badges get away with it; a danger signal does not.
- **Urgency glyphs are inline SVG too (#871).** `UrgencyGlyph` (flag = overdue and the due-soon status line; clock = stale; there is no stopwatch: the Standard due pill has no glyph, see § Cards) follows the rule above: `currentColor`, `w-3 h-3`, `aria-hidden`, so the badge's tone token colors it and it never renders as an emoji or a fallback-font character the way `⚑` did. The text-variation-selector allowance (`U+FE0E`, § Threshold and status encoding) is for the analytics heatmap and **does not apply to the card face**: no system-signal glyph on the card face (the urgency/overdue flag, the stale clock, the checklist overdue flag) is a text character. Because the SVG is `aria-hidden`, its meaning must also be in text (visible, or `sr-only`), and the file is in `CARD_FACE_FILES` in `onTintTokens.test.ts` so its color classes are scanned.
- **Icon always, numeral only above 1.** At one blocker the numeral repeats what the icon says. The exact count always appears in `aria-label` and `title`.
- **`role="img"` + `aria-label` are required, not optional.** At a count of 1 the element contains no text node, so without them it has no accessible name at all. `title` is retained for the sighted hover tooltip only — it is not a reliable accessible name.
- **Tone only — no fill, no border.** It is therefore not a pill and creates no third exception to the filled-pill rule in § Badges and labels. The precedent is the urgency badge, not the label or custom-field chip.
- **`blocker_count` must be in `arePropsEqual` and in `hasMetadata`.** Without the first, the memo swallows the WebSocket update and the badge never appears; without the second, a card whose only metadata is "blocked" drops the whole metadata row.
- Never duplicate it into `CardPeekPopover` — the peek carries metrics *hidden* at low density, and nothing is hidden here.

These signals are reserved for the system: **shape and text carry the meaning, hue only reinforces it** (WCAG 1.4.1). Required reading before `ux-design` on #871, #1149, #1150 and #1133.

- **Default priority when several apply on one card face: blocked > overdue > due soon > health > stale.** This orders the signals when more than one applies; it does not redefine the urgency badge, whose own order stays overdue > due soon > stale > recent (§ Cards, `cardUrgency.ts`). Health is a reserved slot in this order, not a promise of a card-face indicator (see the table). Lower-priority signals stay reachable in the card detail and tooltips. Lane over-limit lives on the lane header, so it never competes for the card face.
- **Admin-colored choices render as chips, never as card borders.** Custom-field choice colors (`CHOICE_COLORS`) and label pills (arbitrary user-chosen colors, § Badges and labels) are decoration their owners control: they appear only inside their own chip or pill. The card border and tint belong to the system (overdue border, aging ring, selection). System signals use the fixed tokens and shapes above, so a "Blocked" choice or label painted red stays visibly a chip and cannot be mistaken for the blocked signal.
- **No signal is keyed to a label or choice name.** Never match on the text "Blocked", "Urgent" or similar to trigger a signal; signals derive from system fields (block state, due date, `is_stale`, health).
- **Do not reuse the reserved tokens for unrelated meaning.** `urgent` is the priority color and `stale-severe` is the 3x aging stage (see Color tokens); neither is generic danger.

**Departures from the 1.3 UI spec (decided, do not relitigate per feature):**

1. **`HEALTH_STATUS_STYLES` plus a shared shape component** replace the spec's color-only health dot. Each status has a distinct SVG shape and a word. Neither exists in the tree yet; #1133 adds them, and must not ship a hue-only health indicator.
2. **`text-warning-on-tint` on untinted light surfaces, for the card face (shipped in #871).** Plain `text-warning` was orange-600, 3.56:1 on white, before #2029 (now orange-700, 5.18:1); the due-soon badge and the other warning-toned text this section specifies (due soon, stale below 2x) use the on-tint token even without a tint behind it. #2029 settled the token question by retuning light `--warning` app-wide (§ Color tokens), so other `text-warning` uses on `bg-surface` clear AA without a swap. Verified against `index.css`: dark `--warning-on-tint` `#FDBA74` (253 186 116) is 8.67:1 on `surface` and 10.59:1 on `surface-sunken`; light `#9A3412` (154 52 18) is 7.31:1 on `surface` and 6.98:1 on `surface-sunken`. `--danger-on-tint` (`#FCA5A5` dark, `#991B1B` light) holds 7.71 / 8.31:1 on `surface`. Pinned in `onTintTokens.test.ts` (#2046).
3. **The blocked glyph carries a duration for manual blocks.** The card face shows one blocked indicator for manual and relation blocks, not two badges: the glyph, plus the elapsed time (`⊘ 3d`) when a manual block exists. A relation-only block keeps the icon-only `blocker_count` form with no duration (#1149 architect review). A glyph alone says "blocked" but not "for how long"; the elapsed time is part of the signal, not a tooltip extra.
4. **Escape priority 42** is allocated to the card-detail block/unblock reason form (§ Escape priority inside the card detail panel). Like any nested form there, it registers through `useEscapeStack`, not an input-level `onKeyDown`.
5. **No `X` shortcut.** The #871 spec proposed `X` to toggle selection; it was denied because selection already has a mechanism. Block/unblock is reached from the card detail's header **Block…** and the banner's **Unblock** (#1149), and since #2059 also from the card context menu (**Block card…** / **Unblock card**, § Card context menu) and the ⌘K palette's card commands (§ Command palette ownership). Both open the sheet with the form open and its field focused, through `CardDetail`'s `blockFormRequest`; neither adds a dialog. Still no bare `X`, and none of `⌘⇧B` / `⌘⌥B` / a scoped `⌘Z` (1.3 UI spec Part 9 keyboard budget: recommended by the spec, none added; owner sign-off pending on the #2059 MR).

**Implementing the blocked signal (#1149).** Decide "is this card blocked" with `isCardBlocked()` (`src/utils/blockedState.ts`), never by reading `card.is_blocked` on the client: CardDetail adjusts `blocker_count` optimistically when a relation changes, and the server-derived flag lags until the next copy. `isManuallyBlocked()` alone decides the elapsed time (the card border is not a blocked signal: only an overdue card has a colored border). The indicator's accessible name and `title` come from `blockedIndicatorLabel()`, so the face, the tooltip and a screen reader say the same thing. `blocked_at` / `blocked_reason` change only through `blockCard()` / `unblockCard()` (`src/api/cards.ts`); never send them in a PATCH (the server ignores them). The indicator's name cuts the reason at `BLOCKED_LABEL_REASON_MAX` (120) characters so a column scan does not read paragraphs; the full reason lives in the card detail banner. Durations come from `formatBlockedDuration()` everywhere, Analytics included, so a sub-day block reads in hours and never as `0d`; a duration column pairs with a count column under unambiguous headers (**Time blocked** / **Times blocked**, never "Blocked" / "Blocks").

**When an action's success removes the trigger that opened its form, name the focus target in code.** `useConfirmFocusReturn` covers Cancel and Escape only: it returns focus to the trigger that opened the form. When success unmounts that trigger (Block replaces the header's **Block…** with the banner; Unblock replaces the banner's **Unblock** with **Block…**), focus would fall to `<body>`. Move it explicitly to what replaced the trigger (`CardBlockSection` focuses the banner after a block; `CardDetail` focuses **Block…** after an unblock), and pin it with a test.

**An inline form's reserved helper/error slot is a live region when focus does not move on error** (`role="status" aria-live="polite" aria-atomic="true"` on the always-mounted slot, as `CardBlockSection` does). A server error that lands while focus is already in the field changes the `aria-describedby` target's text, which screen readers do not re-read; the live region announces it.

## Card-face quick-edit chip affordance (custom fields, #371)

Pinned custom-field chips on the card face (`CardItem`, checkbox/dropdown types only) are a deliberate exception to the hover-reveal-by-default convention above and to § Inline description fields' hover-only pencil-icon pattern: the dotted-underline edit affordance (`border-b border-dotted border-fg-tertiary` on the value text) is **always visible at rest**, not gated behind `group-hover:opacity-100`.

**Why:** VoC input flagged that Sam (occasional, non-daily user) gets no opportunity to learn a hover-only affordance exists on a card face he visits only a few times a week — by the time he'd hover to discover it, he's already concluded there's no way to edit the value inline. A persistent, low-contrast dotted underline is discoverable without training and adds no visual weight to the chip beyond the browser's own `<abbr title>` convention for "this text is a control."

This exception is scoped narrowly to the pinned-chip quick-edit affordance itself. It does **not** relax the hover-reveal convention for anything else on the card — the card's other hover-only controls (the selection checkbox, etc.) keep their existing `opacity-0 group-hover:opacity-100 focus:opacity-100` treatment. Do not generalize "always visible" to other inline-edit affordances without a matching VoC finding; hover-reveal stays the default.

**Empty pinned fields keep a ghost chip where the card face can set them (#2193).** An unset pinned field renders the dense-style dashed ghost (`border-dashed border-line`, `text-fg-tertiary` name, `—`) at **every** density when quick edit can set it (checkbox/dropdown with `boardId` + `onCardUpdated`): it is `role="button"`, `tabIndex=0`, labelled `{name}: not set. Press Enter to edit.` (`… to set it to Yes.` for a checkbox), and opens the same popover, or sets the checkbox, as a set chip does. At comfortable and standard, an unset text/number/date/URL/multi-select field, and any unset field on a read-only render (share page, viewer), still renders nothing: an inert ghost there is clutter with no card-face action behind it. Dense keeps a ghost for every type, editable or not; on a read-only render, or for a type quick edit cannot set, the dense ghost is inert (no `role`, `tabIndex` or `aria-label`; the visible text and `title` carry it). A control whose resting state is empty names its outcome, not just its action (`set it to Yes`, not `toggle`). The ghost stays quieter than a set chip (dashed border, tertiary name, no dot, no icon or fill), and it has no hover treatment because the set chip has none; never make it heavier. Accepted trade-off: a newly pinned checkbox or dropdown shows a ghost on every card without a value, up to two per card at comfortable, which costs some at-a-glance scan; that is the owner's call on #2193, not a bug. One predicate (`showsPinnedChip` in `CardItem`) decides both the chip and whether the metadata row renders, so the two can never disagree. The server pin cap (2) bounds the extra chips. *Superseded 2026-11-14 (#2193):* the #371 ux spec §2 rule "comfortable/standard omit an unset pinned field entirely" — it left a cleared dropdown or checkbox with no way back from the card face, while Board Settings still counted it toward the pin cap, which read as "can't re-pin".

## Number custom-field formatting (#1391)

1. **One formatter.** Every read-only rendering of a number value (card-face chip, row chip, card detail, peek, filter chip) goes through `formatCustomFieldValue` → `formatNumberValue` in `utils/customFieldValue.ts`. Never format a number value inline at a call site. With all three options at their defaults it returns the raw string untouched — no grouping is added to an unformatted field. With decimals empty but a prefix or suffix set, a plain decimal keeps its typed digits and gains grouping (`33000` → `$33,000`, #2387); an exponent or `+` form stays as typed. A non-numeric stored value renders raw. The minus sign goes before the prefix (`-$5.00`). **Chips do not character-slice a formatted number:** the card-face (16) and row (20) character caps cut the suffix — the unit — first, so `chipValueText` leaves a number with any format option whole and lets the chip's CSS `truncate` clip it only when it truly does not fit (the `title` carries the full text). Unformatted numbers and every other type keep the character cap. **The card-face chip shows a formatted number compact (#2387):** `formatNumberCompact` (`$33k`, `$1.2M`, at most one decimal, lower-case `k` per the reference; below 1,000 or with no format option it is exactly `formatNumberValue`). The number value span is `truncate shrink-0 max-w-full`: flexbox shrinks every shrinkable item at once (by shrink factor × base size), so a value at the default shrink loses width alongside the name (`$3…`) whatever the name's `shrink-[3]`. Pinned, the name is the only item that shrinks (down to nothing, ellipsizing as it goes), and the value ellipsizes only when it alone is wider than the chip (a long prefix/suffix with many decimals). Every other type's value keeps `truncate min-w-0`. `e2e/card-number-chip-compact.spec.ts` measures this at a 165px card; jsdom cannot. The `title` keeps the full `formatNumberValue` text and an `sr-only` twin speaks it. Only the card face compacts: the peek, the peek sheet, card detail, Key facts and row chips show the full value.
2. **The settings Format block** (`components/Board/NumberFormatFields.tsx`, shared by the Card fields and Swimlane fields tabs) renders **only** while the selected type is `number`: a `Format` section label, then `grid grid-cols-2 sm:grid-cols-3 gap-3` (Decimals wraps to a second row on phones) of three `<label>`-wrapped inputs — Prefix and Suffix (`maxLength={10}`, placeholders `e.g. $` / `e.g. h`, never trimmed), Decimals (`type="number" min=0 max=10`, empty = as typed). Below it, one reserved `text-xs min-h-4` slot holds `Preview: …` (`text-fg-muted`, the formatter applied to `1234.5`; `min-h-4` because a long prefix/suffix can wrap it) or, for invalid decimals, `Enter 0 to 10.` (`text-danger`, `role="alert"` on that error span only — never on the preview or the slot, which would announce every keystroke — with `aria-invalid` + `border-danger focus:ring-danger-emphasis` on the input) — never both. Invalid decimals block Save. A non-number type sends none of the three keys; the server clears them on a retype.
3. **The adorned number input.** In `CustomFieldValueInput`, a prefix and/or suffix wraps the raw `type="number"` input in `inline-flex w-auto min-w-28 max-w-full items-center bg-surface border border-line rounded focus-within:ring-2 focus-within:ring-primary-emphasis focus-within:border-transparent` — never a fixed width, so two 10-character adornments cannot squeeze the number — the input itself is borderless `bg-transparent` and keeps the plain input's width (`w-20` sm / `w-32` md) with a `min-w-[4rem]` floor, and each adornment is a `shrink-0 select-none whitespace-pre text-fg-muted` span with `aria-hidden="true"`. Because the adornments are hidden from assistive tech, the input's `aria-label` carries the unit: `{field name} ({prefix suffix})`, e.g. `Budget ($ USD)`. With neither set, render the original plain input — no wrapper.

## Custom-field choice color picker (#1391)

- **One control per choice row, in both field-editor tabs.** `components/Board/ChoiceColorPicker.tsx` renders in front of each choice input, only while the type is `dropdown` or `multi_select`: a `p-0.5` (24px hit area) button around a `w-5 h-5 rounded-full` swatch: filled with the explicit color's `base` (`border border-line-strong`), or — for *Automatic* — a **hollow `border-dashed border-line-boundary` circle with no fill**. Never fill Automatic with the hash `choiceColor`: a filled circle reads as a picked color, and a multi-select entry with no color shows no dot at all. `aria-label="Color for {choice}: {Name|Automatic}"` (also the `title`), `aria-haspopup="dialog"`, `aria-expanded`; disabled while the choice is blank. The selected swatch shows a check icon **and** `ring-2 ring-fg ring-offset-1 ring-offset-surface` — the `text-on-primary` check alone is under 3:1 on amber, green and teal, so selection never rests on it.
- **Keyboard:** one roving tab stop; arrow keys move focus (Up/Down by a row of 4) without selecting, Space/Enter select and close, focus returns to the swatch button. Escape closes **only** the popover — `useEscapeStack` at 47 (see the modal allocation list; from the custom body it first returns to the grid, #2096); a click outside, or focus leaving the picker (Tab out — a `focusout` whose `relatedTarget` is outside the wrapper), closes it without a change and without pulling focus back. No focus trap.
- **Edge handling inside the scrolling settings panel.** On open, the picker measures the viewport space below its trigger and opens upward (`bottom-full mb-1` instead of `top-full mt-1`) when under 200px is left, and the popover calls `scrollIntoView({ block: "nearest" })` on mount, so one opened on the last choice row is never half out of view.

- **Custom colors (#2096).** Under the radiogroup sit two stacked text buttons in the `Reset to automatic` style, each its own Tab stop: `+ Custom` (aria-label `Custom color`; with a custom value it reads `Custom` after a 12px `w-3 h-3 rounded-full border border-line-strong` dot of the hex, aria-label `Custom color, selected`), then `Reset to automatic`. `+ Custom` swaps the popover body (grid and both buttons) for the shared `CustomColorPanel` inline with `focusSquare`, seeded from the stored hex, else the current key's `base`, else the automatic `choiceColor`. Entering or leaving the custom body re-measures the flip (420px for the custom body, 200px for the grid) and calls `scrollIntoView({ block: "nearest" })`. Escape (the popover's one registration at 47) and Cancel in the custom body return to the grid with focus on `+ Custom`. Escape on the grid closes the popover. Apply writes the upper-case hex to the draft, closes everything and focuses the swatch button. A custom value fills the trigger swatch with the hex (`data-swatch="custom"`), names it `Color for {choice}: Custom color`, checks no radio, and opens the popover focused on `+ Custom`. The popover root carries `data-dismiss-layer` (`utils/dismissLayer.ts`), so a press on the Board Settings backdrop closes only the popover and keeps the edits. The wrapper's `onBlur` ignores a null `relatedTarget`.
- **A hex is stored as applied, even one equal to a preset.** Unlike `ColorSwatchPicker` (where a stored `#3b82f6` is the Blue swatch), choice colors are stored verbatim: a palette key is a key, and an applied hex stays a custom color (`Custom color`, no radio checked) even when it equals a preset's `base`. Keys keep their recorded per-theme pair, so the two are not interchangeable.
- **Coarse-pointer hit areas.** The popover's text buttons (`+ Custom`, `Reset to automatic`) and the shared `CustomColorPanel`'s Cancel and Apply carry `max-sm:min-h-11 [@media(pointer:coarse)]:min-h-11`: the `max-sm:` half is the phone rule above (it holds at 390px without touch emulation), the coarse-pointer half covers tablets. The panel stays `w-[200px]`; its button row is `flex justify-end`, so the taller buttons never widen it.
- **Every reader resolves key-or-hex through one helper.** A stored `choice_colors` value is a palette key or an upper-case `#RRGGBB`. Read it only through `resolveChoiceColor` / `explicitChoiceColor`, then `choiceColorBase` (dot or swatch), `choiceColorLabel` (accessible name) and `choiceBadgeStyle` (badge pair). A hex badge gets its pair from the contrast helper (`colorChipStyle`, #2094); a key keeps its recorded pair. Never index `CHOICE_COLORS` with a stored value, and never drop hex in a payload builder (`choiceColorsPayload`), or a settings save erases custom colors.
- **Renaming resets the color, and the editor says so.** Colors are keyed by the choice text: editing or removing a choice drops its entry from the draft (`withoutChoiceColor`), and `choiceColorsPayload` sends only trimmed, current choices whose color resolves (a known key or a hex). The note `Renaming a choice resets its color.` (`text-xs text-fg-muted`) sits directly under the choice list, shown only while at least one choice in the draft has an explicit color — with nothing to lose it is noise. Choice names are user text used as object keys, so draft and payload maps are built with `Object.fromEntries` / read with `Object.hasOwn` (`withChoiceColor`, `draftChoiceColor`, `choiceColorsPayload`): a plain `obj[choice] = …` silently drops a choice named `__proto__`.

## Card-face external links (#352)

- **A native card may carry one nested link — the MR/PR badge — and it follows the lens nested-link rules with drag-safety added.** The badge in `CardItem` is a real `<a href target="_blank" rel="noopener noreferrer">` inside the clickable, draggable card root. It stops propagation on `onClick`, `onPointerDown` (so dnd-kit never starts a drag from it) and `onKeyDown` (so Enter never reaches the card's key handling), and never calls `preventDefault` (cmd/middle-click must still work). Style: `text-info`, `text-xs`, the shared `ExternalRefGlyph`, `max-w-[10rem]` + `truncate font-mono` ref text, full ref in the accessible name (`"{ref}, {Provider}, opens in new tab"`) and in `title` together with the **real host** (`"{Provider} {ref} — {host} (opens in new tab)"`) — provider and ref are free text an editor chooses, so the tooltip is where a reader verifies where the link actually goes. It is the **first** item inside the `!compact` branch of the metadata row (the row clips right-to-left); at `comfortable` density it renders the glyph only, and the peek popover lists `{Provider} {ref}` as plain text — never a link, the peek is a hover tooltip. A glyph-only badge must never be the sole way to read the reference.
- **Every user-controlled `href` passes `isHttpUrl()` (`utils/externalRef.ts`) at the render site, even when the server already validated it.** When the guard fails, render the same content as a non-interactive `<span>` (`role="img"` + `aria-label` on the card face) — never an anchor with the raw value. An `href` is an XSS sink, and data can arrive from older rows or imports.
- **Icon-only informational glyphs on the card face are at least `w-3.5 h-3.5`.** `w-3 h-3` is for decorative glyphs that sit beside text; when the glyph is the only visible indicator (and the click target), step it up.
- **Immediate destructive text buttons get a real hit area.** A bare-text action that commits with no confirm (e.g. the link section's Remove) carries at least `px-1.5 py-0.5` and sits `gap-3` from adjacent actions, so reaching for its neighbor does not mis-hit it.
- **No brand logos for external providers.** One generic PR glyph for GitHub, GitLab and Other; the provider is named in text (detail panel) and in the accessible name. Logos would not track the theme color and add trademark/asset burden.

## URL custom-field links (#1390)

Established by the `url` custom field type. `components/Card/CustomFieldLink.tsx` is the **one** renderer for a URL value — card detail (`full`), the card-face and swimlane-row chips (`host`), and the editor's `Open link ↗` helper (`action`). Do not hand-roll a second anchor for a custom field value.

1. **A link inside a clickable or draggable surface stops propagation and never calls `preventDefault`.** A link nested in a card (dnd-kit drag + click-to-open) or a swimlane label panel (double-click-to-edit) stops `onClick`, `onDoubleClick`, `onPointerDown`, `onMouseDown`, `onTouchStart` and `onKeyDown` from bubbling, so it neither opens the card, starts a drag, nor edits the row. It must not `preventDefault`: the link has to open, including cmd/middle-click. `CustomFieldLink`'s `stopPropagation` prop does exactly this; the MR/PR badge (§ Card-face external links) is the same rule applied by hand.
2. **External links use `target="_blank" rel="noopener noreferrer"`, an `aria-label="Open {host} in new tab"` (chip), `"Open {url} in new tab"` (full URL) or `"Open link in new tab"` (the `action` helper, whose visible text is "Open link ↗" — the accessible name must contain the visible text, WCAG 2.5.3), and only an `http:`/`https:` `href`.** Anything else — a legacy `javascript:` value, an import, a value from a newer server — renders as plain `text-fg-secondary` text with no `href`, never an anchor holding the raw value. The guard runs at render time (`normalizeUrl` + `isHttpUrl`) even though the server already validated the value. A pinned chip shows the hostname only (leading `www.` stripped) with the full URL in the chip's `title`. The link focus ring is `focus:ring-2`, not `focus-visible:` (§ Focus ring consistency).
3. **URL inputs normalize bare domains to `https://`, validate on blur and Enter only, and keep invalid text in the input without saving it.** `normalizeUrl` (`utils/customFieldValue.ts`) trims, prepends `https://` when there is no scheme (`localhost:8080` is a host and port, not a scheme), and **rejects** — never rewrites — any non-http(s) scheme. An invalid value shows its error in the always-rendered `min-h-4` slot under the input (`aria-invalid`, `aria-describedby`, `border-danger`), `onCommit` is not called, and Escape restores the last saved value. A server `400` is mapped to the same copy (`urlErrorFromServer`) in the same slot. The error is `role="alert"` and is the input's `aria-describedby` only while shown — the `Open link ↗` helper is never the input's description, and it is hidden while the input holds unsaved text (it links the saved value). A legacy value that fails the type check is edited through the same blur/Enter editor, never the per-keystroke fallback. No per-keystroke or debounced commit for this type, whatever `debounceMs` says. **A Save-button surface must listen to `onInvalidChange`**: clicking Save blurs the input first and the invalid text is refused, so a form that does not track it saves without the edit and closes as if it had succeeded. `EditSwimlaneModal` is the reference — invalid text blocks Save, keeps the modal open and refocuses the field; a server `400` naming the field (`'{name}': …`) is routed back into that field's slot.
4. **An invalid input keeps a danger indicator while focused.** The standard input focus classes (`focus:ring-primary-emphasis focus:border-transparent`) erase a `border-danger` exactly while the user is fixing the value. When an input is invalid, swap them for `focus:ring-danger-emphasis` and keep the border — build the class list conditionally, never by string-replacing a token out of a shared class string.

## Threshold and status encoding

- **A color-tinted element with no visible text label of its own must also carry a glyph and text (WCAG 1.4.1).** Status pills and chips that already show a visible label (e.g. `GroupDetail` priority chips, invite status pills) comply as-is. The analytics heatmap (`AnalyticsView`) gives every cell a distinct-shaped `aria-hidden` glyph (`▲` High, `◆` Warning, `●` OK, each followed by the text variation selector `U+FE0E` so it never renders as emoji) plus `sr-only` level text, and renders a `Heatmap legend` list (`text-xs text-fg-muted`, outside the scroll wrapper, above the footnote). Do not rely on hue or alpha alone for a threshold, health, or status display that has no visible label. The heatmap glyphs are `text-[10px]` on purpose (verified #1892). The glyph is the sighted user's non-color cue for the level, so it is informative, not decorative; it is exempt from the `text-xs` floor only because it is a single `aria-hidden` shape (not text), sits on a `w-5 h-5` chip in the legend beside the visible level label that defines it, and is backed in each cell by the `sr-only` level text and the `title`. The exemption covers exactly that: one `aria-hidden` shape glyph with a visible legend. Any glyph that is letters or digits, or that has no legend, keeps the `text-xs` floor.
- **Health status uses inline SVG shapes, not glyphs (#1133).** The glyph allowance above (`▲` / `◆` / `●` with `U+FE0E`) is for the analytics heatmap's cells. Board and group health supersedes it for its own display: the shape comes only from `HealthStatusShape` (`components/Common/HealthStatusShape.tsx`, `viewBox="0 0 12 12"`, `w-3 h-3`, `aria-hidden`, `focusable="false"`, on `currentColor`): filled circle On track, triangle At risk, diamond Off track, hollow circle No status. A font glyph's advance width and baseline shift with the font and can render as emoji; the SVG keeps one box in every pill and radio card. Do not re-inline the paths.
- **Reconciling with #969 ("none of them a font glyph").** That rule governs magnitude ramps, where glyph advance width and baseline would distort step size. This is a threshold/health display, not a magnitude ramp, so text-variation-selector glyphs paired with text are acceptable here.

## Threshold marks on custom fields (#1122)

- **Shape and weight, never hue, on the card face.** A number or date card-field value at or beyond its threshold gets `ThresholdMark` (`components/Card/ThresholdMark.tsx`): a 12px inline SVG on `currentColor`, `aria-hidden`, `focusable="false"`, one chevron at warning and two at alert, mirrored for a "below" threshold. The value turns `font-semibold text-fg`. No `text-danger`/`text-warning`, no tint, no border change: § System signals reserves red and amber for urgency and priority. A font glyph (`›`/`»`) is not used, for the same baseline reason as `HealthStatusShape`.
- **Words always travel with the chevron.** The chip's `title` reads `{name}: {value} ({phrase})` and an `sr-only` suffix carries `, {phrase}`. The hover peek shows the phrase visibly (pinned fields on their own `card-peek-thresholds` line; non-pinned ones in parentheses on the existing fields line), and `CustomFieldEditRow` shows it under both the input and the read-only display. Phrases come only from `thresholdPhrase()` (`Alert: at or above $6,000`, `Warning: 3 days from today or earlier`): inclusive boundaries are worded "at or above/below", never "over".
- **The peek's `card-peek-thresholds` line is a deliberate, bounded second line.** It is an exception to the peek single-line rule (§ Card density, the hover peek paragraph, and #1308's one-line fields exception): the words are the accessible-to-sighted half of the chevron, so it wraps rather than truncates, and it is capped to the pinned marked fields only.
- **The card detail Key facts strip marks a pinned field the same way.** `buildKeyFacts` (`utils/cardKeyFacts.ts`) computes the level with `thresholdLevel()` and puts the phrase in the fact's accessible name (`{name} {value}, {phrase}. Go to {name}`), its static label and its `title` (`{name}: {value} ({phrase})`, as on the chip); `CardKeyFacts` draws the same `ThresholdMark` and weight. A new surface that shows a pinned number or date value takes the mark and the words together, or neither.
- **A quick-edit `aria-label` must carry the phrase.** An `aria-label` replaces the chip's text, sr-only suffix included, so an editable chip spells `{name}: {value}, {phrase}. Press Enter to …`. Number and date are not quick-edit types today, so this guards a future change.
- **A marked chip gains no `cursor-pointer` or other affordance.** The chevron is not navigation; only the existing quick-edit types are clickable.
- **One evaluation rule.** `thresholdLevel(def, raw, now, timeZone)` in `utils/customFieldValue.ts` is the only place that decides the level: inclusive, alert beats warning, numbers by the server's finite rule, dates by day offset from today in the viewer's timezone (blank = UTC, the same `todayInTimezone` fallback as due dates), a non-canonical server date (written by an old pod during a rolling deploy) gets no threshold mark until its next edit, as the upgrade notes say, anything unparseable unmarked. Never re-implement it in a component.
- **Card fields only (1.3).** Swimlane row chips, filter chips and the Summary view show no marks in this release; swimlane-field thresholds need their own decision on admin-only disclosure (#2217), and filter chips and Summary tables are tracked on #2221.
- **The settings block shows the legend** (`› warning, » alert, shown in bold on cards`) in its reserved help slot, replaced by the error when the draft is invalid; an invalid draft blocks Save.

## Bulk operations (#1733)

1. **A bulk operation reports partial failure and keeps the selection.** Every handler in `BulkActionToolbar` (Move, Assign, Priority, Archive, Delete) applies the fulfilled results to state, and when any card failed it shows `{failed} of {total} cards could not be {verb} — {reason}.` and leaves the selection intact so the user can retry (cards that succeeded stay selected too). It calls `onClearSelection()` only when every card succeeded. Never `Promise.allSettled` and then clear the selection unconditionally. (Staged lists such as the Board Settings "To be added" list follow the opposite, per-item pattern; see #1299 in § Inline error messages.)
2. **Name the real cause, in plain and number-neutral words.** Derive the reason from the response with `failureReason` and blame a limit only for the codes in `LIMIT_CODES`: "a swimlane limit was reached" for the `swimlane_*` codes in `SWIMLANE_LIMIT_CODES` (#1150), "a column limit was reached" for the column codes; otherwise it says permission, network, not found, changed by someone else or "something went wrong". A reason follows both "1 of 1 card" and "2 of 5 cards", so it uses no plural pronouns. Archive and Delete pass a 403-specific override ("you can only archive cards you created"); no handler hardcodes a cause. Mixed causes read "for more than one reason".
3. **The toolbar's message slot is a polite live region and the one place bulk results are reported.** It is a persistent `role="status" aria-live="polite" aria-atomic="true"` wrapper, always mounted, with the message swapped inside (conditionally mounting the region is unreliable for announcements). The message wraps to two lines (`line-clamp-2`) with the full text in `title`; "Working..." stays outside the region and is `aria-hidden`.
4. **Every bottom-centered `fixed` or `absolute` box sets an explicit width (#2071, #1439, #119).** A box centered with `left-1/2 -translate-x-1/2` has only half its containing block to shrink-fit into, so without a width it collapses (a toast into a narrow tall column) or overflows (a row of controls). Toasts use `w-max max-w-[min(24rem,calc(100%-2rem))]` (`ToastRegion.tsx`), never `max-w-sm` alone. `BulkActionToolbar` is a row of controls, so it uses `w-max max-w-[calc(100%-2rem)] flex-wrap justify-center`: natural width on a wide screen, a second row at phone width. Measured at 320px before the fix: 495px wide at x=-88, off both edges (right edge 407.6) with Move to... unreachable; after: 288px at x=16 (16px gutters), 86px tall. Never make it `overflow-x-auto`: the Move, Assign and Priority menus are absolutely positioned children and would be clipped. The menu anchoring switches at 540px, independent of wrapping (the bar still wraps up to about 563px, and wraps at any width while a partial-failure message is showing): at 540px and below the trigger wrappers are `static` and each menu is `inset-x-0`, so it anchors to the bar and spans its width inside the gutters; a `left-0` menu anchored to a mid-row trigger ran 39px off-screen at 320 (`max-w` caps width, not position). From 541px up the menus are anchored to their triggers and were measured inside the viewport. Group separators are `hidden sm:block`, so below 640px a wrapped row never starts or ends on a stray tick; from 640px up they show and the bar is one row unless a message wraps it. The wrapped height is what `--bulk-toolbar-h` publishes, so the toast region clears both rows. Pinned in `bulk-toolbar-viewport.spec.ts` (320, 375 and 1024: bar width at least the viewport minus the gutters on phones, one row at 1024, button containment, and each menu's box inside the viewport gutters) and `bulkActionToolbar.test.tsx`. Design debt, not fixed here: the close button's position when the bar wraps and 44px coarse-pointer targets (#2134).

5. **The toolbar gates on the client with the context menu's rules and names the cause (#2173).** `BulkActionToolbar` takes `cardActionCtx` from BoardView (one `CardActionContext`, never derived again in the toolbar) and reads availability from `cardActionEntries()`, so Move, Assign, Priority, Archive and Delete are disabled for exactly the selections the context menu disables them for. **Refused for every selected card:** the button is `aria-disabled` (never native `disabled`, which is for `busy`), stays focusable, carries the reason in `title` and an `sr-only` `aria-describedby` span, and its handler guard makes activation do nothing but write the reason into the status slot (an ownership refusal in the rule-2 wording: `2 of 2 cards could not be assigned — you can only assign cards you created.`; a role, maintenance or demo gate as its own sentence). The reason is not visible on keyboard focus by design (a native `title` shows on hover only; the `sr-only` description serves screen readers and activation shows it to everyone). Activation clears the slot and sets it on the next tick so a repeat is announced again, and when a role or maintenance gate and ownership both apply the slot names the gate the button's `title` names (the first one `cardActionEntries` reports). **Delete is gated the same way** (and keeps its demo-mode behavior, which wins): `CardDeleteConfirm` takes the `CardActionContext` as `actionContext` and, for a mixed set, does not send the cards `cardRefusal(card, 'delete', ctx)` refuses, counting them failed with `REFUSAL_CLAUSE.delete`. Without a context it sends every card and the server's 403 decides (it never skips on its own). There is no visible per-button reason line: that is the menu-item pattern, and a wrapping toolbar row has no room for it. **Refused for some:** the executors skip the cards `cardRefusal()` says the server refuses, count them failed, and add the ownership reason (`for more than one reason` when a server failure adds another); the client check only spares requests known to fail, and the server stays the enforcement point. **Lenient:** an unknown creator, assignee or current user is left to the server. The reasons are one number-neutral table, `REFUSAL_CLAUSE` in `utils/cardActions.ts`, shared by the toolbar and the context-menu and palette executors (`moveCardsToColumn`, `assignCards`, `setCardsPriority`, `archiveCards` take the context); never re-word a refusal per surface, and never copy an executor loop into a surface. Assign's clause says "you can only assign cards you created": the server lets a card's creator assign their own card, so "needs a moderator or admin" is wrong.

   | Action | Refused when (per card) | Reason clause |
   |---|---|---|
   | Move | assigned to someone else, not created by or assigned to the user | a card assigned to someone else can only be moved by its creator, its assignee or a board admin |
   | Assign | created by someone else | you can only assign cards you created |
   | Priority | created by someone else | you can only edit cards you created |
   | Archive | created by someone else | you can only archive cards you created |
   | Delete | created by someone else (the confirm skips them: `CardDeleteConfirm` takes the same context and does not send them) | you can only delete cards you created |

   Moderators and admins are never refused; the hosted demo visitor is widened for everything but Delete.
6. **The status slot's text is controlled by BoardView.** The toolbar takes `message` / `onMessageChange`; BoardView clears it when the selection gains a card it was not written for, or empties, and keeps it when the selection only shrinks (a refusal describes the selection it was written for, but after a partial archive or delete the succeeded cards leave the board and are pruned from the selection, and clearing then would wipe the failure the user needs to read) and routes a context-menu or palette failure into it when the action's target set is the whole selection and the toolbar is up (`reportCardAction(…, selectionResult)`). No new context or store.

## Card context menu (#2059)

The 1.3 UI spec Part 9 § 2 menu for acting on a card without opening it. `CardContextMenu` renders it; `BoardView` owns the state, the target set and the executor, which it shares with the ⌘K palette's card commands (§ Command palette ownership). Availability comes from `cardActionEntries()` in `src/utils/cardActions.ts`, which mirrors the role gating of `BulkActionToolbar` and `CardDetail`; never re-derive it per surface.

- **A control that exists only at `pointer: coarse` must not depend on a state a tap cannot reach.** The `⋯` button shows on the selected or focused card; a tap on a card opens the sheet, so the touch route is selection (where a checkbox is reachable) or the card focus returns to when the sheet closes. That is documented in `docs/features/board.md`; a device pass (spec open conflict 4, tracked in #2104) decides whether `⋯` must show on every card at coarse pointer. The title takes `[@media(pointer:coarse)]:pr-14` exactly while the button can show, so it never runs under it. The context-target outline drops its `bg-info/10` fill under an aging tint, as the selection does (#1841).
- **Opening paths.** Right-click a card; `Menu` or `Shift+F10` on a focused card (anchored to the card's bottom-left); at `pointer: coarse` only, a 44px `⋯ More actions` button on the selected or focused card (never a hover reveal). **No long-press path**: a touch long-press is the drag start (#1287) and release-without-movement is unverified on device (device pass tracked in #2104), so `CardItem` ignores a `contextmenu` whose pointer type is touch. A keyboard-generated `contextmenu` (no pointer position) anchors to the card, and the one the `Menu` key fires right after its keydown does not open the menu twice.
- **The card owns right-click.** `CardItem` stops the event, and `BoardCell`'s `onContextMenu` also ignores any `contextmenu` from inside a card face, so the add-card shortcut fires only from empty cell space, in a populated cell too.
- **Target set.** A card inside the selection acts on the whole selection; a card outside it acts on that one card and leaves the selection unchanged, with a transient `ring-1 ring-info bg-info/10` outline while the menu is open (transient-open is info; persistent selection stays `primary-emphasis`).
- **Not over an open sheet.** No menu while the card detail sheet is open (`onOpenCardMenu` is withheld, so a right-click there gets the native menu): the portaled menu would take focus out of the `aria-modal` sheet, the same reason the selection checkbox is withheld (#1914). The palette acts on the open card instead.
- **Items and groups**, one engraved separator between groups: Open card (`Enter` hint) / Copy link to card · Move to… ▸ / Assign to… ▸ / Set priority ▸ · Block card… or Unblock card (state-aware) · Archive card / Delete card… (`text-danger`, `MENU_ITEM_FOCUS_RING_DANGER`, last). Several cards: a `text-xs` header ("3 cards") and Open, Copy link and Block are disabled with "Select one card". The submenus list the same choices as the bulk toolbar's menus (columns; Unassign plus every non-viewer member; the four priorities), from one source: `moveChoices` / `assignChoices` / `priorityChoices` in `utils/cardActions.ts`, used by the context menu, the palette and `BulkActionToolbar`; the toolbar's delete confirm is the same `CardDeleteConfirm` (#2103). Do not re-derive these lists in a surface. **Pointer grace (#2106):** moving the pointer from an open submenu's trigger row onto another row closes the submenu only after `SUBMENU_CLOSE_GRACE_MS` (200 ms); entering the submenu or the trigger again cancels the close, opening a submenu or closing the menu clears it. An open trigger carries `aria-controls` naming the submenu (a `useId()` id; omitted while closed, as it would point at nothing). Tests drive this with fake timers restored in `afterEach`.
- **Disabled with a reason, never hidden.** A disabled item is `aria-disabled`, stays in the roving order, and shows its reason on a visible second line (`text-xs text-fg-tertiary`, also its `aria-describedby`): "Viewers can't block cards", "Select one card", "Only the card's creator or a board admin" (for Assign, Set priority, Archive and Delete only when every creator is known and none is the user, otherwise it stays enabled and a refusal reports through the bulk failure wording; for Block / Unblock whenever the user is not known to be the creator and is not a moderator or admin, because those open the sheet's form and must match `CardDetail`'s `canBlock` exactly, or the sheet would open with no form), "Assigned to someone else: only its creator, its assignee or a board admin" for Move (only when every target card is known to be assigned to someone else and created by someone else, the server's `move_card` rule). Every PATCH takes the server's own-content gate, which is why Set priority is ownership-gated like Assign; no write the menu or palette offers as enabled is one the server is known to refuse, the maintenance line, or the demo copy (`DEMO_BLOCK_REASON`; Archive and Delete take `DEMO_CARD_FOOTER_NOTE`, following the demo card sheet, which withholds them; the bulk toolbar agrees since #2105: Archive and Delete stay visible but `aria-disabled` with the same note in `title` and `aria-label`, and the handlers no-op). Activating one does nothing and re-announces the reason through the menu's always-mounted `sr-only` status region. **The visible reason line is `aria-hidden`**, so it is read once, as the description, and not also inside the item's name; the palette's disabled rows do the same.
- **Keyboard.** `role="menu"` / `role="menuitem"` buttons with `tabIndex={-1}` and roving focus: Up/Down wrap, Home/End, a letter jumps to the next item starting with it (only while the menu has focus). `ArrowRight` opens a submenu and focuses its first item; `ArrowLeft` closes only the submenu. Tab closes the menu (focus to the card, then the browser moves on). An outside press, focus moving outside, a window resize or an outside scroll closes it, except a scroll of a card face, which is ignored (the trigger may be a few px stale) through `ignoreScrollFrom` (#2397; § Modals and dialogs, anchored `fixed` popovers: `useAnchoredPlacement`, hidden until placed, focus after placement).
- **Layers.** Menu `z-[45]`, submenu `z-[46]`: above the bulk toolbar (40) and every board dropdown, below `ModalWrapper` and the palette (`z-50`). **Escape 59** (one entry: submenu first, then the menu), recorded in the modal list; it outranks the delete confirm's 40 only because the menu always closes before the confirm opens. Escape, Tab and choosing an item return focus to the target card, so a surface the item opens (the sheet, the delete confirm) captures the card as its opener (#1775).
- **Block / Unblock** closes the menu, opens the card sheet and sets `blockFormRequest`, so `CardBlockSection` focuses Reason (or Resolution). Cancel lands on the header's **Block…** inside the sheet, not on the board card the spec named: the sheet is `aria-modal`, and the board card is outside its trap. Closing the sheet returns focus to the card.
- **Delete card…** opens `CardDeleteConfirm` (same copy and ownership note as the bulk toolbar's confirm, `aria-disabled` "Deleting…" in flight, Escape swallowed); it never runs from one click.
- **Results.** Partial failure uses the § Bulk operations wording and keeps the selection; a full success on the whole selection clears it. Single-card results go through the shared toast region (§ Toasts, key `card-action`, #2107). **Every action leaves a result both a sighted and a screen-reader user can perceive:** an action whose effect is not visible on the board (Copy link, a delete that removes the card, "Deleted “title”.") is a `success` toast (4 s); announce-only success is allowed only when the board itself changes in view (Move, Assign, Priority, Archive). **A failure persists until dismissed or replaced** (a `danger` toast, #1772); only successes auto-clear. A blocked clipboard is a failure. BoardView keeps an `sr-only` status (`card-action-status`) for the announce-only case. A failure or partial result over the whole selection goes to the toolbar's status slot while the toolbar is up, not the toast (§ Bulk operations rule 5); a full success clears the selection, which unmounts the toolbar, so it keeps the announcer or toast, and a card outside the selection keeps the toast.
