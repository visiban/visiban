## Column kebab menu (#965)

Each column header carries a `⋮` overflow kebab as the discoverable surface for column-scoped actions. The kebab is the only keyboard-reachable path to column settings and delete — no separate `✎` icon button. Inline rename is additionally reachable by Tab + Enter/Space on the column name itself, which is a real `<button>` for admins (#1376).

- **Trigger:** `OverflowMenu` instance with `ariaLabel={\`Actions for column "${column.name}"\`}` so screen readers announce *which* column is being acted on. The trigger uses the standard kebab styling and is wrapped in `opacity-0 group-hover/col:opacity-100 focus-within:opacity-100 transition` so it is hidden at rest, revealed on column hover, and stays visible when keyboard focus enters the menu (per the hover-reveal-controls rule).
- **Items, in order:**
  1. `Rename` — sets the column name into the inline editor (the same editor the admin column-name button opens on click, Enter, or Space)
  2. `Edit settings…` — opens `EditColumnModal` (color, WIP/weight limits, allow card creation, is_done)
  3. `Add policy…` — only on a column **without** a policy (#1101); opens `EditColumnModal` on its Policy tab. A column with a policy reaches the editor through the header's Policy button instead (its popover's **Edit policy**), so the kebab never offers two paths to the same editor.
  4. `Delete column` — danger-styled (`OverflowItem.danger: true`), preceded by an engraved separator. Routes to the confirmation dialog.
- **Non-admins see no kebab affordance** — the control is hidden entirely from the DOM, per the *Conditional admin-only elements* rule. Do not render a greyed-out `⋮` glyph, a disabled trigger, or a tooltip explaining missing permission; affordances Sam (occasional, non-admin) cannot use should not look like affordances at all.
- **Double-click on the column header** continues to open `EditColumnModal` as a power-user shortcut (the name button itself does inline rename on a single click / Enter / Space); the kebab is the discoverable path.

## Column delete confirmation (#965)

Deleting a column is permanent and removes every card in it (active and archived). The confirmation dialog applies a tiered safety pattern:

- **Empty column** — a plain `Cancel` / `Delete` modal is sufficient. There is nothing destructive to mistype against; adding name-typed friction here is noise.
- **Column with cards** — the dialog renders the same name-typed danger-zone pattern used for board deletion in `BoardSettingsModal`: an input with the column name in `font-mono`, a `text-xs text-fg-muted` instruction line above it, and a `Delete` button that stays disabled until the typed value matches the column name exactly. Pressing Enter inside the input commits when the value matches. Closing the dialog (Cancel, Esc, or backdrop click) resets the input.
- The confirmation copy explicitly says how many active cards and that archived cards in the column will also be deleted. *This cannot be undone.* is the closing line.

The swimlane delete confirmation (`EditSwimlaneModal.tsx`) reuses the same copy pattern for the deletable (empty) case: a declarative `{name} will be permanently deleted.` line, a `text-danger` line warning that any archived cards in the swimlane will also be permanently deleted, and the `text-fg-muted` *This cannot be undone.* closer. It does not reuse the tiered pattern above — a swimlane that still has cards blocks deletion outright (a single `OK` acknowledgment, no typed-confirmation tier) rather than offering the column's name-typed override; that `OK` button has no column counterpart, but still takes the standard `px-3 py-1.5` sizing rather than a one-off size. Keep the two dialogs' shared copy and button sizing (`px-3 py-1.5`) in sync; a wording or sizing change to one without the other is a drift, not a deliberate divergence.

## Column drag-to-trash gating (#965)

The destructive column trash drop zone is **opt-in via ⌥ (Alt)**, never visible by default during a column drag. Reorder is the common case; deletion is a deliberate, modifier-gated gesture.

- The trash zone renders only when `activeColumn !== null && altHeldDuringColumnDrag === true`. The Alt-tracking `keydown` / `keyup` / `blur` listeners register only while a column drag is active so the global-keyboard footprint is empty at rest.
- The drag overlay shows a small hint below the dragged column name: `Hold ⌥ to delete` (`text-xs text-fg-muted`) flips to `Drop on trash to delete` (`text-xs text-danger`, `aria-live="polite"`) the moment Alt is held. The hint is the discoverability cue for the gated gesture.
- Dropping on the trash zone routes to the same name-typed confirmation dialog as the kebab `Delete column` path — there is one canonical column-delete dialog, never two.

## Column headers

Reference: `docs/development/board-redesign.md` § Column headers and `board-redesign/components.png`. Rewritten for #2270; it replaces the pre-redesign stat-row, accent-strip and truncated-name rules.

- **A panel tinted with the column color.** `rounded-lg border` at 10% of the column color as the fill and 30% as the border, over the page background (`bg-sunken`), through `columnTintStyle(color)` in `utils/colorContrast.ts` (it resolves `color-mix` against the live `--surface-sunken` token, so both themes follow `index.css`). The tint is opaque because the header row is sticky. A non-hex color falls back to `bg-surface border-line`. **Text on the tint is `text-fg` and `text-fg-secondary` only** (never `fg-tertiary` or `fg-muted`); `colorContrast.test.ts` pins both at 4.5:1 over a sample of the RGB cube in both themes. A new tinted surface uses the same helper rather than its own `/10` literal.
- **Content, top to bottom:** collapse chevron, color dot (the drag handle), name, policy button (when set), add-card button, kebab (admins, hover/focus-revealed); then the meter; then the count line. Column name: `text-[13px] font-semibold text-fg`, **one line, truncated with an ellipsis** (`truncate`, #2389; reverses the earlier wrap rule because a 165px header broke names mid-word, "Prosp/ect"), never wrapping or breaking mid-word. The full name stays the accessible name (truncation is visual only) and is also the `title` (the admin rename button's title reads `{name} (click to rename)`). **The collapse chevron is hidden at rest** (#2389, the reference draws only `+` until hover): `opacity-0 group-hover/col:opacity-100 group-focus-within/col:opacity-100 focus:opacity-100 [@media(hover:none)]:opacity-100`, never `display:none` or `hidden`, so Tab reaches it, it stays in the a11y tree, and a touch device (no hover) shows it at rest. At rest the header holds only the dot, the name and `+` (#2450): the chevron is `absolute` in the header's left padding and the admin kebab's wrapper is `absolute right-[38px] w-7` (just left of `+`, overlaying the end of the name area, `bg-surface` masking the ellipsis), revealed by opacity only: hover, focus-within, an open menu (`has-[[aria-expanded=true]]`) and no-hover. Width is never animated (`transition` does not animate it), so a reveal reflows nothing, and the count line and rename error share the name's x (`pl-[18px]`). The kebab's menu escapes because it renders in a portal, not because of any overflow setting. Known limitations (ux-review, #2450): the full name reaches keyboard and touch users only through the accessible name and the rename input (a `title` shows on pointer hover only), and the chevron is a bare 7x8px icon button (no 44px target) with a bare "Collapse column" name on every column; these and the kebab fade-out are tracked as follow-ups in #2646. Export board and Board settings in the board `⋯` menu deliberately repeat the toolbar buttons (the reference lists them); do not dedupe. Pinned in `columnHeaderKeyboard.test.tsx`.
- **States (count line / meter):**

  | State | Count line | Meter |
  |---|---|---|
  | No limit (or limit 0) | `2 cards` (`1 card`, `0 cards`) | none |
  | Under limit | `2 / 4` | column color, proportional |
  | At limit | `4 / 4` (neutral; title "Column is at its WIP limit (4/4)") | column color, full |
  | Over limit | `8 / 6 over`, `text-warning-on-tint font-semibold`, title "Over WIP limit" (hard limit: `⛔` prefix and title "WIP hard limit — no override possible") | `bg-warning`, full |

  The meter is 3px (`h-[3px] rounded-full bg-surface-active` track), `role="meter"` with `aria-label="WIP in {name}"`, `aria-valuenow` capped at the limit and `aria-valuetext="{n} of {limit}"`. Over-limit is **warning, not danger**: the count and meter use warning tokens, and the word "over" keeps it from being color-only. `Board.show_wip_at_limit` no longer changes the header (the count line always shows `n / limit` when there is a limit); the expanded header ignores the prop. The **collapsed** 40px strip still honors it (#972): exactly at the limit with the setting on, the count badge turns `text-fg font-semibold`, an `aria-hidden` `=` in `text-fg-secondary` follows it, and the title reads `Expand "{name}" · At WIP limit (n/n)`. Never the warning color or `⚠`, which stay over-limit only; over WIP or weight keeps its own treatment. **The collapsed button's accessible name carries the limit state** (`Expand {name}, at WIP limit (n/n)`, `, over WIP limit (n/limit)`, `, over weight limit (n/limit)`): its `aria-label` replaces its content and `title` is not reliably announced, so the aria-hidden glyphs never carry state alone.
- **Weight budget** is secondary: when over, `Weight {n}/{limit}` (`text-warning-on-tint font-semibold`, title "Over weight budget") follows the count on the same line. It has no meter.
- **No top accent strip on the expanded header** (removed in #2270). The collapsed 40px header keeps `border-t-2 border-t-warning-emphasis` when over WIP or weight, plus the `⚠` glyph and a title naming the reason.
- **Add-card button** (`aria-label="Add card to {column name}"`, `title="Add card"`, `+` icon, visible at rest). Rendered only when the viewer can edit and the column allows card creation; otherwise absent, never disabled. It opens the new-card input in the column's first visible lane: BoardView dispatches the `visiban:add-card` event (`ADD_CARD_EVENT`) on that lane's `[data-board-cell][data-column-id]`, and the cell opens its own input, so the draft and focus return stay with the cell.
- **Sticky.** The header row is `sticky top-0 z-20 bg-sunken` inside `[data-board-scroll]` and stays visible while lanes scroll; there is no corner cell. `e2e/board.spec.ts` scrolls past the first lane and checks the row is still at the top of the scroll box.
- Column color dot: `w-2.5 h-2.5 rounded-full flex-shrink-0` in the column's assigned color.
- Collapse chevron (a 7x8px SVG triangle): `absolute left-0 top-[13px] text-fg-secondary hover:text-fg transition` (a control, so not `fg-faint`, #2030).
- **Policy button (#1101) — a recorded exception to § Hover-reveal controls.** A column with a policy shows a **Policy** button (clipboard icon + the word) right after the name, **visible at rest** for every reader, not hover-revealed like the kebab. The policy is information everyone needs before moving a card, not an action, and Sam (occasional) would never find a hover-only cue. Below `lg` it is the icon alone (`hidden lg:inline` on the word) with the same accessible name: `aria-label="Column policy for {name}: {n} entry criteria, {m} done criteria"` (singular "criterion" for 1), `aria-haspopup="dialog"`, `aria-expanded`. At rest `text-fg-secondary hover:text-fg hover:bg-surface-hover`; open `text-info bg-info/10`. It is `shrink-0`, so the name truncates first. A column without a policy shows nothing (admins get **Add policy…** in the kebab). No other column-header control may claim this exception without recording its own reason here.
- **Policy popover (`ColumnPolicyPopover`).** `role="dialog"`, `aria-label="Column policy for {name}"`, 340px wide (capped at the viewport), anchored and dismissed exactly like the other anchored popovers (the removed `SwimlaneFieldsPopover` was the original) (§ Modals and dialogs, #1455: `useAnchoredPlacement`, focus after placement, a focusable `role="region"` body with the bottom fade). Header: `{name} policy` plus the mode tag (**Advisory** / **Confirm on entry**, a neutral `bg-surface-hover` pill). Sections **Entry criteria** and **Definition of done**; an empty list reads `No criteria yet.` An admin gets **Edit policy** in the footer, which moves focus to the Policy button before opening `EditColumnModal`, because the popover unmounts and the modal restores focus to its opener. It is non-modal and deliberately untrapped, so it also closes when keyboard focus moves outside the panel and its trigger (a document `focusin` check), never floating over the board without focus in it. It also closes, and its anchor is cleared, when the policy is removed over the socket, so a policy added back later never reopens it at a stale position. Escape closes the popover first (`useDropdownEscape`, 25, above BoardView's 10/12/15). "Updated by / when" is cut from v1: there are no `policy_updated_*` fields.
- **A non-modal popover that closes on `focusin` outside it must not portal its nested menus (#2205).** A portaled menu lives under `document.body`, outside the panel, so focusing one of its items fires the outside-`focusin` close and the popover vanishes mid-choice. Leave `portalMenu` off for dropdowns inside such a popover (`LaneFilterPopover`); the menu then scrolls within the panel's list, which is why that list carries `scroll-pb-10`. An in-flow menu is clipped by that list's `overflow-y-auto` when the list is short (#2231), so the popover tracks open menus through `onOpenChange` (a keyed Set, cleared when a row unmounts) and measures the open menu (its bottom edge relative to the list) in a layout effect and gives the list `min-height: min(<measured px>, <max-height>)` while any is open, then scrolls the list so the menu's first options (and its trigger row) are in view when the menu is taller than the capped list; a new popover with in-flow menus in a scrolling body must do the same. Its list height reserve (`visibleMaxHeight(2 * POPOVER_VIEWPORT_MARGIN, …)`: 12.5rem, or 15rem while the ignored-rules line shows, #2214/#2337) is verified by `e2e/lane-filters.spec.ts` at a 520px-tall viewport; re-run it after adding chrome to the panel. Single-key board shortcuts listen on the document and skip only text fields, so such a popover stops propagation of unmodified printable keys on its root (Escape and modified keys still pass).
- **Lane-filter built-in fields (#2336).** The field picker lists **Lane name**, then **Contact email** (admins only, with the shared `AdminOnlyFieldGlyph` on its option, never on the trigger, chip or Reads as), then the custom fields by position. Headings **Built-in** / **Custom fields** appear only when both groups are present. When a custom field's trimmed, lower-cased name equals a built-in's label, the built-in (never the custom field) reads "Lane name (built-in)": `laneFilterFields` sets it once on the synthetic definition so every surface agrees. Picking a text field (built-ins included) resets the operator to `is`. Collision naming is per viewer, and the built-in always yields: the ` (built-in)` suffix is computed only against custom fields this viewer can see, so a member and an admin may see different names for the same saved rule. Never compute it against fields the viewer cannot see — that would leak that an admin-only field exists.
- **Lane filters trigger visibility (#2336).** One helper, `laneFilterAvailable(customLaneFieldCount, laneCount, filter)` in `utils/laneFilter.ts`, gates both the filter bar's **Lane filters** trigger and the Filter panel's Lane filters row. Neither may test `laneFields.length` alone: with the built-ins it is never 0.
- **No anchored-match examples (#2336).** Wildcard and **contains** match any part of the value, so a placeholder, hint or doc example must never imply "starts with", "ends with" or "exact domain". The Contact email placeholder is `e.g. @acme.com`, never `*@acme.com`.

## Board grid cells

Reference: `docs/development/board-redesign.md` § Cells and `components.png` (Cells and drag and drop). Rewritten for #2270.

- **A cell is a well**: `bg-canvas` (the deepest surface), `rounded-lg`, 6px padding (`p-[5px]` plus a 1px `border-transparent` that the hover border reuses, so nothing shifts), 6px between cards (`gap-1.5`). No `border-r` grid lines: the column separators and the cell gap carry the grid.
- **Lane height follows content.** A cell is `min-h-14` (56px) when empty and otherwise as tall as its cards; the lane is as tall as its tallest cell. Cards sit in a `flex-col` stack and are never stretched to the lane height, so a tall cell leaves its neighbors' cards at their natural height (the neighbor's well grows, its cards do not). The per-lane height preference (`swimlaneHeights`) is still a minimum.
- **Empty addable cells (#962)**: when a cell has no cards, `column.allow_card_creation && canEdit` and it is not editing, the cell wrapper itself is the keyboard-reachable creation surface and the whole cell is the target.
  - `role="button"`, `tabIndex={0}`, `aria-label="Add card to {column.name} in {swimlane.name}"` (names the column and the lane). When a grid overlay gives the cell a value, that reading is appended to this same label (§ Board grid overlay slot); an `aria-label` overrides every descendant, so an `sr-only` reading inside would be discarded.
  - **Quiet at rest**: a single `+` (`text-fg-muted`), centered, in a `pointer-events-none aria-hidden` overlay (`data-testid="empty-cell-add-affordance"`). **On hover or focus** the cell gains a dashed edge (`hover:border-dashed hover:border-line-strong`, same for `focus:`; hover feedback only, exempt from the boundary-token rule per the `border-line-strong` contrast rule near the end of this file, #2505) and the label `Add card` appears next to the plus (`hidden group-hover/cell:inline group-focus/cell:inline`); `focus:ring-2 focus:ring-inset focus:ring-primary-emphasis` marks keyboard focus. The dashed edge is not shown at rest.
  - Click anywhere, or Enter / Space when focused, opens the new-card input. Double-click and right-click on cell space still work; a right-click on a card face opens the card context menu (§ Card context menu, #2059).
  - During an active card drag, the overlay is hidden so the drop-target indicator owns the frame.
- **Populated cells** keep one add button that fills the cell's remaining height (`flex-1 min-h-11 mt-1 w-full`: at least 44px, so it stays a touch target when cards fill the cell, #2320; deliberately not `relative` so an expanded `absolute z-0` card paints over it; the cell is `flex flex-col`; #2319), so blank well space below the cards is clickable. At rest it is a quiet `+` (`text-fg-muted`; `text-fg-secondary` on a grid-overlay tint, #459). Its accessible name is the empty cell's, `Add card to {column.name} in {swimlane.name}` (#2320), so a screen reader hears where the card goes. On hover or focus it shows the empty-cell look: `border-dashed border-line-strong`, `bg-surface-active/50`, and the `Add card` label (the wash on both the empty cell and this button is `surface-active/50`, never `surface-hover`: `surface-hover` equals `canvas` in light mode, so a `surface-hover` wash on a well is invisible there, #2320); the ring is `focus:ring-2 focus:ring-inset focus:ring-primary-emphasis` (never `focus-visible:`). A 1px `border-transparent` at rest keeps nothing shifting. During any drag it is `opacity-0 pointer-events-none` (stays in layout). Never `invisible`: a `visibility: hidden` element drops keyboard focus, and the focus does not come back when the drag ends (#2320). The wrapper is not `role="button"`, so Tab from the last card reaches the button without the cell intercepting Enter.
- **A creation affordance fills the space it implies.** If blank space in a container reads as "add here", the add control must cover it, not sit as a small strip beneath it: one real button (one tab stop) reusing the empty-cell hover look.
- **Never render two creation affordances on one cell.** Empty cells have the cell-as-button only; populated cells have the fill-height button only.
- **The column header's add-card button reaches a cell through the `visiban:add-card` event** (`ADD_CARD_EVENT`, `utils/addCardEvent.ts`); the cell listens only while it can create cards.
- **One shared grid template (#2300).** The sticky header row, every lane's cells row, every collapsed strip and every `RowSeparator` overlay set `grid-template-columns` from `boardGridTemplate()` in `components/Board/boardGrid.ts`, built once in BoardView from the column list: `16px` outer gutters, one fr track per column weighted by its saved width (`columnTrack()`: `minmax(0, ${w/220}fr)`, exactly `minmax(0, 1fr)` at the default 220px, so an unresized board is equal-width), `40px` for a hidden or collapsed column stub, one column's width per sub-column for a gated stage (#2278, #2531: `columnTrack(width, subCount)`, `N fr`, floor `N x 160 + (N-1) x 8` in `trackFloor`; two stay `minmax(0, 2fr)`), and an `8px` track between columns. The 8px gap is a real separator track, not `column-gap`, because the `ColumnSeparator` / lane separator in it is interactive (hover highlight through every row, click to insert a column, drag to resize the column to its left). Never give a header, cell, strip cell or separator a pixel `width` inside the grid; it fills its track. Place things on the grid with `columnTrackLine(i)` / `separatorTrackLine(i)`, never with summed pixel offsets. Anything that must not add a track (the column trash zone) is absolutely positioned. Column resize is kept (#1990): `viewPrefs.columnWidths` (clamped 160..600 by `setColumnWidth`) is a track weight, never a px `width`. A drag keeps the column's right edge under the pointer: raising one weight also raises the sum every fr track divides by, so scaling the weight by the track's growth alone lags the pointer. `measureTrackLeftOf` reads the weights from the row's specified (inline) template, the px from its resolved one, and the track floors from the wrapper's `data-track-floors`; `resizedColumnWidth` then solves `f = min(T·S_o/(C−T), T/k_o)` for the target width `T` (fluid fr space `C`, other weights `S_o`, px per fr `k_o` once the min width holds the grid open). Unmeasured (jsdom) it adds the px delta. Never treat a saved width as px anywhere else either: the column drag overlay is `w-full` and DragOverlay sizes it from the dragged cell. Hidden and collapsed stubs are not resizable. Both column separators (header `ColumnSeparator` and the lane cells' separators) use the one `startInsertGesture` from `boardGrid.ts`: insert on release unless dragged more than 4px, report the drag offset past 4px.
- **Sideways scroll.** The board is one scroll box (`[data-board-scroll]`, `overflow-auto`). Its grid wrapper (`data-testid="board-grid"`) is as wide as the box with a `min-width` of `boardGridMinWidth()`: 1240px, or the width at which the column with the least px per fr still gets its 160px floor (N × 160px plus the gaps between them for a gated stage with N sub-columns), plus gaps, gutters and stubs, when that is wider. So a many-column board, or one with a column resized far wider than the rest, scrolls instead of squeezing a column under 160px; for an unresized board of plain columns this is 160px per column. Below it the grid scrolls inside that box and the page never scrolls sideways (`e2e/board.spec.ts` checks alignment at 1200px and the 400px case).
- Board totals (swimlane/column/card counts) live at the right of the Show row (§ Show chips); there is no corner cell.

## Board grid overlay slot (#1147)

The board grid has one pluggable shading layer. An overlay (`src/gridOverlays/`) supplies
a per-cell `{value, label}`; the slot owns the scale, every class, the legend, and the
empty state. Rules:

- **An overlay supplies numbers, never classes.** `GridOverlay.compute()` returns values
  and labels only. The ramp, the non-color channels, the legend and the empty state live
  in `src/gridOverlays/scale.ts` and `slot.ts`, so #969's dual-encoding rule is enforced
  once for every overlay instead of once per overlay. An overlay that *could* ship a
  hue-only ramp is a bug in the slot, not in the overlay.
- **Severity is encoded three ways, and none of them is a font glyph (#969).** Tint
  (`bg-primary-emphasis/10 /20 /30 /40`) + a bar pinned to the cell's bottom edge
  (`h-px / h-0.5 / h-[3px] / h-1`, `bg-primary-emphasis` at `/50 /70 /85 /100`) + the
  value itself. Never `▁▃▅▇` or any block-element glyph: they do track `currentColor`,
  but their advance width and baseline are font-dependent, so the ramp's step size is not
  reproducible across platforms. Never `⚠` / `⛔` on a magnitude overlay — those belong to
  actionable severity (§ Column headers, § Move-blocked toast), and a high card count is
  not a problem.
- **A generic overlay ramps one hue; it never borrows success→warning→danger.** A scalar
  the slot cannot interpret means "more/less", not "safe/dangerous" — `bg-warning/*` is
  the card aging tint and `bg-danger/*` is over-WIP (and, on cards, the 2× aging stage), so a red cell would assert a judgment
  the overlay cannot justify. (The card aging ramp is the deliberate exception: it is a
  severity signal, not a generic scalar, so it does step yellow → orange → red → deep red —
  see § Card aging ramp. It still has no green step.) The ramp is `primary-emphasis`, identical in both themes, so
  it is verified once. **Never `bg-info/*` inside a cell:** `/10` is the active-toggle
  state and `/15` the filter-match pulse on collapsed stubs. The drop target is `bg-primary/20` (§ Drag states), so `bg-info/*` never appears in a cell.
  The ramp starts at `/10`; `/5` is below the perceptibility floor over `bg-canvas`.
- **The tint is the first child of the cell root, `z-0`, `pointer-events-none`,
  `aria-hidden`; the value badge is a sibling at `z-[5]`.** A positioned descendant paints
  above non-positioned in-flow content regardless of DOM order, so the card stack and the
  affordances after it carry `relative` and beat the tint on DOM order. The badge needs the
  opposite outcome and cannot get it from DOM order at all: `CardItem`'s root is
  `relative z-0`, so a z-auto badge earlier in the subtree paints *underneath* the first
  card. The three numbers in play are exact — `z-[5]` clears the cards, stays **below** the
  (former) sticky swimlane label panel (`z-10`, removed in #2271) and the sticky header row (`z-20`) which a badge
  must never cover when the grid is scrolled, and still yields to a hovered card
  (`hover:z-20`) so the card's own selection checkbox stays usable in the same corner.
  The built-in `cards.length` badge (`data-testid="cell-card-count"`) is the same case and
  carries the same `z-[5]` (#1162); any new absolutely positioned cell affordance that must
  sit over the cards needs it too.
  Never put the tint on the cell root's `bg-*`: the root already carries `bg-canvas` and
  the drag-over `bg-surface-hover/40`, and a third `bg-*` on one node is a Tailwind
  ordering coin-flip.
  The overlay value badge is an opaque tab (`top-0 right-1 rounded-b bg-canvas px-1
  leading-[13px]`), #459. Opaque, because a card's border would otherwise run through a
  value as wide as `12.0d`. Exactly 13px tall, because that is the room above a card's
  contents: the cell's 6px well (5px padding, 1px border, #2270), the card's 1px border, then the checkbox's 7px inset (`top-[7px]` on the card, so the 3px the thinner well took away is given back there);
  the title starts at 14px, or 13px in the compact grid (compact body padding is `pt-[7px]` for exactly this reason: `py-1.5` would put the title's box 1px under the tab). Never lower or in
  another corner: a full compact grid has no free row, so a bottom corner lands on a card's
  avatar, and adding room would reflow the grid, which this slot forbids. `e2e/grid-overlay-dwell`
  measures the tab's box against every card's title, checkbox and avatar in both layouts.
  `text-fg-secondary` on `bg-canvas` is 13.59:1 dark and 9.45:1 light, so the badge passes on
  every step. Cards are opaque and paint above the tint, so a card's own text is never on
  it. What does sit on the tint is the populated cell's `+ Add card` button, which takes
  `text-fg-secondary` on a tinted cell (7.71 dark, 6.01 light at `/40`) instead of its usual
  `text-fg-muted`; `text-fg-tertiary` is 4.47 and 4.40 there and fails. The bottom bar is not
  a text carrier and need not reach 3:1 against the tint (2.14 light at `/40`): it repeats
  the numeral, it is not the only way to read it. The tab is above a card at rest, so the
  card needs no lift to show its checkbox; a hovered card (`hover:z-20`) still rises over it.
  The checkbox's box starts at 13px, but its 2px focus ring starts at 11px and `CardItem`'s
  classes are pinned by the board baseline screenshots (§ Board presets), so the tab fades
  (`group-has-[[data-card-id]_:focus-visible]/cell:opacity-0`) while a keyboard user is on
  a control inside a card. `opacity-0`, never hidden, so the reading stays available. The
  coarse-pointer button's 44px hit area also starts under the tab (a 25×4px band), but the
  tab is `pointer-events-none` and the visible `⋯` starts at 17px, so nothing is lost there.
- **An overlay may declare a `scale` of absolute steps, as numbers and words only.**
  `GridOverlay.scale` holds lower bounds and legend wording, never classes, so the ramp
  still lives only in `scale.ts`. Use it when the unit has a fixed meaning (#459: days), so
  a cell is not called hot merely because it is the worst on a healthy board. On an absolute
  scale: a value below the first bound is a real reading (the badge alone, no tint, no bar,
  announced as `below level 1`), a 0 is a reading too and the overlay omits a cell to mean
  "no value", the flat rule does not apply, and the legend names each step and adds a row
  for below the scale. Everything else stays relative-to-max. **The value the slot steps is
  the value the badge shows:** an overlay on fixed bounds rounds before it returns, so
  `3.0d` can never sit in the "under 3" step.
- **An overlay that leaves visible cards out says so in the legend.** `GridOverlay.note`
  returns one sentence with the count, or null. The per-cell reading is not enough, since
  only a screen reader hears it, and a badge has no room. A legend's unused-level dash is
  `aria-hidden` with `sr-only` "no cells" beside it: screen readers skip a bare em dash.
- **`compute()` never reads the clock.** An overlay whose value depends on time declares
  `refreshMs` and reads `ctx.now`, which `useOverlayClock` floors to that interval. So the
  grid is rebuilt only when the bucket changes, and an overlay that declares none is never
  rebuilt because time passed. Never add a per-second tick for a value that shows to a
  tenth of a day.
- **A dwell time comes from `column_entered_at`, never from `last_moved_at`.** A
  swimlane-only move, an archive and a restore all write a movement, so `last_moved_at`
  is not when the card entered its column. `last_moved_at` is the staleness signal (§ Card
  aging ramp); the visit rules are the *Flow metric definitions* ADR's, computed on the
  server. A client-side move has to keep the field true until the response lands, which is
  why `useBoard` writes it in two places and no others: `placeCardOptimistically` sets it
  for the move, and `rollbackMovedCard` restores it if the move fails. A column leaving
  done needs a re-read, since its cards have no time yet; `BoardView` routes that through
  the drag-deferred resync (#1463), never a bare `silentReload()`.
- **A cell tint or z-order change needs a browser check in both themes before merge.**
  jsdom renders no paint order, so a vitest suite will pass over a layer that is invisible
  in the product. Class-level assertions (the z value, the tint token) are a guard against
  regression, not evidence that the layer is visible.
- **The layer is suppressed on the cell being dragged over.** Drop feedback owns the
  background channel — same precedent as hiding the centered `+ Add card` overlay during a
  drag.
- **One scalar per cell corner.** The top-right slot renders *either* the built-in
  `cards.length` badge (at ≥ 2) *or* the overlay's value badge, never both.
- **A cell whose `aria-label` is set must carry the overlay reading inside that label.**
  An empty addable cell is `role="button"` with an `aria-label`, and an `aria-label`
  overrides every descendant's text — an `sr-only` reading there is silently discarded.
  Append it to the cell's label and mark the visible badge `aria-hidden` instead.
- **The legend floats; it is never a strip.** Every above-grid strip is in-flow and
  `shrink-0`, so it shrinks the `flex-1 min-h-0` scroll container — that is displacement,
  which this slot forbids. The legend is `absolute bottom-4 right-4 z-30
  pointer-events-none` inside a `relative` wrapper around the **scroll container only**,
  so it can never cover `BoardActivityDrawer`. `bottom-4` clears `.board-scroll`'s
  always-visible 10px custom scrollbar (`src/index.css`) and `pointer-events-none`
  means a graze can never eat a scrollbar drag. `z-30`
  is deliberately below `BulkActionToolbar` (`z-40`) and the shared toast region (`z-[55]`, § Toasts) — a
  transient message always wins over a passive key. It fades (never unmounts) during a
  drag, and drops to a single compact row below `lg` via `useIsLargeViewport`.
- **The legend's empty state is filter-aware, and it is the second one-line empty state
  in the system.** § Empty states' centered-icon pattern is for a surface with nothing in
  it, and the board is full of cards, so the legend uses the one-line form at `text-xs
  italic` in `text-fg-muted`, the same tone as the card-detail sub-sections since #2030:
  faint is a decorative tone and this is the only sentence the panel shows. The copy must
  name the actual cause — `No values match the active filters.` when `isFiltered`, and
  `No values on this board yet.` otherwise. "Nothing on this board" is a lie when the
  filter bar is what emptied the overlay.
- **`role="group"`, never `role="region"`** — the board is capped at four landmarks
  (§ Top chrome). Swatches are `aria-hidden`; each legend row carries an `sr-only` level
  prefix, and an unused level renders `—`, never `0`.
- **The Overlay picker lives in the View menu (#2269).** It is a `SingleSelectDropdown` with `portalMenu` inside the View panel, below Card density and Card layout. It maps "None" to `selected={null}` so the trigger reads `Overlay` at rest and takes the primitive's active treatment, showing the overlay's own name, exactly when one is on. It is a selection, so it never moves to the overflow menu.
- **Overlay ids are a persisted contract.** `board:{boardId}:grid-overlay` stores the raw
  id and unknown ids decay to `none` through `resolveGridOverlayId` — a board preset
  (#1146) or a stale value may name an overlay this build has never heard of, and an
  un-overlaid board is a strictly better failure than a board that does not render. Never
  rename a shipped id; `label` is free to be reworded.
- **Never gate the overlay on `canEdit` or `isAdmin`** — it is a local reading preference
  with no server write, so every role gets it. It renders only in `view === "board"`.
- **Two live regions on the board is deliberate.** The overlay announcer sits beside the
  DnD announcer because they are driven by disjoint actions (a pointer drag vs. a toolbar
  click); the one-region-per-action rule targets two regions racing on a *single* action.
  Cell values themselves carry no `aria-live`: they change from other users' WebSocket
  events, and announcing those would make the board unusable with a screen reader.

## Board presets (#1146)

A preset is a named bundle of how the board view presents a board (`src/boardPresets/registry.ts`). In 1.3 there are exactly two, code-defined: **Classic** and **Default**. There is no Classic rendering (#2279): the redesigned board is the board, and `classic` is only a persisted id that resolves to it. Rules:

- **`classic` resolves to the redesigned board (#2279; owner decision 2026-11-14: no users, so no Classic fallback).** The id stays accepted in `Board.default_preset`, `?preset=` links and the TypeScript types, and a board or link naming it loads the same redesigned board as no preset (`boardPresetsBoardView.test.tsx` pins both; `e2e/board-redesign.spec.ts` loads `?preset=classic`). Its bundle is still the no-op bundle (the board's own density, no overlay, no fields, no filter). **A preset has no visual effect other than its density (and overlay and filter, which are board state, not card face):** Classic keeps the board's own density, Default sets Standard, and both draw the same card. There is no Classic-only card face, urgency glyph, border or snapshot: a card-face change lands for every preset. **The visual baseline is `e2e/board-redesign.spec.ts`**: `toHaveScreenshot` images of the seeded sample board (`e2e/fixtures/redesign-board.ts`, from `docs/development/board-redesign/sample-board.json`) in light, dark, collapsed, peek, activity, menu, empty and phone states, plus the loading skeleton, filter matches nothing, offline, load error, view-only, Filter panel and `...` (More board actions) menu states. A deliberate visual change updates those images in the same MR.
- **Baseline images are generated in the CI image, never on a developer machine.** Snapshots are `*-chromium-linux.png`; regenerate them with the CI image so they match byte for byte (macOS renders fonts differently and its `*-darwin.png` files are never committed): `docker run --rm -v "$PWD":/work -w /work mcr.microsoft.com/playwright:v1.59.1-noble bash -c 'npm ci && VITE_API_URL=http://localhost:8000 npm run build && CI=true npx playwright test e2e/board-redesign.spec.ts --update-snapshots'` from a copy of `frontend/` without `node_modules` (keep the image tag equal to `playwright-e2e` in `.gitlab-ci.yml`). Baselines must come from the `vite preview` production build that CI compares against (hence the build step and `CI=true`), not `vite dev` (#2485). Review each changed image against `docs/development/board-redesign/` before committing. The captures follow each reference's theme (board-light is light; the others are dark), the desktop board shots use a 1440x2180 viewport so the lower lanes are in the image, the peek image is the Shift+click panel, and the activity image replays seven `card.moved` socket events (the drawer keeps no history of its own).
- **Resolve density and overlay once, through `useBoardPreset`.** `BoardView` reads `boardPreset.display` for both; never compute `override ?? board.card_density` or read `board:{id}:grid-overlay` anywhere else, or a board default preset is half-applied. Precedence: a `?preset=` link (applied by writing the keys), then the member's own keys element by element, then `Board.default_preset`, then the board itself.
- **No new server state; one per-user marker (accepted by the owner ruling on #1146, 2026-11-03).** A preset writes the two existing per-user keys (`board:{id}:card-density-override`, `board:{id}:grid-overlay`), the URL, and the marker `board:{id}:preset` naming the preset that wrote them (none when the board default was applied, which clears the keys). The active preset is the marker, else `Board.default_preset` (`resolveActivePresetId`), resolved from those current inputs on every render: no in-tab choice may outlive the input it recorded, or a tab and a reload disagree (applying the board default records no marker, so a later change of board default is followed). **Never infer a preset from the keys' values**: they predate presets, so a member's own 1.2 density or a stored `none` overlay is their own setting even when it matches a preset, and Settings → Display must not say "Set by preset" for it (`densitySource`). A new element (fields, filter, attention) writes its own existing state, and a change to an element's meaning bumps `BOARD_PRESET_SCHEMA_VERSION`.
- **Preset state belongs to one board.** `App` renders `BoardView` with `key={board.id}`, because the `/boards/:id` route stays mounted across ids; without it every board-scoped hook (density, overlay, preset, its notice and Undo) carried over to the next board. `useBoardPreset` also resets itself if `boardId` changes under it, and an Undo never writes to a board other than the one its snapshot came from.
- **Ids are a persisted, public contract.** They are stored in `Board.default_preset` and in `?preset=` links and mirrored by `BoardPresetId` in `backend/boards/models.py`. Never rename or remove one; names and descriptions are free to change.
- **No domain semantics.** A preset references field definitions and choices by id and ships none of its own; no preset names a label, a field, or a business concept.
- **Picker.** `SingleSelectDropdown` with `portalMenu` and `triggerPrefix={PresetIcon}`, the first row of the View menu panel (#2269; it used to lead Row 2's Zone 2), never in the overflow menu (a selection, like the Overlay picker). The trigger fills the panel width, and focus returns to the View button after Undo or a notice dismissal, since the picker is only mounted while the panel is open. Trigger reads `Preset` at rest and the preset's name otherwise, fills the panel width (`w-full`); accessible name `Preset: <name>` plus `, modified`. Each option shows its one-line summary as its `description`; the board default is marked `Board default` in that line (not `Default`, which is also a preset's name). Choosing the active, unmodified preset changes no state but raises a short `info` toast (`“<name>” is already applied`, 4s, key `preset-already-active`, no Undo, #2124) so the choice is acknowledged and announced (a no-op that the member can mistake for a dropped click is acknowledged this way, never closed silently; it is a courtesy toast with no action, so at the cap of 3 it may wait behind a real notice); the ⌘K apply command does the same. The trigger carries `title=<preset name>` while a preset is active (the truncated name is otherwise unreachable), via `SingleSelectDropdown`'s `triggerTitle`.
- **Modified.** A dashed `border-line-strong` `Modified` text tag on the trigger (exempt from the boundary-token rule because its text names it, per the `border-line-strong` contrast rule near the end of this file, #2505); the menu's `menuHeader` lists each difference as `Density: Dense (preset: Standard)`, and a `Reset to “<name>”` menu action re-applies it. Once modified, `?preset=` is dropped from the URL, so a reload never silently re-applies the preset over the member's changes. Opening a `?preset=` link overwrites the member's keys, so it raises the same Undo notice (`Applied “<name>” from the link`); its Undo restores the old keys and marker and drops the link. A notice for a change the member did not start stays 20s, not 8s (`PRESET_LINK_NOTICE_MS`): focus is on the page, so pause-on-focus never engages. Every notice's live text ends `Undo is also in the Preset menu.`, visible copy unchanged.
- **⌘K commands.** On a board the palette offers `Apply preset: <name>` for every preset but the active one, and `Reset to preset: <name>` when the active one is modified. They are hidden while the palette has a card target (#2059): the palette is then about that card. They reach BoardView as the `visiban:preset-command` window event and take the picker's apply path (same no-op rule, same notice); the palette learns the active preset from `boardPresets/activePresetStore.ts`, which `useBoardPreset` publishes. No new shortcut key. **Board-scoped palette commands read `<Verb> <noun>: <name>` and reuse the picker's verb** (`Apply preset: Default`, `Reset to preset: Default` beside the picker's `Reset to “Default”`), so a command and its matching picker action and notice say the same thing.
- **Every apply and reset gets an Undo notice** (`usePresetNoticeToast`, an `info` toast in the shared region, § Toasts), in every view (Board, Summary, History, Analytics, Lens): a ⌘K command or a link can apply a preset anywhere, so `BoardView` calls the hook once, above every view branch. A `?preset=` link that changes nothing the member has stored (they picked it, then reloaded) raises no notice. Informational tone like § Post-import notice, auto-dismiss after 8s (20s for a link), paused on hover or focus by the region, announced with an Undo hint.
- **An auto-dismissing notice's Undo must be reachable from the keyboard without racing its timer.** The notice sits far later in the tab order than an 8s timer lets a keyboard user travel, so while it is up the control that caused it offers the same action (the picker's `Undo: Applied “<name>”` menu action). Undo or × in the notice returns focus to that control, because the buttons unmount with it. A new toast that carries the only undo follows the same pattern. `ImportSkippedToast` needs no such path (#2107): it persists when it lists warnings, and its list and `×` are in the Tab order of the region, one Tab from the board grid.
- **Name the source when two controls write one value.** Where a preset wrote the personal density key, the `Use my own density` toggle's description names the preset and what turning it off returns to, and the standalone `Set by preset` line is not repeated; that line appears only when the density comes from a board default preset, which writes no key. The admin section is titled `Board default preset`, never just `Default preset` beside a preset named Default. **Copy that predicts a consequence is conditional on the state that causes it**: the toggle says "the preset will then show as Modified" only when turning it off changes the density (`densitySource.offChangesDensity`).
- **Two writers share the density key.** The standalone line `Set by preset “<name>”: your view shows <density> density.` (`text-xs text-fg-tertiary`, the `aria-describedby` of the admin Card density group) appears only when the density comes from the board default preset and the member has no key (`densitySource.via === "board-default"`). When a preset the member applied wrote their key (`own-key`), the `Use my own density` toggle's description says so instead, names what turning it off returns to (the board default preset's density, else the board's), and is the `aria-describedby` of the switch and of the personal density group. Turning the toggle on seeds the density the member sees now, never `board.card_density` regardless. The board default preset is an admin radio group in the same tab (None / Classic / Default), with a read-only line for everyone else, like Card density.

## Swimlane bands (#2271, #2275)

- **Children-mode lane band (#2370, a documented variant).** In Children mode (`ChildrenModeView`, `?show=children&lane=<lane id>`, numeric id, never a slug) the band keeps the name at 17px and the collapse button (`aria-expanded`; "Collapse {lane}" on desktop, "Collapse lane {lane}, N in progress of M" on phones), and its secondary tier **replaces** the band's fields in this mode only: the lane total from `laneTotalLabel` ("12 in progress of 16", or "2 in progress · 2 planned" when planned children exist: planned never counts as to do or in progress), the lane bar (done, doing, blocked striped, to do), "N blocked" in `text-danger` ("none blocked" / "All blocked" in the rollup wording) and "+N on a board you can't open". **Drawing (canvas 6a, fix round B):** the band is its own `rounded-lg border-line-strong bg-surface` box (the lane's rows sit below it on the page ground, indented `ml-6`, never inside a lane card), with an SVG chevron; order is name, actions, subtitle, `ChildStateBar`, total (the "N in progress" part bold), blocked (`⊘ N blocked` in danger; "· none blocked" joins the total), idle, then "+N" pushed to the end. A **collapsed** band drops Focus, Copy link and `⋮` and adds "Work idle Nd" (`laneIdleLabel`: the card rollup's `movementLine` rule over the lane's server counts and the board's `staleness_threshold_days`; `text-warning`, `-on-tint` on the phone tint). It keeps the total even when "All blocked" (the issue wins over the canvas, which omits it). The band is a `role="group"` named by `laneBandName` ("Acme Corp children: 16 you can open, 4 done, …; 4 more on a board you can't open"). Every count is the server's per-viewer count from `children-view`; never re-derive planned, blocked or hidden on the client (Rule 19). All copy lives in `utils/childrenMode.ts`.
- **Children mode: link, Focus, paging and controls (#2370 fix round A).** `?lane=` (the shared link and the Children lane action) only chooses the lane that opens expanded; every other lane is still drawn, collapsed. **Focus** (the band's Focus and the View menu's Lanes) is the board's `?focus=` filter and is the only thing that hides lanes; Children mode never mutates the grid's collapse prefs for it. Rows are held **per lane** (`LaneStore`, `addPage` in `utils/childrenMode.ts`): a collapsed lane reads its own rows (`?lane=`) when opened, and every lane that is not fully loaded has its own "+N more parents" button, never only the lane holding the last loaded row. The main board-wide read's last lane continues that read; a live re-read re-covers what was loaded, main read first, then each lane read on its own. Reads are **one in flight plus one trailing**: a board event during a read never aborts it. **General rule: a view mode shows only the controls it honors** (Children mode hides the Filter button, the filter bar and its chips, and turns off the `e`/`c`/`f`/`/` grid shortcuts; on a phone the Filters button stays as the route to View options). A child card's **Move** is an icon action inside the card's box (named "Move {title}", visible on hover and focus, always on touch), never a text button beside the card, and stays inside the card's roving stop. A large lane's Open is its own roving stop beside the row title. Lane counts for the Cards-mode Children action read `children-view?counts_only=true`.
- **Lane actions gain Children and Copy link (#2370).** Beside Focus and the admin `⋮`: **Children** (Cards mode, everyone, every band of a board where cards can have children; `SwimlaneRow`'s `childrenAction`, visible text "Children" plus a "N in progress" chip, `aria-label` "Children N in progress, {lane}" so the visible text leads; shown on hover, focus and always on touch like the other lane actions, with the same opacity classes, never `display:none`; it sets `?show=children&lane=<id>`) and **Copy link** (Children mode only). The Children-mode band carries **Focus** (everyone; text button, `aria-pressed`, toggles `?focus=`), **Copy link**, then the admin `⋮` (named `Actions for swimlane "{lane}"`, the same name as in Cards mode: one menu, one name in both modes; Edit swimlane…, Change field order…), in that order. Focus and Children are at least 44px high under a coarse pointer (`[@media(pointer:coarse)]:min-h-11`, also `min-w-11` on the Focus icon button) at every width; Children-mode band and grid controls use `min-h-11 sm:[@media(pointer:fine)]:min-h-8` (32px only for a fine pointer from `sm` up), and the phone band (`PhoneBoard`) shows Children as a 44px footer action. **Dual-input target rule (#2370 ux-review):** a control that is 32px on desktop uses `min-h-11 sm:[@media(pointer:fine)]:min-h-8` (or `h-11 sm:[@media(pointer:fine)]:h-8`), never `sm:min-h-8` or `max-sm:min-h-11` alone, which leave a coarse-pointer tablet at 32px; the Show segmented control and Children-mode cards and Move follow it. A focusable empty grid stop carries an `sr-only` name (the cell's "parent, column, 0 cards"). The in-progress count is the server's lane rollup through `useChildrenLaneCounts` (one `children-view` read per board in Cards mode), never summed from `children_rollup` on the client; no count is drawn until it lands. `docs/development/board-redesign.md` § Swimlane bands lists them.
- **Children mode `?lane=` resolves on the client (#2370 item 1).** `resolveLaneParam` keeps the id only when it is in `board.swimlanes`; anything else is "no lane" (every lane, default expansion), never an error state and never sent to the server, so a deleted lane, another board's lane and a hidden one all read the same. A `404` on a lane read that slipped through (deleted since load) falls back to no lane the same way; only a failure with no lane shows "Children didn't load".
- **Parent lane filter (#2370 way in 3).** `FilterState.parentLaneFilter` (a lane id, URL `f_parent_lane`, saved-filter key pinned by `filter_state_keys.json`) matches on `Card.parent.swimlane_id` for a visible parent only; its options come from `parentLaneFilterOptions` (lanes of parents the viewer can open, read from the cards' own `parent`; a shared lane name carries its board). It shows wherever the Parent row does and ANDs with it; its chip reads "Parent lane: {lane}". The Children tab's last Tab stop (8) is "All children in {lane} (N in progress)", opening Children mode at the parent's lane.
- **Children mode grid (#2370).** Each lane's child-board section is one `role="grid"` ("{lane} children on {board}, by parent") with `row`, `rowheader` and `gridcell` roles and ONE Tab stop (roving `tabIndex`, `data-stop`); arrows move between cards and rows, the parent is the first cell; Home/End go to the row's first (parent) and last stop, Ctrl+Home/Ctrl+End to the grid's. Each child-board heading reads "Parent · column on {parent board}" over "Children on {child board}" (a link), and each column head carries `columnHeadCaption` ("3 of 4 on Delivery · limit 5"; the folded Done column "Count per row · Show opens them") plus, for a column with a WIP limit, a `role="meter"` of the whole column against it (fill `bg-primary-emphasis`, which clears 3:1 on the band surface in light and dark where `bg-primary` measured 2.8:1 in dark; it stays `bg-primary-emphasis` past the limit, see (c) of the Move and live updates entry). The e2e measures every new Children-mode surface: text 4.5:1, the meter fill 3:1. Escape registers at the board tier, **14** (`CHILDREN_MODE_ESCAPE_PRIORITY`): below the View menu's 25 and every dropdown, above BoardView's focus-exit (12), so one Escape leaves the grid (focus to the lane's collapse button) before a second exits lane focus; it returns `false` unless focus is inside a grid. A row with blocked children has a 3px `border-l-danger` accent; planned children fold into "N planned · Show" (`aria-expanded`) in the first column; parents with nothing in progress, and (unless Planned is "Only planned") parents with only planned work, fold into one end-of-lane button worded by `foldLabel`. The options (Lanes, Show done cards, Blocked only, Planned) are passed to `BoardViewMenu` as `childrenOptions`, never drawn in the header. `?show=` is shared with the Show chips: `parseShowChip` reads `children` as "all" and the chip setter never deletes `show=children`.
- **Children mode signal rules (#2370 ux-review).** (a) The locked-row and "+N on a board you can't open" glyph is an inline lock SVG on `currentColor` (`aria-hidden`), never the 🔒 emoji; a lock means "no access" only, and blocked stays the #449 ⊘ glyph. (b) Row-level blocked state is text ("N blocked" in `text-danger`) as well as the 3px accent, never the border alone. (c) A one-line (large lane) row's title expands it, so opening the parent is a separate **Open** control, never a keyboard-only shortcut; it is quiet at rest (`opacity-0`, shown on row hover and its own focus, and on touch once the row is open: canvas 8 § 5 draws no Open on the line). (d) A transient confirmation (Copy link) is visible on the control ("Link copied", about 2s) as well as announced; an `sr-only` region alone is not enough. - **Field order: band slots vs the grid (#1456, #2356).** Band slots (#2356) always use board field order. A per-lane order (#1456, not yet built) applies only to this expanded grid and Edit Swimlane; until #1456 ships the grid uses board order.
- **Clamped values must stay reachable (#2354).** The lane field grid clamps plain-text and URL values to two lines, so each carries its full value in `title`; multi-select chips and choice badges are never clamped (a clamp cuts inline-flex blocks off silently). The grid `<dl>` carries no `aria-label` (it has no role to attach one to); the "Show N more" toggle's `aria-controls` and its lane-named label associate it.
- **Collapse state is unchanged:** per user per board in `useViewPrefs.collapsedSwimlaneIds`. Collapse all / Expand all for swimlanes are the View menu's "Collapse all" / "Expand all" items (#2269), and the Show row's Collapse all lanes button (#2308) drives the same handlers and state. `viewPrefs.swimlaneColumnWidth` is still parsed and saved so old localStorage stays valid, but nothing reads it.
- **Row height drag still works:** the bottom handle sets the cells row's `minHeight`; the band is not part of it. The first column separator has nothing to its left to resize (it only inserts a column); every other lane separator resizes the column to its left, like the header's.
- **The card detail sheet has no lane label to avoid** (`data-lane-label` is gone); it anchors to the column edges (on a gated cell, the card's sub-column, #2540) and falls back to the board's left edge.
- **`SwimlaneFieldsPopover` was removed.** Its #1455 and #1417 rules (leading with what the old `+N` counted, "On row", the density cap) no longer exist. Copy for swimlane fields says "fields", never "pinned", on every surface including admin settings (#2303).

## View menu rows (#2388, #2390)

- **Boolean options in the View menu are native checkboxes, label left and box right.** The reference (`docs/development/board-redesign/menus.png`) draws "Show sub-columns" as a checkbox, not a `Toggle`. Use `<label className="flex items-center justify-between gap-2 cursor-pointer text-sm text-fg max-sm:min-h-11">` around the text and `<input type="checkbox" className="h-4 w-4 rounded accent-primary focus:outline-none focus:ring-2 focus:ring-primary-emphasis">`; the whole row is the 44px phone target.
- **`text-[17px] font-semibold text-fg` is the sanctioned lane, panel and drawer heading size.** Tailwind has no 17px step; the swimlane name and the Activity drawer heading use this exact class string. Do not add a token or substitute `text-base`/`text-lg`.
- **A panel footer's in-text action is `text-info underline hover:no-underline` with the standard focus ring, right-aligned in a `flex justify-between` row**, never inline in a text run (inside a `max-sm:[&_button]:min-h-11` panel an inline button distorts the line height). The View menu's "On the card: <fields> Change" is the model.
- **A `SingleSelectDropdown` that shows its value under a section label sets `unselectedLabel` for the resting text and also passes `ariaLabel` naming the control** ("Overlay: None"); the visible value alone is not an accessible name.

## Column policy editor and confirm-on-entry checklist (#1101)

- **Editor.** `EditColumnModal` has three tabs, **Settings**, **Stage** and **Policy**, as a full tablist (`role="tablist"`/`"tab"`/`"tabpanel"`, `aria-selected`, roving `tabIndex`, Left/Right/Home/End). It is a fixed-height tabbed modal (`h-[85vh] max-h-[640px]`) whose body is one focusable `role="region"` with the bottom fade, and whose Save/Cancel footer is shared by all three tabs. **Add policy…** and **Edit policy** pass `initialTab="policy"`, and **Stage settings…** passes `initialTab="stage"`, each focusing that tab per § Deep-link into a tabbed modal. The Policy tab (`ColumnPolicyEditor`) holds two reorderable lists (**Entry criteria**, **Definition of done**), each at most 8 one-line inputs (`maxLength` 200) with ↑ / ↓ / × icon buttons, and **+ Add criterion** below, whose accessible name begins with its visible text and names the list (`Add criterion to Entry criteria`, WCAG 2.5.3); an empty list reads `No criteria yet.` Reorder is by buttons, never drag, so it works inside the modal's focus trap. The ↑ on the first row and ↓ on the last are `aria-disabled`, not `disabled`, so a moved row's button keeps focus at the ends; **+ Add criterion** at the cap is `aria-disabled` with a visible `Up to 8 criteria per list.` reason tied by `aria-describedby`. Reorders and removals are announced in an `sr-only` `role="status"`. The mode is a § Radio groups card pair: **Show the criteria** (advisory, default) and **Ask the mover to confirm**. The helper under Definition of done is fixed copy: "Definition of done shows as a read-only list in card detail. It never blocks moving out." (read-only list, not "checklist": card detail renders it as display-only bullets). Drafts on both tabs persist while switching tabs; the Name field auto-focuses only on the first open, never when the user arrows back to Settings. Save trims criteria, drops blank rows, sends `policy: null` when both lists are empty, and sends `policy` **only when the drafts differ from the value the modal opened with**, so a rename never overwrites a policy another admin changed meanwhile. With a blank name, Save is `disabled` and the footer's always-mounted status line reads "Name is required." (tied to Save by `aria-describedby`), because on the Policy tab the Name field is out of sight. The anonymous share-link payload omits `policy` (`PublicColumnSerializer`; `PublicColumn` on the client), so the editor carries no share-link warning.
- **Board settings policies section (#2156).** **Board settings → Rules & limits → Column policies** (`BoardSettingsPoliciesSection`) lists every column in `board.columns` order, hidden ones included (a `Hidden` badge only when the viewer hid it), with a one-line summary: `No policy`, or `{counts} · Advisory|Confirm on entry`. Non-admins get a read-only list with the criteria in labeled ordered lists and no buttons; admins get an inline accordion, and demo mode inherits the Rules & limits section's `DemoInert`. Rules the accordion introduces:
  - **One editor open at a time.** Each row is a disclosure button (`aria-expanded`, `aria-controls` only while open, `min-h-11`); the open row mounts `ColumnPolicyEditor` in a `role="group"` labeled by that button, with `useColumnPolicyDraft` seeding the draft at open and never reseeding it from live props. If the open column disappears the row collapses silently.
  - **Switching away from a dirty row uses the inline Confirm/Cancel pattern** (§ Modals and dialogs): a plain wrapper (no `role="status"` / `aria-live`, #2232) reading `Discard changes to “X” and open “Y”?`, announced through `useConfirmAnnouncement`, `Confirm` (`text-danger font-medium`) discards and opens, `Cancel` keeps editing; `useConfirmFocusReturn` returns focus to the clicked row and Escape cancels the prompt at priority `40.6`. A clean row switches without a prompt; clicking the open dirty row collapses and discards like the editor's own Cancel button.
  - **A dirty draft is discarded silently on tab switch or modal close.** No prompt: the section unmounts with the tab.
  - **Focus returns to the row's disclosure button after Save or Cancel**, and a successful save announces `Policy saved for {name}.` in an always-mounted `sr-only` `role="status"` region.
  - **Saves are pessimistic.** Save is disabled until the draft differs from the seeded policy; while saving the editor and Cancel are disabled and the other rows are `aria-disabled`. A failure keeps the row open and the draft, and shows the server message (else `Couldn't save the policy. Try again.`) inline in the row's status region, cleared on the next edit. The request is `PATCH` with `{policy}` only (the column `PUT` requires `name`), then the returned column goes to `onColumnUpdated`.
- **During a drag.** While a card from another column is over a column with entry criteria and no limit blocks the drop, the cell shows an `aria-hidden` **Entry: a · b** pill (same position and opaque surface as the blocked-drop label, `text-fg-secondary`), and the drag live region appends `Entry criteria for '{column}': a; b.` Like a limit verdict, a cell with criteria always announces past the hover throttle. A blocked cell shows only its verdict. The pill is one line and truncates; the live region carries the full list, so the truncation is a known, accepted limit of the visual cue.
- **Confirm on entry.** In `confirm` mode a drop opens `PolicyConfirmModal` (`ModalWrapper`) titled `Move "{card title}" to {column}?` (the card's title, since cards have no short key), with the entry criteria as native `accent-primary` checkboxes. **Move to {column}** is `aria-disabled` with `aria-describedby` on an always-mounted `X of N still to check.` status line until every box is checked; **Keep in {source column}** is the secondary cancel. Escape and the backdrop cancel too. Focus returns to the moved card (`[data-card-id]`) either way, retried for a few animation frames because a confirmed move re-renders the card in its new cell. The modal is keyed by card, column **and the criteria text**, so a policy edit arriving over the socket remounts it with every box unchecked (a new criterion can never be skipped); when the card or column disappears, or the column stops asking for confirmation, an effect cancels the held move, announces "Move canceled, the column or its policy changed" and returns focus to the card. **A limit block wins**: when `placementVerdict` predicts a block, the move is sent as is so the server's refusal raises `MoveBlockedToast`, and no checklist opens; this matches the server's order. The checklist covers drag-and-drop moves (pointer and keyboard) only; the card-detail Move popover, bulk moves, the card context menu's Move to… and the palette's Move card to… (#2059), an admin's "Move anyway (admin override)" from `MoveBlockedToast` after a limit block (`forceMoveCard`), API, MCP and import do not prompt. It is a client-side acknowledgment, never enforced by the server, and the docs say so.
- **Card detail.** The current column's **Definition of done** is a display-only list in the Details tab, after Description: small `bg-fg-tertiary` bullet dots (`aria-hidden`), the same glyph as the popover, never empty boxes, which read as checkboxes that do nothing; `text-sm text-fg-secondary` items; and a `text-xs text-fg-tertiary` "For reference. It never blocks moving the card on." line. Its label keeps the sibling sections' `text-xs font-semibold uppercase tracking-wide text-fg-muted` styling but is an `h3` naming the `section` (a deliberate departure from the sibling `<p>` labels, so screen readers get a named region). Omitted when the column has no done criteria (board-config-gated).

## Issue board lens (read-only external data)

The "Lens" view renders one public GitHub/GitLab repo's issues as a read-only kanban board. These rules cover the lens-specific surfaces and any future read-only external-data view.

- **Read-only external cells and headers are forked, not parameterized.** Do not add a `readOnly` flag to the DnD-coupled `SwimlaneRow` / `BoardCell` / `ColumnHeader`. The lens uses dedicated read-only siblings (`LensSwimlaneRow`, `LensColumnHeader`, the cell markup inside `LensSwimlaneRow`, and `LensIssueCard`) that copy the visual treatment without any drag hooks, add-card affordances, kebabs, rename, or edit pencils. The interactive board components stay focused on the editable board; the lens components stay focused on rendering. This is distinct from the `CardItem` `readOnly` prop (§ Read-only mode for interactive components), which applies to a *single* component used in both contexts — when an entire family of components would need DnD-removal branches, fork instead.
- **Lens issue cards encode state with a pill + surface, never the priority border or opacity.** Issues have no Visiban priority, so `LensIssueCard` uses `border-line` (neutral) on all sides — never the priority/status border colors. Open vs. closed is carried by a state pill spelled as a word (open → `border-transparent bg-success/15 text-success-on-tint`; closed → the neutral state pill, `border border-line text-fg-tertiary`) plus the card face: open `bg-surface`, closed `bg-sunken` with a `text-fg-secondary` title. Hover is `hover:border-line-emphasis`, never a fill. No whole-card opacity (#2238, § Card aging ramp). The card is a `role="button"` div (so the MR chip can be a nested `<a>`) with `cursor-pointer hover:border-line-emphasis` (never a hover fill, `cursor-grab` or `hover:-translate-y-0.5`) and opens `issue.url` in a new tab via `window.open(url, "_blank", "noopener,noreferrer")` only when `isSafeHttpUrl(issue.url)` passes (see *Externally-sourced URLs*); an unsafe URL is a no-op.
- **External-data provenance banner sits outside the grid scroll container.** Any view rendering data sourced from outside Visiban must show a non-dismissible `role="status"` banner with the source identity (`LensProvenanceBanner`: provider glyph + "Read-only lens · {repo}", repo linking to the source). Place it between the toolbar and the scroll container — never inside it (same placement rule as § Mode indicator banners) — so it never scrolls away. When the source truncated the result, append a `text-warning` "Showing first N issues" notice inside the banner. A note that reports data left out by a limit (the lens's "Closed issues hidden" / "Showing up to 50 most recently updated closed issues", #1581) is one line, `min-w-0 truncate` with the full text in `title`, so it never pushes the freshness/Refresh control out of view; it uses `text-info`, not `text-fg-tertiary`, because it names an omission rather than ambient metadata; and it gets no live region of its own, because the banner's `role="status" aria-atomic` already announces it. The banner fill token is `bg-primary/15` (matching the Mode Indicator Banner spec — `bg-primary` tracks the active theme; do not use `bg-info`), and it carries `aria-atomic="true"` so it is announced as a single unit.
- **Multi-lane duplicate cards carry an explicit indicator.** When an issue maps to more than one swimlane value (e.g. multiple matching labels) it renders once in *each* lane — never hidden, never collapsed to one lane. Each duplicate shows a `🔗 ×N` indicator (`text-xs text-fg-muted`, `title` explaining the count) so the reader knows the same issue appears elsewhere. `laneCount` is `issue.swimlane_keys.length`. The `🔗 ×N` span must carry an `aria-label` describing the lane count (e.g. `Appears in 3 lanes`) and the `🔗` emoji itself must be `aria-hidden="true"` — the `title` alone is not a reliable accessible name.
- **Synthetic "(none)" lanes render last.** Backend axes use synthetic keys (`__none__`, `__nostatus__`) for issues with no value on the pivot dimension, and arrive with friendly labels already set (e.g. "(no milestone)", "No status"). Sort these lanes to the end of the grid so real milestones/assignees lead — never interleave or drop them. Match on the *key*, not the label.
- **One shared `relativeTime()` helper — never fork a second formatter.** "Synced X ago" freshness (`LensFreshness`) and the connection-status popover ("Last update: X ago") both import `relativeTime(ts, now)` from `src/utils/relativeTime.ts`. The `now` argument is explicit so callers stay deterministic in tests. Do not re-implement relative-time formatting inline in any new component.
- **The lens reuses the board's shared Row-2 toolbar — no separate lens toolbar row.** The lens's interactive controls (pivot dropdowns, Filters toggle, layout toggle) render in the shared `<nav aria-label="Board toolbar">` (in `BoardView`, via `LensToolbar`), so switching Board↔Lens doesn't reflow the chrome. `BoardView` drives them from the URL params it reads directly (`?column_dim=`/`?swimlane_dim=`/`?state=`/`?milestone=`/`?q=`) + the shared `useCardLayoutPref` — **do not lift `useLensData` up or portal controls.** The one data-dependent control, freshness ("Synced X · Refresh", `LensFreshness`), lives in `LensProvenanceBanner` (next to `useLensData` inside `LensView`), not on Row 2. The Filters button (board-styled, carrying the shared `FilterIcon` from `toolbarIcons.tsx` like the board Filter button (#2321), with the always-visible filled `bg-primary text-on-primary` active-count badge, no `ActiveUnderline` because it is labeled like the native Filter button) toggles the `LensFilterBar` row, whose visibility is local `lensShowFilters` in `BoardView` (initialized `true` when a filter param is active on mount); filter *values* stay URL-persisted. **There is no responsive fold and no kebab (#2302)**: `LensToolbar` wraps like the board's Row 2 (see § Top chrome, "Row 2 wraps") and every control stays inline at any width; the lens pins **no** `ConnectionStatus`, because it is a pull-only mirror with no WebSocket. The Collapse split button uses SplitButton's `size="toolbar"` (`h-9`, bordered, `text-sm px-3`). Row-2 icons come from `components/Board/toolbarIcons.tsx` — import them, never re-inline an SVG copy, or the two toolbars drift. `f` toggles the lens filter row (routed by `viewRef` in `BoardView`) and `⌘⇧L` the layout, matching the native chords.
- **Lens "compact" is the board's `useCardLayoutPref` — multi-card-per-row, not just smaller cards.** Compact reuses `user:prefs:card-layout` (shared with the board). The old `user:prefs:lens-density` is deliberately **not** migrated: the hook has one instance (`BoardView`) feeding both surfaces, so honoring it would silently flip the *native* board into compact for someone who only set it on the lens. The lens cell is `compact ? "grid grid-cols-[repeat(auto-fill,minmax(120px,1fr))] gap-1.5" : "flex flex-col gap-2"` — **auto-fill/minmax, not a fixed 2-column grid** (#1065): lens columns are resizable (see the resizing rule below), so a fixed track count would either waste space at a wide column or crowd cards at a narrow one. The `120px` floor matches `MIN_LENS_COL_WIDTH`'s single-track case; below that, `auto-fill` naturally collapses to one card per row.
- **Lens columns and the swimlane-label sidebar are resizable, forked read-only from the native board (#1065).** `useLensViewPrefs` (`frontend/src/hooks/useLensViewPrefs.ts`) persists `{ sidebarWidth, columnWidths }` to board-scoped localStorage (`board:{boardId}:lens-view-prefs`) — a separate store from the native board's `useViewPrefs`, not an extension of it, because lens `columnWidths` is keyed by the pivot-derived column **string** key (e.g. `"in_review"`), not a numeric board Column ID. Clamp ranges are lens-specific and *not* the native board's: sidebar 120–480px, columns 160–640px (`MIN_LENS_SIDEBAR_WIDTH`/`MAX_LENS_SIDEBAR_WIDTH`/`MIN_LENS_COL_WIDTH`/`MAX_LENS_COL_WIDTH` in `lensDims.ts`). Defaults (200/280) intentionally match the pre-#1065 fixed widths so upgrading users see no shift until they resize.
  - **The drag affordance is `LensResizeHandle`** (`frontend/src/components/Board/Lens/LensResizeHandle.tsx`), a forked, simplified sibling of the native board's `ColumnSeparator`/`RowSeparator` — `role="separator" aria-orientation="vertical"`, absolutely positioned (`absolute inset-y-0 right-0 w-2 translate-x-1/2`) so it adds **zero layout width**: the `translate-x-1/2` centers its hit target on the column's own right border instead of widening the column. Unlike the native separator, a plain click is a no-op — there is no insert-column affordance to disambiguate from a drag, so the handle has no `DRAG_THRESHOLD` and no click handler at all.
  - **One handle per column, in the header only — never re-rendered per swimlane row.** The native board renders `ColumnSeparator` as a real 8px grid track (16px at the outer edges) in every row (for its continuous cross-row hover-highlight strip); the lens deliberately does not, because that strip is exactly the "per-row separator" affordance the issue asked to avoid. Every row already reads the same shared width state (`LensGrid`'s `colWidths: Map<string, number>`, passed to `LensSwimlaneRow`), so one handle in the header keeps every row in sync. The accepted tradeoff: the resize hover-highlight is visible only across the header, not down through the body rows — deliberate simplification for this lower-chrome, read-only view, not an oversight.
  - **Keyboard resize**: `ArrowLeft`/`ArrowRight` nudge by 8px, Shift+Arrow by 32px, while the handle has focus (it's a real tab stop, `tabIndex={0}`) — the only way to resize without a mouse.
  - **Row-height resize is out of scope for #1065** — explicitly deferred pending confirmation with the requester (the issue marks it "optional / confirm"). Because the cards get narrow, compact *also* strips the label/milestone/branch-MR/avatar metadata (keeping `#number` + state pill + multi-lane indicator + single-line title); on the lens one pref drives both layout + metadata (no per-board `card_density`). The empty-cell `—` marker carries `col-span-full` so it stays centered in the compact grid.
- **The current milestone lane is promoted, not recolored — sort-to-front + a "Current" pill.** When `swimlane_dim == milestone`, the lane the backend marks `is_current` sorts to the top of the grid (`LensGrid.tsx`) and carries a `Current` pill on its label panel (`LensSwimlaneRow.tsx`, `bg-primary-emphasis/20 text-info` — the same token pair as the filter active-count badge; do **not** introduce a new hue for it). Position is the primary signal and the pill is the secondary one, so the meaning survives without color (#969): the pill carries the literal word "Current" plus a `title`, never color alone. Only one lane is ever marked. The synthetic "(no milestone)" lane still sorts **last** and is never current. `is_current` is additive on the axis payload — absent means false, so an older client simply renders the old order.
- **Lens collapse/focus stay URL-persisted.** Swimlane collapse (`?lens_collapsed=`, comma-joined `encodeURIComponent`'d keys) and single-lane focus (`?lens_focus=<key>`) live in the URL because a lens link is a shareable snapshot. Both are validated against the live `data.swimlanes` key set on read and silently dropped when stale. The collapse chevron + focus crosshair are **forked read-only affordances** on `LensSwimlaneRow` (copy the native `SwimlaneRow` SVGs; chevron always visible, crosshair hover-reveal with `focus:opacity-100`); focus renders a `LensFocusBanner` (`bg-primary/15`, **not** `bg-info/15`) stacked *below* the provenance banner and outside the scroll container, with Escape-to-exit at `useEscapeStack` priority 12.
- **Lens cards may carry a nested link; switch the card root to `<div role="button">`.** When a lens card surfaces a secondary external link (e.g. the pipeline MR chip), the card root must be a `<div role="button" tabIndex={0}>` with an Enter/Space `keydown` handler — not a `<button>` — because interactive nesting inside a `<button>` is invalid HTML. The nested `<a>` carries `onClick={(e) => e.stopPropagation()}` so the chip opens its own URL while the card body opens the issue; never `preventDefault` the anchor (preserves middle/cmd-click). **Pipeline evidence renders on the existing metadata row** — branch as a `font-mono text-fg-tertiary` `<span>` (`⎇` glyph, `max-w-[10rem] truncate`, full name in `title`), MR as a `text-info` `<a>` (`!{number}`) — never a new stacked row; the left cluster may `flex-wrap` as the sole permitted exception to the single-row metadata rule, justified by the VoC "placement must be explainable" requirement. **closes-vs-references is distinguished by glyph + `aria-label` only, never color** — both stay `text-info` (`⮰` closes, `↗` references). **Empty lens cells render a centered `text-fg-faint` em-dash** (`aria-hidden`, `select-none`); the count lives in the column header stat. The lens cards stay neutral (`border-line`, no priority colors) and the pipeline column headers stay neutral too — do not invent a frontend `pipeline → color` map (the payload axis carries no color; coloring would reintroduce the native-board coupling the lens was forked to avoid).

## Placement limits on the board (#1150)

The "Lane over limit" row of § System signals reserves the signal; this section defines it.

- **Swimlane limit state line.** A swimlane with a `wip_limit` or `weight_limit` renders at most one limit line in its band's stats (`SwimlaneLimitStat` in `SwimlaneRow`, #2271), worst offender first: Over WIP > Over weight > At > Under, the same priority as § Column headers. Under: `WIP {n} / {limit}` in `text-fg`. At: `WIP {n} / {limit} · at limit` in `text-fg`, shown only when the board opts in with `Board.show_wip_at_limit`, exactly as on the collapsed column strip (the expanded column header ignores it, #972); off (the default), an at-limit row reads like Under. Over WIP: `WIP {n} / {limit} over` in `text-warning-on-tint` (`⛔ ` prefix when the row's WIP mode is hard, as on the column header; no glyph otherwise). Over weight: `Weight {n} / {limit} over` in `text-warning-on-tint`. The band's stats cluster is already `font-semibold`. There is no top accent line and no meter (#2275 removed the danger accent: the board redesign shows the lane's over state as warning text, matching the column header's `8 / 6 over`, #2270). The word "over", not the hue, carries the state, and both over-limit states always show, whatever the opt-in. **Number rollup (#2275):** after the limit line, `{total} open` in `text-fg` (`data-testid="swimlane-rollup"`; the title names the field, and an `sr-only` "{field}: " prefix gives screen readers the same, since an `aria-label` on a plain span is not announced), the board's `swimlane_rollup_field` summed by `laneRollup` (`utils/laneRollup.ts`) over the lane's cards not in a done column, formatted with the field's prefix/suffix/decimals; omitted when no number field is chosen or the chosen field was retyped away from number (`resolveRollupField` returns null). The setting itself is § Board-level field chooser settings row. The line always names the metric that produced the state (`laneLimitState` returns it): a weight-only row, Over weight and a weight exactly at its limit show the weight numbers. The text carries the state and never truncates (`shrink-0 whitespace-nowrap`); there is no meter. A collapsed row keeps only the two over-limit lines.
- **Blocked drop target (warning treatment, #2326; owner ruling 2026-11-16: the spec wins).** While a card drag is over a cell whose drop would trip a block or hard limit (`utils/placementLimits.ts` `placementVerdict`, the client mirror of the server rule), the cell takes the spec's drop-blocked treatment, `border-dashed border-warning bg-warning/20`, and the open-target tint, the placeholder and the cell's card-count badge stand down. It is a warning, never danger: the move is refused before anything breaks, the same reason § Move-blocked toast stays amber. The tint is never color only: an `aria-hidden` label, `text-xs font-medium text-warning-on-tint` on an opaque `bg-canvas rounded px-1.5 py-0.5 shadow` pill, names the strictest limit numbers first (`⚠ WIP limit 5/5 · Payouts`, `⛔` for hard), so a long name is what truncates. An empty cell's drag slot follows with `border-warning`. Named deviation from `components.png`: the reason is a corner pill, not the spec's centered amber line. The treatment only predicts; a refusal still raises `MoveBlockedToast`. Screen-reader and keyboard users get the same verdict from the drag live region (`Over column 'X', swimlane 'Y'. Swimlane "Y" is at its WIP limit (5/5), admins can override.`), and the drag-over throttle must never drop an announcement that carries a verdict.
- **Swimlane hard block in the toast.** The § Move-blocked toast hard-block rules (`⛔`, no override link, the resolution line) apply to `swimlane_wip_hard_blocked` exactly as to `wip_hard_blocked`; the resolution line names the swimlane ("To unblock, move a card out of {swimlane}, or ask an admin to raise the WIP limit."). Swimlane variants name the swimlane in the body (`Swimlane "{name}" is at its limit of …`). When one move trips several limits, the server's body names the strictest and the toast names the rest on a `text-xs text-fg-tertiary` "Also: …" line in the same toast, and in its assertive announcement (§ Toasts). Weight limits have no hard mode, for rows as for columns.
- **Edit Swimlane → Limits.** The Limits section sits after the Swimlane fields section and always renders. It holds the paired WIP / Weight fields per § Paired numeric settings fields, each helper slot reading `Now {n} · 0 = no limit` and switching to a `text-warning` "Already over: …" note when the typed limit is below the current count, worded for the enforcement currently selected (not enforced / admins can override / everyone), never promising a block that will not happen; a "Columns that count" fieldset of native `accent-primary` checkboxes (default: every column not marked done; an empty selection is refused in the helper slot, with `aria-invalid` on the first box and focus moved to it); and the enforcement radio cards per § Radio groups: **Follow board settings** (the default, `null`, with a "Board now: …" line stating both the WIP and the weight behavior), **Block, admins can override**, **Block for everyone**. There is no warn-only option (#2048). The modal body is one scroll region per § Modals and dialogs (#1455: `role="region"`, `aria-label`, `tabIndex={0}`, bottom fade) and the footer stays fixed.
- **Scroll regions in a dialog use `role="region"`.** Inside a dialog or popover, § Modals and dialogs rule (a) (#1455) governs: `role="region"` with an `aria-label`. The `role="group"` preference in "Focusable scroll regions" (§ Multi-step import wizards) applies to in-page scroll containers, not to a dialog's body.
- **Retry and the failed socket (#2276).** `BoardLoadError`'s Try again calls the board hook's `reload` (`load` clears `error` first), never `window.location.reload()`.
- **Offline pauses moves (#2325; owner ruling 2026-11-16, spec § States).** While the socket is `reconnecting` or `failed` (BoardView's `movesPaused`, the same states that show `BoardOfflineBanner`), the board's `DndContext` gets no sensors (column and lane drags pause too), a drop already in flight is canceled with "Move canceled, moves are paused while the board is offline" in the drag live region, and every Move path is disabled, never hidden: card menu and ⌘K Move to… and the bulk toolbar's Move to... through `CardActionContext.movesPaused` (`MOVES_PAUSED_REASON`, "Moves are paused while the board is offline", on the item's reason line), and the card detail Move button and the peek sheet's Move / Move earlier / Move later (`movesPaused` prop: `aria-disabled` plus a click guard, never native `disabled`, with `aria-describedby` a visible `text-fg-secondary` line "Moves are paused while the board is offline." rendered only while paused). The peek sheet's Move card and Move earlier / Move later also use `aria-disabled` plus a handler guard, never native `disabled`, while a move is pending and, for a step, at the end of the cell, so the pressed button keeps focus (#1437, #2611). A role or maintenance reason outranks it. The banner reads "Offline. Reconnecting. Moves are paused until the board is live again." (`failed`: "Offline. Live updates are off and moves are paused. Reload the page to reconnect."), and the toolbar's `ConnectionStatus` reads Offline in both states (§ Connection status indicator): the two say the same word, and the text, not the disabled look, says why.
- **Keyboard move (#2327).** No new shortcut keys: the keyboard path is the card menu (Menu or Shift+F10), Move to… For one card its submenu lists "Move earlier in this cell" / "Move later in this cell" first (`reorderChoices`, only the steps that exist), then one separator, then the columns; the submenu is then named "Move within this cell or to a column" (otherwise "Move to column"). A step uses the phone peek sheet's slots (`cellOrderOf`: the previous visible card's `position`, or the next one's + 1, never index ± 1), announces "Card '{title}' moved to place {n} of {count} in its cell" in the drag live region (nothing on a refusal: its toast speaks) and returns focus to the card. Lane moves live in the card detail Move popover; the bulk toolbar moves columns only; there is no drag keyboard sensor. Sub-column stops wait on #1102 and #2278 (both open).
- **Drag states (#2276, spec tokens #2326).** The lifted `CardItem overlay` tilts `rotate-2` with `!-translate-y-1` and takes the deep shadow as the `shadow-2xl` class (no inline `boxShadow`, which would override it); under `motion-reduce` the tilt and lift drop to `rotate-0` and no lift, and the shadow stays (it is not motion). The source card stays in place at `opacity-25`. A cell under a card drag that would not trip a limit takes the spec's drop-target treatment, `border-dashed border-info bg-primary/20` (the token pair of § Design tokens' "drop target" row, never `bg-info/15` or `border-primary-emphasis`), and shows a placeholder where the card lands (`data-testid="cell-drop-placeholder"`, `aria-hidden`, `rounded-md border border-dashed border-info bg-primary/40`, a stronger fill than the cell's `bg-primary/20` so it reads as a block, as tall as the lifted card's measured height, at least 40px). A drop always appends (`handleDragEnd` sends the cell's count), so the placeholder sits after the last card, not where the spec's picture draws it; an empty cell's drag slot takes the same tokens and is the placeholder; before the pointer is over it (neither open nor blocked) the slot is a dashed `border-line-boundary` outline, because the border is the only cue that a card can land there (per the `border-line-strong` contrast rule near the end of this file, #2505). A blocked cell takes the warning treatment above, never the open one.

## Gated stages and tracks (#2278, #1102, #1920)

- **Vocabulary (#2543): a stage is a column; its Stage tab holds its sub-columns and tracks.** In user docs (`docs/features`, `docs/api`) and changelog fragments a stage with sub-columns is a "gated stage", never "split stage". In the UI it is just "stage" or "column" and never "gate"/"gated" (see the "Gate is internal" rule below); code comments and test titles may keep the internal "split" terms. Keep the **Stage** tab and **Stage settings…** names. In user-facing copy and docs reserve "checklist" for a card's checklist, call a multi-select field's picker a "multi-select list", and call a column policy's list "entry criteria".
- **A hint at a point of choice is static text (#2542).** Where a user picks between a checklist item, a child card, sub-columns and tracks, one `text-xs` line (`text-fg-muted`, including the three new Stage tab lines; the Stage tab's older helper lines are pre-existing `text-fg-tertiary` and were left alone) is tied to its control or section by `aria-describedby`. No link, button, dismiss control, banner or extra tab stop.
- **Derive, don't store.** Sub-column placement, track state, gate counts and the keyboard stops come from `utils/stages.ts`. A card's sub-column is `gates_passed` clamped into range (`cardSubColumnIndex`), so a stale copy never disappears from the grid. A sub-column renders its cell's cards in `position` order; `position` is never per sub-column.
- **One Move path.** Drops on a sub-column (`cell:{col}:{lane}:{index}`), the card menu's "Move on to / Move back to" steps and the entry-criteria confirm replay all call `moveCard(..., gatesPassed)`. Omit `gatesPassed` for "server default" (a plain column, a drop on an unsplit cell); `moveChoices` / `parseMoveChoice` encode a sub-column stop as `stop:{column}:{index}`, and keep the four-argument call when it is undefined. Never add a second move endpoint or a client-side refusal.
- **Warn and record only.** Leaving a stage before its last sub-column raises the `gates-open-warning` toast after the move succeeds, always through `utils/stages.notifyLeaveWarning` (BoardView's shared move wrappers, and after `moveCardsToColumn`), never a per-surface copy. Do not block, confirm or disable the drop for it until #1923 adds a board setting.
- **A split cell registers no droppable of its own.** Each sub-column is its own droppable, and the cell's is `disabled`, so `closestCenter` never sees two nested targets under the pointer.
- **Track chips carry state by icon and fill.** Done is a check on `bg-success/20` with `text-success-on-tint`, open a hollow circle with a `border-line-boundary` edge, not applicable a dash on `bg-surface-hover`. Every chip's accessible name spells the state out ("Technical: done"); the phone face prints it too. Chips are not controls: never give one a tab stop. An `sr-only` line before the list says where the value is set ("Tracks, set in the card's Custom fields."), once per card rather than once per chip, so a board of cards stays terse for a screen reader; each chip's `title` repeats it for pointer users as a hover supplement, not the only path. The visible, keyboard-reachable path is a static `text-xs text-fg-muted` line where track rows appear on a card surface: "Set in the card's Custom fields." under the peek's Tracks list and "Tracks show as chips on the card." in the card detail's Custom fields section (only when the card has tracks; no focusable element) (#2542). A label for a group of items inside a `role=button` card goes in an `sr-only` sibling, never in an `aria-label` on the group container: a child's `aria-label` replaces its content in the card's computed name.
- **Dimension fields are tracks, not fields.** Filter `is_dimension` out of every generic custom-field list, pinned count and `show_on_card` row (`isDimensionField`). `CardItem` does this once, at the top, for all of its field rows.
- **Stage settings save through `PUT .../columns/{id}/stage/` only.** Errors are mapped by string `code` first (`version_conflict`, `column_not_found`), then by field key; never parse the message text. "Add track" creates the dimension dropdown before the stage save and records its id on the row, so a retry does not create it twice. UI copy says "done"; the API value is `satisfied`.
- **"Show sub-columns" is a per-browser view pref** (`useViewPrefs`, absent = on). The View menu shows the switch only when a board has a gated stage. It applies at every width: off unsplits the grid cell and removes the phone sub-column switcher (#2531).
- **A stage editor that can save a partial view is disabled until every round-tripped input has loaded.** `PUT .../stage/` replaces the lane exceptions it is sent, so `StageSettingsPanel` is rendered only with the board's full swimlane list (hidden lanes included) and field list; callers pass them explicitly and the Stage tab otherwise shows a can't-load state with no Save. Never fall back to `?? []` for an input the save sends back.
- **A modal tab with its own Save keeps a fixed footer and never discards the other tabs' drafts.** The Stage tab portals Save stage / Cancel into `EditColumnModal`'s footer and stays mounted (hidden) across tab switches so its draft survives. Save stage closes the dialog only when Settings and Policy are clean; otherwise the dialog stays open with a polite "Stage saved" status, the panel remounts on the saved column (`stageKey`) so a second save sends the new sub-column ids, focus moves to the Stage tab (the remount destroys the focused Save stage), and the saved column (with every `remapped` entry so far) reaches the board on the Settings Save or on any close (#2368). While saving, its inputs are disabled and the panel is `aria-busy`; save errors use `role="alert"`.
- **A mutation that remaps other people's cards shows an inline consequence summary before commit** ("3 cards will move from Review back to Doing."), counted by the server when it can (`GET .../stage-card-counts/`, archived cards included and named: "3 cards (1 archived)", #2368) and otherwise from the cards already on the board, mapped with the server's rule.
- **Sub-columns reorder with ↑ / ↓ icon buttons, never drag** (#2368), the `ColumnPolicyEditor` pattern: the first ↑ and last ↓ are `aria-disabled`, focus stays on the moved row's button, and the move is announced in an `sr-only` status. A card follows its own sub-column, so a reorder alone shows no consequence line.
- **A track's name is its dimension field's name** (#2382). Track rows are inputs whose `aria-invalid` and `aria-describedby` (to one `role="alert"` line) mark only the rows the shown message covers (an empty name is reported first); a name must be non-empty and unique against the other tracks and every other board field. Save PATCHes each renamed field first and records the saved name on the row, so a retry does not rename twice; if the stage save then fails, the error starts "Track names were saved." because the rename already landed.
- **Segmented switches use `aria-pressed` buttons in `role="group"`** (BoardViewMenu `segment()`, the phone sub-column switcher), or the full roving `radiogroup` pattern with arrow keys. Never `role="radio"` without the arrow keys. Name each segment with its count ("Doing, 3 cards") and announce the change in a polite status.
- **Selected or current stage and sub-column steps use `bg-primary-emphasis/15`–`/20` + `text-info` (or `text-fg` on a bordered step) + a non-color mark** (`ActiveMark`, a dot). Never `bg-info/10`. One current signal for assistive tech: `aria-current="step"` or sr-only "(current)", not both.
- **Switches are `components/Common/Toggle`**, never a hand-rolled `role="switch"`. A switch row in a menu is a `<label htmlFor>` so the whole row is the target.
- **Controls in a modal reachable from a phone get `max-sm:min-h-11`**, link-style buttons included (pad them). A limit that disables a control (4 sub-columns max, 2 min) uses `aria-disabled` + `aria-describedby` pointing at the reason text, not bare `disabled`.
- **Vocabulary: sub-column, done, waiting.** "Gate" is internal (code, API fields such as `gates_passed`); it never appears in UI copy, toasts or history notes. Never "satisfied" in UI copy. A lane-derived not-applicable says "for this swimlane" in text, not only in a tooltip.
- **A card's move target on a gated cell is a `MoveStop`** (`utils/stages.moveStops`). Every Move surface (peek, phone, card menu, bulk toolbar, card detail) offers stops and sends `gatesPassed`; a change of sub-column alone is a move, never a silent close. Move earlier / later stays inside the card's sub-column (`cellOrderOf(..., column)`).
- **`CardItem`'s memo comparator must cover every prop the face renders**, including `trackStates`, `trackStatesSpelledOut`, `gateProgress`, `gates_passed` and `version`. Compare derived arrays by content: the phone board builds them per render.

- **A gated cell without its header row names each sub-column itself (#2366).** In a read-only grid such as the share view, give each sub-column cell `role="group"` and `aria-label="{stage}: {sub-column}"`, and fold the count into the header item's accessible name ("Doing, 3 cards"). Track chips on the anonymous share view name tracks only and never imply a state: the public payload carries no per-card track state.
- **A filter that matches "any of" a card's child items says so (#2367).** The Track state row carries helper text ("Cards with at least one track in a chosen state") and its chip reads "Any track done".
