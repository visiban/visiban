## Modals and dialogs

- **A control that unmounts itself moves focus to a successor and announces the change (#2211 ux-review).** This includes a dropdown emptied by its own selection (adding the last candidate unmounts "Add a member": focus goes to the new row's Remove). A Remove, Unassign or ✕ that takes its own row or chip out of the DOM moves focus, in the same handler's commit, to a stable target: the control that replaces it (the "+ Add" pill), else the next row's equivalent, else the previous, else the containing group or section (`tabIndex={-1}`). Never let focus fall to `<body>`. Announce the change in a polite `role="status"` line ("Removed Mia Reyes from default team."). Patterns: `LaneTeamAssignee.tsx`, `SwimlaneDefaultTeamSection.tsx`.
- **`role="group"` never goes on a `<ul>` or `<ol>` (#2211 ux-review).** It replaces the list role, so a screen reader loses "list, N items". Put the group (and its `aria-label`) on a wrapping `<div>` and keep the list inside it.
- **A warning row is linked to its actions with `aria-describedby` (#2211 ux-review).** When a row carries a warning line (deactivated, no access, skipped), give the line an id and point each action button in that row at it, so "Remove Dan Kovacs from default team" is read with "No access to Delivery: skipped on new children". Rows without a warning carry no `aria-describedby`.
- **A `phoneBack` full-screen sheet keeps its footer reachable (#2211 ux-review).** With `phoneBack`, ModalWrapper's content wrapper is `max-sm:flex-1 max-sm:min-h-0 max-sm:overflow-y-auto max-sm:flex max-sm:flex-col`, so the body scrolls inside the sheet and never pushes it past the viewport; the form inside is `max-sm:flex-1` and its footer `max-sm:mt-auto`, pinned to the sheet's bottom edge. With the keyboard open (a short viewport) the Save/Add button is still reachable by scrolling the body, not the page. A sheet with `noPadding` (Edit Swimlane) builds the same layout itself: scrolling body, footer outside it.
- **A phone sheet has a header and 44px footer buttons (#2206 rule 7, #2211).** A dialog that becomes a full-screen sheet below 640px passes `phoneBack` to `ModalWrapper` (a `sm:hidden` "‹ Board" button named "Back to board", 44px, before the title, beside Close), and every footer button carries `max-sm:min-h-11`. A destructive footer action (Delete) gets its own row on phone (`max-sm:flex-col`), not a squeeze beside Cancel and Save. A save error sits in the pinned footer, next to Save, with `role="alert"` on the message, so it is not below the fold.

- **An inline confirm that replaces its trigger takes focus on open (#863 ux-review).** `useConfirmFocusReturn` covers the close; on open, focus moves into the confirm: its input when it has one (a password), else its primary button. The prompt's question is announced by the persistent `useConfirmAnnouncement` announcer (the #1435 rule), never by a live region on the prompt itself.
- **`aria-disabled` needs a handler guard (#863 ux-review).** A control kept focusable with `aria-disabled` (in-flight "Sending…", an inert Done) must ignore activation in its handler, because `aria-disabled` does not stop clicks or Enter. A result region is cleared when a new run starts, so an identical result is announced again.
- **A parent-archived state keeps its actions reachable and says why (#2447).** The tab buttons (Add child, Link existing) stay focusable with `aria-disabled`, a handler guard, no hover fill (`aria-disabled:hover:bg-<base>`), and `aria-describedby` pointing at a visible reason. The dialog fallback shows the same reason in a `<p>` that describes the submit button, hides the input fields, and disables submit. The server's `disabled_reason` always wins over client state: a card archived since the panel read it falls into this state on the next options read.
- **Never fake a re-authentication (#863 ux-review).** A "Sign in again" or "Continue with SSO" control must perform a real re-auth round trip. If the surface cannot start one, say what the user should do in text and offer no button; a page reload is not a re-verify.
- **Driving a `SelectDropdown` in Playwright (#2448).** The list closes on any outside scroll, and a click's scroll-into-view inside a scrolling settings pane counts as one, so call `trigger.scrollIntoViewIfNeeded()` before opening it, and wait for the options read to land first (a re-render closes an open list). Scope option queries to `getByRole('listbox')`: the phone's native Section select also exposes `option` roles. Reference: `e2e/child-board-verify-2448.spec.ts`.
- **A scrollable code block is keyboard-reachable (#863 ux-review).** A `<pre>` with `overflow-x-auto` gets `tabIndex={0}`, `role="region"`, an `aria-label`, and the standard focus ring, so keyboard users can scroll it and assistive tech names it.
- **A confirm whose answer is a choice, not a yes (#2054).** The Confirm/Cancel word pair below is for a prompt with one outcome. When the user must pick between two outcomes, name each one on its own button, with the group layout of the turn-on confirm: `role="group"` labeled by a polite-live prompt, the consequence of each action in its own paragraph tied to that button with `aria-describedby`, and right-aligned Cancel (Secondary), the outcome that can break something (Danger) and the outcome that can't (Primary, which takes focus on open). Each consequence paragraph leads with its button's exact label. Every action button goes `aria-disabled` with a handler guard while the request runs, and only the clicked button swaps to the progress label, so focus stays put on failure. Reference: the rotate confirm in `WebhookDetail`.
- **Enter-to-submit and Escape ignore IME composition (#2167).** While an IME composition is active, Enter commits the candidate and Escape cancels it, so neither may submit a form or close a modal. `useEscapeStack` ignores a composing Escape itself; every text-input `onKeyDown` that submits on Enter must test `!isImeComposing(e)` from `src/utils/imeComposition.ts` (it also covers Safari's `keyCode === 229`). Test with `fireEvent.keyDown(input, { key: "Enter", isComposing: true })`.
- **Escape is swallowed while an inline confirm's request runs (#2054).** Consumed, silently and with no effect: the button holding focus already shows the request running, and closing the confirm would read as a cancel and hide a failure. Opening another confirm is refused for the same reason. Reference: `escapeConfirm` and `onConfirmChange` in `BoardSettingsWebhooksTab`.
- **A request whose response is the only copy of a secret holds every way out (#2054).** The server has already replaced the secret, and nothing will ever say the new one went unseen, so Close, the backdrop, Escape, a tab switch and Back all refuse while it runs, rather than prompting: there is nothing on screen yet to ask about. Escape on a running confirm follows the rule above; every other refusal, including Escape on a create, which has no confirm to swallow it, has to be noticed from the control that was refused, so it is a `role="alert"` banner at the top of the tab, scrolled into view, and keyed so that each refusal is announced again; a status slot at the bottom of the tab would leave a dead control. Focus stays where it is. A failure that isn't a plain refusal (no response, or a 5xx) says the change may have gone through and refetches, so the screen shows what the server has before anyone retries. A failed rotate also refetches on a 4xx, because that can be the webhook having been deleted elsewhere. Actions on one view are tracked per action, never in one shared in-flight slot: another action finishing must not re-arm a request still running. Reference: `guard` and `issuingSecret` in `BoardSettingsWebhooksTab`.
- **An exit control offered with an alert sits beside the alert, never inside it, and hands focus to a landmark when it unmounts (#2127, #1772).** A way out that appears once a wait has gone on too long (`Leave anyway` on a create or rotate past `SECRET_PENDING_BOUND_MS`) is a sibling of the `role="alert"` message, linked with `aria-describedby`; the alert holds the message text only and is keyed so each refusal is announced again, while the button is not remounted by a refusal. The banner is scrolled into view when the alert first appears *and* when it changes into the version with a way out (both are effect dependencies). When the control unmounts, focus goes to a named landmark, never to `<body>`: the view's heading after `Leave anyway` (the status heading on the rotate path, `Add webhook` on the create path, or the refused way out the user tried last), and the view's heading if the request answers while the button still has focus, unless what the answer mounts claims focus first. Reference: `BoardSettingsWebhooksTab`.
- **A "may have taken effect" notice is announced through an always-mounted live slot, and its Dismiss returns focus (#2127, #1421, #1435).** A banner that says an action the user stopped waiting for may still have landed (`webhook-left-pending`) is written into a persistent `sr-only` `role="status"` slot at the moment it appears (on `Leave anyway`). The visible banner carries no live role, so the sentence is read once and reliably. Its Dismiss moves focus to the view's heading, and the button is sized `px-3 py-1.5` like the tab's other secondary buttons.
- **Remote-change announcers clear between batches, and the "changed" tag is short-lived and by-name (#2057, departure #2403).** An announcer that coalesces changes made elsewhere (`ANNOUNCE_COALESCE_MS`) empties its region when a new batch starts, so a batch with the same count as the last is still a change and is read. The row tag ("Changed just now") lasts `CHANGED_ELSEWHERE_MS` (30 s), sits on the row's metadata line rather than beside a truncating URL, uses an existing token (`font-medium text-fg`), and carries the changer's name (`Changed just now · by Maya`, #2403): the frame holds `changed_by` as an id only, so the name is looked up in the board's member list the modal already has (no new request). An id that matches no member reads `by another admin`, a null id (the dispatcher) names no one, and a raw id is never shown. A socket reconnect re-reads the list without tags or per-row announcements, as window focus does; it then shows a dismissible `N webhooks changed while you were away` banner when the re-read differs from the list on screen. While the socket is `reconnecting` or `failed` the tab shows `Live updates paused · Updated N min ago` with a Refresh button. An announcement names the new status without the host (`Webhook 2 of 3 is failing: 3 deliveries in a row.`). An open webhook detail gets a dismissible banner for a non-delete change (`This webhook was changed elsewhere by Maya. It is now turned off.`). Departure from Part 9 (#2403): the paused, away and detail banners carry no `role="status"` of their own; they are announced through one always-mounted `sr-only` state slot (`data-testid="webhook-state-live"`), because a region that mounts with its text is not reliably read (#1421).
- **A banner that replaces a vanished subject takes focus (#2057).** When the item an open detail view shows disappears (deleted in another session), the banner that replaces it takes focus on a `tabIndex={-1}` sentence, from an effect keyed on the item going missing, and is announced through the always-mounted slot above. Focus moves only if it was inside the tab or had already fallen to `<body>`; focus elsewhere in the dialog is left alone. The announcement is cleared when the user leaves the banner, so the next disappearance is read again.
- **Departure from 1.3 UI spec Part 9 in the Webhooks tab (#2403).** Everything in Part 9 is built (by-name tag, paused state, changed-while-away summary, detail-view change banner, status-naming announcements). The one deliberate departure: the paused, away and detail banners carry no `role="status"` of their own and are announced through the always-mounted `webhook-state-live` slot (#1421). Dismissing the away or detail banner moves focus to the view heading.
- **Confirm on a restoring action (#863, Part 8 departure 23).** The rule below confirms only the transition that removes access. Turning a webhook back on is confirmed anyway, because it resumes sending data off the server, can skip events (`cursor_expired`) or change the owner (`creator_lost_access`, which also asks for the current password, or a fresh SSO sign-in for an SSO-only account). The confirm says which of those happens. For an SSO-only account the take-over sends no password and the server checks for a recent provider sign-in; the UI says so and, when it is not recent, tells the user to sign in again with the provider rather than offering a button that cannot do it. Reference: `WebhookDetail`.
- Backdrop: `fixed inset-0 bg-backdrop/60 z-50`
- Panel: `bg-surface border border-line rounded-lg shadow-xl`
- Consistent padding: `p-6` for content, `pb-4` for header
- Close button: icon-only variant, top-right corner
- Footer layout: `flex items-center justify-end gap-3` — always `gap-3`, never `gap-2`
- **The backdrop dismisses only on a press that began on it (#2095).** A press that starts inside the panel and is released on the backdrop (a color picker drag, a text selection) fires its click on the backdrop, their common ancestor. `ModalWrapper` records the press origin on `mouseDown` and its click handler requires it. A test that clicks a `ModalWrapper` backdrop must `fireEvent.mouseDown` it first; `userEvent.click` already does.
- **Fixed-height tabbed modals** — when a modal contains tabs with variable content height, give the panel a fixed height (`h-[85vh] max-h-[640px] min-h-0`) rather than only a max-height. This prevents layout jumping between tabs. The scrollable content region uses `overflow-y-auto flex-1` and the panel uses `flex flex-col`. Never use `max-h` alone on a tabbed modal panel.
- **A scroll region inside a popover or dialog must be reachable and visible (#1455).** (a) Make it keyboard-focusable: `tabIndex={0}`, `role="region"`, an `aria-label`, and `focus:outline-none focus:ring-2 focus:ring-inset focus:ring-primary-emphasis`. When it overflows on open, focus it rather than the panel, since a focused ancestor scrolls the page instead. (b) Show an overflow cue: a `h-8 bg-gradient-to-t from-surface to-transparent pointer-events-none` fade pinned to its bottom, rendered only while `scrollTop + clientHeight < scrollHeight`. Never rely on the native scrollbar, which macOS hides. **The fade must never hide a focused control (#2180):** the region sets `scroll-pb-<n>` equal to the fade height (`scroll-pb-8` for the `h-8` fade), and the card detail body, whose fades are `h-6` top and `h-10` bottom, sets `scroll-pt-6 scroll-pb-10`; without it the browser scrolls a focused control to the region's edge, under the fade (Tab, arrow-key `focus()` and `scrollIntoView` all honor scroll-padding). A sticky fade inside padding adds the padding too (see #2179 below). Cover each new region with a Vitest class assertion that pins its `scroll-pb` class. Playwright short-viewport cases in `e2e/overflow-fade-focus.spec.ts` cover EditSwimlaneModal, CardDetail, EditColumnModal, CustomFieldQuickEditPopover, AnchoredMenuPanel (an assignee facet), SingleSelectDropdown (`portalMenu`) and MultiSelectDropdown (#2186); each was confirmed red with its `scroll-pb` class removed. Add one for a new host, using `walkClearOfFades`, which fails unless a fade was mounted at least once (so a case cannot pass because the list did not overflow) and stops once the fade unmounts at the end of the list. `SelectDropdown` has no browser case yet: its four role options only overflow a viewport near 150px tall, and reaching one needs board or group settings fixtures. The earlier "failed on every run" result came from a helper that treated an unmounted fade as a failure, so it is not evidence the case is impossible; its `scroll-pb-8` is pinned by Vitest only until someone adds the case. (c) A popover that closes on outside scroll with a capture-phase listener must ignore scrolls whose target is inside the panel, or scrolling its own list dismisses it. **Named exception to (a):** `MultiSelectDropdown`'s list is not a Tab stop, because it follows the ARIA combobox pattern: focus stays in the search combobox, whose arrow keys move `aria-activedescendant` and scroll the active option into view, and Tab there closes the menu. A second Tab stop on the list would break that keyboard model, not complete it. A popover whose list is reachable only by scrolling has no such alternative and is not covered by this exception.
- **Anchored `fixed` popovers are sized to content and placed from a measurement (#1455).** Cap the scroll region at the visible viewport with `visibleMaxHeight()` (see the visible-viewport rule below), not at a fixed rem height or a `calc(100vh - ...)`. Measure `offsetHeight` in `useLayoutEffect` and place the panel below the trigger, else above it, else pinned to the viewport's bottom edge. **Keep the side chosen at open for as long as the panel still fits there (#1457)**: a filter that shrinks the list must not flip an upward menu below the trigger, and an upward menu keeps its bottom edge at the trigger. Choose the side again only when the list grows past that edge — never slide a panel over its own trigger. Never estimate the height from an item count. Keep it `visibility: hidden` until placed, and dismiss on window `resize` and on any scroll outside the panel (capture phase, ignoring scrolls inside it per rule (c) above). **Named exception to the scroll dismissal (#2397):** an anchored popover whose trigger lives inside a clipping element passes `ignoreScrollFrom` for that element (the card menu passes card faces, which clip the 44px ⋯ button). Scrolls of that element are ignored (the anchor may be a few px stale); every other scroll still dismisses. **Move focus only after placement**, in an effect keyed on `top !== null`, never `useEffect(..., [])`: the hidden first commit's passive effects flush before the placement re-render, and browsers ignore `focus()` on a hidden element. jsdom does not, so assert on the panel's visibility at the moment `focus()` runs (see `swimlaneCustomFields.test.tsx`), not with `toHaveFocus()`. Reuse `useAnchoredPlacement` (placement with the side lock, hidden-until-placed `top`, and the `onResize`/`onOutsideScroll` dismissals) and `useOverflowFade` (the bottom-fade flag) from `src/hooks/` rather than re-deriving them; a popup that is not a React child (the Tiptap mention list in `RichTextEditor`) uses `placeFixedElement` from the same module, re-placed from a `ResizeObserver` because its list renders asynchronously. **Named exception to rule (a) (Tab stop):** a roving-focus `role="menu"` list (`SingleSelectDropdown`'s portal menu) is reached with Arrow/Home/End, so its scroll region is not a Tab stop; rule (b), the overflow cue, still applies. Named exceptions to (a): `AnchoredMenuPanel` (#1482; its content is Tab-reachable checkboxes and buttons that scroll into view on focus, so the region is not a second Tab stop. A portaled panel sits at the end of `<body>`, so Tab off its last control, or Shift+Tab off its first, closes the menu and refocuses the trigger (forward Tab then moves on to the next toolbar control; Shift+Tab stays on the trigger), keeping the order trigger -> panel -> next control (a FilterBar facet menu stays mounted on that close, so its trigger survives to take focus); Escape also returns focus to the trigger), MultiSelectDropdown and SelectDropdown. Both are focus-staying comboboxes driven by aria-activedescendant. Any such component MUST scroll the active option into view on every activeIndex change, or a keyboard user can move the highlight out of the capped list. **Named exception to the resize and scroll dismissal:** the custom color popover (`ColorSwatchPicker`, #2095) skips both while one of its own inputs has focus, because a phone keyboard opening resizes the viewport and scrolls the page exactly as the user starts to type, which would throw the draft away. **Named exception to rule (a) (Tab stop):** the same popover's scroll region takes no `tabIndex`, because every control inside it is a Tab stop and focus scrolls it; rule (b), the overflow cue, still applies. **Scroll padding under a sticky overflow fade includes the container's bottom padding (#2179).** A `sticky bottom-0` fade pins to the inside of the scroll container's padding, but `scroll-padding` is measured from the scrollport edge, so set `scroll-pb` to the fade height plus the container's bottom padding (the custom color popover's `h-8` fade plus `p-3` is `scroll-pb-11`), or focus lands under the fade. **Named exception to the scroll dismissal:** the mention list re-anchors to the live caret on an outside scroll instead of closing, because ProseMirror and the browser scroll the caret into view as the query is typed, which happens exactly when the caret is near an edge, so a scroll dismissal would close the list mid-word. It still ends on `resize`, through Tiptap's own exit path (a `{ exit: true }` meta transaction on its suggestion `PluginKey`, as Escape does), never by only hiding the element, which would leave the suggestion capturing Enter and the arrow keys. `Tooltip`, `RoleInfoTooltip` and `ConnectionStatus` (a line of text or a fixed `w-64` status panel, anchored in the header or toolbar); the `CardDetail` move popover (a fixed form of two selects, an inline error with at most a numbers line and the admin override link (#1772), and two buttons under the Move button in the panel header); its Custom body widens to `w-max` (about 216px) and is shifted to stay inside the editor container, which is still bounded, so the exemption holds); `UserMenu` (a fixed handful of items under the header); the `BulkActionToolbar` Move / Assign / Priority menus (#1482: exempt because of their anchor, not because their content is bounded: the Assign menu lists board members, which is user data. The toolbar is `fixed bottom-4` on the viewport, not inside any scroll region. The Move and Assign menus open upward capped at `max-h-64 overflow-auto`, so only a viewport shorter than about 330px could clip them; the Priority menu has no cap, but it is a fixed list of four priorities); and the `Navbar` notifications panel (#1482: the header is not `position: fixed`, but it stays at the top of the viewport because the app shell is `h-screen overflow-hidden` (`App.tsx`), so it is not inside a scroll region either, and the panel is `absolute right-0 top-8` (on phones, `max-sm:top-full max-sm:inset-x-4`, anchored to the header, #2333) with its list capped at `max-h-80 overflow-y-auto`, so only a viewport shorter than about 400px could clip it; same anchor-plus-cap reason, not bounded content). **`MentionTextarea` `@`-mention list (#2092):** `position: fixed` and kept in the component's own DOM subtree (not a body portal, because the card sheet's focus trap and click-outside dismissal treat a portal as outside the dialog). It is placed from its measured natural height against the textarea's rect: below, else above, else the larger side with `max-height` capped to it so the list scrolls (`overflow-y-auto`, the active option scrolls into view). It never overlaps the textarea (the user is typing in it) and is never pinned; the side is kept while the list still fits there, and side and cap are recomputed on every re-measure. Focus never leaves the textarea (options `preventDefault` on mousedown). Like the Tiptap mention list it is exempt from the scroll dismissal (typing scrolls the caret into view); unlike it, it re-anchors on `resize` instead of closing, because a phone keyboard opening resizes the viewport as the user starts to type. Escape closes it; a click elsewhere leaves it open and anchored to the textarea until the `@`-word ends. Placement measures the visible viewport (#2138), not `window.innerHeight`, so a phone's on-screen keyboard is excluded (see the visualViewport rule below). ARIA (#2137): the textarea is `role="combobox"` (`aria-autocomplete="list"`, `aria-haspopup="listbox"`, `aria-expanded`, and `aria-controls` / `aria-activedescendant` only while open) over a `role="listbox"` of `role="option" aria-selected` rows (divs, not buttons), with `useId`-derived ids so several instances never collide; no `aria-multiline` (ARIA 1.2 does not allow it on `combobox`, so the role drops the implicit multiline and that is accepted) and an accessible name (`ariaLabel`, else the placeholder); a `getByRole('textbox')` query no longer finds it. The `RichTextEditor` (TipTap) `MentionList` has the same list half (`role="listbox"`, `role="option"` divs, `aria-selected`, `useId` ids), and the combobox half (#2149) is set directly on `editor.view.dom` from the suggestion lifecycle while the list is open: `role="combobox"` replaces the contenteditable's `textbox` role (with `aria-autocomplete="list"`, `aria-haspopup="listbox"`, `aria-expanded`, which `textbox` does not support; only attributes ARIA 1.2 allows on `combobox`, so no `aria-multiline`) and an accessible name (the placeholder) if it has none; every attribute touched is snapshotted and restored, not only the role. The list root also `preventDefault`s mousedown so the blur-to-dismiss never fires from a click on its padding or scrollbar. `aria-controls` / `aria-activedescendant` are reported by `MentionList` via `onActiveChange` and follow the arrow keys, and all of it is removed (role restored) on exit, Escape and editor blur, which ends the suggestion. Focus stays in the editor. The role swap on a focused element is not yet verified with NVDA, JAWS or VoiceOver (#2158). Escape priorities are unchanged: 43 for `MentionTextarea`, 31 for the `RichTextEditor` mention popup (edit-mode cancel). Hover tooltips (`pointer-events-none absolute bottom-full`) are `Tooltip`-class and exempt. A new menu whose items come from user data is not exempt. **Named exception to this whole rule: the card detail sheet (#1914).** It is an `aria-modal` dialog, not a popover: it is placed again on open, swap, resize and board scroll-end, may change sides, and never dismisses on resize or scroll. It uses its own `useCardSheetPlacement` (see § Card detail sheet placement), not `useAnchoredPlacement`. The side lock and the resize/scroll dismissals above stay in force for every other anchored popover.
- **Anchored popovers place against the visible viewport's height, not `window.innerHeight` (#2138).** Companion to the anchored-popover rule above. On a phone the on-screen keyboard (and pinch zoom) shrinks `window.visualViewport` but not `innerHeight`, so a list placed below its field could sit under the keyboard. Every placement reads `getVisibleViewport()` from `src/hooks/useAnchoredPlacement.ts` (`visualViewport` `offsetTop` and `height`, falling back to the window where it is unavailable) and passes both to `computeAnchoredPlacement` (`viewportHeight`, `viewportTop`); never read `window.innerHeight` for a popover's available height. Two direct reads remain by design: `ChoiceColorPicker` (`absolute` inside the scrolling settings panel, already exempt per #1457) and `OnboardingTour` (not an anchored-popover adopter: a coach-mark tooltip with no text input). A `visualViewport` `resize` or `scroll` re-places and never dismisses: `useAnchoredPlacement` does this for every hook adopter, and a popup that is not a React child (`MentionTextarea`, the `RichTextEditor` mention list) subscribes with `subscribeVisualViewport(callback)`, which adds and removes both listeners together; clean it up beside the window listeners. ## Toasts (#2060, #1438)

One shared toast region for the whole app, from the 1.3 UI spec Part 9 (a design proposal, not user research). `ToastProvider` (`src/contexts/ToastContext.tsx`) is mounted once in `App`; anything raises a toast with `useToast().notify({...})` (`src/contexts/useToast.ts`; a no-op outside the provider, so isolated component tests need no wrapper unless they assert on the toast). The queue rules are pure functions in `src/utils/toastQueue.ts`, unit-tested on their own. **Never add another independently positioned toast**: today's adopters are the three bridges `MoveBlockedToast`, `DemoWriteBlockedToast` and `ImportSkippedToast` (they raise toasts and render nothing), `BoardView`'s "Card archived" toast (`success`, key `archive`, 5 s, action "View in Archived", which opens the Archived tab of the Activity drawer and dismisses the toast), and `CardBlockSection`'s unblock outcome, because components at one anchor could not know about each other and the later one hid the earlier. Since #2107 the rest have moved too, and **there are no exceptions left**: the board preset notice (`usePresetNoticeToast`, `info`, key `preset-notice`, Undo action without the `undo` guard because the Preset menu offers the same Undo, 8 s or 20 s for a `?preset=` link, focus returns to the picker), `BoardView`'s card-not-found notice (`warning`, key `card-not-found`, 4 s, a deep link to a card not on the board or an open card that left it, #1615), the single-card action results of #2059 (key `card-action`: a failure is `danger` and persists, a result whose effect is not visible on the board such as Copy link or a delete is `success`; a result the board shows itself, such as Move, Assign or Priority, raises no toast and is announced through an `sr-only` status only), and the "You've joined …" confirmation on the group page and the board (`useJoinedToast`, `success`, key `joined`, persists until dismissed). `ImportSkippedToast`'s warnings list is a focusable `ul` inside the region, reached by Tab and tested (`importExport.test.tsx`). `BulkActionToolbar`'s own result slot is **not** a toast (§ Bulk operations rule 3) and stays where it is.

- **Variants: shape + word, hue only reinforces (WCAG 1.4.1).** `success` (`✓`, `bg-surface border-line-strong`), `info` (`ℹ`, the shipped `bg-primary/15 border-primary-emphasis/40` shell over an opaque `bg-surface`), `warning` (`⚠`, `bg-surface border-warning`), `blocked` (same amber shell, `⚠`, or `⛔` only for a hard limit via `hardGlyph`, reserved for the hard WIP blocks and a Hard entry-requirements column per § Move-blocked toast), `danger` (`bg-surface border-danger`, an inline-SVG octagon with an ×, `currentColor`; never `⛔`, which marks the hard WIP blocks and Hard entry mode, and never `⊘`, the card blocked signal). `blocked` and `danger` stay separate so a move refusal stays amber: `blocked` = "the system refused, here is why", `danger` = "something failed". The title is `font-medium` in the variant's `*-on-tint` token, even on the untinted shell (the on-tint tokens out-contrast the plain ones on the tinted shells; ratios in § Color tokens); the body is `text-sm text-fg`, a secondary line `text-xs text-fg-tertiary`.
- **One action at most**, a `text-xs underline` text button in the variant's on-tint token, a sibling of the message, never inside a live region (#1772): `Undo` on `warning`/`info`, `Move anyway (admin override)` on `blocked`. An action never dismisses its own toast; its owner replaces it (same `key`) or dismisses it by key once the outcome is known. An `onAction` that returns a promise shows `pendingLabel` ("Moving anyway…", "Undoing…"), is `aria-disabled` (never `disabled`) and freezes the timer until it settles.
- **Exception to "one action at most": only the `move` blocked toast may carry two actions (#1923, #2571).** `actions[0]` is a compact Primary button ("Fill in and move"), `actions[1]` is the underlined text style above; no other toast gets a second action. The single "Fill in" action on the Warn toast is within the one-action rule. Two-action support itself ships with #2571.
- **Priority:** `danger` = `blocked` > `warning` with action > `warning` > `info` with action > `info` > `success`. **Cap 3 visible.** The stack grows upward; the highest priority sits at the bottom, nearest the anchor, ties newest nearest the bottom. The DOM order is bottom first (`flex-col-reverse`), so Tab follows the visual order bottom to top.
- **Coalescing by `key`** (`move`, `import-summary`, `demo-write-blocked`, `preset-already-active`, `unblock:<card id>`): a toast with the same key replaces the old one in place (same position, timer restarted) and is re-announced only if its text changed. Pick a key for any toast that can repeat.
- **Past the cap** a newcomer evicts the lowest-priority, oldest visible toast, **unless** that toast is `blocked`/`danger` or inside its Undo guard, **or outranks the newcomer** (a lower-priority toast never displaces a higher one; it waits). Otherwise the newcomer waits, and a `+N waiting` line (`text-xs text-fg-tertiary`, plain text rather than the spec's inert button: a button that does nothing is noise in the Tab order) sits at the top of the stack. Because that line is not live, the polite region says "N more notifications waiting." whenever the queue grows; each waiting toast is announced in full when it enters (slots free up highest priority first). An evicted toast was already announced when it appeared.
- **Timing:** `success` 4 s, `info` 6 s, `warning` 8 s, `warning`/`info` with an `undo` action 12 s; `blocked` and `danger` persist until dismissed or replaced. `durationMs` overrides it: the preset "already applied" notice keeps 4 s (#2124); the import notice keeps 8 s (and persists when it lists warnings), "Card archived" its shipped 5 s, and the demo refusal 8 s (#2109, the `warning` default made explicit), the preset notice 8 s (20 s for a `?preset=` link), and card-not-found 4 s. The join confirmation (`durationMs: null`) and a card-action failure (`danger`) persist. Every timer pauses while the region is hovered, while focus is inside it, and while `document.hidden`; on resume the **full** delay restarts. The pause is region-wide (one hovered toast holds them all). **Hover means a mouse:** the region listens to `pointerenter`/`pointerleave` and ignores `pointerType` touch and pen, because an emulated hover from a tap never ends and would freeze the stack.
- **Undo guard.** A toast whose action has `undo: true` cannot be dismissed by the timer, `×`, Escape or eviction for its first 5 s: `×` is `aria-disabled` with `aria-describedby` "Available in a few seconds" (focus is never dropped), and Escape is consumed without effect.
- **Announcements** go through two always-mounted `sr-only` regions in the provider, cleared and refilled one tick later so a repeat is announced: `role="status" aria-live="polite"` for `success`/`info`/`warning`, `role="alert"` for `blocked`/`danger`. They carry the title, the message and "`<action>` available." (or the owner's `announceText`), **never a list, a URL, a secret or a host**. The visible toasts are not live. Because the assertive region is always mounted, an e2e `page.getByRole('alert')` must be scoped to its surface.
- **Inside a modal, inline first, announce once (#1732, #1437).** An `aria-modal` surface traps focus, so a toast behind it is out of keyboard reach and its live regions may be suppressed. A surface inside a modal reports the outcome in its own live region and raises the toast with `announce: false` (visible mirror only). **The raiser names the specific live region that owns the outcome; never infer `announce: false` from a document-wide `[aria-modal]` check** (another open modal has no inline report, so the refusal would go unannounced). The default is announced. Adopters, each with its owning region: `CardBlockSection`'s unblock outcome (its `card-block-status` region), and a move refusal raised while the card sheet's Move popover is open (`data-move-popover`, whose inline `role="alert"` reports every failure; the popover stays open on failure), which replaces the double announcement § Move-blocked toast used to sanction. A new adopter adds itself here with its region.
- **Dismissal.** `×` on every toast, `aria-label="Dismiss notification"`, a 24 px target on desktop and 44 px at `<= 1024px`. Escape dismisses the **focused** toast only, at `useEscapeStack` priority **61** (`TOAST_ESCAPE_PRIORITY`), returning `false` unless focus is inside the region: harmless otherwise, and above the command palette (60), modals (40) and the card sheet (30) in the one case where it matters. Dismissing a focused toast returns focus to the element focused before the user entered the region (recorded on `focusin`), else the board grid (`data-board-scroll`). **Every removal path** (×, Escape, timeout, eviction, an owner's `dismiss(key)`) restores focus the same way when the removed toast held it, and the focus-within pause is recomputed from `document.activeElement` after every change to the stack: a removed node fires no `blur`, so never rely on one.
- **Placement.** `fixed`, `z-[55]`: above `BulkActionToolbar` (40), the grid legend (30) and modals and the card sheet (50), so a `danger` toast is visible over the modal that produced it. **Recorded departure: the region sits above the command palette, not below it.** The spec asks for both "below the command palette" and `z-[55]`, but the palette is `z-50` like every other modal layer, so the two cannot hold together; `z-[55]` wins because a `danger` toast must stay visible over the modal that raised it. While the palette is open, toasts remain visible and clickable at the bottom (the palette panel sits at the top, `pt-[12vh]`), and a click on a toast is not a palette backdrop click. Putting the region below the palette means raising the palette's own layer, a separate change. `BulkActionToolbar` publishes its height as `--bulk-toolbar-h` (`usePublishedHeight`) and the region sits at `bottom: calc(1.5rem + var(--bulk-toolbar-h, -0.5rem))`: 1rem from the bottom alone, 8 px above the toolbar when it shows. Desktop: bottom-center, `w-max max-w-[min(24rem,calc(100%-2rem))]` (the #1439 width rule: never `max-w-sm` alone on a `left-1/2` box). `<= 820px`: `left-4 right-4`, `max-w-[28rem]` centered, safe-area padding. `<= 640px`: full width between the gutters, the message clamps to three lines with the full text in `title`. The action sits on its own line and is a 44 px target at `<= 820px` (`inline-flex items-center` so the label is centered in it), next to the `×` rule at 1024. **A menu that opens out of a toolbar the region floats above outranks the region while open:** `BulkActionToolbar` goes from `z-40` to `z-[56]` while its Move/Assign/Priority menu is open, because those menus open upward into the space the region occupies.
- **One landmark, outside the chrome.** `<section role="region" aria-label="Notifications">`, mounted only while a toast is visible. It is a plain region, not a chrome landmark, so it is a recorded departure from the four-landmark cap (Part 1). On the board it renders through `ToastRegionSlot`, which BoardView mounts as the next DOM sibling after the grid and before `BulkActionToolbar`, so one Tab from the focused card reaches the first toast action; elsewhere it renders at the end of the provider. The region carries `data-keeps-card-sheet-open`, so a click on any toast never closes the card sheet (#1914).
- **A successful block raises no toast (decided).** Blocking replaces the header's **Block…** with the red banner, and focus moves to that banner (§ System signals), so the outcome is already visible where the user is and announced by `CardBlockSection`'s status region. Unblock gets a toast because the banner that said "blocked" disappears.
- **Motion.** Entry uses the shared `animate-fade-in` (120 ms, opacity plus a slight scale) with `motion-reduce:animate-none`; exit is instant. Both are recorded departures from the spec's 100 ms opacity-only fade in and out. No progress bar or countdown ring. Moving between a board (`ToastRegionSlot`) and another page re-parents the region, so its toasts remount and replay the entry fade; accepted as rare and cosmetic.

## Move-blocked toast (MoveBlockedToast)

Content rules for the move refusal. Placement, timing, stacking and announcement follow § Toasts: it is a `blocked` toast (key `move`), persists, and is announced assertively.

- **Use `MoveBlockedToast` for all card move constraint violations** — WIP limit, weight limit, or any future column constraint. Never add a second toast for them, in `App.tsx` or anywhere else.
- **A failure shown by both this toast and an inline error states its cause once per surface and never contradicts the other (#1761, #1772).** `CardDetail`'s Move popover keeps its inline `role="alert"` message alongside the toast; both derive their reason from the same failure (`utils/moveFailure.ts`, `moveBlockedMessages.ts`). Because the open panel's focus trap (#1732) makes the toast unreachable from the keyboard, the popover is a limit variant in its own right (re-confirmed in #1914: the sheet no longer has a backdrop when anchored, and the toast carries `data-keeps-card-sheet-open` so a pointer click on it does not close the sheet, but the trap still keeps Tab inside the sheet): for the six limit codes (the three column codes and, since #1150, their `swimlane_*` counterparts) it adds a `text-fg-tertiary` numbers line (`limitCounts`, never repeating the column name; a swimlane code names the swimlane instead), and for the soft codes `wip_limit_exceeded` / `weight_limit_exceeded` / `swimlane_wip_limit_exceeded` / `swimlane_weight_limit_exceeded` it renders the admin override link "Move anyway (admin override)" (board `admin` or `site_admin` only) under the message, outside the live region, wired to `useBoard.forceMoveCardTo` with the popover's own target, never the shared `pendingMove`. No override for `wip_hard_blocked`, `swimlane_wip_hard_blocked`, `move_failed`, 403 or conflicts. In flight the link is `aria-disabled` and reads "Moving anyway…", the dropdowns, Cancel and Move are disabled, Escape is swallowed, and the header Move trigger ignores activation: every control that could dismiss a popover is inert while an action inside it is pending, so its outcome is never hidden. Changing either dropdown clears the message and the link. A successful forced move clears the toast, closes the popover silently and returns focus to the Move trigger; a failed one shows its cause inline and, if the link is gone, focuses the popover's Move button. The toast is not suppressed: it keeps its own override for when the panel is closed. Since #2060 it is raised with `announce: false` only while the sheet's Move popover is open (`data-move-popover`; the popover stays open on failure), so the popover's inline `role="alert"` is the one announcement; with the popover closed the toast announces (§ Toasts, modal rule); the double announcement this rule used to sanction as an exception (#1773) is gone.
- **Always amber** — border `border-warning`, glyph `text-warning`, title and action `text-warning-on-tint` (§ Toasts). Do not introduce a second color for a different limit type; severity is communicated via icon, not color.
- **`move_failed` is the catch-all variant (#1761).** Any move failure with no more specific code (network error, 5xx, 404, unrecognized 409/503) raises a `move_failed` toast: title "Move failed", body is the capitalized cause (`A network error occurred.`), amber ⚠ (never ⛔), no admin override. Drag-and-drop announces success in the sr-only status region only after the request resolves, never before; on failure that region is blanked because the toast's assertive announcement already carries the cause (one live region per action). A later successful move clears a stale toast.
- **Limit variants always show three things**: what was blocked (column name), why (with numbers), and an admin override link when `isAdmin` is true.
- **Admin override link**: a text action, `text-xs underline` in `text-warning-on-tint` (§ Toasts action slot; the popover's own link is unchanged) — never a button with background fill. While the forced move is in flight it reads "Moving anyway…" and is `aria-disabled`.
- **Who gets "Move anyway" is one helper (#1923).** `utils/forceOverride.ts` (`overrideEligibility`) decides for the toast, the card sheet's Move popover, the peek sheet and the child-card picker; do not re-derive it from the role. Labels are "Move anyway (admin override)" and "Move anyway (assignee override)". A self-assigned assignee and other members get a `text-xs text-fg-tertiary` hint instead, only on soft refusals. The child-card picker uses the same helper, with the reason box inline (Escape 36.5).
- **An assignee override always collects a reason first (#1923)** with `OverrideReasonForm` (required, 500 characters, counter): inline in the popover and peek sheet (Escape 36.5), in a `max-w-md` `ModalWrapper` from the toast. Every override-reason field carries the helper "Visible to everyone on this board." Ctrl/Cmd+Enter submits it. The toast's dialog stays open until the move succeeds (failure in its own `role="alert"` line), then focuses the moved card.
- **A sub-form revealed inside a popover or sheet (the override reason box) follows five rules (#1923).** It resets its open state on every host close, target change, resubmit and success. Closing it returns focus to its trigger, or to a named control in the host, never `<body>`. Typed text survives a failed submit. While it is open the host shows no second Cancel or competing submit. A button dimmed because a required field is empty names the requirement in visible text, linked by `aria-describedby`.
- **`⛔` marks two things, never a third:** a hard WIP block and a Hard entry-requirements column (`entry_requirements_unmet` with `mode: "hard"`, #1923). Both mean "no override for any role". An entry refusal's announcement is the title plus a count ("2 entry requirements unmet"); the "Needs: ..." list stays in the visible body (§ Toasts: never a list in an announcement).
- **Hard-block variant** (`error.code === "wip_hard_blocked"`): use `⛔` as the toast icon instead of `⚠`. This is the only permitted way to signal severity difference between soft and hard constraint blocks — do not change the amber color. Omit the admin override link for all roles. Add a `text-xs text-fg-tertiary` resolution line: "To unblock, move a card out of [column], or ask an admin to raise the WIP limit."
- **Systemic vs. personal block reasons need a fixed, non-admin-authored title** (#1127). When a block is operator-imposed and instance-wide rather than caused by the current user's own state (e.g. `maintenance_mode`), the toast title must be a fixed sentence — not the generic hard-block title, and never left to the operator's free-text `detail` field alone to convey. A terse or generic operator message must not read as "you personally did something wrong." This mirrors the fixed-lead + operator-message pattern in `MaintenanceBanner` (see § Degraded-state site banners): `maintenance_mode`'s title is "The instance is temporarily read-only", with `error.detail` following after the em dash exactly as any other variant's body. This is a deliberate exception to the terse noun-phrase title vocabulary used elsewhere in this table ("WIP limit reached", "Cannot move this card") — do not shorten it to fit that pattern.

## Post-import notice (ImportSkippedToast)

An `info` toast in the shared region (key `import-summary`; placement, pausing and announcement per § Toasts). Informational tone (`bg-primary/15`, `ℹ`), never amber, because the import succeeded and there is nothing to act on, even when it reports dropped values (`import_summary.warnings`). A notice that lists warnings, or reports unmatched assignees (`skipped.assignees`, #2198), persists until dismissed (`durationMs: null`): **a notice reporting a loss the user did not opt into persists; only option-driven skips auto-dismiss.** The option-skips-only notice auto-dismisses after 8s (`durationMs`, not the 6 s `info` default). It now stacks with a move refusal instead of yielding the slot to it (#1438). The headline is the toast's title, so it renders `font-medium` in `text-info-on-tint` (a deliberate change from the old body-weight `text-fg`, per § Toasts). Any scrollable list inside a toast carries `tabIndex={0}`, an `aria-label` and the standard focus ring. The list is capped at 20 plus a server-worded "…and N more". The live region announces the headline and a count only, never the list. Unmatched assignees get their own sentence after "Board imported." and before the "Skipped:" list ("2 assignees didn't match a user and were left unassigned."), never a "Skipped" entry: the card or item was imported, only its assignee was dropped, and the `MAX_LISTED` cap must never fold it into "and N more".

## Common dropdown primitives

`SingleSelectDropdown`, `CheckboxDropdown`, `MultiSelectDropdown` (#1391), and `SplitButton` live in `src/components/Common/`. Do not re-implement these inline in feature components. **Pick the multi-select primitive by when it applies:** `CheckboxDropdown` applies every click immediately (filters); `MultiSelectDropdown` is a searchable checklist that commits **once, on close** (value editors, where one change is several clicks and a save per click would be noise). A `CheckboxDropdown` used as a form cell whose field name sits beside it (the Lane filters popover's multi-select value, #2659) passes `placeholder` (the trigger then reads the picked labels alone, with a `title` for a truncated list), `ariaLabel` and `triggerClassName`; inside a host that closes when focus leaves it, it also passes `menuMode="inline"`, and an inline menu closes when focus leaves the dropdown's wrapper, since only a portaled menu handles Tab itself. The dropdowns follow the dropdown menu spec (trigger: `bg-surface border rounded px-2 py-1`, active/filtered state: `border-primary-soft text-info`). Any new component that needs a select or checkbox dropdown must import from `Common`, never duplicate inline.

- **`SingleSelectDropdown` option groups (#2336).** An option's optional `group` renders headings only when the options carry two or more distinct groups; with none or one the output is unchanged. Consecutive same-group options sit in `<div role="group" aria-labelledby>` named by a `px-3 pt-2 pb-1 text-xs font-semibold uppercase tracking-wide text-fg-tertiary` heading. The double-line separator goes between groups, above the heading, never between a heading and its first option; within a group the usual separators stay. Headings are not menu items, so arrow keys, Home and End skip them. A group heading is a non-focusable label, not a menu item; options without a group never render a blank heading.
- **Selected rows in select-like lists use `Common/SelectedCheck` (#2183).** Never signal selection by border or tint alone (WCAG 1.4.1). The slot is always rendered (`aria-hidden`, fixed `w-*` plus `shrink-0`) so selecting never shifts text; selection state belongs on the row via `aria-selected`/`aria-checked`/`aria-pressed`. Pass a `<surface>-selected-mark` test id and use only `text-info` or inherited color.
- **A soft-capped multi-select refuses the click; it never lets a serializer truncate.** When a multi-select has a maximum selection count (typically a server-side cap), enforce it in the feature component's `onChange` handler — drop the additional selection on the floor — and never leave the cap to a downstream serializer that sorts and slices the array. A slice evicts whichever item sorts last, which is routinely an item the user never touched, so the click appears to succeed while silently changing a *different* selection. `CheckboxDropdown` has no `maxSelected` prop today (`toggle()` always appends), so the handler in the calling component is the enforcement point; the reference implementation is `handleLabelsChange` in `LensFilterBar`. Deselection must stay allowed at the cap, or the control becomes a dead end.
- **Limit and helper text beside a control must be announced, not merely visible.** A cap that silently makes further clicks do nothing is invisible to a screen-reader user, so render the message in a `role="status"` live region that goes from empty to text when the limit is reached (the content change is what triggers the announcement). A bare sibling `<span>` with no role conveys nothing. Where the control accepts `aria-describedby` and the text is static rather than state-dependent, the `id`-bearing helper-span pattern in `FilterBar` (`aria-describedby="filterbar-search-helper"`) is the alternative.
- **A dropdown inside an `overflow-x-auto` toolbar strip must portal its menu.** Per the
  CSS spec, `overflow-x: auto` with the default `overflow-y: visible` promotes the y-axis
  to `auto` too, so Row 2's `h-10` strip clips any `absolute top-full` menu to 40px.
  `SingleSelectDropdown` takes `portalMenu` for this (rendered `position: fixed` through
  `createPortal`). It is opt-in, not the default, because the in-flow menu is what modal
  focus traps and existing call sites assume. Pass it for any dropdown rendered in Row 2
  or inside a scrolling/clipping ancestor (the Edit Swimlane field list, #1478). Its
  portal path follows the "Anchored `fixed` popovers" rule (#1455): measured placement via
  `useAnchoredPlacement`, dismissed on resize and outside scroll, bottom fade via
  `useOverflowFade`, menu at least trigger-width and clamped to the viewport's right edge.
  `SplitButton` measures its anchor once when the menu opens (it is exempt from measured
  placement, see the anchored-popover rule), so it closes on window `resize` and on any
  scroll outside the menu, like the `portalMenu` path (#1171): a resize crossing `lg`
  shifts the toolbar's controls, and scrolling Row 2 moves the chevron, either of which
  would leave a `fixed` menu behind its trigger. Dismiss, never re-measure, for a menu
  anchored once. The `CardDetail` Move popover follows it too (#1171): it is measured from
  the Move button on toggle only, and the card sheet moves itself on resize (#1914).
- **Portaled menus close on Tab and return focus to the trigger on selection (#1478).**
  A portal lands at the end of `<body>`, so Tab from a menu item would leave the dialog
  with the menu still open, and selecting an item unmounts the focused element, dropping
  focus to `<body>`. Close on Tab (focus to the trigger, then let the browser's Tab move
  on) and `focus()` the trigger after a selection.
- **`SingleSelectDropdown`'s menu extensions are additive and opt-in (#1146).** An option may carry a `description` (second line, `text-xs text-fg-tertiary`, read with the label). `menuHeader` is non-interactive text at the top of the menu, never a menu item. `menuActions` are command `role="menuitem"`s listed before the options and share the roving Arrow/Home/End order with them; choosing one closes the menu, returns focus to the trigger and never calls `onChange`. `triggerSuffix` is visible state after the trigger text (the preset `Modified` tag), so it must also go into `ariaLabelDetail` whenever `ariaLabel` is set, because the label replaces the content as the name. `labelClassName` wraps the trigger text (e.g. `truncate min-w-0` with a `max-w-*` on `className`); omitted, the text node renders bare as before. `optionRole="menuitemradio"` gives options that role plus `aria-checked`, so the selection is not color-only (`text-info`); use it on any picker whose selection is a state the user needs to know, and whenever options carry a `description`. A `menuHeader` is wired to the menu with `aria-describedby`. A caller passing none of these renders exactly as before. Design debt: the other `SingleSelectDropdown` callers still expose their selection by color only (#2108).
- **Never `ariaLabel` equal to `label` while nothing is selected (#1146).** `ariaLabel` builds `"<ariaLabel>: <displayLabel>"`, and with no selection `displayLabel` falls back to `label`, which reads "Preset: Preset". Pass `ariaLabel` only while a value is selected, so the visible text is the name at rest.

- **The multi-select custom-field value editor (`MultiSelectValueInput` → `MultiSelectDropdown`, #1391).** (1) **Commit on close, never per click** — Done, Escape, Tab (focus moves on past the trigger), a click outside, or a page scroll/resize closes the menu and commits the whole set once, only if it changed as a set; a rejected save reverts the trigger and shows `Couldn't save {field}. Try again.` (`role="alert"`) under it. (2) **Two-step Escape** — with a search typed, the first Escape clears the search and the second closes. (3) **Chips follow the choice's explicit color** — selected entries render through `MultiSelectChips` everywhere (trigger, card face, row header): a choice with a `choice_colors` key is a tinted `ChoiceBadge`, every other entry a neutral `bg-surface-hover` sub-chip. Never `choiceColor` hash dots on multi-select entries; the menu's option rows stay neutral, and multi-select filter options carry no dot. (Dropdown filter options do carry a dot: the choice's explicit palette `base` when `explicitChoiceColor` resolves a key, else the hash dot — so the filter matches the card face.) (4) **Orphans** — selected entries no longer in `choices` are listed under a `No longer a choice` divider, `text-fg-muted`, checked; they can be unchecked but never added elsewhere. (5) **ARIA** — the sticky search input is `role="combobox"` (`aria-expanded`, `aria-autocomplete="list"`, `aria-haspopup="listbox"`, `aria-controls`, `aria-activedescendant`) over a `role="listbox" aria-multiselectable="true"` of `role="option" aria-selected` rows; the "No matching choices" message sits outside the listbox; the count is a `role="status"` in the sticky footer. (6) **Active row = `ring-2 ring-inset ring-primary-emphasis`**, never a second background: a selected row keeps `bg-primary-emphasis/20` and gets no hover tint. (7) **Arrowing scrolls the active row into view** (`scrollIntoView({ block: "nearest" })`, with `scroll-mt-*`/`scroll-mb-*` clearing the sticky search and footer). Rows `py-2`, Done `px-3 py-1.5` for touch. The menu is portaled, opens upward when there is no room below, and is clamped horizontally to the viewport.

- **Free-text filter inputs in the same row clear on Escape, all of them.** Escape resets the input and blurs. Applying it to only some inputs in a row is worse than applying it to none — a keyboard user who learns the affordance on one input expects it on its neighbors.

### SplitButton

Use `SplitButton` whenever a toolbar action has a dominant single-click behavior plus a menu of granular variants (e.g. Collapse / Collapse lanes / Collapse columns). Rules:

- **Two sibling `<button>` elements** inside a visual container — each with its own tab stop and focus ring. Never implement a split button as a single focus target with two click zones; it fails the WAI-ARIA Menu Button pattern and breaks keyboard access for power users.
- **Segmentation token:** `border-line-strong` on the chevron's left edge — not `border-line`. The stronger token is required so the visual bisection is obvious at rest on `bg-surface`.
- **Primary segment size:** `text-xs px-2 py-1 rounded-l` by default. `size="toolbar"` (the Lens Collapse button, #2302) makes the wrapper `h-9 border border-line-strong rounded` and both segments `text-sm px-3` / `px-2`, matching the board's Filter, View and Activity buttons.
- **Chevron segment size:** `px-1.5 py-1 rounded-r` with a `w-3 h-3` chevron SVG (stroke 1.5). Use the same chevron shape as `SingleSelectDropdown` (`M4 6l4 4 4-4`).
- **Menu open state** on the chevron: `text-info bg-info/10`, identical to the active-toggle treatment used by other Row 2 controls. The primary segment never changes state.
- **Menu panel** uses the shared dropdown chrome: `bg-surface border border-line-strong rounded-lg shadow-lg py-1 min-w-[200px]`, right-aligned to the chevron.
- **Items author their own content** via `renderMenu({ close })` — SplitButton owns positioning, outside-click, Escape handling, and open state; the caller decides the item shape, vocabulary, and disabled logic.
- **Menu vocabulary** must match app-wide terminology. In Visiban, the axis terms are "swimlanes" and "columns" (not "lanes", "rows"). Use action-first copy (`Hide all swimlanes`, not `Collapse lanes`) so occasional users aren't forced to learn domain jargon to operate the menu.
- **Disabled items stay rendered.** If an action would be a no-op (e.g. `Hide all swimlanes` when everything is already collapsed), apply `disabled` to the item rather than removing it — the menu shape is stable across states so users can build a mental model.
- **Two engraved separator groups** inside a collapse-style menu: Hide-variants first, Show-variants second, separated by the canonical double-`<div>` engraved separator. Both groups are always rendered.

### OverflowMenu

`OverflowMenu` in `src/components/Layout/` is the Row 2 kebab (`⋮`) menu. It is driven by an `items: OverflowItem[]` prop so enterprise surfaces (audit log, automation rules) can inject entries without modifying the OSS component.

- **Trigger icon:** `p-1.5 rounded` kebab (`w-4 h-4` SVG with three `r=1.75` circles), `text-fg-tertiary hover:text-fg hover:bg-surface-hover`. Open-state uses `text-info bg-info/10`.
- **First-encounter dot:** uses the shared `user:prefs:overflow-seen` key via `useOverflowSeenPref`. The dot clears on **intentional click of the kebab**, never on the `.` keyboard shortcut — the shortcut proves the user already knows the menu exists.
- **Row anatomy:** `flex items-center gap-3 px-3 py-1.5 text-sm text-fg-secondary`, three slots — a `w-4 text-center` icon, a `flex-1 truncate` label, and an optional right-aligned `<kbd>` shortcut hint styled identically to `KeyboardShortcutsOverlay`.
- **Separators** use `separatorBefore: true` on the item that should be preceded by the engraved double-`<div>`. The separator is implicitly omitted on the first rendered item.
- **Disabled items require `disabledReason`** — the string is rendered as a `title` attribute and contributes to the `aria-label`. A silently-greyed item is a dead end; always explain why.
- **Items are responsive-aware** — at sub-`lg` viewports, fold the direct Row 2 secondary controls into the items array so functionality is preserved without cluttering the toolbar. Do not spray `matchMedia` checks across consumers; use `useIsLargeViewport` / `useIsMediumViewport` hooks and build the items list in `BoardView` once.

- **`SingleSelectDropdown` — `triggerPrefix` slot for decorative icons.** When a trigger needs a leading icon (e.g. `🔍 This board ▾`), pass it via the `triggerPrefix` prop. The component wraps the node in `aria-hidden="true"` — keep the accessible name on the dropdown label, not the icon. Do not bake icons into each option label; that duplicates the glyph across the menu panel and couples the icon to the option rather than the trigger.

## Admin offboarding modal

When a destructive admin action has preconditions requiring data collection (e.g. board ownership transfer before user deactivation), use a dedicated modal — not `ConfirmDialog`:

- Modal follows the standard spec: `bg-surface border border-line rounded-lg shadow-xl`, `p-6` content, `fixed inset-0 bg-backdrop/60 z-50` backdrop
- Must use `useEscapeStack` for Escape key handling; focus must be trapped inside the modal
- Board list: `flex flex-col divide-y divide-line`; each row: board name (`text-sm text-fg truncate` with `title`) + card count (`text-xs text-fg-muted`)
- User picker: typeahead input following `BoardSettingsModal` invite search pattern; include `text-xs text-fg-muted` helper text below the input describing any scoping constraint (e.g. "Only users who are members of all boards listed above")
- Irreversibility warning: `text-sm text-warning` sentence above the confirm button — not a text-input confirmation, not a red banner. Use amber (not red) because the action is reversible by re-transferring manually
- Confirm button: danger variant (`bg-danger-bg hover:bg-danger-bg-hover text-on-danger`) with a label describing both actions (e.g. "Transfer ownership and deactivate")
- If no eligible transfer target exists: block deactivation and show a `text-sm text-warning` message naming the specific board(s) with a direct action prompt (e.g. "Add another member to [board name] before deactivating this user")

## Focus containment for modal surfaces (#1732)

1. **Any element with `aria-modal="true"` must use `ModalWrapper` or `useFocusTrap`, and restore focus on close.** `aria-modal` tells screen readers the background is inert; without a trap Tab walks out into the board behind it. Slide-over panels (`CardDetail`), the bulk-add overlay, the NavDrawer and the command palette call `useFocusTrap(ref, active)` on the `role="dialog"` element (`tabIndex={-1}`). Centered confirm/prompt dialogs use `ModalWrapper`. Never hand-roll a Tab handler (`AdminPage` `ConfirmDialog` did, and it drifted).
2. **`useFocusTrap` restores focus.** It captures the opener while rendering (a child's `autoFocus` has already moved focus by the time effects run) and returns focus there on deactivate or unmount, but only if focus would otherwise be lost (on `body`, or still inside a container that stays mounted but is hidden, like the mobile drawer's aside), so it never steals focus the user moved. Do not add a second restore in the component. When the opener has unmounted, restore falls back to `restoreTarget` and otherwise is skipped, so `OverflowMenu` moves focus to its own trigger before calling an item's `onSelect` (#1775): the surface that item opens captures the surviving trigger as its opener, and both `useFocusTrap` and `ModalWrapper` callers get focus back with no extra argument. `UserMenu` (a separate menu component) does the same in its Keyboard shortcuts handler before dispatching `visiban:open-shortcuts`; any new menu whose item opens a surface elsewhere must do likewise. Do not add a per-caller restore for an `OverflowMenu` item. `useFocusTrap` callers can still pass a surviving element as the third argument, `restoreTarget`, for any other opener that unmounts (a different menu component, or an item whose own handler removes the opener); `ModalWrapper` passes its `restoreFocusTo` prop through as that argument (#2204). A `ModalWrapper` whose confirm removes its own opener (a delete confirm opened from the row being deleted, or from an editor the delete closes) must pass `restoreFocusTo`, preferably as a function, which resolves at close after the same commit removed the opener: the custom-field delete modals (`BoardSettingsFieldsTab`, `BoardSettingsSwimlaneFieldsTab`) resolve the enabled `+ Add field` button (`data-add-field`, list footer or empty state) and fall back to the tab heading (`tabIndex={-1}`). Cancel still returns to the real opener, because the fallback is used only when the opener is disconnected. Pin it with a `document.activeElement` test.
3. **Nested traps are stack-ordered.** Only the most recently activated trap handles Tab, so a `ModalWrapper` confirm opened inside `CardDetail` does not fight the panel's trap.
4. **Every `role="dialog"` has an accessible name** (`aria-label` or `aria-labelledby`). The command palette is a portaled `aria-modal` dialog that keeps its inner `combobox`; non-modal popovers (`SwimlaneFieldsPopover`, `ChoiceColorPicker`, `ConnectionStatus`) are outside rule 1.
