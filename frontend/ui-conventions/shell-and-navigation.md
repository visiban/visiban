## In-app help links (#2589)

- **Docs links render only through `HelpLink` (`components/Common/HelpLink.tsx`), keyed by a typed topic in `help/topics.ts`. Never write a `docs.visiban.com` URL or an `<a href>` to docs in a component.** `docsUrl(topic)` (`help/docsUrl.ts`) builds the version-matched URL: `/vX.Y/` for a release build, `/next/` for a prerelease, `/latest/` when the version is missing or not semver (in practice only tests, since `__APP_VERSION__` is always semver). **Base precedence (#2604):** an explicit `opts.base`, then the runtime Site setting `docs_base_url` (`setRuntimeDocsBase`, fed by site-config in `useInstanceFlagsState` and by a successful save in Site admin → General → Help links), then the `VITE_DOCS_BASE_URL` build-time value, then the version-matched public docs. Both overrides are used verbatim, and each must pass `sanitizeBase` (http(s), no whitespace or backslash) or it is skipped. A placeholder or example for a docs address uses an `example.internal` host, never `docs.visiban.com`, which would pin unversioned links. A build from main reports the last released version, so its links point at that version's docs until a 1.3 prerelease is cut. The registry owns the accessible name: `Learn more about <subject>, opens docs`. Add a topic to the registry (path ends in `/`, anchor without `#`); #2591 checks each anchor against the docs.
- **Static only (#2542).** A help link is visible text or a "?" glyph beside a heading. No banners, tours, first-run dots, dismissal state or persistence.
- **Placement.** In the heading row, right after the heading text (`flex items-center gap-1.5` to `gap-2`), not floating and not in the right-aligned header-actions group. Inside a callout, the `text` variant is the last line of the body. An inline docs link in a `text-xs` footnote is `HelpLink variant="text"` placed last in the sentence after a `{" "}`, so it wraps as a unit and inherits the footnote size; override the visible words with `linkText` where "Learn more" would be vague ("Known limits" in the Analytics footnote) (#2647).
- **One per section.** Never per control, row or toolbar button: a help link is a real tab stop. Dense toolbars have none.
- **Variants.** `icon` (default; 20px "?" circle; `Tooltip` shows the registry summary; `aria-label` is the name; no `title`) beside headings. `text` ("Learn more" by default, overridable with `linkText`; `text-info underline`, external glyph, sr-only suffix) inside callouts and prose. `text-info` is allowed here because it is a link, not an action button (see Section header actions).
- **Touch and focus.** 44px hit area below `sm` via `max-sm:` with negative margins so the desktop layout does not change (the parent must not clip them). Focus ring `focus:outline-none focus:ring-2 focus:ring-primary-emphasis`. Always `target="_blank" rel="noopener noreferrer"`.
- **Names and tooltips.** `subject` is a noun phrase that reads after "about" ("tracks", "bottleneck detection"); the text variant's visible words always start its accessible name. The tooltip summary is one static line of about 60 characters or fewer and is a desktop and keyboard extra (it never shows on touch); the name carries the meaning. The text variant uses `max-sm:-my-2.5` so its 44px target does not add height.
- **Collapsed containers.** A text link inside a collapsed disclosure is correctly out of the tab order until it opens; do not hoist it out.
- **Menu items.** `UserMenu` "Help & docs" stays a `role="menuitem"` anchor and takes only its `href` from `docsUrl(helpTopicForPath(pathname))` (`help/pageTopic.ts`: board, group and admin pages open their own docs; any other page opens the docs home).
- **More rules (#2593).** A row that already hosts an info-tooltip "?" gets no second "?" icon: use the `text` variant beside the content instead (Board settings Members links `permissions` under the member list). A menu or panel's empty and first-run state keeps its help link (Saved filters footer). Never place a help link inside a `role="status"` or other live region that is re-announced. On an `items-baseline` title row, wrap the heading and its link in an `items-center` group (Analytics title). Area, topic and docs section are tabulated in the `help/topics.ts` header; the home page (#2474) and app shell (#2473) are outside #2593's area list, and SSO/OIDC has no UI surface to link.
- **Work-breakdown and board-config surfaces (#2592).** Icon links sit beside the Stage settings Sub-columns and Tracks headings, the card Checklist toggle (a sibling of it, never inside the button), the Children tab heading (empty state and populated), the column WIP limit label, the Field sets heading and the Policy tab hint. Text links sit at points of choice: `work-breakdown` ("Which tool?") in the Stage settings Sub-columns and Tracks hints, under the Add child title hint and in the empty checklist; `child-cards` once in the Add child dialog (also when its board is fixed) and in the empty Children tab; `planned-children` under Needed; `tracks.where` in the card's track line. The #2571 entry-requirements row is not wired until that UI lands. A dense surface (the card face) gets none, and the card's track line has no `work-breakdown` link because its hint names no alternative tool.

## Shared page layouts and parts (#2475)

`components/Page` (barrel `index.ts`: `buttonClasses.ts`, `parts.tsx`, `layouts.tsx`) holds the Consistency sheet's layouts and parts. Page redesigns (#2473, #2474, #2476–#2480) import them instead of restating classes; `src/test/pageParts.test.tsx` pins them and fails on a hard-coded color in the folder (any Tailwind default-palette name, white or black under any color-utility prefix, and hex, rgb() or hsl() literals).

- **Colors map to tokens, no new token.** Page `bg-page`; Chrome (header, drawer, Save bar) the Row 1 surface `bg-sunken`; Panel `bg-surface`; Well `bg-canvas`; Sunken (a box inside a panel) `bg-sunken`; Chip `bg-surface-hover` (its text is `fg-secondary`, § Color tokens); borders `border-line` (panels) / `border-line-strong` (controls), `border-line-boundary` where a border is the only cue (the hollow No status pill, an off switch track). Every pairing reuses one already measured above: status pills use the `/15` on-tint pairs (§ Color tokens #2029), Pending and the selected settings nav row use the Filter panel's `bg-primary-emphasis/10 text-info-on-tint` (7.78 light / 7.15 dark). The Analytics canvas's own `--inset`, warning tint and light danger `#dc2626` are canvas drift, not tokens.
- **Layouts.** `WorkspaceLayout` (full width; Board, Analytics), `OverviewLayout` (max 1200px, a 320px side column from `lg`, below the content otherwise; Home, group page), `SettingsLayout` (max 1240px, a 240px nav with Find a setting, one section per view, a `<select>` below `md`; the active section is `?tab=` so deep links keep working), `CenteredLayout` (one card, max 380px, from `sm`; on phones no card, the content on the page ground with 48px controls). Pages outside the app shell (Centered, the shared board) keep their own `h1`; inside the shell the header owns the `h1` (#2473) and the page heading is `PageHeading`, an `h2` at 24/650 with a one-line description.
- **Parts.** `CardHeading` (15/650), `SectionLabel` (13px uppercase, 0.06em, `fg-tertiary`), `StatusPill` (static, 24px at 12px: On track, At risk, Off track, Pending; its type has no "No status", health rule 3) and `StatusControl` (30px at 13px, adds the hollow No status), `FilterPill` (the Show chips: 34px, selected `bg-primary/[0.22] border-info font-semibold` plus `aria-pressed`; the count is optional, shown only when the page loaded one, see #2476), `ListWell`/`ListRow` (8px rows, wide content scrolls in the well; only an `interactive` row hovers to `bg-surface`, #2484), `SettingsCard` (panel, 10px radius, 18px padding), `Switch` (44×26, saves on change), `SettingSwitchRow`, `SettingTwoSwitchRow` (+ `SettingTwoSwitchHeader`; switches named "<event>, in-app" / "<event>, email"; Email off and disabled while in-app is off), `SaveBar` (only while dirty; `role="status"` "You have unsaved <thing> changes.", Discard Quiet, "Save <thing>" Primary), `InlineConfirm` (danger tint, one sentence naming target and consequence, Cancel Quiet + Danger; the non-modal confirm for any destructive or access-changing row action: remove, revoke, delete, Make admin, Grant access, Transfer boards…; a modal is used only where the action needs typed input, such as the group page's Delete board, Delete group and Transfer ownership typed-name confirmations), `EmptyState` (what is missing and the one action that fills it), `Field` (visible label, required `autoComplete`), `OrDivider`, `BrandTile`, `CenteredHeader`, `StatusCard` (a terminal state in a Centered card; the heading says the outcome, the tone colors only a small mark).
- **Radius and weight.** The canvas's 6px buttons are `rounded`; its weight 650 is `font-semibold`.
- **An `aria-label` on a control with visible text must contain that text (WCAG 2.5.3 Label in Name, #2467).** Lead with the visible words, in order; join separate nodes with a real space (`{" "}`), never `ml-*` or `gap` (name matching does not see margins); counts read "Label, N"; avatar initials come from `avatarVisibleText()`; a shortcut is spelled as in its `kbd` chip. Punctuation, parentheses and symbols are ignored, and axe compares whole words: `⌘` is stripped like punctuation, so "⌘K" in the name reads as the one word "k" and "Cmd K" as "cmd k", which do not match each other; spell the shortcut in the name exactly as the `kbd` chip shows it. Pin with `npx playwright test e2e/a11y.spec.ts`.
- **Rules from the #2475 ux-review.** Pages outside the shell keep an `h1` and a `<main>` in every state, loading and skeleton included (`CenteredLayout` supplies the `<main>`; the shared board supplies its own; a loading state with no visible heading uses an `sr-only` `h1`). A non-modal confirm (`InlineConfirm`) is `role="group"` with an `aria-label` and focuses its Cancel on open, never `alertdialog` without `useFocusTrap`. A control disabled by a dependency states why in text tied by `aria-describedby` (the Email switch: "Turn on in-app to get email."), never opacity alone. A `kbd` chip inside a button stays visible on the button's hover fill (`bg-surface-active border border-line`, `fg-secondary` text) and shows the platform key (⌘K on Apple, Ctrl K elsewhere). Load-failure copy separates gone (404/410: "This board is no longer shared") from could-not-load (anything else: "The board didn't load", Try again). Centered sign-in order: providers (OIDC first), the "or" rule, the form, then the registration line ("Registration is invite-only." / "Registration is closed. Ask an admin for an account." / Create account). A link-style button in a Centered form label row gets a 44px hit area on phones (`max-sm:min-h-11 max-sm:px-2`). The shared-board header's "Shared view, read-only" pill hides on phones so the board-name `h1` keeps room; the summary line under it still says read-only.

- **Rules from #2484 / #2504 (shared-part hardening).** `<Button variant="icon">` requires `aria-label` at the type level; never cast it away. A destructive trigger that only opens a confirm is **Danger outline**; the filled **Danger** is kept for the confirm's own commit, so the trigger never reads as the commit (never `secondary` plus danger class overrides). `ListRow` hovers only with `interactive`, set when the row's main content is a button or link that opens it; a row of text plus its own small controls (invite links, members, Admin users) is not interactive. A field error goes through `Field`'s `error` prop, which sets `aria-invalid`, replaces the hint and is tied by `aria-describedby`; never hand-roll `aria-invalid` plus `hintTone`. `EmptyState`'s `headingLevel` follows the outline: `h4` under a card's `h3`. `InlineConfirm` marks Cancel and the action `aria-disabled` (never `disabled`) while busy, so the focused button keeps focus. A page whose purpose is a timed redirect (invite, email-confirmed, reset-password) uses `RedirectCountdown` with at least 5 seconds (a brief return after a save, such as the Profile save in `SettingsPage`, is out of scope): one polite announcement when it starts and on pause or resume (never per tick), the sentence in `fg-secondary`, and a Pause redirect control at least 24px high (44px on phones) (WCAG 2.2.1, 2.5.8). Danger outline's `/40` border is decorative; the `text-danger` label carries the affordance. A panel with many rows that can each fail announces through one panel-level live region; the rows show the message `aria-hidden`.

## Home status page (#2474)

Home (`pages/Dashboard.tsx`) is the reference Overview page. Pure copy and ordering rules live in `components/Dashboard/homeModel.ts` (unit-tested), not in the JSX.

- **Signals never read 0 for "no data".** Stale and blocked counts come from `health_computed_counts` only where auto health is on; otherwise a row or tile says "Stale, blocked: no data" with the title "Turn on auto health in Board settings to see stale and blocked counts". Listings show a status pill only when there is a status (health rule 3).
- **Desktop and phone variants share one DOM.** The filter is `FilterPill`s on desktop and a native `select` with counts below `sm`; the summary has a desktop and a phone sentence; the row star is a desktop button and a ⋯ menu item on phones; `New board` is the header's primary action on desktop and a 48px floating pill on phones. Each is toggled with `max-sm:hidden` / `sm:hidden`, never by JS width checks.
- **Needs attention uses a decorative severity dot, not `StatusDot`.** Severity (blocked vs stale) is not a health status, so the dot is `aria-hidden` and the meta line carries the words.
- **A fixed phone FAB needs clearance.** The scroll container takes `max-sm:pb-24` and the FAB offsets by `env(safe-area-inset-bottom)`, so it never covers the last row's ⋯ trigger. Count badges (the avatar stack's "+N") keep the 12px minimum even when `aria-hidden`.
- **Transient action errors (a failed star or delete) use their own always-mounted live region (`role="status"`, not a second `role="alert"`)**, never the load-failure alert; they clear on the next action. Loading skeletons carry `role="status"` and an sr-only label.
- **A focus anchor outlives the thing that had focus.** After a confirmed delete or a Retry recovery, focus goes to the All boards section, or to the first-run heading when nothing is listed, never `<body>`.
- **Side lists cap at five (#2487).** Groups and Needs attention show `SIDE_LIST_CAP` rows (`homeModel.ts`); a longer list gets a Quiet, full-width **Show all N** / **Show fewer** toggle that stays mounted (focus is kept), carries `aria-expanded` and `aria-controls`, and is described by its section heading so the two toggles are told apart. No toggle when the list fits.
- **Group avatar stack (#2487).** Up to `GROUP_AVATAR_LIMIT` (3) avatars from the group list's optional `member_preview` (the owner alone on an older server), then "+N" for `member_count` minus the avatars drawn. The stack is `aria-hidden`; the meta line's member count carries the words.
- **One label per list.** A list inside a section that its heading already names (All boards) takes no `aria-label` of its own; a screen reader would read the name twice.
- **Phone order.** `OverviewLayout` drops the side column below the content under `lg`, so on phones and tablets the order is greeting, Jump back in, All boards, then Groups, then Needs attention. Keep that order unless the Phone canvas changes it (to be confirmed against the Phone canvas, #2558).
- **Stage bar (#2483, `components/Dashboard/StageBar.tsx`).** One `role="img"` figure whose `aria-label` lists every stage with its count, zeros included ("Cards by stage: Backlog 2, Doing 0, Done 6"); the first and last stage names under it are `aria-hidden` `text-xs text-fg-tertiary`. One segment per stage that holds cards, `flexGrow` = its count, `minWidth: 2px` so a lone card still shows. The track is `bg-sunken` with an outer `ring-1 ring-line-boundary` (the #2381 boundary rule): `bg-sunken` alone is under 3:1 on `surface`, so an all-zero bar or a pale column color would vanish. Desktop-only on All boards rows, shown on tiles at every width. No `title` when the bar sits inside a button (the tile, `inButton`): the button's name already carries the label. Nothing renders without `stage_counts` (older server) or columns.

## Sidebar and tab navigation

- **A page-level sidebar's section buttons carry the focus ring and mark the active item (#439).** Add `focus:outline-none focus:ring-2 focus:ring-primary-emphasis` and `aria-current={active ? "page" : undefined}` (`type="button"`). The active fill (`bg-primary`) is a visual-only cue; `aria-current` is what tells a screen reader which section is showing. Applies to page-level sidebars only — adopters: the `AdminPage` and `SettingsPage` sidebars.
- **Tab strips inside a modal, panel or drawer follow their own ARIA pattern, not this one.** A strip that switches panels in place is a tab list (`role="tab"` + `aria-selected`, as in `CardDetail`); a strip of independent toggles uses `aria-pressed` (as in `BoardActivityDrawer`). `BoardSettingsModal`'s sections are such a tab list (#2436); see § Board settings layout.

## Top chrome — two-row composition

The authenticated UI is framed by two horizontally-divided chrome rows and a main region. Maintain this skeleton across all routes; feature work lands inside the rows, not on top of them.

| Row 1 | App header (menu button, breadcrumb rooted at Home whose last crumb is the `h1`, star and status, search, primary action, notifications, account; see § App shell) | `bg-sunken border-b border-line` | `h-14` | `text-sm text-fg` | `<header role="banner">` |
| Row 2 | Board chrome (view tabs, Filter / View / Activity / Export / Settings buttons, overflow menu, connection status) | `bg-surface border-b border-line` | `min-h-10` (wraps) | `text-xs text-fg-tertiary` (default; active view tab keeps its own active styling) | `<nav aria-label="Board toolbar">` |

- **The Filters button opens the Filter panel (`FilterPanel.tsx`, #2301), not the filter bar.** It is a presentation over the same `FilterState` that `FilterBar` edits, so URL sync (`f_*` params), localStorage and saved filters are untouched; add a filterable field in `FilterBar`/`filterCards` first, then add its row. The panel is a portaled `role="dialog" aria-modal="true" aria-label="Filters"` popover at tier 25 (Escape closes it and returns focus to the trigger; focus is contained by `useFocusTrap`, so Tab wraps at either end, #2691), in the pinned shell described in the next bullet, 520px wide (`min(520px, 100vw - gutters)`, a single column on phones), with: a "Search fields and values to filter" input (#2437: focused on open, an `Esc` keycap inside it, hidden on phones), a row of scope chips (All fields / Card fields / Swimlane fields, `aria-pressed`), then, in the scrolling body, the "Filtered by" chips (below), then, while the query is non-empty, **Fields matching "q"** (card rows narrow by label as before; lane fields come from `searchFields` in `utils/filterFieldSearch.ts`; each row carries a **Card** or **Swimlane** scope tag) and **Values matching "q"** (one "<Field> is <value>" row per hit with its count, "(hidden on band)" for a lane field set to Hidden, and "Title contains 'q'" last), and with an empty query one row per field (`Search`, `Assignee`, `Label`, `Priority`, `Due date`, `Blocked`, `Lanes` when `laneFilterAvailable` says so (the #2336 gate below), then each custom field) showing its value or "Any",  a "Filtered by" chip group at the top of the body while a chip exists (#2315: the same `FilterChip`s from `buildFilterChips` in `filterChips.ts`, which `FilterBar` also uses so dismissal never drifts; lane rules as "Lanes"-tagged chips; **Clear all** (in the pinned footer since #2691, shown while any filter is active) is `onChange(EMPTY_FILTER)`; **Save filter** (footer, same condition) opens an inline name input in the footer that calls the same `saveFilter(name, effectiveFilters)` as `SavedFiltersDropdown`, Escape cancels the input before closing the panel), and the saved filters as one-click presets in the pinned header (#2695, next bullet; delete, rename and share stay in the filter bar's `SavedFiltersDropdown`). The footer carries the hint "↑↓ move · ↵ add · field:value" (#2691 spec copy; Enter on a name-only query opens that field's editor) beside Clear all and Save filter. **Search rules (#2437):** every field is searchable and filterable whatever its band Show setting; lane field names and values come only from `laneFilterFields(defs, isAdmin)` (never the raw definitions) and `searchFields` re-checks `is_admin_only` against `isAdmin`, where an absent role is a non-admin, so an admin-only field never appears in a name or a value; a multi-select matches its entries (`parseMultiSelect`), never the JSON punctuation; `field:value` (e.g. `tier:gold`) restricts to that field and Enter applies the first value hit; ArrowDown from the input moves through the result buttons (`data-fp-result`) across both groups, with or without a query, ArrowUp from the first returns to the input, and the rows are one Tab stop (a roving `tabIndex`: the last row focused holds it, #2691), while arrows inside an open editor stay native; Escape clears a typed query first (focus back to the input), then closes, all at tier 25 (the save-name input keeps 27). The match highlight is a `<mark>` in `bg-primary-emphasis/10 text-info-on-tint font-semibold underline` (the 7.78:1 pair above), `aria-hidden`, with the plain text in an `sr-only` sibling so the accessible name is not split ("Lab el"). An active row is `bg-primary-emphasis/10 text-info-on-tint font-semibold` with an `ActiveMark`; tint and weight are never the only cue. A row expands in place (one at a time, `aria-expanded`) to native checkboxes, radios or inputs, so mouse and keyboard need no custom handling. The Lanes row does not duplicate the #2205 rules editor: it closes the panel and calls `openLaneFilters`, which shows the filter bar and opens the Lanes popover. The header **Filter bar** switch (#2691) shows or hides the full filter bar (search, scope, My cards, saved-filter save flow); `F` still toggles that bar, so the Filters button deliberately carries no `aria-keyshortcuts` (it would name a key that opens a different surface); it does carry `aria-pressed={filterBarShown}` (true while the bar is shown) and its tooltip reads "N filters active (bar hidden)" when filters are active but the bar is hidden (#2459); an unresolvable id in a row reads "N selected" so the row and the count badge agree. Active-row tint is `bg-primary-emphasis/10 text-info-on-tint` (a persistent active state, so the `primary-emphasis` fill, not `bg-info/*`; `info-on-tint` on that fill measures 7.78:1 on white and 7.15:1 on dark `surface`). Known deviations from the spec, kept on purpose: `F` toggles the filter bar while the Filters button opens the panel (so the shortcut docs and e2e stay valid, and that is why the button has no `aria-keyshortcuts`); the header switch is the panel's only path to the old bar; the panel is 520px (the #2690 canvas draws 380–400px for layout only; #2691 keeps 520px because it fits a field label, a value and a card count without truncating typical values); the "Filtered by" chip row (#2315) sits inside the panel under the search input and scope chips, as the issue says, whereas `menus.png` and `board-redesign.md` show it as a strip below the toolbar (do not move it without revisiting the issue). The spec's Swimlane, Last moved and Track state rows are absent because those filters do not exist and #2301 excludes new filter fields. While the panel is open the "Filters" tooltip is suppressed (`Tooltip` `disabled`) so it never draws over the panel's corner. The panel and the View menu carry `data-shortcut-scope="popover"`, and `BoardView`'s single-key shortcut handler ignores key events whose target is inside one. The trigger's `Tooltip` clones its child, so the trigger ref sits on the button inside the tooltip's `span`; never put `ref` on the direct child of a `Tooltip`.
- **The board and Lens Filters buttons share one pressed rule (#2465):** `aria-pressed` is true only while the filter bar is shown (never because filters are active); the selected tint (`text-info-on-tint bg-info/10 border-info/40`) follows the Filter panel being open (board) or the bar being shown (Lens), or any active filter, so on the board the tint and `aria-pressed` can differ, and the count pill carries the active state for assistive tech via the `Filters, N active` name (`Filters and view options, N active` on the board button when view options are wired). Both buttons also share the hidden-bar tooltip (#2556): "N filter(s) active (bar hidden)" while the bar is hidden and filters are active, else their usual tooltip (the Lens button: "Show the filter bar (F)" or "Hide the filter bar (F)", the shared `filterBarToggleTooltip`, #2691; the board button: "Filters" or "Filters and view options").
- **The accessible name for Row 2 is `"Board toolbar"`, not `"Board chrome"`** — "chrome" is developer jargon that announces as meaningless noise in screen readers. If internal design docs reference "chrome", the landmark label still stays `"Board toolbar"`.
- **No vertical dividers in Row 2 (#2269).** The tabs sit on the left and the buttons on the right with a flex spacer between; the spec's toolbar has no zone separators. Dividers elsewhere (see the Navbar) keep `w-px h-4 bg-surface-hover mx-1` with `aria-hidden="true"`.
- **Row 2 wraps, it does not scroll sideways (#2269).** The outer `<nav>` is `min-h-10 flex flex-wrap items-center gap-x-2 px-3` (no vertical padding, so the tab underline meets the nav's bottom border); nothing folds into the overflow menu by viewport width any more. At 390px the buttons drop to a second line and the page never scrolls sideways. The tabs group alone may scroll inside its own `overflow-x-auto` box. **The Summary, History and Analytics tabs use it too (#2321)**: `min-h-10 flex flex-wrap items-center gap-x-2 px-3` with the tab group in the same `min-w-0 max-w-full overflow-x-auto` box, never a fixed `h-10` row, so all five navs share one wrapping row for parity and wrapping safety. This was not a bug fix: the tabs did not shift at 390px before the move, and the e2e at 390px is a parity regression guard (tab position and sideways scroll), not proof of a fix. **The Lens tab uses this same `<nav>` and wrapper (#2302)**: tabs left, then `LensToolbar`'s own `flex flex-wrap` group (Collapse split button, Filters, layout toggle, the two pivot dropdowns, the custom-pivot note) right, with the same `h-9` bordered button style as Filter/View/Activity. `LensToolbar` never folds by viewport and has no overflow menu or dividers. Keep `portalMenu` on the pivot dropdowns (#1161); the tab group is still an `overflow-x-auto` box. `ConnectionStatus` is the last item and stays pinned to the trailing edge (`ml-auto`).
- **Never add a fifth landmark in chrome** — if a future feature needs a new region, fold it into one of the existing landmarks. Four landmarks (`banner`, `navigation: Breadcrumb`, `navigation: Board toolbar`, `search: Board filters`) plus `main` is the cap.
- **Always query landmarks by accessible name in tests** — with multiple `<nav>` elements in the tree, bare `getByRole('navigation')` is ambiguous. Use `getByRole('navigation', { name: 'Board toolbar' })`.

## Filter panel shell (#2691)

- **Filter panel pinned shell and Filter bar switch (#2691).** The panel is a `flex flex-col overflow-hidden` box capped at `min(600px, 80vh, <visible viewport>)`: a pinned header (`data-testid="filter-panel-header"`: the "Filters" title, an "N active" count hidden at 0, the **Filter bar** switch, then the search input, scope chips and Saved presets), a body that is the only scrolling region (`filter-panel-body`: Filtered by chips, the field rows, search results), and a pinned footer (`filter-panel-footer`: key hints, Clear all, Save filter and its name input). At any list length, 40+ fields included, the switch, search and footer stay visible. ## Avatar chips

- Shape: `rounded-full flex items-center justify-center flex-shrink-0`
- Size: `w-6 h-6 text-xs font-medium text-on-primary`
- Background: deterministic color based on user — use a consistent palette (teal `bg-palette-teal`, amber `bg-warning-bg`, violet `bg-palette-violet`, rose `bg-palette-rose`, etc.)
- Content: 2-letter uppercase initials only
- **Position on cards (compact only; the calm face puts it in the label row, § Cards): `absolute bottom-1.5 right-1.5 z-10`, not a flex child of the metadata row (#1411).** `CardItem`'s metadata row is `overflow-hidden` with no wrap at rest; an avatar rendered as the row's last flex child (`ml-auto`) is the first thing silently clipped when the row overflows — backwards, since the avatar is the one metadata element with no density gate. The content wrapper carries `relative`, and the metadata row carries `min-h-5 pr-7` whenever `card.assignee` is set: `pr-7` keeps clipped chip content from running under the avatar's corner, and `min-h-5` (20px, the `xs` Avatar's height) gives the row the vertical footprint the avatar needs. Both are required — the reservation is the row's height plus its right padding together. **This reservation must hold even when the assignee is the only metadata on the card** — `card.assignee` stays in `hasMetadataRow`'s OR-chain for exactly this reason: an otherwise-empty row still has to render, and because an empty flex row has zero height, `pr-7` alone reserves nothing vertically (the avatar would overlap the last title line by ~12px); the `min-h-5` is what pushes the card's bottom edge below the avatar, or the absolutely-positioned avatar sits on top of the title with nothing stopping it. Dropping that clause because "the avatar isn't a row child anymore" was a real regression caught by ux-review (#1411) — don't reintroduce it by a different path.
- Never show more than the initials — no full name, no tooltip required (but allowed)
- **Always use the `Avatar` component** (`src/components/Common/Avatar.tsx`) — never hand-roll avatar circles with inline palette arrays or hardcoded background colors. The `Avatar` component owns the canonical `-600` tone palette and handles initials, image avatars, and deterministic color assignment.
- **Sizes:** `xs` (20px), `sm` (24px, default chip on cards), `trigger` (28px, reserved for nav/chrome menu triggers — sits between chip and user-header sizes), `md` (32px), `lg` (40px)

## Connection status indicator

`ConnectionStatus` (`src/components/Common/ConnectionStatus.tsx`) is the single canonical component for surfacing WebSocket state. Do not re-introduce a second `LiveIndicator`, and do not render a bare `●ᅠLive` in feature components.

- **Prominence rule — quiet when healthy, loud when degraded.** Connected state is a bare success dot with the word "Live" shown only at `lg+` viewports (`labelClass: "hidden lg:inline"`). Every other state — `connecting`, `reconnecting`, `stale`, `failed` — always shows its label with an amber or red pill background so Maya/Jordan can see degraded state at a glance.
- **Pulse and reduced motion.** The healthy dot stays static per the prominence rule (a pulse was proposed in #199 and declined in favor of #851). Degraded-state dot pulses follow the general reduced-motion rule in § Motion and reduced motion.
- **Five states:**
  - `connected` → `text-success` dot, no background
  - `connecting` / `reconnecting` / `stale` → `text-warning-on-tint bg-warning/10 border border-warning/30 rounded px-2 py-0.5` (the connecting and reconnecting dots pulse with `animate-pulse motion-reduce:animate-none`; stale is static)
  - `failed` → `text-danger-on-tint bg-danger-bg/30 border border-danger-emphasis/40 rounded px-2 py-0.5`
  - **Board offline banner follows the same tone (#2342):** `BoardOfflineBanner` is amber (`border-warning/40 bg-warning/10 text-warning-on-tint`) while `reconnecting` and danger (`border-danger-emphasis/40 bg-danger-bg/30 text-danger-on-tint`) once `failed`, so the banner and the chip agree on severity and both use `text-danger-on-tint` for the failed state (plain `text-danger` on that tint was 2.98:1 on surface, 2.76 on canvas in light). `danger-on-tint` on `bg-danger-bg/30` measures, dark: 8.32 canvas / 7.35 sunken / 6.28 surface; light: 4.75 canvas / 4.94 sunken / 5.13 surface (tightest is light canvas, margin 0.25, so do not darken the fill or lighten the text). Pinned in `onTintTokens.test.ts`. The copy differs between the two states, so tone is never the only channel.
  - **Labels (#2325):** `Live`, `Connecting…`, `Stale`, and `Offline` for `failed`, and for `reconnecting` on the Board only (BoardView passes `reconnectingLabel="Offline"`: its banner says Offline too, and a chip saying "Reconnecting…" beside it contradicted it). Pages with no banner or paused moves (GroupDetail) keep the default `Reconnecting…`. The `failed` `aria-label` starts with the visible word ("Offline, real-time updates unavailable", WCAG 2.5.3). The two are still told apart by the pill (amber vs red), the `aria-label`, and the popover ("Reconnecting… attempt n." vs Reload page).
- **Stale detection:** `useIsStale(status, lastEventAt, thresholdMs = 60_000)` flips `connected` into the `stale` variant when no event has arrived within 60 seconds. Do not poll; the hook schedules a single `setTimeout`.
- **Popover:** click trigger opens a `role="dialog" aria-label="Connection status"` popover (`w-64 bg-surface border border-line-strong rounded-lg shadow-xl p-3`). Dismissal via Esc (`useEscapeStack` priority 25), outside-click, or re-clicking the trigger. On Esc close, refocus the trigger.
- **Popover actions:**
  - connected / stale → "Refresh board" Quiet button (only when `onRefresh` is passed — board pages yes, group page no)
  - failed → "Reload page" danger button
  - connecting / reconnecting → informational only; no button
- **Accessibility:** trigger carries `aria-haspopup="dialog"`, `aria-expanded`, and a state-specific `aria-label` ("Real-time updates active" / "Offline, reconnecting to real-time updates" / …). Include an inner `<span role="status" aria-live="polite" aria-atomic="true" className="sr-only">` that announces degraded states to screen readers; stay silent when connected.

## Ancestor breadcrumbs

Use this pattern whenever showing a full ancestor chain (e.g. group hierarchies):

```tsx
<nav aria-label="Group breadcrumb" className="flex flex-wrap items-center mb-1">
  {ancestors.map((ancestor, i) => (
    <span key={ancestor.id} className="flex items-center">
      {i > 0 && <span className="text-fg-faint mx-1.5 select-none" aria-hidden="true">/</span>}
      <a
        href={`/groups/${ancestor.id}`}
        onClick={(e) => { e.preventDefault(); navigate(`/groups/${ancestor.id}`); }}
        className="text-sm text-fg-tertiary hover:text-fg focus:outline-none focus:ring-2 focus:ring-primary-emphasis rounded transition max-w-[12rem] truncate"
        title={ancestor.name}
      >
        {ancestor.name}
      </a>
    </span>
  ))}
  <span className="text-fg-faint mx-1.5 select-none" aria-hidden="true">/</span>
  <span className="text-sm text-fg-secondary max-w-[12rem] truncate" title={current.name}>{current.name}</span>
</nav>
```

- Ancestor links: `text-sm text-fg-tertiary hover:text-fg focus:outline-none focus:ring-2 focus:ring-primary-emphasis rounded transition`
- Separator `/`: `text-fg-faint mx-1.5 select-none` with `aria-hidden="true"`
- Current item (non-linked): `text-sm text-fg-secondary`
- Per-item max-width: `max-w-[12rem] truncate` with `title` attribute for full name
- Container: `flex flex-wrap items-center` — wraps on narrow viewports
- Root-level items with no ancestors render nothing (omit the `<nav>` entirely)

**Navbar breadcrumb override:** the top-chrome breadcrumb in `Navbar.tsx` uses the same pattern but renders the terminal (current) segment as `text-sm text-fg font-medium max-w-[18rem]` instead of `text-fg-secondary max-w-[12rem]`. The board/page name is the primary context indicator in the chrome, so it reads brighter and has more room to breathe. Standalone ancestor breadcrumbs elsewhere keep `text-fg-secondary max-w-[12rem]`.

## Command palette ownership (#869)

The command palette is owned by `GlobalCommandPalette` at two shell-level mount points:

1. **Inside `BoardPage`** (inside `BoardProvider`) — mounts on every `/boards/*` route so the palette is available on every sub-tab (Board/Summary/History/Analytics) and has access to board cards via `useOptionalBoardContext()`.
2. **Inside `AuthenticatedRoutes`** (above the route tree, only when pathname does NOT start with `/boards/`) — mounts on Dashboard, Group, Settings, and Admin so `⌘K` works everywhere.

Mutual exclusion by pathname guarantees only one `⌘K` keydown listener is ever registered. Do not mount a third palette. Do not register a `keydown` listener for `⌘K` in any feature component — the `GlobalCommandPalette` owner is the single source.

- **Action dispatch goes through `window` CustomEvents** — the palette fires `visiban:open-card`, `visiban:filter-my-cards`, `visiban:show-history`, `visiban:open-settings`, and the existing `visiban:open-shortcuts`. `BoardView` subscribes to the board-scoped subset. Do not reach into `BoardView` state from the palette directly — event-based delegation keeps the shell / board boundary clean.
- **Off-board actions are filtered automatically** — actions marked `boardOnly` in `CommandPalette.STATIC_ACTIONS` are suppressed on Dashboard/Group/Settings/Admin so the palette doesn't offer operations that would target no board. `Show keyboard shortcuts` is route-agnostic and surfaces everywhere.
- **Card-scoped commands (#2059).** Card commands carry `cardTarget: true` and are listed only when a target resolves, in this order: the card whose sheet is open, the card that had keyboard focus when the palette opened (captured from `document.activeElement` before the palette takes focus; only the card **face** itself counts, via `focusedCardFaceId()`, never its selection checkbox, a quick-edit chip or the `⋯` button, so toggling a checkbox leaves the selection as the target), the selection; otherwise none. **Hover is never a target.** `GlobalCommandPalette` asks the board over the synchronous `visiban:card-target-query` window event (BoardView fills `detail.response` with the cards, a summary for the "Acting on …" header and each command's availability from `cardActionEntries()`), and runs a command by dispatching `visiban:card-action` with `{ cardIds, action, value? }`, never by reaching into BoardView. `→` on a card result (caret at the end of the query) drills into that card's commands; `←`, or Backspace on an empty query, backs out, and the palette's single Escape entry (60) backs out one level before it closes. **Drill-in and choice levels announce themselves** through the palette's always-mounted status region ("Card actions for {card}", "Choose a column", "All results" on the way back out); the visible "Acting on …" header alone is not an announcement. Commands ending in `…` open a second list inside the palette (columns, people, priorities). **No Delete in the palette**: a destructive command reachable by typing must not be one keystroke from Enter. A disabled command is listed, with its reason on a second line, only when a typed query matches it; activating it re-announces the reason through the palette's always-mounted `sr-only` status region. With no target, a query that names a card command shows the non-interactive "Card actions" group ("Select, focus or open a card to act on it." / "Or search for a card and press →."), in `text-xs text-fg-tertiary italic`: it is an instruction, not an empty marker, so not the § Empty states one-liner tone (`fg-muted`; it was `fg-faint`, below 4.5:1, until #2030).
- **Placeholder adapts per surface** — `GlobalCommandPalette` passes a `placeholder` prop per pathname. Board: `Search cards, boards, actions…`. Dashboard/Group: `Jump to board…`. Settings/Admin: `Jump to…`. Copy must match what the palette can actually do on that surface.

## Keyboard shortcuts — noise budget and registry (#868)

Shortcut wiring lives in three places: the board-scoped keydown listener in `BoardView` (for on-board bindings like `b`/`s`/`h`/`a`, `l` (lens-gated — only when the Issue Board Lens is available), `e`, `y`, `f`, `c`, `/`, `.`, `?`, `⌘,`, `⌘\\`, `⌘⇧E`, `⌘⇧L`), the shell-level listener in `GlobalCommandPalette` (`⌘K`), and the `g`→`u` chord listener in `Navbar` (opens the user menu). New listeners should use `shouldIgnoreShortcut()` from `src/utils/keyboard.ts` so typing letters into inputs, textareas, and rich-text editors never triggers the shortcut; the existing `BoardView` and `Navbar` listeners currently use equivalent inline typing-context checks instead.

- **`aria-keyshortcuts` noise budget — single-key or single-modifier only.** Every toolbar affordance that responds to a bare-letter shortcut (B/S/H/A/E/F/Y) or a one-modifier chord (⌘K, ⌘\\, ⌘,) must carry the corresponding `aria-keyshortcuts` attribute so screen readers announce the binding. Do **not** expose two-modifier chords (⌘⇧L, ⌘⇧E) via `aria-keyshortcuts` — exposing every chord drowns assistive technology in noise and offers no navigation benefit. Surface richer chords in the shortcuts overlay and tooltip only.
- **Platform-aware formatting — always route through `src/utils/platform.ts`.** `formatShortcut({ mod, shift, alt, key })` renders visible hints (⌘⇧L on Mac; Ctrl+Shift+L elsewhere). `formatAriaKeyshortcuts()` renders the ARIA 1.2 canonical form (`Meta+Shift+L` / `Control+Shift+L`). Never hard-code the Mac glyphs or the `Meta+` prefix at a call site.
- **Tooltip hints — the shortcut follows the label.** Two forms, by surface. **Board toolbar buttons that carry a shortcut (Export and Settings, #2435):** `"${label} ${formatShortcut(...)}"`, a space and no parentheses (`Export board ⌘⇧E`, `Board settings ⌘,`), because that is how the #2435 artboard ("1 · Toolbar") draws them and the issue asks for the artboard exactly; a new toolbar button with a shortcut uses this form too. **Everywhere else:** parenthesize, `"${label} (${formatShortcut(...)})"`. The Activity toolbar button keeps the parenthesized form (`Open activity drawer (⌘\)`): it predates the artboard, which draws no hint for it, so it is the one toolbar exception until a design changes it. Either way the hint comes from `formatShortcut`, never a literal glyph. The overflow menu's own `shortcut` slot already renders the hint inline; set it there instead of baking the hint into the item label.
- **The shortcuts overlay is the canonical registry.** Every non-trivial binding must appear in `KeyboardShortcutsOverlay.tsx` grouped under one of the four sections (Navigation / Board view / Board actions / Help) and in `docs/features/keyboard-shortcuts.md`. Descriptions are imperative (`Switch to Board view`, not `Board view`) so each row reads as a command.
- **Sequential chords render as separate chips, never one.** Sequential chords (press, release, press — e.g. `G` then `U`) render as separate <kbd> chips joined by "then", never as one chip, so they can't be mistaken for a simultaneous combo like ⌘K.
- **Card actions add no letters (#2059).** The card context menu opens with `Menu` / `Shift+F10` on a focused card (platform keys, zero budget cost), and the palette drill-in uses `→` / `←`; both are in `KeyboardShortcutsOverlay` and `docs/features/keyboard-shortcuts.md`. Typeahead inside an open menu is not a global shortcut. The keyboard path to Block is focus card → `Menu` → **Block card…**, or `⌘K` → "bl" → Enter. The spec recommends adding none of the candidate chords, and none was added (owner sign-off pending on the #2059 MR); their costs: `⌘⇧B` (Chrome/Firefox bookmarks bar on macOS), `⌘⌥B` / `Ctrl+Alt+B` (`AltGr` on European Windows layouts, `∫` on macOS), a scoped `⌘Z` (users expect it to undo any edit).
- **A control is allowed to have no shortcut, on purpose.** The grid overlay picker
  (#1147) deliberately has none and carries no `aria-keyshortcuts`: it is a cosmetic
  reading layer, it is Tab-reachable in Row 2 at every supported width, and the bare-letter
  set is already crowded. Do not "complete" it with a binding — the budget above is the
  reason it was left out.
- **Command palette surface-awareness — suppress actions that have no target.** When adding a new action to `CommandPalette.STATIC_ACTIONS` that requires a board (opens a card, toggles filters, switches view), set `boardOnly: true` so `GlobalCommandPalette` filters it out on Dashboard/Group/Settings/Admin. Route-agnostic actions (open shortcuts overlay, log out) must *not* carry the flag.

## Board search scope toggle

The filter bar's search input carries a `SingleSelectDropdown` scope toggle to its left when `onScopeChange` is provided by the parent. Scope is URL-persisted via `?scope=all` (absent ⇒ `board`) so the selection is link-shareable. Rules:

- Trigger copy follows the selected option (`This board` / `Everywhere`) with a leading `🔍` via `triggerPrefix`
- Selecting `Everywhere` sets `?scope=all` **and** dispatches `visiban:open-palette` — until #191 ships, the palette is the cross-board search surface
- While `scope=all`, the board search input is disabled (`disabled:opacity-40 disabled:cursor-not-allowed`) but its value is preserved, and a helper line `Searching across all your boards` appears below (`text-xs text-fg-muted`, `aria-describedby` wired to the input)
- Placeholder is the exact string `Search cards on this board…` — keep US English and the ellipsis character
- Do not conflate scope with `FilterState` — scope is a search-surface selector, not a card-filter dimension; keep it in its own state/URL merge in `BoardView`

## Hosted demo surfaces (#1179)

The public demo (`demo_mode`, read from site-config via `useInstanceFlags()`, never from the deprecated `User.demo_mode`, #1913) runs behind a server-side, deny-by-default write fence: everything except card create/edit/move, archive and checklist writes answers `403 {"code": "demo_read_only"}`. The SPA's job is to make refused things look refused **before** the visitor tries them.

- **Fixed-lead refusal copy.** Every refusal reads `This is a shared demo — {surface clause}.` The lead clause is identical everywhere and never reworded per surface, so the visitor learns to read it as "the demo, not you" (same convention as maintenance mode's fixed title). All strings live in `src/constants/demoCopy.ts` — add new surfaces there via `demoReason()`, never inline.
- **`aria-disabled`, never native `disabled`, on a control the fence blocks.** Native `disabled` drops the control from the tab order, hiding the reason from keyboard and screen-reader users. Guard the handler as well (`onClick={() => { if (!demoMode) ... }}`) and style with `opacity-40 cursor-not-allowed`. Playwright treats `aria-disabled` as non-actionable, so e2e specs that prove "a click does nothing" use `click({ force: true })`.
- **Reason surfacing — two sub-patterns, same disabling mechanism.** (A) where there is room, an always-visible reason line tied to the control with `aria-describedby` (comment composer, attachment upload, Board Settings); (B) for compact toolbar/nav buttons, `title` + the reason folded into `aria-label` (`"New board. This is a shared demo — …"`) — sidebar and Dashboard New board / Import / New group.
- **Whole regions: `DemoInert`** (`src/components/Common/DemoInert.tsx`). When many controls must go inert together (Board Settings' admin sections), wrap them in `DemoInert` with ONE shared notice id instead of threading a prop through every control: a per-control prop fails open for the next control someone adds; a region fails closed. It renders `role="group" aria-disabled="true" aria-describedby=<notice>` and blocks activation in the capture phase while leaving everything focusable. Only wrap controls that write to the server — personal, browser-local prefs (card-density override, hidden columns) stay live. The region dims with `opacity-60`, lighter than the `opacity-40` used on a single refused control: a whole section at `opacity-40` becomes hard to read, and the visitor still needs to read the current settings — only changing them is refused. `opacity-60` is reserved for this whole-region case.
- **Ownership-gated buttons mirror the server's demo carve-out.** The server lets the published visitor (a plain MEMBER) archive, unarchive and reassign cards others created while `DEMO_MODE` is on. Components that derive those buttons from `is_moderator` widen the check with `demoMode && role === "member"` — a display heuristic, never a copy of the server's username check — and widen **only** the writes on `DEMO_ALLOWED_WRITES`. Card delete is not on it, so Delete stays unwidened (withheld in demo mode, disabled with the shared reason since #2105).
- **Typed text is kept.** A refused composer never sends, so nothing clears it — make the submit handler a no-op in demo mode rather than letting it fail.
- **`DemoModeBar` color divergence.** The in-app bar uses the **mode-indicator** tone (`bg-primary/15`, § Mode indicator banners) in its normal state — the visitor opted into the demo — and flips to the **degraded-state amber** (§ Degraded-state site banners, `⚠`, one fixed sentence) from 5 minutes before the reset, because at that point the sign-out IS being imposed on them. No exit control in either state. Announce transitions only, through an `sr-only` live region; the visible bar is not live, or the minute label would be re-announced every tick.
- **Reset times are browser-local** (`formatClockTime()` in `src/utils/date.ts`), computed from the server's `demo_next_reset_at` — never hardcode a cadence or a timezone.
- **An absent reset is a real state, not a missing value (#1180).** When `demo_next_reset_at` is null (e.g. the Helm chart's `demo.reset.enabled=false` leaves `DEMO_RESET_SCHEDULE` empty), the login banner must not fall back to assuming an hourly — or any — cadence. Gate the reset-countdown sentence on the concrete `demoNextResetAt` value, never on the raw schedule string, and render a shared-state disclosure instead: "Other visitors can see and change everything here, and it is never reset." Never let an empty/absent schedule silently read as "every hour, on the hour."
- **Fallback toast is a safety net.** `DemoWriteBlockedToast` (shell-level, fed by `auth:demoWriteBlocked` from `api/client.ts`) catches refusals from surfaces that were not disabled up front. It is a `warning` toast in the shared region (key `demo-write-blocked`, polite) and stays up 8 s, the `warning` default, set through an explicit `durationMs` (`DEMO_TOAST_MS`; owner decision on #2109, 1.3 UI spec Part 9). If it fires during normal use of a surface, that surface is missing its up-front affordance — fix the surface, do not reword the toast.
- **A background save nobody clicked is silently skipped, not `aria-disabled` (#1193).** Some refused writes have no control to disable at all — `ThemeServerSync`'s cross-device theme PATCH fires from a `useEffect`, not a click. Showing a toast for a save the visitor never asked for is noise, not an affordance; the fix is to not send the request in demo mode (`if (!demoMode) { ...PATCH... }`, with `demoMode` from `useInstanceFlags()`) and let the local/optimistic state keep applying. Same treatment as the onboarding tour's completion save, which needs no code guard at all — `seed_demo_data` seeds the published visitor's `has_completed_tour` flag `true`, so that save never fires in the first place.
- **A control whose primary purpose is navigation is never `aria-disabled`, even when it also fires a refused side-effect write (#1193).** Clicking a notification row both navigates to the related card and marks it read; `aria-disabling` the row to block the refused mark-read write would also block the navigation the visitor actually asked for. Skip the side-effect write silently instead (same as the background-save case above), and give the *explicit*, standalone version of the same action — here, the "Mark all read" button, which does nothing else — the up-front `aria-disabled` affordance.
- **A hover-reveal control that becomes demo-gated goes always-visible at `opacity-40`, not `group-hover:opacity-100` (#1193).** Per-row delete controls (comment ✕, attachment ✕) are normally hidden until hover/focus. In demo mode that would recreate exactly the "refused only after you try it" problem this section exists to close — a visitor who never hovers never learns the control is dead. Drop the `group-hover`/`opacity-0` classes for the demo-gated branch and render the disabled control at a flat `opacity-40` instead, same reasoning as the pinned custom-field chip's always-visible exception to the general hover-reveal default.
